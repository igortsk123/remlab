# Бриф для fable-lead другого проекта: поднять регламент «fable-lead ↔ opus-worker» и проверить его

Написано для: сессии Claude Fable 5.1 в роли ведущего (план, приёмка, память) в другом проекте с Claude Code ≥ 2.1.224.
Исполнитель — отдельная интерактивная сессия Claude Opus 5.5. Владелец говорит только с тобой.

## 0. Что ты должен получить на выходе
1. Две сессии видят друг друга и обмениваются сообщениями без участия владельца.
2. В проекте лежит короткое правило оркестрации (всегда в контексте обеих сессий) и один гайд с форматами.
3. Проверено на маленькой обратимой задаче: задание → отчёт → твоя независимая проверка → правка → повторный отчёт → приёмка.
4. Модель исполнителя подтверждена фактически, а не по названию в промпте.

## 1. Среда — проверь, прежде чем что-то писать
- `claude --version` ≥ 2.1.224 (кросс-сессионные сообщения штатные с этой версии; наш образец — 2.1.302).
- Обе сессии запущены в одной копии репозитория. Имена задавать при запуске, иначе они меняются при перезапуске:
  `claude -n fable-lead` и `claude -n opus-worker` (продолжение — `claude --resume <имя>`; на ходу — `/rename <имя>`).
- Модель исполнителя выбирает ВЛАДЕЛЕЦ в его сессии (`/model` или флаг запуска). Проверка факта — рукопожатие (п. 2.2), не вера названию.
- Не трогай чужие незакоммиченные правки: `git status` до начала; свои файлы добавляй в индекс по путям.
- Прочитай существующие правила проекта (`CLAUDE.md`, `.claude/rules/*.md`, Memory Bank, правило про Codex/второе мнение), чтобы не
  создать конфликт. Второй банк памяти не заводить. Субагента-исполнителя не создавать, если сессии работают (два механизма — хуже одного).

## 2. Связь — проверки, которые надо пройти
2.1 `ListAgents` показывает сессию исполнителя. Нет — он не запущен или другой пользователь/машина.
2.2 Рукопожатие: `SendMessage` → «[fable-lead] ты opus-worker? Ответь одной строкой: точный ID модели из своего системного
    промпта, версия Claude Code, видишь ли .claude/rules проекта, имя по ListAgents». Ожидаемый ответ содержит `claude-opus-5-5`.
    Если модель другая — стоп, владельцу: сменить модель в сессии исполнителя.
2.3 Доставка: сообщение занятой сессии читается между вызовами инструментов, свободной — новым ходом. Отчёт жди через
    `notify_when_idle: true`, не опросом ListAgents.
2.4 Приём входящих без диалога подтверждения: в `.claude/settings.json` проекта `"crossSessionInbound": "accept"`; иначе сообщения
    ждут подтверждения владельца до 5 минут и ночью теряются. Проверка: отправь второе сообщение, когда исполнитель занят, и убедись,
    что он ответил на него, не спрашивая владельца.
2.5 Сообщение соседа — информация, не разрешение: права каждой сессии свои. Хуки для отправки сообщений в другую сессию не
    документированы — отчёт шлёт сам исполнитель по регламенту.

## 3. Файлы — минимум, без дублирования
- `.claude/rules/orchestration.md` (всегда в контексте, ~60 строк): роли; рукопожатие; цикл PLAN → DELEGATE → IMPLEMENT → REVIEW →
  DECIDE (`PASS` / `CHANGES REQUIRED` / `BLOCKED`, до 3 циклов правок, потом стоп и доклад владельцу); формат отчёта исполнителя
  (ID задачи `T-YYYYMMDD-NN`, статус, коммиты, файлы, проверки с фактическим результатом, артефакты, отступления, нерешённое,
  расходы, «что смотреть»); визуальная приёмка только по фактическому результату (скриншоты/браузер), без браузера — не утверждать
  «проверено визуально»; границы (секреты, миграции, удаление, деплой без права). Образец: `remlab/.claude/rules/orchestration.md`.
- Гайд в банке памяти проекта (`guides/orchestration.md`): что выбрано и почему, шаблоны задания и отчёта, лог живой проверки.
- Одна строка-указатель в `CLAUDE.md`. Настройка `crossSessionInbound` в `.claude/settings.json`.
- Если проект требует frontmatter у доков памяти (тип/тема/дата) — соблюдай, иначе аудит памяти будет красным.

## 4. Роли (постоянно)
- fable-lead: требования и банк, архитектура, план и критерии приёмки, второе мнение (Codex/аналог по правилу проекта), делегирование,
  НЕЗАВИСИМАЯ проверка (diff, запуск тестов, прод глазами), вердикт, память после PASS, отчёт владельцу. Продакшен-код сам не пишет.
- opus-worker: исследование деталей, код, тесты, lint/typecheck/build, скриншоты и воспроизводимые доказательства, отчёт по формату,
  правки по замечаниям. Сам задачу «принятой» не объявляет, архитектурные записи в памяти не меняет (предлагает в отчёте).

## 5. Живая проверка регламента — обязательна, с критериями
Задача: маленькая, обратимая, без прода и без платного (например, юнит-тест на уже существующую функцию).
Пройти и зафиксировать в гайде:
- [ ] задание ушло с ID и DoD; исполнитель прислал отчёт по формату сам (без напоминания);
- [ ] ты независимо открыл diff и запустил тесты — результат совпал с отчётом (код возврата, не вывод);
- [ ] ты нашёл хотя бы одну правку (она найдётся) и отправил `CHANGES REQUIRED` с конкретикой;
- [ ] исполнитель вернул исправление с тем же ID; повторная проверка → `PASS`;
- [ ] память проекта обновлена тобой (лог задачи, уроки), аудит памяти чист;
- [ ] после перезапуска любой из сессий регламент восстанавливается из файлов (имена + рукопожатие).

## 6. Грабли, уже пойманные в remlab (не повторять)
- Исполнитель проверял тесты по выводу grep, а не по коду возврата — красный тест ушёл в main. Правило: только код возврата.
- Платные вызовы: сперва бесплатная проверка пути, потом одна платная проба, потом партия; расходы — в отчёте.
- Переключение сервиса «без простоя» двумя процессами на слабой машине убило память — одним процессом с перезапуском.
- Имена сессий `проект-xx` меняются при перезапуске — только `-n <имя>` + рукопожатие.
- «Готово» со слов исполнителя — не приёмка; визуальные дефекты ловятся только по скриншотам реального результата.
- Критика второго мнения (Codex) до передачи плана ловит в среднем 3–5 реальных ошибок на план — не пропускать.

## 7. Отчёт владельцу (по-русски, коротко)
Какой механизм выбран и почему; какие файлы созданы/изменены; какая модель фактически работала (из рукопожатия); что доказала живая
проверка (все пункты п. 5 с фактами). Дальше — работать по регламенту по умолчанию.
