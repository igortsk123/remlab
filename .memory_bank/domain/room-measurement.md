# Замер комнаты по фото и подбор мебели «по факту»

Первая линия проекта, предшествующая мебельному треку: пользователь фотографирует комнату →
код измеряет её и мебель → показывает, что реально влезет, и как это будет выглядеть.
Код: `services/room-measure/` (перенесён 2026-08-04, до этого жил вне репозитория и потому
в памяти отсутствовал — см. `changelog/memory-log.md`).

## Несущий принцип
**Геометрия — истина, генерация — убеждалка.** Масштаб и позиции считает детерминированный код;
нейросети только именуют объекты и рисуют картинку. Тот же принцип независимо переоткрыт
2026-08-03 в мебельном треке (см. `core/layout.md`).

## Конвейер

1. **Масштаб.** Лист A4 на полу как эталон + `solvePnP` → поза камеры, матрица K, перевод
   пикселей в сантиметры (`cv_refine.py`, `geometry_solver.py`). FOV выводится из модели
   телефона, если она известна (`run_auto.py`), иначе прайор (iPhone SE3 ≈ 62°).
2. **Сегментация сцены.** SegFormer ADE20K (`nvidia/segformer-b2-finetuned-ade-512-512`) —
   пол, стены, окна; кэш `.npy` рядом с фото.
3. **Объекты.** Grounding DINO с открытым словарём (`gdino_test.py`) → канонизация ярлыков
   (`taxonomy.py`: сырой англ. ярлык → класс → тип «опора/пол/стена/предмет») → уточнение имён
   vision-моделью по кропам (`openai_vision_name.py`), дешёвый перевод (`openai_translate.py`).
4. **План пола сверху** (`run_plan.py`): габариты видимой комнаты + footprint мебели (ширина по
   полу, глубина из справочника) + свободная зона.
5. **Само-проверка размеров** по справочнику типовых габаритов (`object_catalog.py`,
   `sizes_prior.py`, `run_f3.py`) и иерархия «что на чём стоит» (`run_f2.py`).
6. **Fit-check** (`fit_check.py`): Shapely, детерминированно — «влезет / велик на N см / что
   убрать»; две ориентации товара; габариты товара берутся из фида, зона — из плана пола.
7. **Подбор товаров** под зону (`product_match.py`, `run_match.py`): реальные позиции каталога
   с ценой, магазином и ссылкой.
8. **Визуализация замены** (`run_viz.py`): стереть старый предмет (LaMa через fal.ai) и вставить
   товар в ВЫЧИСЛЕННОМ масштабе по 3D-габариту.

## Что надёжно и что хрупко

- **План сверху надёжнее строить на геометрии пола (A4 + solvePnP), чем на карте глубины** —
  прямая пометка автора в `run_plan.py`: «надёжный результат на floor-геометрии, без
  depth-хрупкости». Depth остаётся отдельным слоем для высот и окон.
- **Глубина предмета из одного кадра ненадёжна** — берётся из справочника габаритов, а не из фото.
- **По одному студийному фото товара невозможно восстановить невидимые стороны** (подтверждено
  и внешним ресёрчем 2026-08-04) — отсюда протокол съёмки и справочник глубин.

## Протокол съёмки (для нормального результата)
3–5 кадров, лист A4 на полу, в каждом кадре виден уголок потолка; кадры с перекрытием, чтобы
сшить половины комнаты. Один кадр даёт ненадёжную глубину.

## Связь с мебельным треком
- `fit_check.py` решает ту же задачу, что hard-проверки прод-ядра (`services/planner-solver`),
  но со стороны «влезет ли товар в замеренную зону» — переиспользовать, а не писать заново.
- Схема `run_viz.py` (стереть → вставить в вычисленном масштабе) — прямой прототип того, что
  нужно генерации кадров по плану (`plans/llm-layout-planner.md`).
- Справочник габаритов пересекается с `tools/scout/typical-dims.json` — свести в один источник.
