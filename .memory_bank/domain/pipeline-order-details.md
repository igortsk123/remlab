# Порядок конвейера — детали

Сводка и таблица этапов — [[pipeline-order]].

## Почему обрезка стоит между отбором и очередью мешей
Вырезка — вход генератора: что срезано с фото, того не будет в меше; что прилипло от фона,
станет геометрией. Ставить её раньше отбора значит резать 32 тысячи карточек вместо 14 700;
ставить позже очереди — платить за генерацию по заведомо негодному входу. Внутри этапа
работают точечные правки по ролям: ковру возвращается потерянное поле (сеть держит только
линии узора), вазе/кашпо/статуэтке — силуэт вместо оптической прозрачности, коллажи и обрывки
фона отсеиваются (ADR-0133, уроки 319–322).

Мягкий декор (роли не `hunyuan3d` по `tools/scout/rules/asset-strategies.json`, `tools/scout/mesh_queue.py:_mesh_needed`) режется тоже — вырезка нужна витрине и вклейке, — но в очередь
мешей не попадает: плед, штора и ковёр рисуются плоско по фото, меш им ничего не добавит.

## Вердикт вырезки едет в задании
`mesh_queue.export()` кладёт в задание `role`, `photo_verdict` и `assessor_version`; забракованное
на обрезке на карту не отправляется вовсе. Нода прогоняет ТУ ЖЕ цепочку `preprocess.prepare`
с той же ролью, поэтому маска воспроизводима, а расхождение вердиктов видно в манифесте.
До 29.08 в задании был только `image_url`, и нода резала исходник заново — наша вырезка была
справкой рядом с конвейером, а не его входом (критика Codex).

## Незакрытые места
1. **Планировщик генерации** (между 5 и 6) — ЗАКРЫТО: дневная партия набирается по приросту готовых сетов ярусами
   (комплекты по близости к готовности → дефицит заменителей → пилот проблемных ролей …) — `tools/scout/mesh_scheduler.py`,
   ночной шаг `mesh_schedule` (`tools/scout/refresh_daily.sh`); `mesh_queue.py:run` ведёт только спрос. Открыто — мерить: полностью готовые сеты, покрытие ячеек, сколько слотов разблокировал каждый меш,
   p50/p95 времени «в очереди → принят», возраст старейшего задания приоритета.
2. **Публикация ассета** (между 6 и 7): атомарный пакет GLB + канонический поворот + размеры +
   SHA маски + превью, после которого выставляется `asset_ready`. Сейчас готовность собирается
   по кускам из разных таблиц.
3. **Гейт `MESH_GATE_PHASE` переключать не по общей доле SKU:** 80% каталога бесполезны, если
   не хватает одного обязательного класса диванов. `hard_new` — когда shadow-сборка даёт целевое
   число полных сетов; `rolling` — по одному сету, у которого 100% нужных предметов готовы (это
   свойство сета, а не глобальный процент); `full` — когда у критических слотов есть замена.
4. **Судья (этап 8) в ночной цепочке отключён**, и перед ним нужна проверка выполнимости солвером.

## Судья (перенесено из Tier 1, 14.10)
Судья (`judge.py`) отключён — запускается только по команде владельца.

## «Сеты только с мешами» — неверно (перенесено из Tier 1, 14.10)
Мягкий декор мешей не получает; у предмета есть представление ПО СПОСОБУ ОТРИСОВКИ — покрытие считать как `asset_ready(strategy)` (`tools/scout/render_strategy.py`).

## Банк комплектов — ночная автоподмена (22–24.10, ADR-0318, планы conv-14/conv-14b)
- **Ночной порядок** (`tools/scout/refresh_daily.sh`): обогащение и решения → `mesh_family_early` → `mesh_bind_early` (до сборки:
  ворота сборки читают `mesh_required`) → `bank_prepare` (чёрный список строит в начале сборки — текущие решения + семейства,
  `bank_pending.policy_blocks`; сборка кандидата `sets3.next.json` в изолированной копии, инварианты, сверка медиа
  `catalog_media.sync_sets` — сборщик пишет прямую ссылку фида, партнёрскую ставит только сверка) → `bank_pending` (ожидание по
  ячейке; спрос мешей `bank_candidate`) →
  `bank_promote` (готовые ячейки, экзамен, manifest) → писатель `bank_refresh.py` (сейчас `write_enabled=false`).
- **Цепочка одной ночи (06.11, room-bank-01 этап А, T-20261106-60):** `tools/scout/refresh_daily.sh` задаёт `BANK_RUN_ID`
  (`night-<время>-<pid>`) и идёт `bank_prepare && bank_pending --night && bank_promote` с `--run-id`; писатель `bank_refresh` — только
  при целой цепочке (`bank_chain_ok`), сбой любого звена — строка `DIGEST:` «цепочка ночи … остановлена», живой банк не трогается,
  остальная ночь идёт как прежде (`tools/scout/tests_refresh_order.py`, подмена `FAIL_STEP`).
  Связка — `tools/scout/bank_run.py`: prepare кладёт номер в отчёт и в паспорт кандидата `<кандидат>.run.json` (номер + sha256 байт,
  `bank_run.py:attest`); pending и promote принимают только отчёт своей ночи и тот самый файл кандидата (`bank_run.py:candidate` —
  `pending_due`, путь, sha в отчёте и паспорте), promote судит ровно сверенные байты и пишет номер в manifest; писатель принимает
  только manifest своей ночи (`bank_refresh.py:write` — `run_id`, возраст `write_manifest_max_age_h`). Отказ — `ERROR:` + `DIGEST:`
  (`bank_run.py:refuse`); без `--run-id` — код 2 (`bank_run.py:need`).
- **Намерение писателя (`bank_refresh.py:recover`):** перед заменой живого банка — снимок-поколение, затем намерение intent.json в папке поколений
  (sha «до» и «после», готовая запись журнала), затем rename; намерение снимается последним. `recover` идёт в начале записи и отката:
  поколение уже в журнале — снять намерение; живой = «до» — `recover/abort`; живой = «после» и идентичность сошлась — доводка журнала,
  не сошлась — возврат снимка (`recover/restore`); живой ни то ни другое — отказ, код 1, разбор руками и `bank_refresh.py recover --abandon`.
- **Готовность ячейки** — `tools/scout/bank_ready.classify` по роли слота: cutout-роль = в продаже + живое фото + текущая ссылка (вырезка
  не требуется: вырезок мягкого 0, показ их не использует); ковёр — w,d; меш — гейт геометрии. Типы ожидания: `wait_asset`, `wait_catalog`,
  `redo`, `blocked_policy`, `legacy_unknown`. Журнал решений по мешам — файлы (`tools/scout/rules/mesh-asset-decisions.json`,
  `~/scout-scenes/mesh-asset-decisions.jsonl`), без БД.
- **Удержание** (`tools/scout/bank_keep.py`): источник — прошлый кандидат (`BANK_KEEP_FROM`), состояние `sets3.next.keep.json`; три
  сборки с разным `PYTHONHASHSEED` → 126/126 одинаковых `selection_hash`.
- **Скрытый сет** — `tools/scout/rules/bank-candidate.json:hidden_roles` = [диван]; демо его не берёт ни вариантом, ни источником ленты
  (`flat215_demo.hidden()`); при правиле «ушла любая ключевая роль» скрывалось 26 сетов и демо теряло полные варианты.
- **Столовая по площади** — одна функция `compose2.dining_capacity(m2)` для окна подбора стульев и обрезки (было: окно на 4 стула, ставится
  2 при m2 < 22 → пустое окно молча снимало стол); снятие стола пишет `coverage_gap`.
- **Факты 22–23.10:** живой банк — 126 ячеек, идентичность цела, но 187 ушедших позиций в 103 сетах, контракты лечения каждую ночь
  останавливает предохранитель `heal_policy` 25 %; ночь 23.10 — 0 подмен (кандидат пересобирался с нуля: совпадение 1109/2754 → keep).
  Свежая сборка даёт 8–10 ячеек со сломанным порядком тиров — follow-up conv-14b.

## Публикация демо — копия прежней версии и откат (06.11, T-20261105-59)
- **Ночью** `flat215_demo` собирает демо, `flat215_publish` везёт его на прод — только если прошли ворота лёгких копий моделей
  `demo_rt` (`tools/scout/refresh_daily.sh`, `tools/assets/demo_rt.sh`).
- **Сборка пишет выходные json подменой**, не обрезкой: временный файл в той же папке + fsync + `os.replace` (`tools/scout/atomic_io.py:write_json`,
  в `tools/scout/flat215_demo.py` — `_AIO`); в `tools/flat3d/build-scene-bundle.mjs:writeAtomic` и `tools/flat3d/demo-cams.mjs` —
  временный файл рядом + rename (без fsync).
  Упавшая посреди записи сборка оставляет прежний файл целым — публикация не увозит обрывок.
- **Публикация** (`tools/scout/publish_demo.sh`): перед rsync на сервере — полная копия живой папки (без `topsprites/`) в
  `<папка>.prev-<ГГГГММДД-ЧЧММСС UTC>` рядом, хранится `PUB_KEEP` (3); затем `rsync --checksum --delete` внутри той же папки (каталог
  не подменяется — монтирование Caddy). `PUB_DIR` — только `demo` или `test/<имя>`; публикация и откат одной папки — под `flock`.
- **Откат** `publish_demo.sh --rollback [метка]` (без метки — самая свежая обычная копия; повтор — ещё на шаг назад): содержимое
  переставляется переносом внутри той же папки, прежнее ложится в `<папка>.prev-<метка>-undo` (отмена — `--rollback <метка>-undo`);
  `--list` — какие копии есть. Самопроверка без сети — `tools/scout/tests/test_publish_demo.py` (CI).

## Комнаты — реестр возможностей и вход (06.11, T-20261106-72)
какие шаги есть у типа комнаты (каталог, витрина, спрос мешей, банк) —
`tools/scout/room_profile.py:CAPABILITIES`; кортежей комнат в коде нет, неизвестный тип — отказ. Спрос мешей: по слотам — только

## Банки других комнат — спальня, прихожая (06–07.11, план room-bank-01 этапы Б–Ж)

  правка `bank_*` selftest или `rules/bank-*.json` меняет эталон — прогон и `--record` тем же коммитом).
- **Флаги комнаты** — `tools/scout/rules/bank-candidate.json:rooms.<комната>.{enabled,prepare_enabled,promote_enabled,write_enabled,
  rehearse_enabled,publish,mesh_gate}`; нет ключа — выключено, правила гостиной не наследуются. `BANK_WRITE` без `--room` — только
  гостиная. Спальня (с 07.11) — все включены, `publish: live` (ночной `mesh_publish` выкладывает её модели); прихожая — только сборка
  кандидата, живого банка нет.
- **Идентичность** — `tools/scout/room_identity.py:cell`/`set_id_of`: id набора от ячейки `room_id|purpose|band|style|tier` (формат
  `bed-xxxxxxxx`), матрица — из профиля (`tools/scout/compose_bedroom.py:cells`), в записи `provenance` (правка профиля её меняет).
- **Поколение 0** — только `tools/scout/room_bootstrap.py --room bedroom run --confirm-lead` при `write_enabled`; откат — живой
  переименовывается в папку поколений. Суд `room_bootstrap.py:verdict` — `compose_bedroom.check_bank(spare='warn')`: нехватка запаса
  замен у поколения 0 — строка журнала поколения; ночная замена — `spare='hard'` (решение ведущего 06.11).
- **Писатель учится комнате** (`tools/scout/bank_refresh.py`): ключ ячейки из спецификации; новые ячейки дописываются в хвост, вне
  матрицы — `retired` (решение ведущего 07.11 «add + retired»). Чужой manifest (поле `room`) — отказ.
- **Репетиция** `tools/scout/bank_rehearsal.py:rehearse` (флаг `rehearse_enabled`): копия живого банка и журнала → настоящий
  `bank_refresh.write` в копию → откат по SHA; живой банк, прод и сеть не трогаются, сбой — WARN.
- **Сборщики:** `tools/scout/compose_bedroom.py`, `tools/scout/compose_hall.py` (правила `tools/scout/rules/bedroom-composition.json`,
  `tools/scout/rules/hall-composition.json`), общее (цвет, палитра) — `tools/scout/compose_common.py`; порядок кандидатов: меш готов → сгенерирован →
  нет → брак; на позиции `has_mesh`/`mesh_defect`; `report.json → shortage, mesh_need`. Стиль без товаров ядра ночью не собирается
  (`compose_bedroom.py:core_skip`, пропуск — в отчёт), суд не ослабляется.
- **Стили комнат:** спальня — 6 (`bedroom-composition.json:styles`, владелец 06.11 «вся квартира во всех стилях», отменяет ADR-0330 п.3),
  прихожая — 5 без неоклассики (`hall-composition.json:_styles_why`, владелец 07.11). Квота и спрос мешей берут стили из правил комнаты.
- **Прихожая:** каталог — `tools/scout/hall_catalog.py` + `tools/scout/rules/hall-roles.json` (`room_catalog.py` не тронут); солвер —
  `services/planner-solver/planner/hall.py`, проверки `hall_checks.py:validate_hall`; вход — `is_entrance` в `tools/scout/flat215-hall.json`.
  Роль «прихожая» (комплекты-стенки без размеров) в 3D не идёт — её доля квоты ушла в «шкаф-купе»; банкетку добирают пуф/скамья по
  форме (≥ 60 см, Ш/Г ≥ 1,4, Г 25–52, В 38–52). Оценка стиля — `style_score.py --source hall` (свой `style-scores-hall.json`).

  прогрев, досъёмка (06.11: привязка 05.11 21:28 собрана до решений разворота — новые модели не доходили до демо).
- **Выкладка своих моделей** — `tools/scout/room_publish.py` по привязке (спальня; с 07.11 и гостиная); галерея берёт тот же файл

  Смена файла под тем же msid фото не обновляет — переснимать.
- **Кружки цвета** («Цвета этой модели») — по семье `sku.fam` (представитель), не по msid (`tools/scout/flat215-demo/index.html:famKey`).

  (`d_catalog`). Откат — `effective: false` или `FLAT215_EFFECTIVE_DIMS=0`.

## Стыки этапов (ADR-0272)
Пороги — `tools/scout/rules/pipeline-map.json`, расчёт — `tools/scout/pipeline_map.py`, страница `/test/pipeline/`; тревога при смене состояния, напоминание жёлтый/72 ч, красный/24 ч.
