## Цель
Кнопка «кадр» в демо работает одинаково, включена DEV-машина владельца или нет: рендер считается на
проде (или на арендованной GPU по требованию), сервис живёт в `docker-compose` и деплоится как всё,
первый кадр не ждёт 25 секунд молча, при очереди человек видит место и время.

## Источник задачи
Обследование 13.10: `/api/render` на проде идёт через обратный ssh-туннель на DEV (`draft_service.py:247-279`,
`tools/scout/dev_render_backend.sh:25-31`, ADR-0139 «временный костыль»); без DEV — медленный и
худший локальный рендер, 60/час, один за раз, иначе 429 (`:280-317`); `draft:8099` поставлен `docker cp`
вне compose (`domain/deployment-details.md:70,79`); холодный кадр ~25 с, опрос сдаётся после 40 попыток
(`index.html:768, 2303`). `project-state.md` «Ждёт владельца»: апгрейд VDS (4–8 ядер / 8 ГБ).

## Дополнение 13.10 от соседней сессии (remlab-a8, проверить при «деплой»)
Прод-контейнер `remlab-draft` собран РУКАМИ: в `/app` лежат копии файлов с `.bak` от 08.09, и они
разошлись с репозиторием. 13.10 демо из-за этого падало: в контейнере был старый
`planner/models.py` без поля `hung`, отсутствовали `improve_mode.py` и `styles.json`. Файлы доложены
`docker cp` — при пересоздании контейнера это потеряется. Поэтому п.2 ниже («сервис в compose,
образ из CI») — первый по приоритету, а не второй.

## Скоуп — что входит
1. **Замер:** сколько стоит кадр на проде сейчас (CPU, время, качество) и на DEV; какие шаги
   рендера тяжёлые (`draft_render.py`) — таблица владельцу с тремя вариантами: А) апгрейд VDS и
   рендер на проде; Б) GPU по требованию (Salad/fal) с кэшем по хешу сцены; В) предрасчёт всех
   кадров пресетов ночью + живой рендер только для своих правок. Рекомендация — В + А.
2. **Сервис в compose:** `draft` как сервис с образом из CI, env, лимитами памяти, health-эндпоинтом;
   `deploy-remote.sh` его катит; туннель DEV — выключен (или остаётся как ускоритель с явной меткой
   «качество/скорость» в ответе, не молча).
3. **Очередь и статус:** задание → позиция/оценка времени → прогресс; клиент не сдаётся по счётчику,
   а по таймауту сервера; кэш кадров по хешу снимка сцены (`b2b-05`).
4. **Прогрев:** предрасчёт кадров пресетов при публикации (`publish_demo.sh` → `warm`), чтобы «2 вида»
   на карточках всегда были готовы без DEV.
5. Процесс-тест: «кадр по пресету отдаётся < 2 с из кэша; живой кадр — < N с, N из замера».

## Скоуп — что НЕ входит
- Смена движка рендера (scene3d остаётся).
- GPT-улучшение кадров (отдельное решение владельца, платное).
