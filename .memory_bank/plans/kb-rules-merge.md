## Цель

Вшить знания source-KB (Mitton/Nystuen, снапшот r20260810a) в текущий зонный движок так,
чтобы правила ДОПОЛНЯЛИ друг друга без противоречий (конгруэнтность через constraint-CI и
приёмку «0 хуже»): композиции band 50+ (два дивана / диван+пара кресел), политика парности
и цвета, подбор и укладка ковра, Г-геометрия стыка, клиренс-чек-слой из KB.

## Источник задачи

Владелец, 2026-08-10, после ручных демо по KB (`/test/set112-manual/`,
`/test/set112-50m2-manual/`): «продумай, как имплементировать; два РАЗНЫХ дивана — странно;
либо одинаковые, либо диван + два одинаковых кресла; с ковром надо что-то сделать; правила
должны дополнять друг друга, не противоречить, быть конгруэнтными».

## Факты (проверено по коду/данным)

- `services/planner-solver/rules/zones.json` — 10 посадочных групп УЖЕ включают 2-диванные
  (`sofa_facing_sofa`, `two_sofas_2armchairs`, `sofa_loveseat*`) и парные кресла
  (`armchair_pair`, `sofa_2armchairs`); проблема не в отсутствии групп.
- `tools/scout/compose2.py` — есть «Разнообразие v2» (анти-повтор крупных связок МЕЖДУ
  сетами) и `palette_score` (цветовая близость cls/rgb); политики парности ВНУТРИ сета
  («2 дивана → одинаковые/совместимые») НЕТ — из-за неё Босс ХЛ ≠ Челси в одном сете.
- `occupancy.json`: диван↔столик hard [32,50], preferred [40,45] — КНИЖНОЕ 30–46
  согласуется (supported); ТВ: диагонали [1.2,2.5]+hard 400 — книжные вилки (52″: 210–335)
  внутри (supported); ковёр-канон: `rug_longer_than_sofa` [30,50], `rug_beyond_sofa_side`
  [15,20], anchor «передние ножки» — есть, но НЕТ (а) подбора РАЗМЕРА ковра под кластер в
  композиторе, (б) центрирования по ОСИ главного дивана в солвере.
- Каталог ковров — 26 SKU (дыра каталога, отмечена ещё в А2) — политика подбора упрётся в
  ассортимент.
- Уроки ручных демо (сегодня): Г-стык двух диванов обязан быть ТОРЕЦ-К-ТОРЦУ (бок-к-спинке
  = один загораживает другой); ковёр кладётся по оси главного дивана, под передние ножки
  обоих диванов; люстра-центр-комнаты конфликтует с крупным кластером в центре (нужна
  демоция «сдвиг к центру зоны»); экран для дистанций >3 м — помечать «55″+».
- Решение владельца 10.08: правила «рынка США» из KB — рабочие (СП в системе нет);
  габариты — только конкретные SKU, недостающее — inventory-прайор.

## Скоуп — что входит (волны)

### W0 — экспорт кандидатов и классификация (без изменения прода)
`services/knowledge-db/kdb/export_rules.py`: из canonical KB → таблица кандидатов
(claim → параметр rules/*.json, значение, сила, страница-пруф). Классификация КАЖДОГО
текущего параметра occupancy/zones против KB: `supported | contradicted | too_strict |
too_weak | missing | semantic_only` (по 11_next_stage_plan). Выход —
`docs/kb-rules-classification.md` таблицей: **конфликты решает владелец**, supported —
фиксируются пруф-ссылками (закрывает вопрос №2 рефери об источниках).

### W1 — политика парности и состава больших групп (композитор)
В `compose2.py` + данные:
1. Группа с «диван 2»: (а) приоритет 1 — same model (один mid/коллекция, второй экземпляр);
   (б) приоритет 2 — тот же магазин + `palette_score`-близость (порог утвердит владелец) +
   сопоставимая глубина (±10 см); (в) иначе группа ДЕМОТИРУЕТСЯ до «диван + кресло×2
   (одинаковые)» — пары кресел уже поддержаны ролями «кресло/кресло 2».
2. «Угловой + прямой одной коллекции» — допускается только при same-collection признаке
   (редкость — не строить эвристик, просто разрешить точное совпадение).
3. Подбор ковра ПО КЛАССУ КЛАСТЕРА: требуемый мин-размер = столик + фронт главного дивана
   + `rug_beyond_sofa_side`; band 50+ → класс ≥200×290. Нет подходящего SKU → ковёр
   опускается честно (без «маленький под столик б/о привязки»), лог дыры ассортимента.

### W2 — геометрия групп в движке (зоны/солвер)
1. Шаблоны 2-диванных групп в `zones.json`: явный Г-стык **торец-к-торцу** (запрет
   конфигурации «бок-к-спинке» — новый check с кодом в severity.json, класс S1).
2. Ковёр: кандидаты центрируются по ОСИ главного дивана группы (не по комнате/зоне),
   покрытие: столик целиком + фронтальные ножки диванов (действующий канон «передние
   ножки» сохраняется — только центрирование добавляется в скоринг).
3. Демоция люстры: если геометрический центр комнаты попадает в footprint посадки
   глубже N см (константа в occupancy.json, предложение 15) — сдвиг к центру зоны отдыха;
   правило владельца «люстра по центру» остаётся дефолтом.
4. ТВ-дистанция: аннотация «рекомендуемая диагональ» в выдаче (55″+ при >3 м) — метаданные,
   не блок.

### W3 — чек-слой клиренсов KB + конгруэнтность (гейт волны)
1. Внедрить ТОЛЬКО утверждённые владельцем позиции W0 (missing/too_strict) в
   `occupancy.json` — числами с пруф-комментарием (страница книги).
2. **Конгруэнтность механически**: (а) `test_contracts` (совместная выполнимость пар
   правил — урок 204) прогон на каждом изменении; (б) приёмка 252 A/B: **0 сцен хуже**,
   отдельный разрез band 50+; (в) новые проверки — по severity-классам, не бинарно.
3. Регресс демо-сцен: обе ручные раскладки (15 м², 57.5 м²) — фикс-тесты «солвер даёт не
   хуже ручной по hard/soft» (цель, не гейт первой итерации).

### W4 (опционально, флаг, дефолт ВЫКЛ) — Judge-подсказки
`kdb query --plane C` как источник bounded-подсказок для сцен-провалов приёмки (анализ
ПОСЛЕ солвера, без геометрии от LLM) — только отчёт, в прод-скоринг не вмешивается.

## Риски
- Ассортимент: одинаковых пар диванов в фидах может быть мало → приоритет (в) «диван +
  2 кресла» станет основным — это ок по книге (обе композиции канонические).
- Приёмка может показать регресс от новых чек-кодов → severity S1/S2 (мягкие), не hard,
  до вердикта приёмки.
- Каталог ковров (26 SKU) ограничит W1-подбор — фиксируем дыру, не костыляем.
