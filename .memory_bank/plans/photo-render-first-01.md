## Цель
Человек нажимает «Сделать фото» → через понятное время видит РЕНДЕР своей расстановки (те же 2 ракурса, что сейчас у фото) →
кнопка становится «Улучшить фото» → нейросеть получает уже рендер вместе с фото товаров, тем же конвейером, что сейчас (вместо
кадра из браузерного 3D). Одинаково на /demo и в турах; проверка — с телефона.

## Источник задачи
Владелец 17.11 TG 1510 (голос): «вместо „сделать фото“ запускать не GPT, а рендер… выбираем два ракурса, как сейчас… как только
рендер готов — показывает рендер, а кнопку менять на „улучшить фото“… это же фото отправлять в GPT, уже отрендеренное, вместе с
товарами… тем же пайплайном… везде одинаково, проверять с телефона». Основа — ADR-0419 (рендер Blender бесплатно, мебель как есть),
ADR-0424 (камера Б), план `render-3d-01.md`, Codex `_intake/codex/2026-11-17-quality-price-eval-answer.md`.

## Как сейчас (по коду)
- Страница шлёт кадр браузерного 3D + расстановку → `/api/render` (тур — `/api/trial/<id>/photo`) → сервис `tools/scout/draft_service.py`
  на DEV (systemd `remlab-render`): очередь `draft_jobs.JobStore`, `_LOCK` = 2 одновременных, ETA `draft_guard.queue_eta`, денежный
  гейт `_paid_gate`, реестр кадров → нейросеть «только улучшить» (`improve_mode.py`, ADR-0302/0305).
- Рендер Blender — только пробы: `tools/scout/cycles_probe/demo_scene_dump.mjs` (сцена /demo → JSON+GLB через `lib/viewer3d/scene-export.ts`)
  → `render_cycles.py` (CPU, ~4–5 мин/кадр 1536 px 64 выборки на 4 потоках).

## Шаги (общий план директора и Codex, 2 круга: `_intake/codex/2026-11-17-photo-render-first-answer.md`, `…-r2-answer.md`)
Одна логика для /demo и ЛЮБОГО нового тура (TG 1518); без особых случаев по ID; сгенерированное — только конвейером.
1. **Контракт снимка** (рабочий 1; директор утверждает). Страница шлёт правки расстановки и позы C1/C2; сервер сверяет комнату, товары,
   ассеты с данными квартиры и каталога, ограничивает числа, строит сцену теми же правилами экспорта (`lib/viewer3d/scene-export.ts` —
   дополнить свет: сейчас `lights: []`, :242; без бокового `scene.json`/GLB декора проб `render_cycles.py:91/695`), хеш — после
   канонизации. Готово: 2 гостиные + 2 спальни, пары «3D | Cycles» — те же SKU, места, камеры.
2. **Замер времени и качества** (рабочий 2 по матрице директора; параллельно с 1 — подготовка). 2 гостиные + 2 спальни × C1/C2:
   1536×1117/64/4 потока, 1536×1117/32/4, 1024×744/32 на 2 и 4 потока; по 2 прогона, выбранный режим ×3 (≥ 24 замеров); холодный и
   тёплый, два заказа одновременно через `tools/ops/heavy_slot.py`. Числа: p50/p95 от нажатия до ОБОИХ кадров, подготовка, ожидание
   слота, CPU, пик RAM, вред другим DEV-сервисам, дефекты материалов. Итог владельцу → решение CPU / пилот GPU (❓1).
3. **Отдельное задание Cycles** (рабочий 1): свой тип, очередь, ETA и пределы в `draft_service.py`/`draft_jobs.py`/`draft_guard.py`
   (не слоты нейросети: сейчас 40 записей/2 ч, ожидание слота 600 с — `draft_jobs.py:24/94`, `draft_service.py:160`); отказ до
   постановки при заполнении, склейка одинаковых хешей, один процесс Blender с лимитами времени/RAM/диска и остановкой дерева,
   интерактивные раньше прогрева, ID и результат переживают перезапуск.
4. **Два маршрута: рендер и улучшение** (рабочий 1): `app/api/render/*`, `app/api/trial/[id]/photo/route.ts`, `lib/trial/repo-photo*.ts`.
   Рендер тура — та же проверка `photo_ok`/версии/размеров, НО без брони и квоты AI-фото; свои лимиты по человеку/IP/туру и бюджет
   ядро-минут до очереди. «Улучшить» — только из готовой пары рендеров того же состояния → действующий конвейер нейросети + связь
   кадров в трассе (ADR-0013). Ошибка рендера — текст и «Повторить», без тихого перехода на нейросеть.
5. **Экран — до кода** (рабочий 2 готовит снимки, директор показывает): 375×667 и ПК — ожидание (очередь и диапазон из замера, не
   «≈1 мин»), готовый рендер, улучшение, ошибка, два ракурса; место «Улучшить фото» во вкладке «Фото»; подписи RU/EN (❓3).
6. **Машина состояний страницы** (рабочий 2, единственный правит `index.html`): «Сделать фото» → «Рендерится» → «Рендер» (2 кадра) →
   «Улучшить фото» → «Улучшается» → «Улучшено». ID задания восстанавливается после закрытия вкладки; правка во время ожидания —
   старый кадр помечен снимком прежнего состояния, для новой расстановки снова «Сделать фото». Проверки — `tools/ops/demo-walk/`,
   `tools/ops/demo-i18n-scan.mjs`.
7. **Тур с нуля сквозь весь путь** (рабочий 1 — сервер и очередь автофото `lib/trial/auto-photos-queue.ts`; директор — приёмка): создание
   → подтверждение → публикация → покупатель → правка → рендер C1/C2 → улучшение → перезагрузка. Автофото — по ❓2.
8. **A/B входа нейросети и кэш** (директор): 4 состояния × C1/C2, тот же промпт и фото товаров, меняется только вход (рендер / браузерный
   кадр); слепая оценка SKU, формы, числа предметов, ракурса, затем красоты; пары — владельцу. Прогрев — только если замер покажет
   пользу; ключ: состояние, обе камеры, размер/качество, версии экспорта/Blender/света, хеши ассетов.
9. **Выпуск** (все в своих областях): контрактные и нагрузочные тесты зелёные; телефон и ПК, /demo и НОВЫЙ тур; очередь, перезапуск,
   потеря сети, двойное нажатие, отказ Blender, обе квоты; метрики `job_id`, `scene_hash`, версии, времена, ошибки, источник входа AI.

**Решения владельца (17.11):** ❓1 (TG 1523) — ожидание решить после замера, но рендер СРАЗУ на видеокарте в конвейере: есть живая
машина Salad (меши) — рендер на ней вне очереди, нет — облачная видеокарта по API (RunPod/fal/…), чтобы человек не ждал; постоянную
Salad пока не держать; сравнить цены. ❓2 (TG 1525) — автофото тура рендером, нейросеть только по кнопке. ❓3 — экраны снимками до кода.
**Где разошлись:** узкий кадр для телефона — не в первом выпуске (телефон нарочно получает широкий кадр, `index.html:11771`); выгода —
только по замеру.

## Видеокарта (владелец TG 1523; Codex `_intake/codex/2026-11-17-render-gpu-route-answer.md`)
**Поправка владельца 17.11 TG 1585:** «если машину держать всё равно — Salad для рендеров отдельную, недорогую» → своя группа Salad
только под рендер (дешёвая карта, напр. 3090 $0,09–0,20/ч ≈ $65–145/мес круглосуточно) — основной путь; RunPod — запасной при
вытеснении/занятости. Режим (круглосуточно или по часам) — ❓ TG 1586/1597. Меш-группу под фото не трогаем.
**Поправка владельца 17.11 TG 1596 (голос):** «с RunPod работал — тоже долго включаются и машину искать; на Salad можно взять дорогой
тариф — машина найдётся всегда» → **RunPod убран.** Основной путь — своя группа Salad под рендер, высокий приоритет, держится
включённой (3090 ≈ $0,20/ч, 4090 ≈ $0,44/ч — выбор по пробе); при вытеснении — запасной рендер на CPU DEV (честное ожидание), пока
Salad ставит замену. Аккаунт и ключ Salad есть (меш-пул) — проба без нового аккаунта. Абзацы про RunPod ниже — история решения.
Шаг 2 «замер» теперь — пилот GPU ≤ $5 (стоп при $4 начислений), CPU DEV — только запасной путь.
- **Основной путь — RunPod Serverless, RTX 4090** ($1,34/ч; 0 постоянных, 1 максимум, короткий простой, тайм-аут задания), оба ракурса
  в одном процессе Blender. Контроль — смешанный класс L4/A5000/3090 ($0,75/ч) и Modal L4 (третьим). fal — нет (только H100/PRO 6000 от $4/ч).
  Оценка (не замер): пара на тёплой 4090 ≈ 85 с оплаты ≈ 3 ₽; холодный старт неизвестен (десятки с — минуты).
- **Salad — ускорение, не обязательный путь:** «живая» по `queue_run.py:103` ≠ свободная (меш в работе, VRAM после Hunyuan); нужен
  атомарный допуск на `instance_id` с lease на пару, меши не прерывать; образ один (меши + Blender, арбитр GPU); `idle_guard.sh:34` и
  `salad-deadman.py` должны видеть lease, иначе группу остановят посреди кадра. Испытание — после RunPod.
- Сцена: манифест с хешами + подписанные короткие URL на GLB/карты, кэш воркера по хешу; секретов в образе нет. Объём сцены — измерить.
- `render_cycles.py:109` сейчас явно ставит CPU — включить OptiX явно, проверить фактическую GPU.
- Пилот: 4 пары 4090/64 (холод/тепло), 2 пары 128, 2 пары смешанный класс; раскладка ожидания (очередь, старт, загрузка, BVH, кадры,
  OIDN, idle), цена за готовую пару, два заказа сразу, потеря воркера между кадрами. **Нужен аккаунт RunPod (карта владельца) — ❓.**

## Скоуп — что НЕ входит
- Мебель в рендере не меняем (ADR-0419). Свет/пересвет окон — отдельный пункт П1.78. Сторож кадров — `plans/render-qa-gate-01.md`.

## Критерии приёмки
- [ ] Рендер на кнопку: на GPU своей группы Salad (высокий приоритет; вытеснение → CPU DEV), p50/p95 от нажатия до ОБОИХ кадров (холод/тепло), цена за пару; DEV-CPU — только запасной
- [ ] Рендер совпадает с 3D расстановкой страницы (те же товары, позы, ракурс) — пары «3D | рендер» на 2 гостиных + 2 спальнях
- [ ] «Улучшить» шлёт рендер + фото товаров тем же конвейером; трейсинг (ADR-0013) пишет вход-рендер
- [ ] /demo и тур одинаково; RU/EN; без ID в коде; отказ рендера — запасной путь, без «вечного ожидания»

## Риски
- Время CPU и общие ядра DEV (16 на все машины) — очередь при наплыве; кэш по умолчанию смягчает.
- Расхождение сцены страницы и Blender (контракт с версией и хешем лечит).
- Нейросеть по рендеру может «перерисовать» товар сильнее/слабее, чем по браузерному кадру — сравнение парами до включения.
