## Цель
Одна ссылка, где владелец глазами проверяет ВСЕ готовые меши: по 20 на страницу, у каждого
вертящаяся 3D-модель и одна кнопка «переделать». Нажатие сразу пишется в БД как факт ручной
проверки и ставит меш в общую очередь на перегенерацию (не больше двух раз на товар).

## Источник задачи
Промпт владельца 05.09: «постранично по 20 мешей на страницу, все меши, 1 кнопка под каждым
"переделать"; по кнопке фиксируй решение в базе, что была ручная проверка, и автоматом ставь
в очередь». Уточнения владельца в этой же сессии:
1. показывать **вертящуюся 3D-модель** (не картинки-ракурсы);
2. переделка идёт в **общую очередь** (порядок конвейера не меняем);
3. **максимум 2 переделки** на товар, и «обязательно помечать, когда помечен на переделку»;
4. модели возить на сервер **партиями**, кнопка «следующая партия» — текущая удаляется, едет
   следующая, «я подожду»;
5. **удалять можно только копии** на сервере, исходники на DEV — никогда.

## Факты, на которых стоит план (проверено сегодня)
- Мешей на DEV: **1490** `model.glb` (`~/scout-scenes/meshes-hunyuan/meshes/hunyuan21/v2`, 31 ГБ);
  в реестре `asset_revisions` 1347 не-legacy ревизий (реестр догоняет диск). Перечень для
  страницы берём с диска — это то, что реально существует.
- Один меш = 7,6 МБ (геометрия 1,5 МБ + текстуры в base64 внутри JSON). Скорость DEV→прод
  измерена: **2,2 МБ/с** → 200 мешей ≈ 1,5 ГБ ≈ **12 минут** заливки.
- Прод-сервер: свободно **17 ГБ**, там же приёмник конвейера (до 8 ГБ) и сайт → держим на
  сервере не больше ОДНОЙ партии ~1,5 ГБ.
- Готовый образец моста DEV↔прод: `/lab/mesh-review` (кука владельца `MESH_REVIEW_SECRET`,
  машинный `MESH_REVIEW_MACHINE_TOKEN`, решения append-only, курсор `after_id`) —
  `app/api/lab/mesh-review/*`, `lib/mesh-review/auth.ts`, `tools/scout/mesh_review_sync.py`.
- Механика переделки уже есть: перегон с новым seed (`mesh-reseed.json`, `apply_repairs.py`)
  и статус **`owner_reject`**, который предикат готовности `tools/scout/mesh_ready.py` уже
  понимает как «в сеты не брать».
- Общая очередь конвейера — файл `tools/scout/mesh-queue-v1.json` (11 704 задания), курсор
  позиционный (`--skip done --limit n`), файл перечитывается на каждой пачке → дописывание в
  ХВОСТ безопасно. Предохранитель бегущего конвейера `MESH_MAX_JOBS=12000` — запас всего ~296.
- Пул Salad сейчас **стоит** (`группа остановлена и не стартует — кредиты`), генерация не идёт:
  переделки будут копиться в очереди и поедут, когда пул оживёт. Страница говорит об этом прямо.

## Как устроено
**Прод** (Next.js + прод-Postgres) — страница и решения владельца:
`/lab/mesh-audit?page=N` (вход тот же, что у mesh-review — существующая закладка владельца).
**DEV** — истина по мешам: список, файлы, применение решений, очередь.
**Мост** — тот же паттерн, что у mesh-review: DEV пушит список по Bearer, забирает решения
курсором, отчитывается о состоянии партии.

Карточка меша: `<model-viewer>` с постером (лёгкий рендер 320px) — модель грузится по клику
(20 моделей сразу = 150 МБ, поэтому по требованию + переключатель «загрузить все на странице»);
подпись — роль, название, sku, дата генерации, seed/попытка; одна кнопка **«переделать»**.
Помеченный меш вместо кнопки показывает бейдж «на переделке 1/2» (после двух — «нужна замена
товара/фото», кнопка выключена).

Партии: страницы 1–10 = партия 1, 11–20 = партия 2 и т.д. (200 мешей ≈ 1,5 ГБ). Кнопка
«следующая партия» / «загрузить эту партию» пишет запрос в БД; DEV-служба раз в минуту видит
запрос → удаляет НА ПРОДЕ каталог текущей партии → заливает новую → отмечает «готово».
Страница показывает прогресс («партия готовится: 84 из 200»). Постеры публикуются для всех
мешей сразу (~45 МБ) и не удаляются — поэтому любая страница видна всегда, даже вне партии.

Что происходит по кнопке:
1. append-only решение в прод-БД (ревизия, кто, когда) — это и есть «была ручная проверка»;
2. карточка сразу помечена;
3. DEV в течение минуты: `asset_revisions.status='owner_reject'` (меш выходит из сетов и
   автозамен) + задание с новым seed дописывается в хвост `mesh-queue-v1.json`;
4. вторая пометка — второй перегон; третьей нет: статус «нужна замена товара/фото» и
   отдельный список для владельца.

## Скоуп — что входит
- Прод: 3 таблицы, 3 API-ручки, страница с пагинацией и кнопкой, вендоренный model-viewer.
- DEV: скрипт синхронизации (список/решения), скрипт партий (публикация/удаление копий),
  скрипт постеров; шаг в `post_steps()` конвейера, чтобы новые меши сами получали постер и
  попадали в список; крон раз в минуту.
- Тесты: идемпотентность решения, лимит 2 переделок, границы пагинации, маппинг страница→партия,
  предохранители удаления и места на диске.

## Скоуп — что НЕ входит
- Сжатие/децимация мешей (владелец смотрит ОРИГИНАЛ бит-в-бит — так честнее; урок с
  декимированным запасным путём).
- Оценка ориентации (это отдельный поток `/lab/mesh-review`) и любые правки геометрии.
- Приоритетная волна переделок (владелец выбрал общую очередь).
- Автоматическая замена товара при «нужна замена» — только список.

## Риски и как страхуемся
- **Место на проде** (17 ГБ, там же приёмник конвейера): одна партия ≤ 1,5 ГБ, проверка
  свободного места ДО заливки, удаление строго по захардкоженному пути партии.
- **Исходники**: в скриптах нет ни одной операции удаления над `~/scout-scenes/**`; удаление
  только на проде и только внутри каталога партии (проверка префикса + тест).
- **Бегущий конвейер**: правки касаются только `post_steps()` — применятся при следующем
  перезапуске, бегущий процесс не трогаем (пул сейчас стоит, перезапуск бесплатен).
- **`MESH_MAX_JOBS=12000` при 11 704 заданиях** — на переделки остаётся ~296 мест; при упоре
  скрипт откажет с внятным сообщением, а не молча потеряет задание.
- **Пул без кредитов**: очередь копится, страница честно показывает «генерация стоит».
- **Память на DEV** при рендере постеров — короткоживущие процессы по ~20 мешей (урок 391).
- **VPN-нода `remnanode` на том же сервере** — не трогаем.
