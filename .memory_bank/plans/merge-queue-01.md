## Как устроен сборщик (MVP)
- **Где:** `tools/ops/merge_queue.py` + обёртка `tools/ops/merge-queue.sh`; код — только в worktree `worktree-merge-queue-1112` до влития (урок 516).
  Запуск в MVP — вручную директором/менеджером (`r 'tools/ops/merge-queue.sh <ветка>[@sha] …'`); крон — позже, после «ок» директора.
- **Вход:** 2–4 ветки или SHA (`ветка@sha` — проверяем ровно этот хеш, не вершину ветки, урок 612); пакет автора — необязательный JSON
  (`--pkg`: T-ID, что проверил сам, риск) — в отчёт.
- **Пробное слияние:** временный worktree `~/remlab-logs/mq/<ЧЧММСС>/wt` от текущего `main` (`git worktree add --detach`, основную копию и
  ветку main не трогает, `fetch` не делает). Ветки — по очереди `cherry-pick merge-base..sha` (как вливает директор). Конфликт → `--abort`,
  ветка выбывает строкой «конфликт», остальные идут дальше. Две ветки с `flat215-demo/index.html` — вторая в отчёте с пометкой «общий ресурс».
- **`node_modules`:** `pnpm install --offline --frozen-lockfile` (жёсткие ссылки из хранилища pnpm, без сети; урок 611). Симлинк на
  `node_modules` основной копии не берём: next/tsc разрешают пути через реальный путь и при другом lockfile молча берут чужие версии.
- **Один полный прогон** под `tools/ops/heavy-slot.sh mq-full --min-gb 3 --cores 3` (по `--stats`: набор `full` пик 1,5 ГБ, сборка RSS 2,4 ГБ,
  vitest ~2,6 ядра): `pnpm typecheck` → `lint` → `test` → `build` → prepush-набор (`prepush-check.sh --files <изменённые>`) → аудиты памяти
  (`memory-audit.mjs --check`, `memory-project-audit.mjs`; при `_kit/gate-mode.txt` = warn — предупреждение, не падение). Первый упавший
  шаг останавливает прогон. e2e, docker, db-init — в CI после push (как сейчас).
- **Падение:** (1) повтор упавшего шага на том же наборе — прошёл → «мигает», вину на ветку не вешаем; (2) тот же шаг на чистом main — падает →
  «main красный», ветки не виноваты; (3) деление пополам по префиксам набора (main+B1, main+B1+B2 …) — только упавшим шагом; (4) виновная
  выбывает, набор без неё — снова полный прогон. Худший случай на 4 ветки с одной виновной: 1 полный + 1 повтор шага + 1 шаг на main +
  2 шага бисекции + 1 полный = **2 полных + 4 одиночных шага**; с двумя виновными — ещё ≤ 2 шага + 1 полный.
- **Отчёт:** `~/remlab-logs/mq/<ЧЧММСС>/report.md` — строка на ветку `ветка · SHA · ok | конфликт | падает: <шаг>: <тест>`, время
  прогона, пути логов; `summary.json` и логи шагов рядом. Временный worktree удаляется `git worktree remove`, если всё зелёное; при падении
  остаётся для разбора.

## Как директор запускает вместо ручной пачки — одна команда
`r 'cd /home/pakar/igor/remlab && tools/ops/merge-queue.sh worktree-a-1112 worktree-b-1112@<sha> worktree-c-1112'`
→ через 6–15 мин в выводе и в `~/remlab-logs/mq/<ЧЧММСС>/report.md`: строка на ветку и «Вливать в этом порядке: …». Директор вливает
зелёные ветки ровно этими SHA (cherry-pick/ff, как сейчас) и пушит сам. Шаги можно сузить: `--steps typecheck,test`. До влития сборщика в
main — тот же вызов из worktree: `cd .claude/worktrees/merge-queue-1112 && tools/ops/merge-queue.sh …`.

## Режим «в тени»
Не пушит, не вливает, флага вливания в MVP нет. Каждый прогон — строка в `~/remlab-logs/mq/journal.tsv` (время, ветки, SHA, база, вердикт,
минуты). Неделя статистики: сравнить вердикты с фактом (влита ли ветка, был ли откат main/красный CI после). Переход к авто-вливанию —
только словом владельца, при «ложный зелёный» = 0 и «ложный красный» только из-за мигающих тестов.

## Риски
- Директор (и algor) вливают руками одновременно — сборщик проверяет на снимке main и пишет базу в отчёт; код в main сменился —
  вердикт «устарел», прогнать снова. Main и основную копию сборщик не меняет.
- Грязное дерево main — не важно: берём закоммиченный `main`, не рабочую копию.
- Кроны берут скрипты из основной копии — код сборщика до влития только в worktree; крона в MVP нет.
- Worktree без данных вне git (урок 662) — прогон равен CI (там их тоже нет); регресс, экзамены, снимки остаются у автора.
- Мигающие тесты (селфтест очереди под нагрузкой, test_beam) — повтор шага до бисекции.
- Отказ сборщика — ничего не ломает: директор вливает как раньше; упавший worktree остаётся, повтор — новой папкой.
