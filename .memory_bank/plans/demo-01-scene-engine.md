## Цель
В демо (`tools/scout/flat215-demo/index.html`) сцена гостиной рисуется в браузере тем же движком, что и `/flat`
(`lib/viewer3d/viewer.ts`, класс FlatViewer): заменил диван или подвинул столик — картинка меняется на следующем кадре,
без кнопки и без ожидания сервера. Серверный растеризатор (`tools/scout/mesh_render.py`, `draft_render.scene3d_frame`)
остаётся для трёх дел: ночные карточки стилей, запасной путь без рабочего WebGL, лист 2048×3072 для платного «Улучшить»
(ADR-0184). Три копии сцены (viewer.ts, служебный three.js в демо `openScene` IH:3255–3363, numpy) сводятся к одной
живой модели сцены и одному браузерному рендереру.

## Источник задачи
Владелец 14.10: «Должен быть общий движок. Мы делаем 3D, и из этого 3D собирать фотографию. Если 3D открывается за
секунду, почему фото не за секунду? Заменили диван — сразу, без кнопки, показывается новая сцена.» Критика Codex —
`_intake/codex/2026-10-14-demo-engine-critique.md` (вердикт: «делать иначе — общий browser-renderer для живой сцены без
постоянной генерации PNG; numpy оставить как прогрев/fallback/GPT-лист»).

- `/flat`: FlatViewer без React (`viewer.ts:1-6`), профили `DESKTOP_QUALITY`/`LITE_QUALITY` (`viewer.ts:59-78`), детект
  программного WebGL (`viewer.ts:33-44`), `snapshot()` через `toDataURL` (синхронный, `viewer.ts:1020-1024`), undo
  (`lib/configurator/history.ts`). Фото-режим шлёт тот же `/api/render` (`components/flat3d/PhotoView.tsx:54`).
- Лёгкие копии моделей (`tools/assets/runtime_mesh.py`, `/rt/`): 40 моделей; у 36 моделей пяти вариантов демо — 2.
  Без копии `lib/configurator/data.ts:20-32` молча берёт исходный GLB 4,5–9,8 МБ → вход в 3D 30–60 МБ.
- Камеры: у ходьбы в FlatViewer `z + cos(a)` (`viewer.ts:1005-1013`), у серверного кадра `z − cos(a)`
  (`draft_render.py:252-256`, урок 414) — фото-позы в FlatViewer нет.
- `syncObjects()` при смене координат удаляет и создаёт объект заново (`viewer.ts:257-304`, `:1139-1147`) — для
  перетаскивания это слишком дорого.

## Скоуп — что входит
1. **Общий бандл рендерера.** Из `lib/viewer3d/*` + тонкого адаптера данных демо собирается стабильный ESM-бандл с
   публичным API (`createScene(container, manifest)`, `update(manifest)`, `setPhotoPose(cam)`, `setMode('photo'|'walk'|'top')`,
   `exportFrame(w,h,'image/jpeg')`), публикуется рядом с демо (`/demo/lib/scene.js`, версия в имени). НЕ копировать
   `_next/static`-чанки; НЕ переводить демо в Next (ADR-0158: демо — один html без сборки, `docker-compose.yml:19-21`,
   `lib/embed/page.ts:11-23`). Один источник версии: демо и `/flat` импортируют одну сборку, расхождение версий — стык в
   `pipeline_map`.
2. **Манифест сцены** (`contracts/scene-manifest.ts`): комната (контур, проёмы), предметы (`role`, `msid`, x, y, rot, w, d, h,
   elev, yaw), декор, камеры, `stateId` (см. `demo-02`). Его читают и браузер, и `draft_render` (через `payload()`), и
   `fromDemoVariant` — одна модель сцены, три потребителя. Посадка и оси уже общие (`lib/viewer3d/meshes.ts:1-14`,
   `rooms.ts:1-10`) — закрепить transform-тестом «браузер и сервер ставят модель в одну точку».
3. **Фото-поза.** Контракт камеры плана → FlatViewer (та же конвенция, что `cams_from_request`; проверка скаляром
   «взгляд·направление-на-центр > 0.8», урок 414). Фото = тот же канвас в фиксированной камере, не PNG на каждое движение;
   `exportFrame` — только для сохранённого артефакта (JPEG/WebP), после `pointerup`.
4. **Движение без пересоздания.** В `syncObjects` координаты/поворот исключить из сигнатуры объекта: перемещение —
   `position/rotation` существующего Object3D; пересоздание только при смене `msid`/размеров.
5. **Лёгкие копии как ворота релиза.** `runtime_mesh.py`: ключ актуальности — хеш/версия исходного GLB, а не факт
   существования (`:243-247`); пары desktop+lite для ВСЕХ моделей текущих вариантов и первых N (из правил) кандидатов
   каждой ленты; стык в `pipeline_map`: «модель демо без актуальной лёгкой копии» = красный, демо не публикуется
   (`flat215_demo.py` проверяет перед `publish_demo.sh`). Остальной склад (794) — фоновый запас по мере волн.
6. **Предзагрузка и кэш.** При открытии карточки грузятся модели варианта (lite ≈ 1,2–1,8 МБ на сцену, desktop 2,3–3,5 МБ);
   кандидаты ленты — лениво при наведении/прокрутке, не вся лента (≈ 36–68 МБ). Кэш с перепроверкой уже есть (b2b-12).
7. **Профили и запасной путь.** Аппаратный WebGL: 1344×896, DPR 1, текстуры 512, одна тень 1024; телефон: 896×600, без
   теней; программный рендер (SwiftShader/llvmpipe) или `webglcontextlost` или пробный кадр дольше порога → серверный
   эскиз как сегодня (`makePhoto('draft')`), с честной подписью. Мобильный профиль выбирать по пробному кадру, а не по
   ширине окна (`FlatConfigurator.tsx:63-68`).
8. **Серверный путь остаётся:** ночной прогрев карточек (ADR-0280), лист для «Улучшить» (ADR-0184), запасной эскиз.
   Headless-браузер на сервере НЕ вводим (2 ядра без GPU = тот же SwiftShader; решение отдельным замером, если понадобится).
9. **Сторож DEV-рендера:** `tools/ops/dev-checks.sh` проверяет `127.0.0.1:8600/health` и туннель; убит earlyoom → перезапуск
   `dev_render_backend.sh` + строка в дайджест (урок 14.10: сутки без DEV-кадров молча).
