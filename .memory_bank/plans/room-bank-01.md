## Цель
У каждой комнаты свой живой банк (`sets-bedroom.json`, потом `sets-hall.json`), который ночью обновляется так же
безопасно, как у гостиной: кандидат → проверки → доля замен → запись с поколением → откат. Включение комнаты
не включает писатель гостиной (он выключен до контрольной ночи после T-53).

## Источник задачи
Предложение Работника 2 (T-20261105-32/6, часть Б, только чтение) и список «что осталось до главной» (T-32/5).
Сейчас (по ссылкам из отчёта, ведущий сверяет в шаге 0):

- **Банк спальни.**
  - Демо спальни берёт `BEDROOM_SETS` → живой `sets-bedroom.json`, если есть, иначе кандидат `.next` (`flat215_demo.py:1130-1139`, `bank_paths.py:97`).
  - Живого файла нет. `room_bank_output` отказывается писать живой путь (`bank_paths.py:93-101`).
- **Сборщик спальни.**
  - `compose_bedroom` пишет кандидат не атомарно (~`:677`).
  - `check_bank` всегда возвращает 0 (`:594,:688-693`).
  - `--nightly` работает только для включённых комнат, а включённых нет (`flat215-bedrooms.json`).
  - В `refresh_daily.sh` не вызывается.
- **Главная.** Комната включается реестром `data/partners/demo.json:64-71` (`enabled`), это читает `flat215_demo.py:521-530`. `FLAT215_ROOMS_ENABLED` для витрины запрещён (`:533-547`).

## Критика Codex 06.11 (`_intake/codex/room-bank-2026-11-06-answer.md`, ведущий сверил ключевое)
- Нынешние `bank_*` — не «гостиная с другими путями»:
  - ячейка `(band, style, tier)` (`set_identity.py:31`);
  - `set_id` спальни зависит от SKU (`compose_bedroom.py:134`) — замена = новый набор, а не новое поколение ячейки;
  - promote гостиной со своими правилами столовой и сцен;
  - готовность из `products` (`bank_ready.py:151`), а у комнат канон — `offer_asset_binding`.
- **Дыра и у гостиной.** Шаги ночи не связаны: `step` возвращает код, но `bank_prepare`/`pending`/`promote` вызываются подряд без `&&` (`refresh_daily.sh:411-419`). Promote читает существующий кандидат, а не результат этой ночи (`bank_promote.py:479`). Нет `run_id`, сквозного prepare → pending → promote → refresh. Между заменой живого файла и записью журнала нет восстановления после падения (`bank_refresh.py:233-244`).
- **Первый живой банк неоткуда продвигать** (`bank_promote.py:492`, `bank_refresh.py:184`) — нужен bootstrap «поколение 0».
- **`check_bank` без последствий.** Нарушения в обычной сборке не меняют код возврата (`compose_bedroom.py:688`; `--check` возвращает 1).
- **Экзамен не тот.** `bedroom_exam.py` проверяет статические наборы, не кандидата.
- **Демо-сторож.** Аналог гостиной `replaced/dropped` к спальне неприменим.
- **Порядок ночи.** `room_catalog` идёт слишком поздно (`refresh_daily.sh:435`).
- **T-53 (`slot_catalog_compatible`) и T-59 (откат публикации)** — обязательные предпосылки, не «если успеют».

## Этапы
- **А. Цепочка ночи гостиной (предпосылка и для включения писателя гостиной).**
  - `run_id` от prepare до refresh: promote и writer проверяют, что кандидат и отчёты — этой ночи.
  - Шаги цепочки через `&&`.
  - Восстановление после падения между снимком, заменой и журналом (журнал-намерение до rename, проверка при старте).
  - Тесты: устаревший кандидат/manifest/`run_id` → отказ; падение в каждом окне → восстановление.
  - Гостиная `parity` = 0.
- **Б. Ядро `RoomBankSpec`.** Пути live/candidate/report/pending/generations, правила, ключ ячейки; адаптеры composer
  (`room_profile.COMPOSERS`), каталога и готовности, strict/exam/demo; общий writer/rollback.
  - Без `--room` — адаптер гостиной, побайтно прежнее (golden-тест всех `bank_*`).
  - Таблица флагов living/bedroom `write_enabled` во всех 4 сочетаниях.
- **В. Спальня: идентичность и bootstrap.**
  - Ячейка `(room_id, purpose, band, style, tier)`, стабильный `set_id` без SKU.
  - Полная матрица 60 ячеек (запрет пропавших, лишних и дублей).
  - Происхождение в кандидате: `profile_id/version/content_sha`, `composer.plugin`, digest правил.
  - Bootstrap поколения 0 — проверенный кандидат + слово ведущего.
- **Г. Спальня: сторожа.**
  - `compose_bedroom`: атомарная запись, ненулевой код при нарушениях/HARD.
  - Strict по текущему каталогу (наличие, URL/фото, слот ↔ роль, размеры, ядро, тумбы, тиры, разнообразие, `planner.validate` HARD = 0).
  - Готовность витрины по стратегии профиля (меш: binding `ready` + `published_3d`).
  - Экзамен на фактических ячейках кандидата.
  - Демо old/hybrid: вариант не пропал, нет нового `incomplete`, ядро на месте, нет `dims_unknown`, меш опубликован.
  - Доля ≤ 25 % целыми ячейками, группировка с `room_id` и `purpose`.
- **Д. Ночь.**
  - Порядок: блок гостиной → `room_catalog` → `room_bindings` → prepare спальни → публикация мешей кандидата `--rooms-only` → `room_bindings` → pending → promote → [refresh + проверка] → демо → публикация.
  - Флаги банка комнаты не зависят от флага показа (`rooms[].enabled`).
  - Сбой спальни: живой банк спальни остаётся последним годным, гостиная и публикация идут; неопределённое состояние → демо не публиковать.
  - Расширить `tools/scout/tests_refresh_order.py`; внедрение сбоя на каждом шаге.
- **Е. Тень.** Две ночи спальни с репетицией записи в копию и откатом по SHA. Одна контрольная ночь гостиной после T-53 при `living.write_enabled=false`.
- **Ж. Включение.** Только `bedroom.write_enabled` — по слову ведущего. Показ спальни на главной — решение владельца после T-59, T-51, T-49/3 и приёмки глазами.
