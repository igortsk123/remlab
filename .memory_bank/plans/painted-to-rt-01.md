## Цель
Крашеная модель (результат покраски StableGen, `blender/painted.glb`, 15,7 МБ) сама попадает в конвейер лёгких копий и уходит на сайт
весом ≤5 МБ; тяжёлая не выкладывается молча, а идёт по лестнице «512 → упрощение → отказ с причиной». Порог — данными в `rules/`.

## Источник задачи
- Владелец TG 2671 (20.11): крашеная модель не может весить 125 МБ, прежние для сайта — 7–8 МБ; правило П-4 «модель на сайте ≤5 МБ» (ждёт «да» владельца).
- Замер T-20261120-144/1 (р.4, принято директором): шаг `tools/assets/runtime_mesh.py` даёт 15,70 МБ → 1,50 МБ (1024, KTX2+meshopt) / 1,41 МБ (-lite 512),
  139 904 грани без изменений; кадры и копии — `~/remlab-logs/t144-1120/` (`compare_*.png`, `rt1024.glb`, `rt512-lite.glb`). Вывод: 1024 годится,
  512 — только запасной (мыльнее текстура, цветные размывы на швах ножек).
- Находка того же замера: конвейер крашеные НЕ подхватывает. Покраска пишет только `<папка прогона>/blender/painted.glb` в `~/remlab-logs/...`
  (`tools/scout/stablegen/sg_runpod.py:197`, `sg_salad.py:393`, `sg_queue.py:120` — на ветке `worktree-stablegen-1119`, в `main` их нет);
  `runtime_mesh.fetch_source` берёт модель только из `~/scout-scenes/mesh-pilot-gallery/<id>/model.glb` (или `/test/mesh-pilot10/`), а галерею
  `tools/scout/salad/gallery_build.py` собирает лишь из `~/scout-scenes/meshes-hunyuan/meshes/hunyuan21/v2/*/*/` с `manifest.json` и ролью-стратегией `hunyuan3d`
  (`tools/scout/asset_strategy.py:strategy`, `rules/asset-strategies.json`).

## Скоуп — что входит
- (а) Выход покраски кладётся в склад мешей как обычная модель: `model.glb` + `manifest.json` (sku, role, источник=покраска, вариант, sha, отчёт сторожа).
- (б) Стратегия роли для покраски — данными в `rules/asset-strategies.json` (сейчас копию получает только `hunyuan3d`).
- (в) Ночной шаг `tools/assets/demo_rt.sh` собирает копии крашеных сам (рецепт ночи 1024 + `-lite` 512), `publish_rt.sh` выкладывает на `/rt/`.
- (г) Явная привязка «кто победил» для одного SKU: крашеная модель выигрывает у Hunyuan ТОЛЬКО если прошла сторож покраски; без mtime.
- Автопроверка П-4 «≤5 МБ» + лестница для тяжёлой (512 → simplify → отказ с причиной) + порог данными `rules/rt-weight.json`.
- Автоочистка шага (что чистит сам — ниже).

## Скоуп — что НЕ входит
- Сама покраска (качество текстуры, половинчатые ножки дуб/чёрный — отдельный журнал дефектов `plans/mesh-type-rules-01.md`, не от сжатия).
- Упрощение формы по умолчанию (simplify=0 остаётся: потеря силуэта на ≤5 МБ не нужна, замер выше).
- Старые Hunyuan-модели `/test/mesh-pilot10/` весом 7–8 МБ: порог П-4 для них — вопрос владельцу (пункт ❓ ниже), в этом плане только измеряем и показываем список.
- Платные прогоны, выкладка, перепокраска товаров.

## Масштаб (жёсткое правило владельца 20.11, TG 2338)
- Время и деньги на ~50 000 товаров: упаковка одной модели ≈ десятки секунд CPU (gltfpack, замер T-144: единицы-десятки секунд на 140 тыс. граней), денег 0 (локально, `heavy-slot --prio 0`);
  на 50 000 ≈ порядка суток CPU одной машины при 1 ядре → ночью пакетами, `--ids-from-demo` и очередь туров ограничивают объём реально нужным (демо+туры, не весь каталог).
  Объём на выходе: 1,5 МБ × 50 000 = 75 ГБ — на прод-диск не лезет (свободно ~17 ГБ), поэтому публикуем только модели демо/туров (как сейчас), а не весь каталог.
- Как случай распознаётся автоматически: стратегия роли и `source` в `manifest.json` (покраска/Hunyuan); «тяжёлая» — по факту размера копии > порога из `rules/rt-weight.json`, без списков товаров.
- Глазами: выборка по одному товару каждого класса из `mesh-type-rules-01` (К1–К4…) на 1024 и 512, плюс все отказы сторожа веса с причиной.

## Шаг перевыпуска

## Автоочистка (что чистит шаг сам)
- Промежуточный `<id>.src.glb` (оптимизированный GLB до упаковки, до ~16 МБ) — удаляется после упаковки (`runtime_mesh.py:~459 os.remove(tmp)`); при ОТКАЗЕ по весу тоже (не оставлять 16 МБ на отказ × N товаров; сегодня на пути отказа `os.remove(dst)` есть, для `tmp` — проверить в задаче 2).
- Частичные/битые копии: отказавшая по весу или по текстуре копия `<id>.glb` удаляется, запись манифеста — `refused` с причиной; на `/rt/` остаётся прежняя годная копия.
- Копии, которых больше нет в демо/очереди туров (товар заменили/победитель сменился), — не удаляются шагом (прод rsync без `--delete`); их выводит отчёт ночи списком «лишнее на /rt/ ≥ N дней», удаление — правилом диска `rules/dev-disk-clean.json` (approved владельцем) или отдельным шагом ведущего, не этим планом.
- Склад покраски: `session.blend` (≈100 МБ из 125) после успешного прогона уже удаляет `slim_run` (`sg_queue.py` `SLIM_DROP`); в склад (а) пишутся только `model.glb` и `manifest.json`, не `session.blend`.
- Временные файлы gltfpack пишет в системный tmpfs, TMPDIR не слушает — штатная перепаковка без KTX2 при квоте (`build_copy`), ничего нового не чистим.
