## Цель
`products.in_stock` перестаёт быть синонимом «есть в фиде»: наличие вычисляется одним
reconciler'ом из трёх независимых источников (фид, статус партнёрской программы, свидетельство
о карточке), переживает ежедневный `load3.py` и не может быть перезаписано мимо контракта.

## Источник задачи
Владелец нашёл диван divanboss (`divan-atlanta-2-rogozhka-malmo-siniy`, eid
`7430502010629678213`), которого нет в продаже (карточка 404), а у нас `in_stock=true`.
Разбор 31.08: поломка общая для каталога. Команда владельца — «делай план и исправляй».

## Диагноз (проверено по коду, БД, фидам, API и живым HTTP-запросам)
1. Фиды Гдеслона не отдают `available` (9 фидов, 87k офферов) — сигнала из фида нет вовсе.
2. `load3.py` наличие и не читает: `'t'` в copy-строке (`:124`), `in_stock=true` в upsert
   (`:173`), финальный `in_stock=(e.status='active')` (`:243`) = «есть в фиде + есть цена».
3. API Гдеслона отдаёт `available="true"` даже для карточки, отвечающей 404 — не источник правды.
4. Вердикты `health.py` (`:74`) и `linkcheck.py` (`:112`) пишутся прямо в `products.in_stock`
   и стираются наутро: 14 снятых 31.08 в 11:00 лежат в свежем фиде со `status='active'`.
5. `linkcheck --probe`: 400 ссылок/день, непроверенные идут первыми (`ts=0`) → порога `fails>=2`
   не достигает никто (у всех 353 мёртвых `fails=1`); снятий по проверке страницы в БД нет.
6. `linkcheck --probe` выбирает `where in_stock` (`:92`) — снятый товар не перепроверяется
   НИКОГДА, то есть ошибочное снятие необратимо автоматикой.
7. `gdeslon_api.py --retire` (`:90`) снимает товары магазина, закрывшего программу, но идёт ДО
   `load3` (`refresh_daily.sh:120` vs `:124`) — при живом фиде товары закрытого магазина
   воскресают. nonton спасло лишь то, что его фид перестал скачиваться.
8. `health.py` покрывает только товары `sets*.json` (721 из 20 544) и для divanboss/mnogomebeli
   считает живым, если слова 2–4 названия (БЕЗ цвета) есть на странице серии (`:38-40`);
   у mnogomebeli `direct()` вообще подменяет карточку страницей серии (`reflink.py:29`) —
   такая страница в принципе не может доказать наличие конкретного варианта.
9. `refresh_daily.sh` не имеет блокировки: `.last-refresh` пишется в конце (`:285`) — cron,
   `@reboot` и ручной `--force` могут пересечься.

Цена: 353 ссылки с HTTP 404 числятся в наличии (divanboss 256, tvoydom 97); покрытие проверкой
10% каталога; снятий по состоянию карточки — ноль за всё время.

## Решение (контракт)

**Формула наличия — одна, и материализует её один писатель:**
```
in_stock = feed_status = 'active'                     -- есть в свежем фиде и с ценой
       AND shop_program_state <> 'retired'            -- партнёрская программа жива
       AND page_state NOT IN ('gone','oos')           -- карточка не признана мёртвой
```
- Прямые записи `products.in_stock` убираются отовсюду (`load3.py:163,173,243`, `health.py:74`,
  `linkcheck.py:112`, `gdeslon_api.py:90`, `resurrect.py:34`); остаётся один
  `reconcile_availability()` в `stock_truth.py`, вызываемый каждым, кто меняет источник.
- Сторож в конце цикла: расхождений между формулой и `products.in_stock` — ноль.

**Свидетельство о карточке — по контракту магазина, а не по HTTP-коду вообще.**
`SHOP_EVIDENCE` в `page_alive.py`: для каждого магазина — что доказывает страница
(`sku` — карточка конкретного варианта, `series` — только страница серии) и чем читается
наличие (корзина / `quantity` / текстовый маркер).
- `series`-магазины (mnogomebeli): HTTP 200 → `unknown` ВСЕГДА (серия не доказывает вариант);
  404 серии → `gone`.
- `sku`-магазины (divanboss, divan.ru, tvoydom, mdm, gipfel): 404/410 → `gone`;
  200 + положительный сигнал → `alive`; 200 + явный OOS/`qty=0` → `oos`; 200 без сигнала →
  `unknown`; 403/429/капча/таймаут/сеть → `unknown` всегда.

**Снятие — только по подтверждённому свидетельству:**
- первое отрицательное наблюдение → `suspect`, товар НЕ снимается, ссылка ставится в очередь
  подтверждения (повтор через ≥15 минут в том же прогоне);
- второе независимое отрицательное по тому же `url_hash` → состояние применяется;
- `unknown` между ними не подтверждает и не сбрасывает; смена ссылки (`url_hash`) обнуляет
  накопленный негатив;
- положительное свидетельство возвращает товар в наличие само (без `resurrect.py`).

**Предохранители (staging → гейт → применение):**
- наблюдения пишутся всегда, статус — только через гейт;
- на магазин: при `n ≥ 30` доля отрицательных > 20% ИЛИ > 3× исторического уровня → результаты
  магазина в карантин + алерт, наличие не меняется;
- глобальный второй уровень: > 20% отрицательных за прогон → карантин всего прогона;
- поток 429/капчи по домену → домен замораживается до следующего прогона;
- смена более 10% активного ассортимента магазина за прогон → только алерт, без применения.

**Покрытие и вежливость:** 3500 проверок/день: 20% — товары боевых сетов (ежедневно),
15% — подтверждения/`unknown`-ретраи, 65% — хвост по давности. Круг каталога ≤ 8 дней.
Один одновременный запрос на хост, пауза 2–5 с с jitter, домены параллельно, `Retry-After`
уважается. Снятые товары тоже перепроверяются (иначе снятие необратимо).

**TTL не меняет наличие сам:** `alive` — перепроверка 7–14 дней (товары сетов — 24–48 ч),
`gone` — 1/3/7/30 дней, `unknown` — 1 ч / 6 ч / сутки. Вердикт старше 90 дней помечается
`stale` и алертится, но наличие по возрасту не снимается.

## Скоуп — что входит
- Таблицы `product_page_observation` (append-only факты), `product_page_status` (результат
  reducer'а), `shop_status` (состояние партнёрской программы).
- `page_alive.py` — классификатор ответа магазина + `SHOP_EVIDENCE`, импортируется без побочных
  эффектов, `--selftest`.
- `stock_truth.py` — reducer наблюдений → статус, `reconcile_availability()`, сторож инвариантов.
- `stock_check.py` — обход по бюджету, троттлинг, staging, гейты, очередь подтверждений, отчёт.
- Правки писателей: `load3.py`, `gdeslon_api.py`, `health.py`, `linkcheck.py`.
- `refresh_daily.sh` — `flock`, порядок шагов, бюджет проверки.
- `catalog_media.py` — page-dead сильнее карантина фида.
- Метрики покрытия/снятий в `sync_metrics.py`.
- Зачистка каталога — ЧЕРЕЗ новый механизм (с подтверждением), не разовым UPDATE.

## Скоуп — что НЕ входит
- Смена источника каталога, парсинг остатков вне карточки товара, headless-браузер для SPA.
- Правки TS-части (контракт `in_stock` не меняется; чтения `in_stock` в TS нет).
- Переезд `sets*.json` в БД, переработка `sets_incremental`.
