## Цель
Методика «что отдавать на меши» работает АВТОМАТИЧЕСКИ в ежедневном конвейере; сеты собираются
только из товаров с годным мешом; фронт каждого меша определяется каскадом
orienter+flipper → mesh_front → VLM → человек (единая страница с быстрыми кнопками).

## Источник задачи
Владелец 28.08: «зафиксируй методику отбора мешей; правило: сеты только из товаров с мешами;
меши всегда через Salad (соседняя сессия собирает образ); встроить отбор в конвейер; ориентация
orienter+flipper, неуверенное — через GPT, спорное — человек по единой ссылке с кнопками».

## Границы с соседним планом (mesh-bulk-salad-hunyuan)
Соседний план владеет ГЕНЕРАЦИЕЙ: образ Hunyuan 2.1, `tools/scout/salad/*`, `mesh_pilot.py`,
`mesh_gate*.py`, `mesh_make.py`, `mesh_render.py`, R2, PBR-приёмка. Этот план — ДО и ПОСЛЕ:
очередь отбора, правило сетов, каскад ориентации, страница проверки. Интерфейс между планами —
файл очереди (`queue.json`: SKU, роль, фото-hash, параметры) и манифест ассета в R2.

## Методика отбора (зафиксирована владельцем 28.08 — канон)
1. Роли — только слоты сетов (композиция + собранные сеты), текстиль/ковры/плоские настенные — нет.
2. Ворота пригодности: `in_stock` + живое фото + enrichment `quality ≥ 0.65` (те же, что подбор).
3. Направленные роли (фронт нужен): диван, кресло, стул, тв-тумба, стеллаж, комод, стенка,
   витрина, камин, банкетка со спинкой — ≈4 900 сейчас; остальные роли сетов — меш нужен,
   фронт symmetric_by_role. Таблица — `domain/viz-fidelity-playbook.md` §Роли.
4. Пул живой → отбор пересчитывается ежедневно (cron), очередь — дельта против готового.

## Блоки

### 1. `mesh_queue.py` — автоочередь (расширение шага MESH_QUEUE в refresh_daily)
- Кандидаты: роли слотов × ворота (SQL как в подборе, `enrich_bridge.quality_ok`).
- Дифф против готового: манифест ассета (R2/локальный реестр) по ключу
  SKU+фото-hash+генератор+версии; изменилось фото → перегенерация.
- Приоритет: (а) товары, СТОЯЩИЕ в сетах сейчас; (б) кандидаты слотов (top-N по скорингу);
  (в) остальной пул годных. Дневной лимит денег — уже есть у прогона очереди.
- Выход: `queue.json` для Salad-конвейера соседнего плана. Сам НЕ генерит.

### 2. Правило «сеты только из товаров с мешами» — этапно
- Точка: `sets_incremental._slot_ok` (уже проверяет replace-registry) + отчёт сборки.
- Этап A (shadow, сразу): метрика mesh-coverage по сетам/ролям в отчёте каждой сборки;
  сборка не блокируется. Этап B (hard, после наполнения кэша ≥порога владельца):
  слот требует manifest со статусом ≥ scene_ready; для направленных ролей — ещё и
  resolved-ориентацию. Переключение — флагом, решение о моменте — владелец по цифрам coverage.

### 3. `orient_pipeline.py` — каскад фронта (после генерации, на DEV-VM cron)
- Вход: новые годные GLB. Шаги: (1) orienter+flipper (CPU ~5с) → raw_to_canonical-кандидат,
  p, prediction set; (2) mesh_front на канонизированном меше (сидячие — авторитет);
  (3) правило ролей NONDIRECTIONAL → symmetric; (4) авто-резолв: методы сошлись/один уверен;
  (5) не уверено → VLM qwen3-vl (признаковый промпт, выбор из вариантов) — статус vlm;
  (6) спорное (конфликт методов, VLM не уверен/противоречит) → очередь человека.
- Вердикт: `orientation.json` рядом с ассетом: raw_to_canonical quaternion (det=+1),
  status (auto|vlm|human|symmetric|review), источники+версии (orienter ckpt, FRONT_VERSION,
  VLM model), equivalence. GLB не перезаписывается. Legacy front_yaw ↔ ry(−θ).

### 4. Страница проверки человеком — единая ссылка
- `/lab/mesh-review` (или /test/review/) — список спорных SKU: фото карточки + 4 рендера
  (0/90/180/270), быстрые кнопки «фронт — этот» + «не определить/брак».
- Write-path: API route в Next.js (паттерн `app/api/lab/*`) + таблица Drizzle
  `meshOrientReviews` (sku, glb_hash, chosen_yaw, судья, ts); токен-доступ.
- DEV-конвейер забирает вердикты (API pull в cron) → human-вердикт = финальный авторитет,
  кэшируется навсегда (пока не сменился glb_hash).

## Гейты приёмки плана
- Очередь пересчитывается ежедневно без ручных шагов; повторный прогон = 0 лишних генераций.
- silent_wrong_front среди auto-confident = 0 (мера — по human-вердиктам со страницы).
- Человеку доходят только спорные (десятки, не сотни): замер доли по первой партии.
- Сеты в этапе A не деградируют; переход к B — только решением владельца.
