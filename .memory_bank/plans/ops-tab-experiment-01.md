## Цель
Неделю раздавать независимые задачи рабочим Sonnet по очереди «старая вкладка» / «свежая сессия» и померить, дешевле ли
свежая сессия на принятую задачу без потери качества. Сторож не даёт директору нарушить очередь и сам считает итог.

## Скоуп — что входит (после критики Codex 20.11, `_intake/codex/2026-11-20-tab-experiment-guard-answer.md`: CHANGE)
1. **Реестр опыта** `data/logs/tokeny/opyt-vkladki.tsv` (вне git), только дописывание, запись под замком (flock):
   - `register <T-ID> --tip kod|proba` — фиксирует задачу; плечо — **случайно, переставленными блоками по 4** внутри типа
     (директор плечо не выбирает и не видит заранее);
   - `bind <T-ID> <sessionId>` — привязка сессии: `свежая` — новый UUID без единого ответа модели до задания, больше никогда
     не используется; `старая` — UUID из пула старых вкладок (зафиксирован до опыта, уже делали задачи), вкладку выбирает
     инструмент по кругу, не директор;
   - `pass` / `otmena <причина>` / `blocked` — закрытие; отменённые и BLOCKED остаются в счёте плеча.
2. **Сторож — на ВХОДЕ рабочего:** хук `UserPromptSubmit` (в `.claude/settings.json`, команда — прямой запуск
   `tools/hooks/guard_opyt.py`, без «если файл есть»; при сбое — БЛОК, если харнесс это умеет: сверить `onFailure` по докам
   code.claude.com/docs/en/hooks при деплое). Срабатывает только на входящие задания: первая строка
   `[директор|fable-lead] T-…/<цикл> · задание|правки|доработка`; остальные сообщения (владелец, отчёты) не трогает. Блок, если:
   T-ID нет в реестре или не привязан к ЭТОМУ `session_id`; свежая сессия уже имела задачу; в сессии уже открыта другая
   задача; правки/доработка не в той сессии, где цикл 1; реестр недоступен или неоднозначен. Ловит SendMessage по имени и по
   сокету, переименование, не ту вкладку и ввод через tmux. Директору — ранняя подсказка не нужна (вырезано как лишнее).
3. **Мягкая проверка** каждые 15 мин в обходе директора: `opyt_vkladki.py proverka` — новые T-ID мимо опыта, одна задача на
   сессию, свежие не переиспользованы, хук жив, реестр доступен; нарушения, отмены — строкой владельцу. Снять защиту может только
   владелец (своим словом), тихого выключателя нет.
4. **Счёт** `opyt_vkladki.py itog`: расход рабочего — usage его привязанной сессии на отрезке «выдано → PASS» (не только по меткам:
   метки сбрасываются после 2 ч простоя); старт свежей сессии отдельно НЕ прибавлять (он уже в usage первого ответа); сжатия —
   диапазоном low/base/high, в т.ч. сжатия старых вкладок между задачами опыта; директор — по меткам фаз. Показывать: медиану
   $ PASS и разброс, весь расход плеча / число PASS, долю PASS и PASS с первого цикла, критические дефекты и откаты; время —
   календарное до PASS отдельно от ожидания платной машины / heavy-slot / окна разрешения; доработку по слову владельца — отдельно.
5. **Ровные условия:** обе руки — Sonnet 5.5 high, одинаковый параллелизм; свежую сессию не открывать сверх обычного числа рабочих.
6. **Правила:** `.claude/rules/orchestration.md` § «Расход токенов» — на время опыта действует этот план; итог — ADR вручную.

## Скоуп — что НЕ входит
- Порог сжатия (293k) и состав Memory Bank не меняются (Codex: не менять два рычага сразу).
- Ведущие и менеджеры — без изменений, опыт только на рабочих Sonnet.
- `tools/tokeny/` (модуль кита) не правится — только чтение.

## Правило решения (Codex: при 15 задачах одна задача = 6,7 п.п. — это ориентир, не доказательство)
- Набор: ≥15 закрытых задач в каждом плече или 7 дней; меньше 10 — продлить.
- Принять свежие: явная экономия и по медиане $ PASS, и по «весь расход / PASS» (ориентир −15 %), без критических дефектов.
- Показатели расходятся или выгода и вред одинаково возможны — неопределённо, продлить. Выигрыша нет или серьёзные дефекты — нет.
- Контроль: % недели `/usage` (limit-tekst) по дням. Вердикт и ADR — директор вручную по таблице, не автоматом.

## Масштаб (жёсткое правило владельца 20.11, TG 2338)
- Не про товары: на выход — ≈30–40 задач за неделю; инструмент читает журналы сессий (как `tokeny`, секунды).
- Распознавание автоматом: задания и правки — по меткам первой строки (уже обязательны), сессия — по `~/.claude/sessions`.
- Глазами: итоговая таблица директора + выборка 3 задач из каждого плеча (бриф, отчёт, замечания).

## Риски
- Задач у рабочих pakardev мало (правило TG 992 «новых задач на pakardev не давать») → опыт не наберёт числа. ⚑ владелец:
  разрешить задачи на pakardev для опыта или вести опыт у менеджера router (там свой сторож не стоит — он на pakardev).
- Задачи неоднородны (покраска с платными машинами ≠ правка теста) → сравнение медиан по типам: `код`/`проба`/`проверка`
  (тип в `vydat`), чередование внутри типа.
- Свежая сессия забывает решения вне брифа → бриф самодостаточный (уже правило); замечания директора считаются.
- Хук на SendMessage: проверить, что харнесс передаёт `tool_input` SendMessage в PreToolUse (проба в деплое).
