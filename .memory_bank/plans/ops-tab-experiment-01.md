## Цель
Неделю раздавать независимые задачи рабочим Sonnet по очереди «старая вкладка» / «свежая сессия» и померить, дешевле ли
свежая сессия на принятую задачу без потери качества. Сторож не даёт директору нарушить очередь и сам считает итог.

## Источник задачи
- Владелец TG 2388: «есть ли смысл сократить разговор на шаг» → Codex `_intake/codex/2026-11-20-context-size-answer.md`:
  единственный рычаг — свежая сессия рабочего на независимую задачу, ожидание −5–9 % расхода; мерить опытом.
- Владелец TG 2414: «да… не забудь сам своё предложение, надо сделать так, чтоб ты строго его соблюдал — сторожей сделать».
- Владелец TG 2417: «план согласуй с кодексом по сторожам».

## Скоуп — что входит
1. **Реестр опыта** `data/logs/tokeny/opyt-vkladki.tsv` (вне git, как прочие данные tokeny): строка на задачу —
   T-ID · плечо (`старая`|`свежая`) · рабочий (имя сессии, sessionId) · время выдачи · время PASS · итог (`PASS`|`отмена`|`BLOCKED`).
2. **Инструмент** `tools/ops/opyt_vkladki.py` (stdlib, импортирует `tools/tokeny/tokeny.py` только для чтения журналов):
   - `vydat <T-ID>` — назначает плечо: чередование по реестру (следующая независимая задача — плечо, которого меньше;
     при равенстве — противоположное последнему); пишет строку; печатает плечо и что делать (старая — какой из простаивающих
     рабочих; свежая — команда запуска новой видимой сессии);
   - `pass <T-ID>` / `otmena <T-ID> <причина>` — закрытие задачи;
   - `proverka` — сверка за период: каждое задание `T-…/1 · задание`, отправленное рабочему (журналы сессий), есть в реестре;
     плечо соблюдено (см. сторож); правки `T-…/N≥2` ушли в ту же сессию, что цикл 1; печатает нарушения, rc≠0;
   - `itog` — по каждой закрытой задаче: $ рабочего по меткам (API-прайс, уже считает `tokeny`), $ проверки ведущего
     (фазы `проверка`), число вызовов, циклов правок, время до PASS, сжатия (`compact_boundary` в журнале сессии рабочего;
     оценка их $ по `preTokens`), $ старта свежей сессии; медианы по плечам и решение по правилу ниже.
3. **Сторож — жёсткий:** хук `PreToolUse` на `SendMessage` в `.claude/settings.json` → `tools/hooks/guard_opyt.py`:
   - срабатывает только на сообщения, чья первая строка `[директор|fable-lead] T-…/<цикл> · задание|правки`
     и адресат — рабочий (сессия с именем `rabochiy-*` по `~/.claude/sessions/*.json`, сопоставление по pid в имени сокета);
   - цикл 1 без строки в реестре → БЛОК «сначала `opyt_vkladki.py vydat <T-ID>`»;
   - плечо `свежая`, а у сессии-адресата в журнале уже есть другое `· задание` → БЛОК «нужна новая сессия»;
   - плечо `старая`, а сессия-адресат новая (в журнале нет прошлых заданий) → БЛОК;
   - цикл ≥2 в другую сессию, чем цикл 1 → БЛОК;
   - сбой самого сторожа (нет файлов, кривой JSON) → пропуск с предупреждением в stderr, не блок (не останавливать работу);
   - опыт закончен (реестр закрыт строкой `КОНЕЦ`) → сторож молчит.
4. **Мягкий сторож:** шаг в будильник обхода директора — `opyt_vkladki.py proverka`; нарушение → строка в отчёт владельцу.
5. **Запуск свежей сессии:** видимая сессия tmux на pakardev (окно `rabochiy-svezh-<T-ID>`):
   `claude -n rabochiy-svezh-<T-ID> --model claude-sonnet-5-5 --effort high --remote-control rabochiy-svezh-<T-ID>`
   в папке remlab (ключи — сверить при деплое по `claude --help`); бриф — SendMessage как обычно; после PASS — выход
   из сессии и закрытие окна. Старая вкладка — один из `rabochiy-pakardev-1..4`, уже делавший задачи.
6. **Правила**: `.claude/rules/orchestration.md` § «Расход токенов» — снять противоречие «только свежая фоновая» / «в ту же
   вкладку»: на время опыта действует этот план; итог — ADR.

## Скоуп — что НЕ входит
- Порог сжатия (293k) и состав Memory Bank не меняются (Codex: не менять два рычага сразу).
- Ведущие и менеджеры — без изменений, опыт только на рабочих Sonnet.
- `tools/tokeny/` (модуль кита) не правится — только чтение.

## Правило решения (Codex)
- Набор: ≥15 принятых задач в каждом плече или 7 дней, что раньше; меньше 10 в плече — опыт продлевается.
- Свежие сессии — норма, если медианный $ на принятую задачу ниже на ≥15 % И первый PASS, время до PASS и циклы правок хуже
  не более чем на ~10 %. Иначе — остаётся старая вкладка. Итог — ADR + правка `orchestration.md`.
- Контроль: рост % недели `/usage` (limit-tekst) по дням — API-доллары не равны лимиту.

## Масштаб (жёсткое правило владельца 20.11, TG 2338)
- Не про товары: на выход — ≈30–40 задач за неделю; инструмент читает журналы сессий (как `tokeny`, секунды).
- Распознавание автоматом: задания и правки — по меткам первой строки (уже обязательны), сессия — по `~/.claude/sessions`.
- Глазами: итоговая таблица директора + выборка 3 задач из каждого плеча (бриф, отчёт, замечания).

## Риски
- Задач у рабочих pakardev мало (правило TG 992 «новых задач на pakardev не давать») → опыт не наберёт числа. ⚑ владелец:
  разрешить задачи на pakardev для опыта или вести опыт у менеджера router (там свой сторож не стоит — он на pakardev).
- Задачи неоднородны (покраска с платными машинами ≠ правка теста) → сравнение медиан по типам: `код`/`проба`/`проверка`
  (тип в `vydat`), чередование внутри типа.
- Свежая сессия забывает решения вне брифа → бриф самодостаточный (уже правило); замечания директора считаются.
- Хук на SendMessage: проверить, что харнесс передаёт `tool_input` SendMessage в PreToolUse (проба в деплое).
