# Забытые процессы не держат папку от переноса (logs_archive)

## Зачем
26.11 три забытых процесса 1,7–2,7 суток держали 14 ГБ на основном диске pakardev: два цикла-«ждуна» файла,
который уже не появится (`while [ ! -f … ]; do sleep`, `until grep … ; do sleep`), и пробный `python3 -m http.server`
с рабочей папкой внутри. Перенос на второй диск считает их «живым прогоном» / «занятой папкой» и пропускает.
Забытые `tail -F` старше 12 ч скрипт уже не считает (правило «наблюдатель»), а ждунов и серверы — считает.

## Правило (общее, без ID)
Процесс НЕ держит папку, если одновременно:
1. старше `stale_holder_hours` (12 ч, в `dev-disk.json → archive`);
2. его командная строка — только ожидание: цикл `while/until … sleep N` без запуска тяжёлого (python/node/blender/…)
   внутри цикла, ИЛИ `python3 -m http.server` / `tail -F`;
3. он не держатель heavy-slot и не в реестре групп Salad;
4. в папке за эти 12 ч нет новых файлов (свежесть — как сейчас).
Такой процесс — строка «забытый ждун/сервер — не держит: pid, возраст, команда» в выводе и в DIGEST (чтобы видеть, кого гасить).
Процесс скрипт НЕ убивает — только перестаёт из-за него держать папку; после переноса ссылка на месте, путь живёт.

## Шаги
1. Классификатор `stale_holder(cmdline, age_h)` рядом с правилом «наблюдатель»; порог — из правил.
2. Тесты на временной папке: ждун >12 ч — не держит; ждун <12 ч — держит; цикл с python внутри — держит;
   http.server >12 ч — не держит; держатель heavy-slot — держит всегда.
3. Тест прописан в job CI, где идёт `test_logs_archive.py`.
4. Сухой прогон на pakardev: какие папки освободились бы и сколько ГБ.

## Конвейер (4 строки)
- Вход: процессы pakardev + папки `~/remlab-logs` первого уровня.
- Что чистит шаг: ничего не удаляет; переносит на HDD со ссылкой, как сейчас.
- Salad или наши ядра: наши, лёгкое.
- Где ещё действует: только pakardev (`remlab-logs-archive*.service`).

## Критерии
- Тесты зелёные, CI зелёный; сухой прогон показывает ждунов строкой «не держит».
- Ни один живой прогон (heavy-slot, Salad) папку не потерял.
