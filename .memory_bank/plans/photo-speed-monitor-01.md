## Источник задачи
Владелец 07.11 голос TG 395: «оставляем как есть (модель). Сделай мониторинг, чтобы мы знали, с какой скоростью у нас обработка идёт,
и посмотри приоритетную обработку за деньги — на будущее».

## Что известно (T-33, 07.11)
- Модель — `gpt-image-2.5-sunburst` medium (ADR-0302; flare отвергнут владельцем 07.11 по пробам T-33/2).
- Замер T-33/1: наша подготовка ≈ 1,6 с из ≈ 38 с; модель на пути покупателя — медиана 32,7 с, ночью 28,9 с.
- Журнал заданий — `~/scout-scenes/dev-render.log` (пишет `tools/scout/dev_render_backend.sh` / сервис рендера); там же отказы шлюза
  (например, «ШЛЮЗ ОТКАЗАЛ: HTTP 503» 07.11).
- Приоритет за деньги: у OpenAI «Priority» (с 30.07.2026 — «Fast mode») только у Responses/Completions; у моделей картинок в прайсе
  лишь Standard и Batch (Batch — вдвое дешевле, медленнее; кандидат для ночной досъёмки). Через Vercel — тоже нет (T-33/1). Вывод: купить
  скорость нельзя; следить за ней — можно. Новая версия той же линейки `gpt-image-2.6-sunburst` (та же цена) — кандидат на будущий бенч
  (решение владельца).

## Решение
1. Скрипт `tools/ops/photo-speed.py` (без сети, только журнал): за сутки и за 7 дней — число заданий, медиана и 90-й процентиль:
   подготовка / ожидание модели / сохранение / всего; отдельно путь покупателя и ночь; отказы (шлюз 4xx/5xx, таймаут, резка) — число
   и доля. Формат журнала разобрать по коду, при нехватке полей — добавить в журнал недостающие метки времени (одна строка на задание).
2. Пороги — `tools/scout/rules/photo-speed.json`: база = замер T-33 (модель ≈ 33 с, всего ≈ 38 с); WARN, если медиана «всего» за сутки
   > базы × 1,3, 90-й процентиль > 70 с или отказов > 10 % (и ≥ 2). Пусто за сутки — не ошибка, строка «заданий 0».
3. Ночной прогон: строка `DIGEST: фото — N заданий, ждали медиана X с (модель Y с), 90 % ≤ Z с, отказов K` + WARN по порогам
   (`refresh_daily.sh`, шаг без сети и без денег).
4. Для ведущего: `tools/ops/photo-speed.py --days 7` — таблица по дням (сводка владельцу «скорость фото»).
