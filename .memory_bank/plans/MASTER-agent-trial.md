## Цель
Любой агент недвижимости (UK) заходит на лендинг → «попробовать бесплатно» → кидает фото или PDF планировки (+ необязательно текст
объявления с размерами) → конвейер сам: стены → 3D → расстановка по нашим шаблонам → реальные товары → фотокадры → ссылка на 3D-тур.
Ждёт с анимацией и таймером (цель ≤ 3 мин) или оставляет почту — ссылка придёт, когда готово.

## Источник задачи
Владелец, TG 277–282 (09.11.2026): «демо итоговое как макро задача… лендинг (построй его, просмотрев всех конкурентов… мои комментарии
читай обязательно)… лучше в течение 3 мин уложиться. Генерацию фото можно в параллель в несколько потоков… Если в 3 мин не уложиться —
пиши, подумаю». «Это общая большая задача, а 3D — подзадача». «Пиши мета-план и иди по нему».
Конкуренты с комментариями владельца — `_intake/competitors-2026-11-09.md`.

## Поправка 09.11, вечер — главнее таблицы и критериев ниже (TG 1302, 1310–1325, 1364–1365, 1377, 1379, 1382)
**Конечный результат (владелец TG 1382):** агент зашёл на лендинг, загрузил планировку — и всё работает сразу, без дополнительных этапов:
получил 3D-расстановку со стилями, разными, для всех спален и гостиной.
**Цепочка (один автоматический конвейер, ручных шагов нет):** лендинг → загрузка → ожидание с галочками → стены (промежуточная публикация, не `done`) →
страница = ровно `/demo` под этот план, пустые комнаты с крутилкой → расстановка гостиной и всех спален по действующим шаблонам со стилями, реальные товары →
мебель появляется с анимацией без перезагрузки → AI-фото догружается → две ссылки (агенту и покупателю). Подробности и задачи З–О — `plans/agent-trial-08-demo-as-template.md`.
**Что меняется в таблице:**
- Серый тур снят (T3+T4, срез): итог — `/demo` как шаблон; форма и ожидание — из ветки страниц без файлов серого тура.
- T6 спальни **не отложены**; T6а отложена только «узкая односпальная». Кровать не вписывается в площадь — не ставить; сообщение: «нет подходящих товаров согласно действующим шаблонам».
- T2: волна кроватей остановлена сторожем 15:58; новая — после главной цепочки, без узких 90 см, малой партией; снятие запрета — словом владельца.
- Обещание вместо «≤ 3 мин»: **«ссылка сразу, ход виден, всё появляется по готовности»** (TG 1365); срок в минутах — после замеров.
- T1: шаг «введите одну длину» убран из автоматического пути: масштаб не прочитан — честный отказ по комнатам, вопросов агенту нет. T6 — `plans/agent-trial-04-bedroom.md` (все спальни, все этажи).
- Порядок (повторная проверка советника, `_intake/codex/master-agent-trial-2026-11-09b-answer.md`): стенд планировок → единый контракт версий данных → страница на фикстуре → загрузка, воркер, промежуточная публикация → гостиная и все спальни, модели кроватей → состояния по комнатам, опрос версий, этажи, две ссылки → фото, сроки, бюджеты, согласие, письмо → новое фото владельца.
**Приёмка вместо «≤ 3 мин»:** владелец со своего нового фото, без нашей помощи: лендинг → загрузка → `/demo` под план с мебелью и стилями в гостиной и во всех спальнях, этажи, обе ссылки; отказ по комнате — честный текст, не пустота.

## Правка тура: черновики и «Подтвердить планировку» (план `trial-confirm-plan-01`, T-20261111-16, 11.11)
- **Таблицы:** `trial_room_edits` и `trial_opening_edits` (028/029) + `db/init/032-trial-plan-confirm.sql`: `confirmed_at`, `rebuild_id`,
  `draft` (неподтверждённое изменение уже подтверждённой строки), `dims_ok` (галочка «размеры верны»); `trial_rebuilds.progress` (ход).
  Прежние строки 032 считает подтверждёнными.
- **Черновик:** правка с `draft: true` (`lib/trial/repo-room-edit.ts`, `lib/trial/repo-opening-edit.ts`) пишет строку без `confirmed_at` или
  `draft` у подтверждённой (`lib/trial/repo-draft.ts`), пересборку не ставит, суточный лимит не тратит. Лимит черновиков 80
  (`lib/trial/upload-limits.ts:TRIAL_ROOM_EDIT_LIMITS`, сверх него 429 `draft_limit`). В сборку едут только подтверждённые
  (`lib/trial/repo-rebuild-worker.ts:editsOf`). Свой новый проём (`u…`), подтверждённый, но не построенный, и снятый черновиком, при
  подтверждении удаляется целиком (`repo-draft.ts:confirmDrafts`): его нет ни в сборке, ни в `GET edits`.
- **Кнопка:** `POST /api/trial/[id]/confirm` (`app/api/trial/[id]/confirm/route.ts`, `lib/trial/repo-confirm.ts:askConfirm`): все черновики
  подтверждаются под ОДНУ пересборку `edit` (`progress.confirm`), пустая тоже; повтор `request_id` даёт тот же ответ, при активной пересборке `busy`.
  Галочки `rooms_ok` → `dims_ok` → воркеру `dimsOk` → флаг `user_dims` (`tools/floorplan/room_edits.py`). Публикация помечает `built`
  только правки своей пересборки (`repo-rebuild-worker.ts:publishRebuild`).
- **Чтение страницей** (право по `k`; `lib/trial/repo-plan-status.ts`, пути в `KEYED` из `lib/trial/tour-page.ts`): `GET edits` (черновики,
  галочки, время подтверждения, `dropped`), `GET rebuild-status` (комнаты «в очереди / считаем / готово», «N из M», оценка и сколько прошло).
- **Ход и оценка:** воркер пишет ход по комнатам (`tools/floorplan/conveyor.py:EditRebuild._progress_init`, `_progress_mark`) через пульс
  (`tools/floorplan/worker.py:Heartbeat.progress`, `repo-rebuild-worker.ts:heartbeatRebuild`); оценка времени по замерам стадий прошлых
  пересборок (`lib/trial/rebuild-eta.ts:stageEst`, `etaOf`; замеры пишет публикация в `progress.timings`).
- **Перечитать (T-16/2):** воркер получает черновики отдельно (`draftEdits`, `draftOpeningEdits`) и переводит их той же картой
  (`conveyor.py:Reparse.draft_map`); сервер переписывает их ключи (`lib/trial/repo-reparse-map.ts:applyReparseMap`), не легшие и
  пришедшие во время перечитывания снимает, причины кладёт в `trial_rebuilds.progress.dropped_drafts`; `GET edits.dropped` показывает их до
  следующего подтверждения. Карта старого воркера без `drafts` черновики не трогает.
