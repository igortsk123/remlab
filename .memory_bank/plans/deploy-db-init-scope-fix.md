## Цель
Вернуть «Deploy prod» в зелёное и восстановить реально работающий smoke-тест с авто-откатом
(с 01.09 он не выполнялся ни разу).

## Источник задачи
Владелец: «были ошибки на гитхаб заливки, возможно там давно код неактуальный — проверь».
Проверка показала: заливка кода исправна (`main` == `origin/main`, CI gate зелёный, прод на
последнем коммите). Падает workflow **Deploy prod** — с 2026-09-01T13:56Z ни одного зелёного
прогона (проверено по 100 последним запускам).

## Диагноз (доказан логом job 101256447530)
```
psql:/docker-entrypoint-initdb.d/008-mesh-binding.sql:14: ERROR: relation "products" does not exist
```
- `db/init/*.sql` = схема **боевой** БД. Деплой заливает их `scp db/init/*.sql` и применяет
  циклом `psql -v ON_ERROR_STOP=1` (`.github/workflows/deploy.yml:85,97`).
- `008-mesh-binding.sql` и `009-photo-origin.sql` (добавлены 01.09) — **каталожные** миграции:
  `alter table products`, `alter table asset_revisions`, view `product_mesh_state` поверх
  `mesh_demand`. Ни одной из этих таблиц на проде нет и быть не должно — каталог живёт только на
  дев-БД `remlab-devdb` (контракт прямо записан в `tools/scout/db_migrate.py:4-6`).
- Проверено на проде: `\dt` → 12 таблиц, `products` отсутствует. Приложение эту таблицу нигде не
  читает (grep по `app/ lib/ db/` пуст) → боевая база не пострадала, чинить надо расположение файлов.
- Почему это не поймали раньше: ручной `deploy.sh` перечисляет SQL-файлы явно (001–007) и не
  падает; глоб есть только в GitHub-workflow.

## Последствие, которое опаснее красного значка
Падение происходит **после** `docker compose up -d` — образ выкатывается, прод не отстаёт. Но шаг
«Smoke-тест + откат при провале» после провала предыдущего шага **пропускается GitHub-ом целиком**:
с 01.09 никто не проверяет, что сайт после выкатки отвечает, и **авто-откат на `:prev` отключён молча**.

## Разбор Codex (05.09) — что план пропускал
Полный ответ — `_intake/codex-prompts/q-deploy-db-init-scope.answer.md`. Проверено мной по факту:

1. **[блокер, подтверждён] `git mv` НЕ починил бы деплой.** На сервере
   `ls /opt/remlab/db/init/` = 001…009: workflow копирует файлы `scp`-ом поверх и применяет глобом
   ВСЁ, что там лежит. Серверные копии 008/009 пережили бы перенос, и следующий деплой упал бы так же.
   Нужна синхронизация каталога с удалением лишнего (`rsync --delete`), а не `scp`.
2. **[блокер, подтверждён] деплоится не тот коммит, что прошёл CI.** Триггер — `workflow_run`, но
   checkout берёт `ref: main`, а тег образа — `github.sha`; для события `workflow_run` это HEAD
   ветки по умолчанию на момент запуска, не SHA проверенного прогона. Надо
   `github.event.workflow_run.head_sha` одним `TARGET_SHA` во всех шагах.
3. **[блокер, подтверждён] `!cancelled()` сам по себе делает страховку ЛОЖНОЙ.** `compose up -d`
   идёт ДО миграций, поэтому после провала SQL новая версия уже работает; smoke по одному коду
   200 «подтвердит» успех. Нужны: миграции ДО активации, проверка `ok=true` И `version==TARGET_SHA`,
   откат только когда сайт реально не отвечает.
4. **[подтверждён мной независимо] цель отката протухла на 6 недель.** `docker tag ${IMAGE}:latest
   remlab-app:prev` не срабатывает: сервер тянет образ по SHA, локального `:latest` у него нет.
   Факт: `remlab-app:prev` = `sha256:d36362…` (22.07), работающий контейнер — `sha256:7295bd…`.
   Значит откат вернул бы прод в июль. Чинить обязательно ДО включения smoke на путях с ошибкой.
5. **[подтверждён] ручной `deploy.sh` уже разошёлся с CI:** копирует 001–007, а применяет только
   002–006 — `007-mesh-review` на существующей БД не применяет. Нужен ОДИН прогонщик миграций.
6. **[подтверждён] замок `/opt/remlab/.deploy.lock` не покрывает деплой целиком** — cleanup-сторож
   может снять тег между `pull` и `up`. Критическую секцию брать под тот же замок.

Отклонено с обоснованием: Codex требует до правки перенести control-plane DDL
(`mesh_demand`, `asset_revisions`…) из `mesh_queue.py` в миграции. Это правильно по сути, но это
рефакторинг конвейера мешей (файл читает и образ Salad-ноды), а не починка деплоя: сегодня ничего
не сломано — на дев-БД все таблицы есть. Мешать два риска в один выкат нельзя → follow-up.

## Скоуп — что входит
- Перенос двух каталожных миграций в `tools/scout/` + **удаление их серверных копий** (`rsync --delete`).
- Один прогонщик `db/init` (`tools/apply-db-init.sh`) для CI, GitHub-деплоя и ручного `deploy.sh`.
- Порядок деплоя: замок → цель отката из образа РАБОТАЮЩЕГО контейнера → pull → БД+миграции →
  активация приложения → smoke точного SHA → откат только при реально мёртвом сайте.
- `TARGET_SHA` = `workflow_run.head_sha` во всех шагах (деплоим ровно проверенный коммит).
- CI-гарда `db-init`: чистая БД → все файлы → повторный проход → проверка обязательных таблиц.
- ADR + обновление сводок памяти.
