## Цель
После нажатия «Сделать реалистичнее» покупатель ждёт только нейросеть (25–40 с), а не 27 с нашего серверного рендера сверху.
Браузер уже рисует эту сцену в 3D — снимаем из неё оба вида, склеиваем на сервере и отправляем в модель.

## Источник задачи
Владелец 17.10: «мы же сейчас 3D рисуем моментально… в чём проблема два вида с этого же 3D сфотать, грубо говоря склеить и отправить».
Замер d8 (бенч 17.10, `tools/ops/bench-realistic.py`): «наша часть» 26–34 с на каждом прогоне, модель 13–40 с; на проде кэш листа
есть только у прогретых расстановок, после замены мебели кэша нет — покупатель ждёт 27 с + модель.

## Что есть (сверено d8 17.10)
- Кнопка → `makePhoto('realistic')` → `POST /api/render` с `payload()` (комната, товары, `cams` C1/C2 с позой, пол/стены, `src_id`)
  (`tools/scout/flat215-demo/index.html` ~2817–2850). Сервис `tools/scout/draft_service.py` (`/render`, лимит тела `MAX_BODY = 2 МБ`,
  :356) → `draft_render.render(quality='realistic')` → `improve_mode.build()`: `scene3d_frame` рисует два вида 2048×1512 на процессоре
  (DEV, `dev_render_backend.sh`), склеивает с розовой полосой (`BAND_PX`), лист эталонов `_identity` (кэш `_IDENT_CACHE` по набору
  товаров), страница исходников `_publish_sources` (scp на прод), промпт `prompt_for`. Ответ модели режется `_split_pair`, кэш ответа
  `_improve_cache(src_id)` — повтор не платит.
- Браузерная сцена: `lib/viewer3d/viewer.ts:exportFrame(width,height,type,quality)` рисует кадр любого размера текущей камерой и
  возвращает Blob (используется для картинки коллекции); позы C1/C2 — `goToPose` (demo-09), «тот же кадр, что снимет нейросеть».
- Без 3D (`LIVE.ok===false`, заглушка) кнопка работает через серверный рендер — остаётся как запасной путь.

## Решение
1. **Страница.** При нажатии: для каждой позы C1, C2 — `goToPose` (без анимации, в offscreen-размере) → `exportFrame(2048,1512,'image/jpeg',0.85)`
   → data-URL; в `payload` добавить `views: [{camera:'C1', data}, {camera:'C2', data}]` и `clay: [роли без меша]` (серые заглушки — из
   `LIVE.scene.models()`), остальное как сейчас. Камера возвращается в прежнее положение; покупатель видит ход на кнопке.
   Телефон: если два кадра 2048 не собираются (ошибка/память) — 1536×1152, затем запасной серверный путь.
2. **Сервер.** `improve_mode.build()`: если в payload есть `views` обоих ракурсов — НЕ звать `scene3d_frame`; привести кадры к
   `SIZE` (2048 на ширину, высота по пропорции), склеить с полосой как сейчас; `clay` — из payload. Лист эталонов — из `_IDENT_CACHE`
   (прогрев: страница при открытии окна дёргает дешёвый `POST /render?prepare=1` или первый вызов терпит +2–3 с). Страница исходников —
   публиковать ПОСЛЕ ответа модели (не на горячем пути). Лимит тела `MAX_BODY` → 8 МБ (два JPEG 2048×1512 q0.85 ≈ 0.4–0.7 МБ каждый);
   проверить лимит у прокси перед сервисом (Caddy/контейнер `remlab-draft`) и у туннеля на DEV.
3. **Кэш и деньги.** Ключ ответа — `stateId` (+ пол/стены) как сейчас (`src_id`); повтор нажатия — без оплаты. Кадры из браузера в
   реестр не пишутся как «фото» — только результат модели.
4. **Запасной путь** без 3D и при ошибке экспорта — серверный рендер, как сегодня; в ответе `timing` помечать, откуда кадры
   (`frames: browser|server`) — видно в логе и в живой проверке.
5. **Метрика.** В логе сервиса «улучшение: наша часть X с (кадры из браузера)»; X ≤ 2 с при прогретых эталонах.

## Критика Codex (17.10, `_intake/codex/2026-10-17-browser-frame-critique.md`) — обязательные уточнения
1. **Захват кадра — атомарный `captureAtPose(pose, w, h)` в движке**, не `goToPose` + `exportFrame`: `goToPose` анимирует 650 мс и ничего не
   возвращает (`viewer.ts:649`, `demo-scene.ts:199`), камера обновляется в цикле кадра (`viewer.ts:1297`), на телефоне включён наклон
   (`index.html:4698`), выделение рисуется в WebGL (`viewer.ts:1177`). `captureAtPose`: отдельная камера или мгновенная проекция позы,
   ждёт `ready` всех мешей, выключает tilt/выделение/призраки, рендерит, восстанавливает всё в `finally`.
2. **Размер кадра — ровно `2048×1489`** (лист `SIZE` 2048×3072, полоса `BAND_PX` 94: `(3072−94)/2 = 1489`, `improve_mode.py:38,278`);
   проверка пропорций отвергает иное (`improve_mode.py:476`). Телефонный запасной профиль — `1536×1117` (та же пропорция), не 1536×1152.
   Сервер детерминированно приводит к этому размеру до склейки.
3. **Ключ кэша и идемпотентность — серверный**, не `stateId` (он намеренно без камер, `index.html:3765`; новая кнопка шлёт пустой
   `srcId`, `index.html:4486`; сервер читает кэш только по `src_id`, `draft_render.py:3304,3348`). Ключ = хэш(упорядоченные C1/C2 +
   стиль + отделка + набор эталонов + `PROMPT_VERSION` + модель/quality); single-flight/резервирование ключа против двух одновременных оплат.
4. **`clay` — из статуса движка**, не из `LIVE.scene.models()` (подпись пишется до загрузки меша и не меняется при заглушке,
   `demo-scene.ts:225`, `viewer.ts:436,459,1489`). Движок отдаёт по роли `loaded|stub|pending`; `pending` — ждать, `stub` — в `clay`
   и в промпт («grey schematic object»), а не только в диагностику.
5. **Транспорт и метрика.** Два JPEG в Base64 внутри JSON + `fsync` всего задания в `jobs.json` (`draft_jobs.py:91`) + пересериализация во
   внутренний HTTP (`draft_service.py:260`) + прокси на DEV (`:403`) — тяжело для телефона. Делать: multipart (или предзагрузка кадров
   отдельным запросом → ссылки/хэши в задании), в job — только ссылки; мерить **клик → начало вызова модели** (а не `_t_our`, который
   стартует после загрузки тела, `draft_render.py:3315`). `_IDENT_CACHE` процессный (`improve_mode.py:248`) — `prepare` греет именно
   DEV-worker. Локальный source сохранять атомарно до модели, откладывать только `scp/index` (`draft_render.py:1647`).
- **(а) iPhone SE:** 2048×1489 ≈ 3 Мп, пик памяти +35–70 МБ; SE 2020/2022 — вероятно ок, SE 2016/под давлением — нет; обычный холст уже
  ограничен 2,3 Мп из-за `context lost` (`viewer.ts:530`). Гарантии «2 с» на телефоне нет — замер на реальных устройствах, ранний профиль 1536×1117.
- **(б) Отличия кадра браузера от серверного:** свет PBR + панорама за окном (не критично — модель переосвещает); критично — наклон,
  контур выделения, незагруженный/каркасный предмет (полупрозрачная коробка `meshes.ts:165` против серверной непрозрачной clay-формы),
  иной crop: промпт объявляет IMAGE 1 абсолютным источником геометрии (`improve_mode.py:94`). Отсюда п.1 и п.4.
Критерий «наша часть ≤ 2 с» читать как «клик → начало вызова модели ≤ 2 с на компьютере; на телефоне — замер и честный отчёт».

**Требование владельца 17.10 (из demo-09 «полосы»):** кадр снимается в пропорции устройства покупателя — на телефоне вертикальный лист
(два вида 2:3 друг под другом → лист и размер согласовать с `SIZE`/`BAND_PX`, см. критику п.2), на компьютере 3:2; тогда «Фото» без полос по построению.
