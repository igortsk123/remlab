# render-prep-speed-01 — фото за ≈15 с после смены любого товара

**Зачем.** Владелец TG 1739–1747 (18.11): смена дивана, любого товара или нескольких → фото должно приходить ≈15 с.
Сейчас 33–39 с при нагруженном DEV, 25–30 с на свободном (замер рабочего 2, T-07/1): подготовка сцены 14–19 с,
докачка новых моделей на машину 4,5–5,4 с (16–21 МБ), Blender на 4090 ≈10,5 с. «С кодекс согласуй и делай» (TG 1745).

**Вход.** Замер cProfile: `~/remlab-logs/prep-probe-1118/run-054454` (pakardev). Codex: `_intake/codex/2026-11-18-scene-prep-speed-answer.md`.
Код: `tools/scout/render_exec.py` (`_prepare`, `_prepare_fresh`, `_dump_cached`, `_prep_key`, ассеты), `cycles_probe/export_scene.py`,
`cycles_probe/demo_scene_dump.mjs`, `cycles_probe/demo_scene_entry.ts`, `draft_render.py:scene3d_frame`, `opening_ir.py:paint_beyond`,
`mesh_render.py:load_parts`, `render_prewarm.py` (ветка worktree-render-prewarm, T-07).

## Шаги (порядок — по Codex, сверено с замером)
1. **Трасса по шагам** на каждый заказ в `timing` (импорт, план, меши, картинки, запись; браузер: запуск, загрузка, выгрузка данных
   квартиры, сборка, растения, GLB; докачка ассетов; Blender). Замер p50 на 5 сменах товара (1 товар, 3 товара) на свободном DEV и при двух
   заказах сразу. Без этого не оптимизировать — две ветки идут параллельно, ускорение не той ветки даст 0 с.
2. **Ключи кэша — до любого переиспользования** (Codex п.2): что из входа меняет файлы сцены, но не попадает в ключ (`render_snapshot.py`
   room — только размеры; `_dump_cached` — имя каталога сборки; живые данные квартиры в выгрузке). Найденное — в ключ по содержимому.
3. **Браузер:** безусловная пауза 1,5 с в `demo_scene_entry.ts` → условие готовности (с тестом паритета); один постоянный браузер,
   новая страница на задание, потолок памяти, перезапуск по счётчику/ошибке, запасной путь — нынешний процесс.
4. **Python:** заранее загруженный родитель + новый дочерний процесс на задание (fork); выгрузка без рисования картинки-превью
   (`compile_scene` растр, `paint_beyond`), сохраняя `_push_from_supports`, порядок мешей, камеры, метаданные.
5. **Докачка моделей:** модели всех товаров из горячего списка и вариантов — на машину при включении (заготовка T-07), чтобы смена
   товара не качала 16–21 МБ.
6. **Blender на машине (владелец TG 1749 «а подготовку также сократить»):** сейчас новый процесс Blender на каждый заказ
   (`render_gpu/render_worker.py:151`, `--persistent 1` — только внутри пары ракурсов): запуск + сборка сцены ≈2–4 с из ≈10. Постоянный
   Blender на машине, принимающий задания, со сменой только изменённых предметов; кадр побайтно тот же (те же сэмплы, шумодав).
   Новый образ — проба на отдельной группе ≤ $0,05, боевая — после PASS директора.
   **18.11 ОТЛОЖЕНО по замеру** (метки Blender в образе -prep1, set1): старт 0,3 → GPU 0,6 → сцена 1,8 → C1 5,2 → C2 7,4 → выход 8,5 с;
   не-кадровое ≈2,9 с, выигрыш постоянного процесса ≈1,5–2,5 с при риске расхождения кадров. Шаг 5 в виде «модели товаров на машину»
   не нужен: меши уже ассеты по sha (T-24/8). Вместо них — **5б:** картинки декора вынести из `demo_nodes.glb` (≈16 МБ на заказ:
   выгрузка 3,8 + скачивание 2,3 ≈ 6 с из ≈22) в файлы по sha — DEV-сторона рабочий 1 (T-10), машина рабочий 2 (T-09).
7. Только потом — кэш разобранных мешей по содержимому, сжатие npz, md5 (Codex: эксперимент, отклонить, если итог хуже).

## Критерии приёмки
- Кадры не меняются: файлы сцены побайтно или по разобранному содержимому (вершины, UV, текстуры, положения, камеры) и итоговые
  кадры ΔE ≤ 1 на 6 комнатах (гостиные + спальни) и 3 сменах товара.
- Время: подготовка сцены p50 ≤ 5 с на свободном DEV; смена 1 и 3 товаров на прогретой машине — p50 ≤ 15–18 с (честный итог, если не
  достигнуто, — с разбивкой, где остаток).
- Память DEV: постоянные процессы ≤ 1,5 ГБ в простое; два заказа сразу — без отказов.
- Запасной путь (флаг выкл.) даёт нынешнее поведение; тесты в CI.
- Без ID комнат/товаров/туров в коде; боевой 8600 не перезапускать (выкладка — директор).
