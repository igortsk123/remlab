## Решение (минимальный набор, порядок — Codex 05.11, принят ведущим)
1. **Видеть все правки (кит).** Корень — по пути изменённого файла (worktree распознаётся); журнал правок — общий для всех
   копий (в git-dir основной копии, `.git/memory-bank/`), `memory-health` читает старые и новые логи.
   Зачем: без этого «какие доки задеты» и метрики недостоверны.
2. **Отчёт «что задето» при приёмке (кит, `tools/memory-impact.mjs`).** `--base main --head <ветка>`: реальный diff (`git diff -z`) →
   доки, описывающие эти файлы → для каждого `обновлён` / `верен без правок` / `в очередь сверки`. Рабочий прикладывает отчёт;
   канон правит ведущий или ночная сверка (одна копия пишет — нет конфликтов в `core/*`). Сначала предупреждение, потом
   блок только на новом непогашенном.
3. **PLAN-LAG (кит, opt-in; в remlab — с доской T-ID).** План `draft/in_progress/partial`, а после его последнего коммита есть
   кодовые коммиты с его slug/T-ID → предупреждение «план отстал на N коммитов». Правило канона: будущее живёт только в `plans/`,
   в `core/domain` — одна строка «Запланировано: план `<slug>`; в коде нет». Ссылки — `файл:символ`, не номера строк.
4. **Ночная сверка (кит — шаблон таймера; remlab — таймер на pakardev).** Один процесс на проект (`flock`), чистая копия вне
   `.claude/` от свежего `origin/main`, ветка `memory/nightly-<дата>`; очередь собирается заново: доки задетые вчерашним diff →
   `--drift-report` с задетыми названиями → `importance: high` и возраст дрейфа → частота чтения → ротация старейшего.
   Бюджет: 1–2 дока или ≤ 60 утверждений за ночь, ≤ 0,5 % недели; пустая очередь — ночь пропускается. Утром ведущий
   смотрит ветку и вливает; авто-влива нет (аудит проверяет форму, не истинность), вернуться к вопросу через 2–3 недели.
   Учёт — `tokeny` (метка задачи ночной сверки) и `memory-health --log-verify`.
5. **Храповик дрейфа (кит, после 2 недель телеметрии).** Нынешний долг — исходная точка; ошибка — новый непогашенный дрейф
   у дока, задетого этим изменением, и `high`/задетое название старше 7 дней; остальное — срок 14–30 дней и ночная очередь.
6. **Релиз кита и раскатка.** Довести 1.10 (тесты, коммит, тег), затем новый тег с пп. 1–5 → remlab, tamara, sup2
   (`upgrade.sh`), запись в `FLEET.md`.
7. **Мера.** `memory-eval` раз в 2 недели по кругу remlab → tamara → sup2 (≈1 % недели одной учётки), с 2–3 вопросами об эксплуатации.
