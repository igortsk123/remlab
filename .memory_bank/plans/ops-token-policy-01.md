## Цель
Одинаково на всех проектах (remlab, tamara, sup2-repo) и машинах (pakardev, algor, common): оптимальный (не «супер-эконом») расход
токенов, сводка «сколько потрачено, сколько банк памяти стоит и экономит, сколько осталось лимита» — по запросу с любой машины.
Банк каждого проекта один — на pakardev (на algor/common папки проектов смонтированы sshfs).

## Политика (что одинаково везде)
1. **Порог сжатия.** Opus 5.5 — `autoCompactWindow: 293000` (сжатие ~260 тыс.), Fable 5.1 — 400000; в `.claude/settings.json` всех трёх
   проектов и в `~/.claude/settings.json` всех трёх машин (для прочих папок). Зачем: ≈ −8…−11 % у tamara и sup2 при умеренном
   числе сжатий; 200k не берём — двойное число сжатий съедает выгоду. Fable 400k — предварительно, до своего замера.
2. **«Авто-/clear» = сжатие при простое.** `idleCompaction: true` + `env.CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS = 120000` в проектных
   настройках: рабочая вкладка, простоявшая час между задачами, сжимается до сводки — следующая задача стартует с ~80 тыс., а не 200+.
   Задача — в ту же вкладку с самодостаточным брифом (как сейчас). Ведущих не чистим. Это не `/clear` (сводка прошлого остаётся):
   связанное продолжение — `/compact` с фокусом; несвязанная задача, когда владелец рядом, — новая вкладка; перед сжатием — состояние
   в план/блокнот (Codex 05.11).
3. **Одна модель на сессию** (кэш), effort — по-прежнему по проекту.
4. **Учёт — один инструмент на всех.** Общий `tokeny` (версия tamara) в каждом проекте одинаковой копией из кита `memory-bank-template`
   (модуль кита, не форк): ночная выгрузка каждой машины в общую папку на pakardev, сводка по запросу `tools/tokeny/svodka.sh [--proekt X]`
   на любой машине — токены, $ по API, % недели каждой учётки, строка «Память».
5. **Процент лимита.** На каждой машине одна маленькая CLI-сессия-«счётчик» со statusline (пишет `~/.claude/usage-log.jsonl`) — выбор
   владельца 05.11 (вариант Б); телеграм-бот для сводки владелец даёт отдельно, по образцу других проектов.
6. **Польза банка.** `tools/memory-eval/` в каждом проекте; опыт раз в 2 недели по очереди (remlab → tamara → sup2), 10 свежих вопросов,
   ≈1 % недели одной учётки; итог — в сводку и `changelog/memory-eval.log`.
7. **Размер банка.** Бюджеты аудита (TIER0-RULES, DECISIONS-BLOAT, TIER1-BLOAT) — разбирать в каждом `/memory-check`; remlab сейчас:
   правила 34 KB > 26, decisions 69 KB > 56.

## Задача T-30 (черновик, ждёт слова владельца на код): «на 1 %» без чужой работы учётки
Владелец 05.11 (TG 84): «придумай алго, который вычищает пики на pakardev, заодно будем знать, сколько уходит на Windows и в др. местах».
Алгоритм (ведущий, по разбору `na1/seg.py`, `anal.py`):
- **Ступеньки.** По `usage-log.jsonl` своей машины, в пределах одного окна `resets_at` (а не 7 календарных дней; начало окна —
  `resets_at − 7 д`, дефект `tokeny.py:845` по Codex): момент первого появления каждого значения % → отрезки (начало, конец, +п.п.,
  наши $ всех проектов машины на отрезке). Ночная выгрузка кладёт отрезки в файл машины — сводка на любой машине видит все три учётки.
- **Разложение.** На отрезках окна — МНК без свободного члена `п.п. = a·$ + b·часы`, `b ≥ 0` (фон). Наши токены на 1 % = `1/(4a)` млн
  взвешенных; «вне наших машин» = `b·часы` п.п. за окно (и в час). Пики: отрезок с остатком выше p90 (п.п. много при малых $) — выкинуть
  и пересчитать один раз; выкинутые п.п. тоже идут в «вне машин».
- **Порог.** Меньше 20 п.п. или 10 отрезков в окне — «мало данных» (сейчас порог 1 п.п.); прошлое окно учётки — запасной ответ.
- **Самопроверка.** На algor/common фон должен выйти ≈0 (сегодня так: −0,000 и −0,005 п.п./ч) — тест на их сохранённых отрезках;
  синтетика с известными a и b восстанавливается ±10 %.
- **Вывод `/tokeny`:** «pakardev (Ultra): наши ≈5,2 млн на 1 %; вне наших машин ≈ 9 % недели (≈1,3 %/ч)»; algor/common — как сейчас + «вне: 0».
Где код: модуль кита `_optional/tokeny` → копии remlab/tamara/sup2 (кроны — только worktree). Без денег.
