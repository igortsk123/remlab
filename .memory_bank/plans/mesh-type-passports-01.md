## Рамка «реестр + тень»
**Фаза 1 (этот план).**
- Реестр: 30 типов (23 из черновика + `статуэтка`, `бра`, `зеркало`, `полка`, `растение`, `стенка`, `часы` — роли, которые уже есть в `rules/asset-strategies.json`, а `статуэтка` ещё и в фикстуре `tests/fixtures/category-roles-mini.json:149` и в `salad/components.py:29`). Семь добавленных — минимальные паспорта «только `route`», `provisional`.
- Тень: К1 на кроватях, К3 на подушках пишут вердикт и метрики в **новую таблицу** `passport_shadow`; ни один вердикт не меняет `photo_assessment.verdict`, очередь и платные входы. Ошибка сторожа ловится и пишется в журнал, вырезка не падает.
- Гейты платных входов подключены в режиме **`observe`**: возвращают «пропустить», но считают «заблокировал бы» (по ролям без паспорта, по вердиктам К1/К3). Отчёт ночи — строка со счётчиками.
- Что **не** входит: блокировка платного, смена `ASSESSOR_VERSION`, перенос ролевых наборов из `components.py`/`hybrid_mask.py`, чтение `paint.*` покраской, С1, подбор признака слабого рисунка К3, новые меши и платные прогоны.

**Фаза 2 (отдельный план, после недели тени и приёмки).** `enforce` для К1/К3 (только если исходы на фикстуре приняты); неизвестная роль → `unknown_type` без платного меша; ключ замера с ролью; `paint.*` читает `sg_drive`; ролевые наборы грузятся из паспорта.
**Закон рамки:** паспорт с `provisional: true` не может быть в режиме `enforce` и не влияет на маршрут — это проверяет `--selftest` (схема отвергает такой паспорт).

## Ключи и версии (Codex п.1–2)
Фактическое состояние (main `41ce10b1`):
- `photo_assessment` — ключ `(source_sha, assessor_version)` (`mesh_queue.py:141-147`); `ASSESSOR_VERSION = 'a1'` (`salad/preprocess.py:28`) входит в выборку «что ещё не оценено» (`cutout_sync.py:319-332`, `todo`); кэш вырезки — `<sha>.png` (`cutout_sync.py:358`).
- Репозиторий уже говорит, что вердикт без роли небезопасен: `photo_hash.py:414-425` (тест останавливает появление роли комнат из `GROW_ROLES`/`SOLID_SILHOUETTE_ROLES`, пока ключ не получит роль).
- Версия реестра внутри `assessor_version` (как было в прежней редакции плана) **отменяется**: смена одной роли пересчитывала бы всю базу.

Решение:
- **Ключ замера** — `(source_sha, normalized_role, measurement_version)`; `normalized_role` — `base_role` (`asset_strategy.py:32-35`) + `aliases` паспорта. **Версия замера** — отдельно для каждого сторожа (`k1.v1`, `k3.v1`): растёт, только когда меняются пиксельные вычисления.
- **Политика** — `policy_digest` = sha256 канонического JSON одного паспорта (пороги, подтипы, `guards[]`). Хранится в каждой строке вердикта. Пороговая правка → `reverdict` из сохранённых метрик, **без пересчёта пикселей**; пересчёт пикселей — только при смене `measurement_version` этого сторожа и только для его роли.
- **Фаза 1: таблица `passport_shadow(source_sha, normalized_role, measurement_version, policy_digest, metrics jsonb, shadow_verdict, created)`**, ключ `(source_sha, normalized_role, measurement_version)`; своя выборка «что ещё не посчитано» (`todo` вырезки не меняется). `photo_assessment`, `ASSESSOR_VERSION`, кэш `<sha>.png` и все их потребители остаются как есть.
- **Фаза 2 (миграция, в этом плане только перечень).** Ключ `photo_assessment` получает роль; потребители `ASSESSOR_VERSION` на правку: `cutout_redo.py:104-124`, `cutout_sync.py:13,332,347,382-407`, `mesh_photo_survey.py:40,235`, `mesh_queue.py:87-89,143-147,271,399,498-530`, `photo_fit.py:97-150`, `photo_hash.py:226,400,466`, `pipeline_funnel.py:23`; миграция через `alter … add column … if not exists` по образцу `mesh_queue.py:151`, дозапись роли из `products.cat_role`, затем смена ключа.

## Точки сторожей (Codex п.6)
Порядок в `cutout_sync.one`: фото → `src` (`:369`) → маска `BACKENDS[BACKEND](raw)` (`:370`) → `chain` (`:373`, внутри `chain_shape` `:282` → `PRE.trim_alpha` `:283`) → вердикт и запись (`:379-385`). Стадии сторожей (схема допускает только их):
- `pre_mask` — сразу после декодирования `src`, до маски (для С1; в фазе 1 не используется).
- `full_frame` — по `shape` до `trim_alpha`; нужны координаты исходного кадра (в фазе 1 не используется).
- `cropped` — после `trim_alpha`, по обрезанной вырезке (**К3**).
- **К1** нужен исходник + вырезка + смещение. Решение: `chain` дописывает в `info['photo']` смещение обрезки `object_xy` (из `getbbox()` альфы формы перед `trim_alpha`; в шаге 1 проверить, что `trim_alpha` режет ровно по нему), К1 вызывается из `one()` после `chain` и до записи, со `src`, `cut`, `info`. Потери координат нет, цепочка и её результат не меняются.
- Несовместившиеся с исходником (10 из 131) — исход `ambiguous`, не `ok` (в тени считается и показывается отдельно).
- `cutout_redo.py` остаётся **неизменяющим** (контракт `cutout_redo.py:12-14`: не трогает `photo_assessment`, боевой кэш) — сторожа в нём работают в режиме `--measure` и пишут только в папку прогона; отдельной команды записи в БД в этом плане нет.

## Масштаб (жёсткое правило владельца 20.11, TG 2338) — с учётом вырезки (Codex п.9)
Прежнее «0 ₽, ≈8 ч» считало только новые сторожа. Честно:
- **Сторожа (тень, только кровать и подушка):** К1 ≈0,08 с по маске + 0,9 с против исходника; К3 до ≈5 с на подушку (замер 89 подушек шёл >7 мин на загруженной машине). Кроватей ~10 %, подушек ~7 % → на 50 000 ≈5 000 × 1 с + ≈3 500 × 5 с ≈ **6,3 ч одного ядра**, на ЦП, 0 ₽. Оценка по замеру, не измерена на 50k.
- **Предусловие — вырезка и хеш фото.** Источник маски сейчас `fal` (`cutout_sync.py:65`, ~$0,0008/фото, `:19`), предел `CUTOUT_DAILY_MAX = 400` в ночь (`:67`) — **50 000 / 400 = 125 ночей** с нуля; бесплатный `local` — ≈14 с/фото на 12 ядрах (`cutout_sync.py:20`) = ≈194 ч машины на 50 000. Хешируется не весь каталог, а `mesh_required ∪ пул подбора` (`photo_hash.py:72-80` (`targets_sql`)), шаг хеша — до 400 в ночь (`cutout_sync.py:556`).
- **Охват сейчас (`cutout_sync.py --report`, 20.11):** оценено 4 162 фото (оценщик a1), хеш известен у 22 225, ждут вырезки 17 585; комнаты: спальня 3 916 из 3 931 целей, прихожая 703 из 703. Теплая часть (уже вырезано) — на ней тень стартует; холодная — по очереди вырезки.
- **Правило плана:** тень считает только то, что уже вырезано; отчёт ночи пишет «охват: вырезано N из M кроватей/подушек, ждут K»; ускорение вырезки (fal $0,0008 × 50 000 ≈ $40 или local) — решение владельца, вопрос ❓2.
- **Шаг 0 перед кодом:** бенчмарк «хеш → вырезка → К1/К3 → запись» на ≥1 000 фото целиком, с загрузкой, БД и очередью; цифры — в приложение. Без него «50k» — оценка.
- **Глазами:** не «все отказы», а ограниченная выборка в неделю: ≤20 ближайших к порогу на правило + 20 случайных из «ok» (оценка пропусков). Новый тип — лист ≤20 карточек владельцу.
- Платное (меши, покраска) в фазе 1 не запускается; тень платное **не создаёт и не увеличивает**.
