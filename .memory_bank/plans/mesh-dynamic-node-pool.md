## Цель
Прогон мешей должен использовать ноды, которые прогрелись ПОСЛЕ его старта, и не терять
задания, упавшие по транспорту.

## Источник задачи
Владелец 31.08: «делай п2» — из двух вариантов по итогам осмотра конвейера выбран
«починить добор нод». Наблюдение: группа `mesh-run10` 9 часов не получала машин, в 16:00
прогрелась ОДНА нода, на ней стартовала волна лечения (91 задание, ~2 мин/меш → ~3 часа).
В 16:42 вторая нода уже качала образ (77%), но текущий прогон её не увидит: `ssh_run.run()`
берёт список портов ОДИН раз (`warm_ports()` перед созданием очереди).

## Критическая оценка (свой разбор + Codex, ответ — `_intake/codex/q-ssh-run-dynamic-nodes.answer.md`)
Совпало: нужен супервизор нод, а не «раз в минуту дёрнуть `warm_ports()` и добавить потоков»;
текущий живой прогон расширять нельзя (нет реестра inflight — второй `ssh_run` продублирует
задание); чинить надо для следующей волны.

Codex добавил то, что я не учёл, и это проверено по коду и логу:
- **Задания теряются уже сейчас.** `transport_failed` пишется в результаты и в очередь НЕ
  возвращается (`ssh_run.py` worker), `ssh_run` всё равно выходит с кодом 0, а `batch_show`
  увеличивает счётчик `done` на ВЕСЬ размер пачки. В логе это видно прямо: «заданий 5, готово 3»,
  «заданий 5, готово 2» — а `done` прибавлял 5. То есть счётчик 115/560 завышен.
- **Мёртвая нода съедает хвост очереди:** воркер после транспортной ошибки берёт следующее
  задание и может мгновенно провалить весь остаток.
- **Идентичность ноды по ssh_port ненадёжна** — порт может быть переиспользован новым
  инстансом; в API есть стабильный `id` (проверено: `id`, `machine_id`, `ssh_port`, `state`,
  `started`, `ready`, `pulling_progress`).
- **`warm_ports()` нельзя звать целиком на каждом опросе:** проба каждой ноды последовательная,
  под `_ssh_gate`, timeout 50 с → до ~8 минут на круг.
- **`cull_slow_pulls()` не работает во время прогона** — он вызывается только в паузах ожидания
  `batch_show`. При 3-часовой волне зависшие загрузки образа никто не пересаживает.
- **Группа может остаться включённой** (деньги): `finale()`/`stop_group()` не в `finally`,
  `batch_show.sh()` не ловит `TimeoutExpired`.

Что из совета Codex я НЕ беру сейчас (обоснованно):
- **Claim/lease на приёмнике** (атомарная бронь до генерации). Дублирование возможно только в
  окне «SSH оборвался, а нода ещё считает». Генерация ~110 с, поэтому дешёвая замена — grace
  ≥ 300 с перед повтором: за это время нода либо опубликовала комплект (повтор придёт как
  `cached` — `worker.py` проверяет `already_done(prefix)` перед работой), либо умерла. Lease
  требует правок и воркера, и приёмника на боевой exit-fi ради риска ценой $0.005 за меш.
- **Pull-очередь (ноды сами берут задания по HTTPS)** — правильное направление после пилота,
  но это переделка приёмника и воркера; не в этот план.
- **Учёт оплаченного времени нод вместо GPU-секунд** в отчёте — отдельная мелкая задача.

## Скоуп — что входит
1. **Супервизор нод в `ssh_run.py`:** опрос API каждые ~45 с; идентичность — `instance.id`;
   health-проба только для НОВЫХ (и остывших) нод, не для работающих; один воркер на инстанс;
   новые ноды подключаются, пока в очереди есть работа.
2. **Единый лимитер стартов SSH-сессий** (≥5 с между началами любых сессий — и проб, и заданий),
   замок держится только на старте, а не на время генерации. Причина — грабля 29.08: залповый
   старт сессий давал пустой вывод.
3. **Жизненный цикл задания:** `transport_failed` → возврат в очередь (до 3 попыток, повтор не
   раньше чем через 300 с и желательно на другой ноде); содержательные статусы
   (`bad_cutout`, `flat_shape`, `slab_suspect`, `input_failed`, `failed`, …) — терминальные,
   их лечит слой приёмки. Нода после транспортной ошибки → `suspect`, воркер уходит,
   повторная проба здоровья через 60 с.
4. **Завершение прогона:** воркеры ждут на очереди, а не выходят по первому пустому
   `get_nowait()`; прогон закончен, когда у всех заданий терминальный ответ.
5. **Чекпойнт после каждого задания** — append-only JSONL (`mesh-run-progress.jsonl`):
   sku, prefix, нода, попытка, статус, время. `mesh-pilot-results.json` остаётся итоговой сводкой.
6. **Коды возврата `ssh_run`:** `0` — все задания терминальны; `75` — нет ёмкости (нет тёплых
   нод); иной ≠0 — остались нерешённые транспортные задания/внутренняя ошибка.
7. **`batch_show`:** двигать `done` на ЧИСЛО терминально закрытых заданий (из сводки/чекпойнта),
   а не на размер пачки; понимать код 75 как «ждём ноды»; `try/finally` вокруг прогона, чтобы
   группа гасилась при любой ошибке; ловить `TimeoutExpired` в `sh()`.
8. **`cull_slow_pulls()` во время прогона** — вызывать из супервизора `ssh_run` раз в ~10 мин
   (перенос логики из пауз `batch_show`).
9. **Тест без Salad:** скрипт-стенд с подменой `warm_ports`/`run_job`, который проверяет:
   поздняя нода подключается; транспортный сбой возвращает задание и уводит ноду; прогон
   завершается; чекпойнт пишется; коды возврата верные.

## Скоуп — что НЕ входит
- Claim/lease и синхронизация публикации одного prefix на приёмнике (`receiver.py` не трогаем).
- Pull-очередь / переделка `worker.py`.
- Тариф и приоритет группы Salad не меняем (правило владельца).
- Пересчёт стоимости по оплаченному времени нод.
- Правки самой волны лечения (`apply_repairs.py`, состав `mesh-reseed.json`).

## Порядок выкатки (важно — конвейер работает прямо сейчас)
1. Правки применяются к файлам, пока идёт текущая волна: запущенный процесс их НЕ подхватит
   (Python держит код в памяти) — это безопасно.
2. Прогнать стенд и `py_compile`.
3. Перезапуск конвейера — по решению владельца, два варианта:
   - **дождаться конца волны** (~2–2,5 ч на одной ноде) и перезапустить `batch_show`;
   - **перезапустить сразу** (рекомендую): сделанные задания вернутся как `cached` за секунды
     (комплекты лежат на приёмнике, `drain.sh --keep` их не удаляет), зато волна сразу увидит
     вторую и следующие ноды. Убивать процессы сразу ПОСЛЕ появления очередного `complete.json`
     — тогда в полёте не будет наполовину посчитанного задания.
4. После перезапуска — смотреть `_intake/batch-run5.log`: в нём должны появиться строки о
   подключении новых нод.
