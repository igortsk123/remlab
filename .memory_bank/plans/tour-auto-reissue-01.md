## Цель
Любая выкладка витрины /demo (ночная и дневная, и откат) сама перевыпускает все живые туры «как есть» на новый код страницы и
сборщика — без ручной команды оператора; результат (перевыпущено / пропущено / отказ) виден в журнале и сводке, расхождение
«тур ≠ /demo» — громко.

## Скоуп — что входит
1. **Обёртка `tools/ops/tour-reissue.sh`** (одна точка запуска, крон и ручной путь зовут её):
   - окружение воркера `set -a; . ~/.config/remlab/env; set +a` (файл не печатается; урок 608), `TRIAL_API_URL`, `TRIAL_WORK_DIR`
     как в юните `remlab-trial-worker`; `TMPDIR` — на диск (`tools/ops/remlab-tmp.sh`);
   - `reissue.py --days 60` (= `REISSUE_DAYS_MAX`: список и так отсекает истёкшие по `result_expires_at`, поэтому дней с запасом —
     срок тура `trialResultDays` 30 на сервере может меняться env, DEV его не знает);
   - под `tools/ops/heavy-slot.sh tour-reissue --cores 1 --prio 2` (низкий приоритет, один процесс сборки за раз — по туру по очереди);
   - замок `flock ~/.remlab-tour-reissue.lock` + флаг «нужен ещё проход»: выкладка во время прохода не теряется — по окончании проход
     повторяется один раз (схлопывание: три выкладки подряд = не больше двух проходов);
   - `stale` (агент успел пересобрать, пока собирали) — один повтор тура сразу в том же проходе;
   - итог — строки: `tour_reissue: туров N · перевыпущено P (из них «данные те же, только страница» R) · пропущено S (busy b,
     expired e, …) · отказ F` и `DIGEST:` с тем же; отказ/сбой ≥ 1 или расхождение (п.3) → `WARN:tour_reissue:` с id туров; код
     выхода 1 при отказе (как у `reissue.py`). Отчёт `report.json` — `~/remlab-logs/trial/reissue/<время>/` (как сейчас).
2. **Когда запускается:**
   - ночь: `refresh_daily.sh` — новый шаг `step tour_reissue bash ../ops/tour-reissue.sh` СРАЗУ после успешного `flat215_publish`
     (упала публикация — шаг пропущен строкой в лог: перевыпуск на вчерашнюю витрину бессмыслен); публикация в ночи зовётся с
     `PUB_REISSUE=0`, чтобы не было второго прохода из хука ниже;
   - днём: хук в конце `publish_demo.sh` (после `check_http`, только `PUB_DIR=demo`, и после публикации, и после `--rollback`) —
     запуск обёртки в фоне отдельным юнитом `systemd-run --user --unit remlab-tour-reissue-<метка> --collect` (выкладка не ждёт
     54 сборок; переживает закрытие сессии; видно в `systemctl --user list-units 'remlab-tour-reissue*'`); `PUB_REISSUE=0` — выключить
     (самопроверка `tests/test_publish_demo.py`); проба под `/test/` перевыпуск не зовёт;
   - дневной итог: отказ/расхождение — сразу `tools/scout/alert.sh` одной строкой (не молча); успех — строка в
     `~/remlab-logs/trial/reissue.log`; ночная сводка добавляет «за сутки дневных проходов K, перевыпущено …» по этим строкам.
3. **Проверка «демо и туры одинаковы»** (в той же обёртке, после прохода, 0 $, без ключей покупателя):
   - ожидаемая витрина = хеш по тем же правилам, что `pinRelease`, посчитанный по файлам, которые прод отдаёт сейчас по
     `https://remont-lab.online/demo/…` (index.html, lib/scene.json, файлы из него, rt-meshes.json) — маленький `tools/ops/demo-release-hash.mjs`
     (общая функция хеша вынесена из `pinRelease`, чтобы правило было одно: TS-модуль + тест «тот же хеш, что у `pinRelease`»);
     сверено 12.11 14:40: прод отдаёт `index.html`, `lib/scene.json`, `rt-meshes.json` байт в байт как сборка `~/scout-scenes/flat215-demo`
     (запрос с `Accept-Encoding: identity` — сжатые копии Caddy не мешают);
   - у каждого перевыпущенного тура `release` из ответа сервера == ожидаемая → страница и движок ТЕ ЖЕ байты, что /demo (значит, те же
     высоты подвеса, двери плана, ленты «Заменить», все константы страницы — они в этих файлах);
   - данные (то, что строит сборщик на DEV): выборочно 3 тура (самый свежий, самый старый, один со спальней) — из исходника
     перевыпуска (`GET /api/trial/worker/reissue/<id>`) берётся новая версия и сравнивается с /demo по признакам правил сборщика:
     метка сборки `build.rules` (см. п.4) равна у тура и у `demo-data.json`; есть план с дверями (`trial.panels[].rooms` + проёмы);
     ленты «Заменить» по ролям непусты там, где непусты у /demo;
   - расхождение → `WARN:tour_reissue: тур <id> на витрине <x>, /demo — <y>` + alert (днём) / `DIGEST:!` (ночью).
4. **Метка правил в данных** (чтобы сравнение было не «на глаз»): `trial_bundle.build` и `flat215_demo.py` пишут в данные
   `build: {git: <короткий хеш HEAD копии, из которой собрано>, rules: <sha256 правил: rules/occupancy.json + rules/*.json сборщика>}`;
   страница поле не читает (только проверка). Если сборщик тура и /demo собраны разным кодом — видно сразу.
5. **Закрытие дыры «новые данные на старой странице»:** публикация версии от «Обустроить»/«Перечитать» (`repo-rebuild-worker.ts`)
   перезакрепляет ТЕКУЩУЮ витрину (`repinJobRelease` вместо `ensureJobRelease`) — тур после пересборки агентом всегда на той же
   странице, что /demo. Первичная публикация тура — без изменений (`ensureJobRelease`). Это правка приложения → выкладка через CI
   (вливает директор). Тур, пропущенный проходом как `busy`, догонит витрину сам при публикации своей пересборки — ждать его не нужно.
5б. **Снимки карточек — пачкой и только где поменялось.** Сейчас каждый опубликованный перевыпуск зовёт `cards.spawn` — отдельную
   службу с браузером (~77 с на 4 ядрах, `tools/floorplan/cards.py`, `reissue.py:one`). 54 тура = 54 браузера в очереди heavy-slot
   (приоритет 1 — выше нашего) после КАЖДОЙ выкладки. Правка `reissue.py`: ключ `--cards batch|off|each` (по умолчанию `each` —
   ручной путь как был); обёртка зовёт `batch` — после прохода ОДИН процесс `cards.py --job a --job b …` под heavy-slot и только для
   туров, где что-то поменялось: новая версия данных ИЛИ витрина сменилась (`release != previous`). Тур «те же байты, та же витрина» —
   счётчик «без изменений», ни версии, ни карточек.
6. **Тесты:** `tests/test_publish_demo.py` — хук зовёт обёртку только для `demo`, не для `/test/`, `PUB_REISSUE=0` выключает, при
   откате тоже; самопроверка обёртки (`tools/ops/tour-reissue-selftest.sh` по образцу `heavy-slot-selftest.sh`: подменённый
   `reissue.py` → счётчики, флаг повтора, код выхода, WARN/DIGEST); TS — общий хеш = `pinRelease`; `repo-rebuild-worker` — тест
   «пересборка перезакрепляет витрину»; Python — метка `build` в данных тура.

## Скоуп — что НЕ входит
- «Перечитать планировку» (`--reparse`) автоматически — это новый разбор листа со сторожем регресса и приёмкой; остаётся командой оператора.
- Новый подбор мебели в готовых турах — перевыпуск «как есть» сохраняет выбор агента (мебель, исходы, правки комнат и проёмов).
- Уведомление агенту о новой версии: агент видит обновлённую страницу при следующем открытии (как при ручном перевыпуске сейчас);
  открытая вкладка не перезагружается. Если нужно «страница обновилась» — отдельная задача владельца.
- Боевой перевыпуск в рамках этой задачи — только `--dry-run`; первый боевой проход — по слову директора после вливания.

## Риски и как закрыты
- 54 сборки подряд нагружают DEV → heavy-slot, `--cores 1`, по одному туру, низкий приоритет; время — по сухому прогону (ниже).
- Плохая витрина ушла в туры → откат витрины (`--rollback`) тоже зовёт перевыпуск: туры вернутся на прежний хеш (папка
  `_releases/<хеш>` не удаляется — её держат другие туры; если удалена — `pinRelease` создаст заново из отката).
- Сборщик стал строже и отказывает старым турам → тур остаётся прежним (сервер не трогает при отказе), WARN с id; массовый отказ
  (> 20 % туров) — `DIGEST:!` владельцу.
- Агент открыл тур во время перевыпуска → видит старую или новую версию целиком (атомарная подмена `release`, версия данных под замком).
- Код DEV отстал от main (воркер/скрипты не перезапущены, урок 608) → метка `build.git` покажет, на каком коде собраны туры.
