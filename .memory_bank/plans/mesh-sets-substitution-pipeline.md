## Цель
Чтобы негодные фото не доходили ни до генерации мешей, ни до сетов; чтобы у каждого занятого
слота был готовый заменитель с уже сделанным мешом; чтобы поломка (пропало наличие, умерло фото,
брак меша) чинилась автоматом заменой на такой заменитель, пересчитывались ТОЛЬКО затронутые
сцены, и человек видел изменённый сет.

## Источник задачи
Владелец 28.08 после разбора вырезки фона: «не отдавай такое в меш и на этапе выбора сетов
проверку добавь… чтоб чётко было понимание вот товары в сетах, а вот товары-заменители, по
которым готовы меши… запускать замену, автоматом пересборка только нужных сцен солвером,
и результат человек видит изменённый сет».

## Что уже есть (не переизобретать)
- `mesh_queue.py` — таблицы `mesh_demand` / `mesh_jobs` / `asset_revisions` / `orientation_state`,
  спрос трёх приоритетов (1 в сетах, 2 кандидат слота, 3 резерв), `job_key = sku|source_sha|pipeline_version`.
- `mesh_ready.py` — единый предикат «есть годный меш» + этапный гейт `MESH_GATE_PHASE`.
- `sets_incremental.py::_slot_ok` — общие ворота подбора и лечения; `--heal`, `--enforce-contracts`.
- `salad/collage.py`, `salad/components.py`, `salad/hybrid_mask.py` — сделаны сегодня, в `main`.
- Ночная цепочка `refresh_daily.sh` со всеми шагами.

## Три дефекта, найденные при разборе (Codex, подтверждены по коду) — чинить ПЕРВЫМИ
1. **`mesh_ready` не привязан к текущему фото.** `mesh_ready.py:31-33` берёт
   `select distinct sku from asset_revisions where status='accepted'` — без сверки с
   `source_sha` актуального фото. Магазин поменял картинку → меш от старой картинки
   продолжает считаться готовым. То есть «готовый заменитель» может оказаться мешом другого
   на вид товара — ровно то, на что владелец опереться и хочет.
2. **Смена фото не замечается.** `mesh_queue.py:240-242` при upsert обновляет `image_url`, но
   **не сбрасывает `source_sha`**, а `ingest()` хеширует только записи с `source_sha is null`.
   Байты под тем же URL меняются молча.
3. **Приоритет липкий.** `priority=least(mesh_demand.priority, excluded.priority)` — бывший
   «в сете» навсегда останется 1, даже уйдя в резерв. Приоритет надо пересчитывать каждым прогоном.

Пока это не починено, всё остальное строится на песке.

## Решение

### Шаг 1. Пригодность фото — измерения отдельно, политика отдельно
Новые таблицы (миграция в `mesh_queue.SCHEMA`):
```
product_photo_current(sku pk, image_url, source_sha, observed_at)
photo_assessment(source_sha, assessor_version, pk(source_sha, assessor_version),
                 mask_sha, metrics jsonb, verdict text, created_at)
```
`photo_assessment` хранит **измерения**, а не только вердикт: `w×h`, bbox товара в пикселях и
доля кадра, число компонент и отброшенное `components.clean`, признаки `collage.py`, оценка
тонких деталей, касание рамки. Смена порогов тогда не требует пересчёта масок.
Ключ — байты фото, а не SKU: у результата для неизменных байтов срока жизни нет.
`assessor_version` обязателен — смена алгоритма не переписывает историю.

`photo_fit(role, metrics) → ok | collage | tiny_object | cropped | unknown` — отдельная
версионная функция поверх измерений. **Пороги зависят от роли:** комоду 300 px товара хватит,
стулу с тонкими прутьями — нет. Пороги берём из бенча по ролям, не из головы.

Про разрешение: жёсткие ворота по абсолютной ширине выкосят весь пул (все фото 450 px).
Дискриминирует доля кадра, занятая товаром — на баннере товар мелкий. Апскейл 450→2048
информации не добавляет и воротами не является.

### Шаг 2. Preflight — маска БЕЗ генерации меша
Вердикт коллажа требует настоящей маски (без неё фактура товара читается как текст — проверено).
Делать его побочным продуктом меш-задания **нельзя**: чтобы узнать, стоит ли генерировать,
пришлось бы сначала оплатить генерацию.

Отдельный шаг `photo_preflight.py`: `fetch → source_sha → маска → метрики → вердикт`.
**Решение владельца 28.08: mask-only батч на Salad** — на своей карте, без загрузки Hunyuan.
Ноль внешних зависимостей и ноль денег; ADR-0131 остаётся в силе, fal в меш-контур не возвращается.
Дольше настраивать, но платный путь и не требуется: гибрид уже вровень с платной BRIA.
Реализация: режим `MODE=mask_only` в `salad/worker.py` — `preprocess.prepare` + метрики +
`components.clean` + `collage.is_collage`, без `pipeline.generate`; отдаём JSON, не GLB.
Отвергнут: fal `birefnet/v2` (~$10 разово на пул) — дешёво, но возвращает внешнюю зависимость.

### Шаг 3. Общий контракт подбора — вынести из `sets_incremental`
`mesh_ready.py:9` прямо признаёт: «первичная сборка идёт МИМО `_slot_ok`». Значит новый предикат
опять заработает только задним числом. Контракт слота выносим в нейтральный `slot_contract.py`
и применяем в трёх местах: первичная сборка (`compose2`), лечение, расчёт резерва.
Без этого шага пункт «чтобы в сеты не проходило» не выполняется по построению.

Политика для `unknown`:
- **shadow** — пропускаем, но считаем (отчёт покрытия);
- уже опубликованные сеты — grandfathered, их фото ставятся в срочный preflight;
- **новые сеты и любые замены — fail-closed**: неизвестно = не берём.
Постоянный fail-open противоречит самой просьбе владельца.
- `mesh_job` создаётся только при `photo_fit = ok` — коллажи GPU не тратят.

### Шаг 4. Резерв — покрытие слотов, а не бакеты
Сегодня priority 3 — это «всё остальное», то есть хвост, а не резерв.
Строим связь **`slot_instance опубликованного сета → совместимые кандидаты`**, где совместимость =
роль планирования + жёсткий подтип/способности (прямой/угловой диван, круглый стол, wall-seat) +
фактический размерный конверт + цена ±30% + атомарность пары/pod + пригодное фото.

**Стиль и цвет — только порядок внутри совместимых, НЕ измерение бакета.** Ключ
`роль×конверт×стиль×цвет` взрывает комбинаторику, а принадлежность к бакету всё равно не
гарантирует прохождение контракта.

Норматив резерва: **2 готовые замены на активный слот**, 3 для якорных ролей (диван, носитель,
обеденный стол), 1 для необязательных. **Минимум из двух магазинов** — иначе падение одного фида
обнуляет резерв целиком. Спрос на GPU считается как задача покрытия дефицитов (один SKU закрывает
много слотов), а не «N штук на роль».

### Шаг 5. Замена — только по жёсткой причине, только на готовое
Жёсткие причины: пропало наличие, умерло фото, `photo_fit ≠ ok`, провал контракта, брак меша.
- Здоровый товар **не менять** только потому, что появился более удобный резерв.
- Замена принимает **только `mesh_ready`** кандидатов (даже в фазах off/shadow — иначе смысл
  «заменитель с готовым мешом» теряется); не нашли — оставляем явный пробел, а не тихую подмену.
- Автовозврата к прежнему SKU нет. Выбывший — **карантин 14 дней**, возврат после 2–3
  подряд здоровых проверок.
- **Не более одной автозамены на сет за ночь**; недавняя замена не отменяется 30 дней.
- Журнал `set_changes(set_id, slot, old_sku, new_sku, reason, source_sha, contract_version, at)`.

### Шаг 6. Точечная пересборка — и стабильный `set_id`
У `sets3.json` нет стабильного идентификатора, сет опознаётся номером в массиве. Для журнала
замен и графа зависимостей это негодно: перестановка сетов перепривяжет сцены не к тем наборам.
**Ввести стабильный `set_id`** (первым делом).

Радиус пересборки — от причины:
| Причина | Что пересчитываем |
|---|---|
| SKU выбыл из продажи | ВСЕ сеты с этим SKU |
| поменялся слот одного сета | только этот сет |
| изменились габариты | все сцены этого сета |
| изменилось только фото при тех же габаритах | layout НЕ трогаем — только меш/рендер |
| изменились правила солвера | точечный режим неприменим, нужен полный экзамен |

Механика: `affected_set_ids` → выбрать из `acceptance-scenes.json` сцены этих сетов →
пересчитать только их → слить с кэшированным отчётом остальных → **проверить глобальные пороги
на объединённом отчёте** → перегенерировать галерею и диф.
⚠️ `_relayout_pending` в `sets_incremental.py:682` сейчас только ставится — потребителя нет; он и
станет входом этого шага.

### Шаг 7. Порядок ночной цепочки (сейчас петля)
Сегодня `sets_heal` идёт ДО `mesh_queue`. Если лечение предпочитает `mesh_ready`, а спрос на меши
считается от сетов — образуется петля «сеты ждут меши, меши считаются от сетов».
Развязка: публикация использует только активы, принятые НА НАЧАЛО прогона; новые задания готовят
СЛЕДУЮЩИЙ цикл. Готовый в этот же цикл меш не ждём.

Порядок: каталог/наличие/`source_sha` → подтянуть вчерашние mesh/review/orientation →
preflight новых и изменившихся фото → пересчитать `mesh_ready` и покрытие резерва →
лечение только готовыми заменами → контракты, reindex → точечный пересчёт сцен и публикация дифа →
посчитать новые дефициты резерва → поставить задания на следующий цикл.

## Скоуп — что НЕ входит (сознательно урезано)
- Стиль и цвет как измерения резерва.
- Прогноз оттока товаров.
- Прод-эскалация на fal после каждого провала маски.
- Попытка использовать меш, сгенерированный в тот же ночной цикл.
- Добор оригиналов фото с сайтов магазинов (450 px) — отдельная задача, влияет сильно,
  но это другой конвейер.

## Порядок работ
1. Три дефекта (`mesh_ready` ↔ текущее фото, пере-хеширование при смене URL, липкий приоритет).
2. Стабильный `set_id`.
3. `photo_assessment` + `photo_preflight` (исполнитель по решению владельца).
4. `slot_contract.py` — общий контракт, подключён к первичной сборке, лечению, резерву.
5. Автозамена: жёсткие причины, только `mesh_ready`, карантин, журнал.
6. Резерв: покрытие активных слотов, 2/3/1, два магазина.
7. `affected_set_ids` + точечный пересчёт + объединённая проверка порогов + диф человеку.

## Проверка
1. Тест на дефект №1: принять меш, подменить `source_sha` товара → `mesh_ready` обязан стать false.
2. Тест на липкий приоритет: SKU уходит из сетов → приоритет обязан вырасти до 2/3.
3. Preflight на 36 товарах бенча: оба коллажа получают `collage`, остальные `ok`.
4. Покрытие резерва: доля активных слотов с ≥2 готовыми заменами — отчёт до и после.
5. Замена end-to-end: снять `in_stock` у товара из сета → ночной прогон → замена на mesh_ready,
   пересчитаны ТОЛЬКО сцены этого сета, диф опубликован, журнал заполнен.
6. Дребезг: два прогона подряд без изменений внешних данных → ноль замен.

## Решения владельца
1. ✅ **Preflight-маска — mask-only батч на Salad** (28.08). fal отвергнут: внешняя зависимость
   ради экономии времени настройки не оправдана.
2. ⏳ Момент перевода `MESH_GATE_PHASE` из shadow в hard — по цифрам покрытия, когда появятся.

## Риски
- Ворота пригодности сузят пул; сначала shadow-отчёт, гейт — по цифрам.
- Preflight всего пула на Salad — это ещё 11.6k заданий на очередь; ставить отдельным дешёвым
  батчем (без Hunyuan в памяти) и приоритетом ниже генерации, иначе он вытеснит меши.
- Точечная пересборка при ошибке даёт отчёт-франкенштейн (часть сцен старым движком) —
  урок 297: при смене правил солвера точечный режим запрещён.
