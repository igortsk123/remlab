# Оркестрация fable-lead ↔ opus-worker (полная версия правила `.claude/rules/orchestration.md`)

## Что выбрано и почему (17.10.2026)
- **Механизм:** две интерактивные сессии Claude Code в одной копии репо + штатные кросс-сессионные сообщения (`ListAgents`,
  `SendMessage`, `notify_when_idle`). Документация: code.claude.com/docs/en/cross-session-messaging (штатная функция с v2.1.224,
  у нас 2.1.302). Проверено 16–17.10: ~40 передач заданий и отчётов за сутки без потерь; доставка — между вызовами инструментов
  занятой сессии или новым ходом у свободной.
- **Почему не субагент** `opus-implementer`: результат субагента живёт в контексте родителя (весь вывод реализации съедал бы контекст
  fable-lead), субагент не держит собственный длинный контекст между задачами и не может сам выкладывать на прод по регламенту.
  Субагент остаётся запасным вариантом, если вторая сессия недоступна: `.claude/agents/` + frontmatter `model: claude-opus-5-5`
  (валидно по docs/en/sub-agents; фактическую модель показывает `/tasks`). Пока НЕ создан — чтобы не плодить два механизма.
- **Модель worker проверена рукопожатием 17.10:** «claude-opus-5-5, Claude Code 2.1.302, правила `.claude/rules` в контексте».
- **Имена:** запуск `claude -n fable-lead` / `claude -n opus-worker`; `claude --resume <имя>`; `/rename` на ходу. Автоимя `remlab-xx`
  не переживает перезапуск → рукопожатие при сомнении.
- **Приём входящих:** `crossSessionInbound: accept` в `.claude/settings.json` (иначе сообщения ждут подтверждения владельца до 5 мин
  и теряются ночью). Хуками слать сообщения другой сессии нельзя (недокументировано) — отчёт шлёт сам worker по регламенту.

## Формат задания (fable-lead → opus-worker)
```
[fable-lead] T-20261017-03 · plans/<slug>.md (коммит <hash>)
Скоуп: … · Банк: core/<…>, domain/<…> · Интерфейсы: … · Ограничения: … (деньги, прод, необратимое)
Тесты: … · DoD: критерии приёмки из плана · После выкладки — отчёт по формату, «что смотреть».
```
## Формат отчёта (opus-worker → fable-lead)
```
[opus-worker] T-20261017-03 · done|partial|blocked
Коммиты: … · Файлы: … · Проверки: typecheck/lint/test/build/e2e — фактический результат · Артефакты: URL, скриншоты, пути
Отступления от плана и почему · Нерешённое/вопросы · Расходы (платное) · Что смотреть
```
## Цикл и лимиты
PLAN → DELEGATE → IMPLEMENT → REVIEW (diff, тесты, прод глазами, скриншоты) → DECIDE (`PASS` / `CHANGES REQUIRED` / `BLOCKED`).
До трёх циклов правок на задачу; повтор той же ошибки или конфликт требований → стоп и доклад владельцу с доказательствами.
Визуальная приёмка — только по фактическому результату (прод/`/test/`, Playwright-пробы `tools/ops/demo-walk/`, скриншоты).
Память после PASS пишет fable-lead; worker предлагает факты в отчёте. ID задач и отчёты — в логе плана (`## Лог выполнения`),
чтобы работа продолжалась после компакции или перезапуска.
