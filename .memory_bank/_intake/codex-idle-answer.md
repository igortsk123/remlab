Диагноз верный. Пачка 5 при 10 репликах экономически не может дать нужную цену: даже во время генерации потолок загрузки — 50%, а постобработка опускает её ниже.

1. Эффект

Формула по вашим данным:

`цена ≈ полезная цена / загрузка = $0.0075 / U`

- Сейчас `U=22%` → `$0.034`, близко к фактическим `$0.031`.
- Для удешевления вдвое достаточно `U≥48%`.
- `U=65%` → `$0.0115`.
- `U=75%` → `$0.010`.

Ожидание `$0.010–0.012` реалистично, но считать надо на принятый меш, включая reseed/брак, а не на любой результат GPU.

Дополнительный крупный простой: каждая пачка заново вызывает последовательный `warm_ports()` и фоновые `ask_gpu`; при `SSH_STAGGER_S=5` десять health-проб и запросов GPU могут отнимать десятки секунд оплаченного времени до полной загрузки. См. [ssh_run.py:42](/home/pakar/igor/remlab/tools/scout/salad/ssh_run.py:42), [ssh_run.py:133](/home/pakar/igor/remlab/tools/scout/salad/ssh_run.py:133), [ssh_run.py:413](/home/pakar/igor/remlab/tools/scout/salad/ssh_run.py:413).

2. Размер пачки

Для текущей архитектуры:

`batch = 4–6 × requested_running_nodes`

При 10 репликах — 40–60, разумный default 50. Это даёт каждой ноде примерно пять заданий и амортизирует хвост медленных моделей.

Для идущей нестабильной ночи:

- начать с 30;
- после двух волн, если оплаченная загрузка ≥60% и нет массовых transport failure, поднять до 50;
- последний batch делать по остатку, одновременно сокращая число реплик.

Считать размер только от числа тёплых нод неверно: супервизор подключает новые ноды каждые 45 секунд, поэтому маленькая пачка закончится раньше, чем они успеют помочь. Это уже поддержано в [ssh_run.py:428](/home/pakar/igor/remlab/tools/scout/salad/ssh_run.py:428).

Долгосрочно лучше вообще одна непрерывная GPU-очередь на 100+ заданий, а не последовательность `ssh_run`. Большая пачка переносима: задания чекпойнтятся по одному, transport failure возвращается в очередь. Но `batch_show` двигает основной курсор только после завершения всего `ssh_run`; при падении процесса возможен повтор до 50 заданий. См. [ssh_run.py:391](/home/pakar/igor/remlab/tools/scout/salad/ssh_run.py:391), [batch_show.py:273](/home/pakar/igor/remlab/tools/scout/salad/batch_show.py:273). Перед пачками 50+ журнал должен уметь восстанавливать курсор либо серверный кэш нельзя удалять до commit пачки.

3. Постобработка

Гасить и снова будить группу между короткими пачками не стоит: скачивание бесплатно, но потеря прогретого пула и spot-ёмкости увеличит календарь на 10–20+ минут.

Сегодня безопаснее:

- batch 30–50;
- постобработка один раз на batch;
- галерею ночью не строить;
- после последнего GPU-задания немедленно остановить группу, затем делать ориентацию, top-view и публикацию.

Сейчас группа остаётся включённой на всём последовательном цикле `drain → registry → repair → orientation → top-view`, а гасится лишь в финале: [batch_show.py:289](/home/pakar/igor/remlab/tools/scout/salad/batch_show.py:289), [batch_show.py:345](/home/pakar/igor/remlab/tools/scout/salad/batch_show.py:345).

Правильная следующая архитектура — генератор работает непрерывно, а отдельный одиночный consumer периодически забирает завершённые комплекты и обрабатывает их. `drain.sh --keep` уже безопасно читает только каталоги с финальным `complete.json`: [drain.sh:8](/home/pakar/igor/remlab/tools/scout/salad/drain.sh:8). Параллельно запускать несколько repair/orientation нельзя без отдельного lock.

4. Дешёвые дополнительные сокращения

- Не запрашивать модель GPU через SSH в каждой пачке; кэшировать по `machine_id` или отключить в прод-прогоне.
- Не ждать `RETRY_GRACE_S=300`, если есть другая живая нода: повторять сразу на ней; пять минут оставлять только при отсутствии альтернатив.
- Перед финальным хвостом уменьшать replicas: десять нод для последних 7–15 заданий не нужны.
- Стартовать группу только после готовности job manifest.
- Метрика ночи: `sum(job_gpu_s) / sum(instance_running_s)`, отдельно startup idle, postprocess idle, tail idle и стоимость на `accepted`, а не только внутренние `$GPU-секунды`.

Приоритет: сейчас `batch=30`, отключить повторный `ask_gpu`; после первой стабильной волны — `batch=50`. Затем вынести постобработку в параллельный consumer и гасить GPU-группу сразу после исчерпания GPU-очереди.
