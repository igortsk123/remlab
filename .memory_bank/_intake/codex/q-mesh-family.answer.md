## Вывод

Идея верная только в формулировке: **одна каноническая геометрия на семейство модели, но отдельный material/appearance на SKU**. Простое наследование `mesh_ready` и URI представителя всеми цветами сейчас даст ложную готовность: графитовый SKU будет показан белым.

## А. Где схема ломается

1. **Идентичностью должна стать семья, не представитель.**

   Сейчас карточка, решения и лимит привязаны к SKU:

   - audit item unique по SKU: [010-mesh-audit.sql](/home/pakar/igor/remlab/db/init/010-mesh-audit.sql:5);
   - лимит переделок `(sku, attempt)`: [010-mesh-audit.sql](/home/pakar/igor/remlab/db/init/010-mesh-audit.sql:42);
   - DEV-инбокс также unique по SKU: [008-mesh-owner-audit.sql](/home/pakar/igor/remlab/tools/scout/008-mesh-owner-audit.sql:43).

   При смене представителя история и лимит обнулятся. Нужны:

   - `mesh_families(family_key, geometry_generation_key, source_sku, status, policy_version)`;
   - membership `sku → family_key + evidence + confidence`;
   - решения и ручной лимит — по `family_key`;
   - `source_sku` можно менять, `family_key` и история остаются.

   `products.mesh_family_rep` на каждой строке — лишняя денормализация, способная разойтись.

2. **Представитель не должен автоматически меняться.**

   Снятие `source_sku` с продажи не делает уже построенную геометрию негодной. Новый меш другого цвета тоже не должен автоматически вытеснять текущий. Переключать `geometry_generation_key` только явным promotion после гейтов/решения владельца.

3. **“Есть решение владельца → этот SKU представитель” неверно.**

   Единственное содержательное решение страницы сейчас — отказ/переделка. Оно, наоборот, запрещает использовать данный generation. `seen_at` также не является положительной приёмкой.

4. **`mesh_ready` нельзя просто распространить по семье.**

   Сейчас он проверяет ревизию, фото и ориентацию одного SKU: [mesh_ready.py](/home/pakar/igor/remlab/tools/scout/mesh_ready.py:38). Для alias-SKU его `source_sha` заведомо отличается от фото представителя.

   Нужен отдельный предикат:

   - `family_geometry_ready` — выбранный GLB прошёл гейты и имеет ориентацию именно этого `glb_sha`;
   - `sku_appearance_ready` — существует материал/перекраска конкретного SKU;
   - итоговый `asset_ready` зависит от режима потребителя.

   Иначе текущий [render_strategy.py](/home/pakar/igor/remlab/tools/scout/render_strategy.py:95) объявит SKU готовым, хотя цвет неверен.

5. **`mesh_dims` тоже нельзя наследовать механически.**

   Он связывает товар и ревизию по одному SKU: [mesh_dims.py](/home/pakar/igor/remlab/tools/scout/mesh_dims.py:54). Общую геометрию допустимо использовать только после независимой проверки, что размеры конкретного варианта совместимы. Нельзя группировать по глубине, которая затем сама достроена из этого меша.

6. **Ключ на основе округлённых размеров нестабилен.**

   Исправление паспорта переместит товар в другую семью. Лучше:

   - стабильный vendor model key как идентичность;
   - роль, размеры, левый/правый угол, число мест, механизм и конфигурация — hard compatibility gates;
   - конфликт размеров не сливать, а отправлять в `family_conflict`.

7. **Эвристика 99272 пока непригодна для production.**

   Удаление хвостового цвета ломается на:

   - многословных цветах;
   - названиях вроде `pure white`;
   - словах цвета как части модели;
   - `левый/правый`, размерах и конфигурации в хвосте.

   Семейство надо находить сравнением нескольких sibling-SKU: названия должны отличаться исключительно распознанной цветовой/материальной фразой при одинаковых структурных признаках. Без sibling evidence — singleton. Число «503 лишних» пока оценка эвристики, не доказанный объём дублей.

8. **Для 114667/114082 лучше `Серия + структура + размеры`, а не “минус последнее слово”.**

   Серия BOSS сама слишком широка. Сохранить число мест, механизм, угловую сторону, модульность и размеры; удалять ткань только при точном совпадении значения `Ткань` с токенами имени.

9. **Нельзя фильтровать живой снимок в `ssh_run._mesh_eligible`.**

   Сейчас эта функция — только страховка роли: [ssh_run.py](/home/pakar/igor/remlab/tools/scout/salad/ssh_run.py:417). Динамическая family-карта изменит длину/позиции уже запущенного списка, а `batch_show` фиксирует `total` и позиционный курсор при старте.

   Семейная дедупликация должна происходить в [mesh_priority.py](/home/pakar/igor/remlab/tools/scout/mesh_priority.py:124) **до записи нового immutable snapshot**. Для перехода:

   - либо дать старому снимку закончиться;
   - либо остановить на границе пачки;
   - построить новый снимок;
   - начать с отдельным `queue_build_id`.

## Б. Уже готовые меши, ориентация и цвет

1. **“Самый ранний меш” — плохой выбор.** Он может быть сделан из старого 450px-фото, старым pipeline, иметь слабый cutout или отказ владельца.

   Порядок выбора:

   1. не отвергнут владельцем;
   2. machine verdict допустим;
   3. ориентация совпадает по полному `glb_sha`;
   4. актуальная версия pipeline;
   5. лучшее фото/cutout/full dims;
   6. стабильный tie-break.

   После выбора canonical generation зафиксировать; не пересчитывать ежедневно.

2. **503 меша не помечать безусловно `superseded`.**

   Они полезны как:

   - альтернативные кандидаты геометрии;
   - будущий источник правильного material конкретного цвета;
   - доказательство и rollback.

   Статус лучше `geometry_candidate/noncanonical`, отдельно от `rejected`.

3. **Ориентация принадлежит GLB, а не цвету.**

   Её можно разделить между вариантами, но только через выбранный `geometry_generation_key` и точный hash. Не создавать фиктивные orientation rows на каждый SKU.

4. **GLB сейчас содержит и форму, и цвет.**

   До появления mesh-color следует честно выбрать одно:

   - alias-варианты имеют `geometry_ready`, но не `asset_ready`;
   - либо продукт явно допускает временный цвет представителя.

   Второй вариант нельзя внедрять молча: он исказит товары в планировщике, сетах и рендере.

5. **Отказ владельца должен браковать canonical geometry всей семьи.**

   И ручной лимит должен считаться по семье. Иначе смена `source_sku` даст ещё две попытки и обойдёт правило владельца.
