#### 4. Публикация партии должна быть атомарной

Схема «удалить текущую → 12 минут заливать новую» плоха. При обрыве сети не останется ни старой, ни новой партии; открытая вкладка начнёт получать 404.

Нужна схема:

```text
/releases/<batch-id>.staging
  → rsync
  → проверка manifest/count/bytes/sha
  → rename в /releases/<batch-id>
  → атомарное переключение active manifest
  → удаление предыдущего release после grace-периода
```

Удалять разрешается только каталог с валидным собственным manifest под фиксированным prod-root. Лучше использовать отдельного SSH-пользователя, у которого вообще нет прав на DEV и остальные каталоги прода.

Критерий «после загрузки ≥6 ГБ» неверен: пред-проверка приёмника уже красная ниже 7 ГБ: [sink_health.py:55](/home/pakar/igor/remlab/tools/scout/salad/sink_health.py:55). Перед staging нужно требовать:

```text
free_now − new_batch_bytes − temporary_overhead ≥ 7 ГБ
```

Размер партии ограничивать байтами, а не только числом 200.

## Ответы по вопросам

### 1. Потеря и повторное применение решений

Существующий мост нельзя копировать буквально:

- запись решения и перевод задачи в `decided` идут двумя отдельными запросами, не одной транзакцией: [decisions/route.ts:27](/home/pakar/igor/remlab/app/api/lab/mesh-review/decisions/route.ts:27), [decisions/route.ts:32](/home/pakar/igor/remlab/app/api/lab/mesh-review/decisions/route.ts:32);
- `apply_decision()` молча возвращает успех, если локальной ревизии нет: [mesh_review_sync.py:145](/home/pakar/igor/remlab/tools/scout/mesh_review_sync.py:145);
- после этого курсор всё равно продвигается: [mesh_review_sync.py:183](/home/pakar/igor/remlab/tools/scout/mesh_review_sync.py:183);
- сам файл курсора перезаписывается неатомарно: [mesh_review_sync.py:185](/home/pakar/igor/remlab/tools/scout/mesh_review_sync.py:185).

Для нового моста нужны:

- транзакция «проверить актуальную ревизию → проверить лимит → вставить решение → сменить состояние»;
- детерминированный idempotency key;
- DEV-ledger `applied_decision_id` с unique constraint;
- курсор двигать только после успешной локальной транзакции;
- неизвестная или устаревшая ревизия — ошибка и повтор, не no-op;
- обратный ACK на прод: `requested → applied → queued → running → generated/failed`.

Повторный push не должен открывать уже решённую ревизию. Клик из старой вкладки после появления нового меша должен получать `409 stale revision`, а не браковать актуальный меш.

### 2. Где ставить переделку

Лучший вариант — DEV-БД, не редактируемый файл:

```text
mesh_regeneration_requests
- request_id / prod_decision_id unique
- sku
- source_sha
- rejected_revision_key
- generation_variant
- enqueue_seq
- status
- error
- timestamps
```

Затем диспетчер создаёт полноценный `mesh_jobs` с seed в ключе. JSON остаётся только атомарным снимком исполнения, а не источником истины.

Это также устраняет невозможность атомарно выполнить нынешние два действия: изменить `asset_revisions` в БД и отдельно переписать файл.

### 3. Партийная публикация

Кроме атомарного release нужны:

- фиксированный `audit_seq`: новые меши добавляются в конец, иначе номера страниц и состав партий поплывут;
- неизменяемый URL с `batch_id/revision_key/glb_sha`;
- сериализация запросов «следующая партия» через CAS/lock;
- состояние `requested/uploading/verifying/active/failed`;
- повторяемый rsync;
- проверка checksum и числа файлов;
- graceful 404/410 в открытой вкладке;
- отдельная квота диска для audit-assets, не конкурирующая молча с sink;
- запрет передачи пути из API прямо в shell-команду.

Страница защищена кукой, но GLB под `/test/...` останутся публичными. Если это нежелательно, нужны подписанные непрогнозируемые URL или авторизованная выдача через reverse proxy.

### 5. Лимит двух переделок

Решение адресуется конкретной ревизии, а лимит считается по устойчивому scope. Я рекомендую:

```text
scope = sku + source_sha + shape_pipeline_version
один reject на одну revision_key
не более двух owner-redo в scope
```

Смена seed не сбрасывает счётчик; смена фото или существенно новой версии генератора начинает новый scope. История SKU сохраняется целиком.

Считать и запрещать третье на проде нужно транзакционно, иначе две вкладки одновременно создадут 2/2 и 3/2. DEV повторно валидирует лимит, но не является первым UX-гейтом.

Надо отдельно уточнить у владельца, входят ли автоматические reseed в эти два раза. Сейчас автоматика допускает только один reseed: [apply_repairs.py:218](/home/pakar/igor/remlab/tools/scout/salad/apply_repairs.py:218). Молчаливо считать его одной из двух ручных переделок нельзя.

### 6. Что лишнее и чего не хватает

Лишнее:

- одновременно крон `--serve`, вызов из `post_steps()` и отдельный долгоживущий сервис. Оставьте один минутный `--tick` под общим `flock`; он работает и при остановленном Salad.
- поднимать `MESH_MAX_JOBS` как решение архитектуры — это лишь отсрочка.
- считать жёстким критерием ровно 1490 карточек: набор будет расти.

Критически не хватает тестов:

- две ревизии одного SKU с разными seed не схлопываются;
- reject не отменяется повторным ingest;
- отклоняется клик из устаревшей вкладки;
- двойной клик/две вкладки дают одно решение;
- падение между `owner_reject` и постановкой задания восстанавливается;
- повторный pull не применяет решение второй раз;
- отсутствующая DEV-ревизия не двигает курсор;
- перестройка очереди сохраняет необработанные задания и rework;
- прерванный rsync не переключает active batch;
- два запроса смены партии не запускают два удаления;
- проверяются manifest, checksum и запас диска;
- delete не может выйти из выделенного prod-root;
- GLB действительно не скачивается до клика;
- ошибка загрузки модели видна владельцу;
- все 1490 физических GLB либо зарегистрированы, либо явно помечены как неаудируемые.
