КОНТЕКСТ
`batch_show.py` — конвейер генерации 3D-мешей на арендованных GPU SaladCloud. Пока конвейер стоит,
ноды всё равно тарифицируются, поэтому цена ошибки — деньги. Конвейер живёт под nohup/setsid,
singleton через flock, горячий перезапуск через флаг `mesh-draining`, при старте ждёт сирот
прошлого экземпляра (`wait_orphans`).

ФАКТЫ (наблюдения, не гипотезы)
1. Шаги пост-разбора запускаются через `sh(cmd, timeout=...)`. Шаг «вид сверху» — это
   `/bin/sh -c 'fails=0; while [ ... ]; do out=$(python topview_render.py); ... done'`.
   05.09 он падал по таймауту 2700 с. Прежняя реализация `sh()` — `subprocess.run(shell=True,
   capture_output=True, timeout=...)`. По таймауту умирала только обёртка `/bin/sh`; python
   оставался жить с `ppid=1`. Пост-разбор идёт каждые `MESH_POST_EVERY_S=900`, поэтому сироты
   копились: к 10:00 их было 20 штук, старейшая работала 21 ч 44 мин. Последствия — съеденная
   память дев-VM (11 ГБ, trimesh не отдаёт память) и блокировка перезапуска: новый конвейер
   честно ждёт сирот до 1500 с, а ноды в это время оплачиваются. 19 процессов сняты руками.
2. `ensure_group_started()` слал POST `/start` всем группам, разрешённым окном тарифа.
   У уже поднятых групп Salad отвечает `HTTP 400 {"type":"replicas_quota_exceeded"}` — в логе это
   повторяется каждые пару минут. Тем же кодом 400 приходит `no_credits_available` («кончились
   деньги»), пропустить который нельзя: без пополнения не поднимется ничего.
3. Действующие инварианты, которые ломать нельзя (ADR-0174/0175):
   стоп-файл сторожа сильнее любого автостарта; группу вне её окна не поднимает никто;
   `group_status()` возвращает `stopped` только если ВСЕ группы остановлены;
   `finale()` обязан отработать при любом исходе шага, иначе группа останется тарифицироваться.

ВОПРОСЫ
A. `sh()` переведён на `Popen(..., start_new_session=True)` + при `TimeoutExpired` — снятие всей
   группы процессов (`os.getpgid`, страховка «не своя группа», SIGTERM → wait → SIGKILL), затем
   повторный `communicate(timeout=15)`, чтобы добрать вывод.
   (а) есть ли сценарий, при котором killpg заденет сам конвейер, соседние шаги или посторонние
       процессы владельца;
   (б) корректен ли порядок kill → communicate: не теряется ли вывод, не зависнет ли вызов, если
       внук успел сделать собственный `setsid`, и не нужен ли drain пайпов отдельным потоком;
   (в) не ломает ли `start_new_session=True` шаги `rsync`/`ssh -o BatchMode=yes`/python; конвейер
       и так живёт без управляющего терминала;
   (г) для шага, который мы уже считаем провалившимся, оправдан ли SIGTERM с ожиданием 10 с, или
       правильнее сразу SIGKILL;
   (д) какие ещё места в `batch_show.py`/`ssh_run.py` порождают потомков с таймаутом и имеют тот
       же дефект (найди их по коду, а не по моему описанию).
B. `ensure_group_started()` теперь сперва спрашивает состояние каждой группы (`group_states()`,
   через curl — WAF Salad режет python-UA) и шлёт `/start` только тем, у кого состояние в
   ('stopped','failed',None); уже поднятые печатает и считает успехом.
   Не создаёт ли это дыру: раньше безусловный `/start` работал «слепым лечением» на случай, когда
   API врёт о состоянии (группа числится `running`, а реплик ноль или все зомби). Что лучше —
   строгая проверка состояния, или строгая проверка плюс редкий безусловный `/start` как фолбэк
   по признаку «пул давно без мешей»? Обоснуй по коду: где именно в конвейере есть сигнал
   «давно без мешей» и что он стоит.
