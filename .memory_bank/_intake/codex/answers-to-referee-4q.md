# Ответы на 4 уточняющих вопроса рефери (свод №9, поправки; remlab 14.08)

Поправки приняты в исполнение MASTER-zones-v3 (владелец дал «деплой»). По вопросам:

## 1. Что значит `+fp`
Тег зоны «камин» (fireplace) как ОТДЕЛЬНОГО фокуса: `+fp` — камин поставлен своей зоной;
`+tvfp` — объединённая схема «носитель ТВ + камин» одной постановкой (паспортная схема
пары); `+tv` — носитель ТВ (тумба или стенка); `+tvw` — носитель, поставленный по вейверу
экрана (единственная стена — оконная); `+tv2` — носитель «последней попытки» с ослабленной
центровкой. Кардинальность exactly_one_carrier касается только носителей (тв-тумба/стенка),
камин под неё сознательно не подпадает — это другая функциональная зона (твоя же оговорка).

## 2. Каким СУЩЕСТВУЮЩИМ правилом валидируется compact_island
Клиренс отодвигания стула — canonical `dining_chair_pullout` = 55 см
(`rules/occupancy.json`): pullout-зоны стола и каждого стула (а) вычитаются из свободного
полигона при постановке (blocked footprint) и (б) проверяются постфактум hard-кодом
ACCESS_BLOCKED. Т.е. «отдельно стоящий, но слишком тесный стол» уже невозможен по hard:
у freestanding-постановки все рабочие стороны имеют ≥55. Разница классов после
переклассификации по топологии: full_island = паспортные 90 со всех рабочих сторон,
compact_island = freestanding с гарантированными 55–89, edge = сторона у стены (без стула
с этой стороны). Нового числа не вводим — граница классов = два существующих числа (55 hard,
90 паспорт).

## 3. Mirror: действительно ли сейчас first-clean
ДА — подтверждаю твой диагноз, это незакрытый дефект нашего пакета E: варианты
перебираются «оригинал → отражение», и первый hard-чистый побеждает; если оригинал валиден,
отражение НЕ сравнивается. Исправляем в V3 (по твоей правке): для Г-дивана оба зеркала
генерируются и при обоюдной hard-валидности сравниваются одним лексикографическим ключом
(тот же ранжир, что внутри отборщика позиций; нового скора нет) + счётчики
generated/hard_valid по сторонам в debug + две сцены-пруфа (left-only-valid /
right-only-valid) append-only.

## 4. Охватывает ли trace альтернативные позиции того же core
НЕТ. Текущий trace (V3-B) фиксирует поиск dining при ОДНОМ выбранном core: счётчики
классов island/edge, причины отказов, ось гейта. Альтернативные ПОЗИЦИИ той же
посадочной ступени не перебираются и в trace не попадают — dining видит только один core
(плюс спуск ступеней через dining_sacrifice). Поэтому принят твой порядок: V3-B/C
(наблюдаемость) → shadow-test альтернативных core-позиций (без изменения выбора, только
замер «дал бы другой core полный остров?») → решение о multi-core search по данным
shadow-теста, beam width — из замера.
