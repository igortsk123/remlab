**1. Как работает живой `/demo`**

Язык выбирается при загрузке: `?lang=ru|en` имеет приоритет над `localStorage['remlab-lang']`, затем учитывается язык браузера; для неизвестного языка запасной — RU. Переключатель внизу страницы записывает выбор, добавляет `?lang=` и перезагружает тот же адрес, сохраняя экран и прокрутку (`tools/scout/flat215-demo/index.html:4190`, `tools/scout/flat215-demo/index.html:9962`). Это **не общий i18n-фреймворк**: часть строк выбирается непосредственно через `LANG`, остальные переводит финальный слой `I18N` — словари, шаблоны и `MutationObserver` для текста и атрибутов (`tools/scout/flat215-demo/index.html:9988`, `tools/scout/flat215-demo/index.html:10104`).

Названия комнат берутся из `apartment_rooms[].titleRu/titleEn` согласно языку; словарь `ROOM` покрывает лишь несколько готовых названий, не произвольные подписи распознавания (`tools/scout/flat215-demo/index.html:5092`, `tools/scout/flat215-demo/index.html:9997`). Роли мебели переводит `ROLE`, причём номер роли отсекается (`tools/scout/flat215-demo/index.html:9988`, `tools/scout/flat215-demo/index.html:10063`). Имена товаров — особый случай: сборка добавляет `name_en/colour_en`, но английское имя показывается только при `FLAT.demoMask.englishNames`; без маски остаётся исходное магазинное имя (`tools/scout/flat215_demo.py:2600`, `tools/scout/flat215-demo/index.html:5866`, `tools/scout/flat215-demo/index.html:5880`). Файл `demo-data.json` в рабочем дереве отсутствует, поэтому поля сверены по сборщику, а не по готовому JSON.

**2. Что распределить по веткам — по важности**

1. **`trial-bundle` — языково-нейтральный контракт данных.** Хранить стабильные `kind`/id/коды исходов и отдельно обе подписи комнаты. Сейчас `titleRu` теряет номер и исходное имя, а `titleEn` без проверки копирует распознанное `name`: RU-план покажет кириллицу в EN (`.claude/worktrees/trial-bundle/tools/scout/trial_bundle.py:315`). Переводить распознанные UK- и RU-подписи **в сборщике**, с сохранением исходника для диагностики; странице оставить выбор `titleRu/titleEn`. Не пытаться лечить произвольные `Bedroom 3`, `Кухня-гостиная` и т. п. конечным DOM-словарём. То же относится к `rooms_geo[].title`, сейчас составляемому из сырого имени (`.claude/worktrees/trial-bundle/tools/scout/trial_bundle.py:141`, `.claude/worktrees/trial-bundle/tools/scout/trial_bundle.py:292`). Передавать код отказа, а не только русский `furniture_text`; добавить `approx` и двуязычный `D.quiz` из действующего правила. Пока сборщик не выдаёт `quiz` или `name_en`, хотя живое демо кладёт правило в данные (`.claude/worktrees/trial-bundle/tools/scout/trial_bundle.py:327`, `tools/scout/flat215_demo.py:1997`).
2. **`demo-template` — все новые надписи и ссылки.** Уже есть RU/EN для «подбираем мебель», отказа и «приближённой формы», но плашка последней зависит от отсутствующего пока `rooms_geo[].approx` (`.claude/worktrees/demo-template/tools/scout/flat215-demo/index.html:1480`). Добавить отдельные тексты и состояния для «не обставляется», неподтверждённого масштаба и двух явно подписанных ссылок `?quiz=0/1`, сохраняя `lang` при копировании. Опрос уже выбирает `*_ru/*_en` из `D.quiz.questions` и открывается покупателю только при наличии правила (`.claude/worktrees/demo-template/tools/scout/flat215-demo/index.html:8985`). Проверить все поверхности — план, карточку, просмотр, атрибуты и ошибки загрузки: последние пока жёстко русские (`.claude/worktrees/demo-template/tools/scout/flat215-demo/index.html:1520`). Для товаров решить маску пробы отдельно от `FLAT`, иначе `name_en` сам по себе не поможет.
3. **`trial-pages` — форма и ожидание.** Сейчас это EN-only: оболочка жёстко `lang="en-GB"`, форма, статусы и функции текстов ошибок английские (`.claude/worktrees/trial-pages/components/trial/TryShell.tsx:13`, `.claude/worktrees/trial-pages/components/trial/UploadForm.tsx:86`, `.claude/worktrees/trial-pages/lib/trial/steps.ts:12`). Передавать выбранный язык во все компоненты и функции текстов, сохранять его после загрузки в `/try/<id>` и туре. Старый `TrialResult` всё ещё запускает серый тур — заменить согласно плану (`.claude/worktrees/trial-pages/components/trial/TrialResult.tsx:13`).
4. **`trial-living` и `trial-bedrooms-all`** должны выдавать коды, роли и товарные поля по общему контракту, а не готовые одноязычные UI-строки; сборщик применяет перевод одинаково к гостиной и всем спальням. Для неподбираемых комнат исход должен быть отдельным от отказа «нет подходящих товаров» (`.memory_bank/plans/agent-trial-08-demo-as-template.md:67`).

**3. Next.js и порядок**

Глобального механизма локализации Next.js здесь не видно; `/test/landing` как маршрута в проверенных деревьях не найден. Есть локальный образец: `/flat` читает `?lang=` и переключает URL без потери прочих параметров (`app/flat/page.tsx:36`), юридические страницы тоже используют `?lang=` (`components/legal/LegalPage.tsx:5`). Наименьший согласованный путь — общий для `/try` тип `ru|en`, небольшой словарь строк и URL-переключатель; `?lang=` передавать через форму, ожидание, обе ссылки и тур, при первом входе учитывать сохранённый выбор/браузер как в `/demo`.

**Риск порядка:** данные → страница → гостиная → спальни нельзя считать готовыми по отдельности: контракт двуязычных имён, кодов состояний, `approx`, quiz и товаров нужно зафиксировать **до** сведения веток; затем проверить RU/EN на планах обоих языков и на всех стадиях. Уже в ветках есть частичная двуязычность страницы, но она не закрывает перечисленные пробелы. В `main` эти ветки ещё не влиты; найденного слитого изменения, противоречащего требованию, нет. Сам план требует снимки на обоих языках (`.memory_bank/plans/agent-trial-08-demo-as-template.md:75`).
