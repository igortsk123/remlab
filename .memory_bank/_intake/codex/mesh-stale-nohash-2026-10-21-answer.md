Вывод в целом верный: инвариант `ready` ослаблять нельзя. Останавливать повтор нужно в очереди, но не простой заменой строки `mesh_priority.py:596`.

1. Где чинить и что затронет

- Правильное автоматическое правило:

  - явный `mesh_rework_requests` — всегда ставить с новым seed;
  - текущий хеш известен и отличается от `mesh_generations.source_sha` — ставить seed 0: новый input hash создаст другой `job_id` (`tools/scout/salad/manifest.py:51-55`);
  - хеш неизвестен, но поколение seed 0 уже есть — не ставить повторно;
  - поколения ещё нет — ставить.

- Нельзя просто отфильтровать `todo` в `tools/scout/mesh_priority.py:596`:

  - `todo` используется и как очередь, и как число «осталось» — отчёт объявит подавленные stale готовыми (`tools/scout/mesh_priority.py:619-624`);
  - из очереди выпадет ручная переделка, потому что `pending_rework()` применяется позднее, внутри `build_queue()` (`tools/scout/mesh_priority.py:423-439`);
  - сейчас туда также попадают `quarantine` и `rejected`, потому что условие — любое `status != ready` (`tools/scout/mesh_priority.py:596`). Для них автоматический seed 0 столь же сомнителен.

  Нужны отдельные множества: `unready` для отчёта и `queueable` для снимка.

- Инвариант оставлять строгим: отсутствие хеша не даёт права на `ready` (`tools/scout/mesh_bind.py:186-204`). Но есть рассинхрон: `mesh_ready()` проверяет другой источник — `mesh_demand.source_sha` (`tools/scout/mesh_ready.py:38-64`). Если там свежий хеш уже известен, правильнее сначала перенести его в `product_photo_current`, а не вводить исключение в инвариант.

- `ready_unverified` сам проблему не решит:

  - он всё равно попадёт в очередь как `!= ready`;
  - не будет опубликован (`tools/scout/mesh_publish.py:58-60`);
  - не попадёт в пул замен демо (`tools/scout/demo_swap_pool.py:68-74`);
  - исчезнет из текущей метрики stale и не войдёт в ready (`tools/scout/pipeline_map.py:66-68`).

  Если нужен отдельный статус для наблюдаемости, логичнее `unverified`, но очередь всё равно придётся исправлять. Проще оставить `stale` и добавить производную причину `photo_hash_missing`.

- `/lab/mesh-audit` не читает `products.mesh_status`: он выводит все последние поколения. При отсутствии хеша ставит внутреннее `unknown`, но в UI предупреждение показывает только для настоящего несовпадения (`tools/scout/mesh_audit_sync.py:223-255`, `components/lab/MeshAuditCard.tsx:103`). После исправления очереди страница не сломается, но стоит показывать отдельный badge «хеш неизвестен».

- Витрина неоднородна:

  - новые stale не публикуются;
  - уже опубликованный stale может остаться видимым: индекс пересобирается по всем файлам на сервере, удаления stale нет (`tools/scout/mesh_publish.py:78-97`);
  - демо исключает из индекса карантин, но не stale (`tools/scout/flat215_demo.py:214-239`).

  Это отдельная дыра: строгий статус в БД не гарантирует снятие старого GLB с витрины.

- Денежный/idle-сторожа `mesh_status` напрямую не читают; они увидят только меньший снимок очереди. `receiver_purge` уже специально опирается на `mesh_generations`, а не на ready/stale (`tools/scout/salad/receiver_purge.py:25-32`). Основной сторож stale — `pipeline_map`, пороги 20/25 % (`tools/scout/rules/pipeline-map.json:88-95`).

2. Откуда берётся отсутствие `product_photo_current`

Писателей только два:

- Основной — `cutout_sync.sync_photos()`, upsert хеша байтов (`tools/scout/cutout_sync.py:215-258`). Ночью запускается с пределом 1000 (`tools/scout/refresh_daily.sh:326-331`).
- `hd_backfill` пишет строку только если HD и SD отличаются (`tools/scout/hd_backfill.py:129-140`). Если строки не было, но байты одинаковые, он обновит лишь `image_url_hd` и оставит `product_photo_current` пустым — явная щель.
- `mesh_queue.ingest()` параллельно считает тот же SHA, но пишет только в `mesh_demand` (`tools/scout/mesh_queue.py:303-329`). Обратного upsert в `product_photo_current` нет; синхронизация сделана только из `product_photo_current` в demand (`tools/scout/mesh_queue.py:402-408`).

Поэтому 295 — не обязательно просто недоделанный бэкфилл. Возможны:

- Товар проходит `mesh_required`, но не входит в пул cutout. Ворота различаются:

  - `mesh_required`: наличие, фото, размеры, факт обогащения и styles (`tools/scout/mesh_bind.py:95-110`);
  - cutout дополнительно требует `status='active'`, цену, active enrichment, payload и quality ≥ 0.65 (`tools/scout/cutout_sync.py:202-207`).

- Хеш есть в `mesh_demand`, но не продублирован в `product_photo_current`.
- Фотография не скачивается. Ошибка только печатается, строка не создаётся (`tools/scout/cutout_sync.py:240-245`).
- Фиксированный `order by sku limit 1000` позволяет постоянно падающим ранним SKU задерживать хвост (`tools/scout/cutout_sync.py:232-236`).
- Щель одинаковых SD/HD в `hd_backfill`.
- В числе 295 могут быть варианты семейства. Инвариант проверяет только представителя (`tools/scout/mesh_bind.py:201-202`), а статус затем копируется вариантам (`tools/scout/mesh_bind.py:237-248`). Очередь варианты вообще пропускает (`tools/scout/mesh_priority.py:74-78`). Считать причину надо только по представителям.

«Без вырезки» само по себе не объяснение: ночной режим отключает assessment, но хеширование выполняется отдельно.

Как отличить смену:

- `mesh_demand.source_sha` против `mesh_generations.source_sha` — уже надёжное сравнение байтов, если `sha_at` свежий.
- Текущий URL против `asset_revisions.manifest.input.image_url` — доказывает смену адреса, но не обязательно байтов.
- `product_enrichment.image_hash` — только хеш URL, не содержимого (`tools/scout/load3.py:111-112`).
- Подмену байтов по тому же URL без повторного скачивания определить невозможно.

3. Как закрыть риск старого меша

- Немедленно: подавить автоматический повтор seed 0 для stale без текущего хеша, сохранив ручные rework и честный счётчик unready.
- До следующей волны: приоритетно хешировать `mesh_required + stale + представитель + нет product_photo_current`, без общего SKU-порядка.
- После хеширования:

  - совпал с поколением → инвариант сам вернёт ready;
  - отличается → товар остаётся stale и законно идёт в генерацию.

- Сделать write-through из `mesh_queue.ingest()` в `product_photo_current` либо вообще оставить одного владельца хеша. Нынешние две таблицы уже расходятся.
- Добавить счётчики/тревогу:

  - `stale_missing_photo_hash`;
  - `suppressed_seed0_regens`;
  - возраст старейшего missing hash;
  - сколько из них имеют свежий `mesh_demand.source_sha`;
  - ошибки скачивания по магазину.

- Не разрешать старт оплаченной волны при ненулевом старом хвосте, например `missing hash > 24 ч`; генерация этот дефект не исправляет.
- Отдельно снять stale из опубликованного mesh-index либо явно решить, что витрина имеет право временно показывать старый GLB.

Итого: аварийная правка — в селекции очереди; системная — устранить две независимые истины хеша. `ready_unverified` добавит новый статус, но не устранит ни цикл, ни риск. Разбивку именно этих 295 по причинам я не подтвердил на живой БД: в текущем окружении закрыт Docker socket.
