# Ответы исполняющего агента на Q1–Q12 свода №9 (remlab, 14.08)

Аудит принят. P0 подтверждаю и беру на себя. План следующей итерации составлен по твоим
пакетам (V3-A…V3-I), логика выбора до trace-пакетов не меняется — как ты и просил.
Ниже — честные ответы из фактической реализации.

## Q8 / P0 — №269 (два носителя): ПОДТВЕРЖДЁН, наш баг, известна точная причина
Это дефект вейвер-пути моего пакета D (свод №8): в сцене set80-Lm носитель встал на
ПРОБЕ ЛЕСТНИЦЫ по вейверу экрана (тег `+tvw`), его роль ушла из банка, но шаг `+tv`
основной цепочки зон не проверяет «носитель уже стоит в блоке» и поставил ВТОРОЙ носитель
другого типа из банка (тег в сцене — `+tvw+tv`, он тебя и навёл). Декларативной
cardinality зон сейчас НЕТ — эксклюзивность жила только в порядке кандидатов и мьютексе
компоузера (D4). Фикс первым пакетом: пропуск `+tv/+fp` при носителе в блоке + данные
`cardinality: exactly_one_carrier` + сторож «0 планов с двумя носителями» + append-сцена.

## Q3 — порядок поиска (frozen core)
Вариант A: dining получает ОДИН уже выбранный core. Лестница посадки выбирает ступень
(с пробой минимума медиа), core фиксируется, dining пробуется на остатке. НО:
`dining_sacrifice` при столе в банке ПЕРЕСОБИРАЕТ ВСЮ сцену с посадкой на 1–2 ступени
ниже — т.е. ограниченный multi-core уже есть по оси «размер посадочной группы», но не по
альтернативным ПОЗИЦИЯМ той же ступени. Твоя гипотеза локальной ловушки жива для случая
«та же ступень, другая позиция core». Твой PACKAGE D принят: сперва trace (V3-B/C),
потом при подтверждении — несколько non-dominated core-кандидатов; beam width — по
замеру, в rules заранее не пишем.

## Q2 — №216 (island_feasible=false при fallback=quality_gate)
Семантическая каша, которую ты верно поймал. Механика: остров ПОСТАВИЛСЯ и был отвергнут
гейтом качества цепочки (fallback честный); затем retry классом edge ПЕРЕЗАПУСКАЕТ
place_dining, и диагноз (включая пробу island_feasible) пересчитывается уже на СУЖЕННОМ
free (после других зон) — там остров уже невозможен → false. То есть false относится к
моменту retry, а reason — к первой попытке. В V3-B `island_feasible` заменяется
счётчиками generated/hard_valid/quality_valid по каждому классу — боолеан уходит.

## Q4 — семантика compact_island
Сейчас класс отражает ПУТЬ кандидата, не топологию: «стол из срединных кандидатов, но
паспортный 90-envelope на финальной позиции не выполнен» (full_island = envelope
выполнен). Поэтому compact может прижаться к стене — твои 12 сцен честные. Принято «B»:
в V3-E режим классифицируется по фактической топологии (wall_attachment стороны →
edge; свободные рабочие стороны → island full/compact по envelope) — без нового числа.

## Q5 — route_active_dining_cm
Семантика: та же ступенчатая эрозия свободного пола (60…120), но pullout-зоны стола и
стульев (существующие клиренсы 55 см) временно считаются ПРЕПЯТСТВИЯМИ — модель «все
сидят / стулья выдвинуты». Это сознательно НЕ гейт и порог 75 к нему не применяется:
75 — норма ПОСТОЯННОГО маршрута; протиснуться 60 см мимо выдвинутого стула — штатная
ситуация обеда. Значения 22,25,41,72,81,89,141 (60–70) — ровно это. Зафиксируем
semantics в данных; порога не вводим, пока корпус не покажет реальные конфликты.

## Q6 — residual_fragmentation
Вычитаются ТОЛЬКО физические футпринты мебели (ковёр — пол). Нормальная комната даёт
связный пол → 1 компонент везде; корреляция с площадью, как ты померил. Согласен:
для gating бесполезна. В V3-F заменяем на inter_zone_gap / largest_unassigned_region
(вычитая envelope ЗОН + циркуляцию) / dead_void_depth — только экспорт, №261/№268 —
корпусные примеры, пороги позже разметкой.

## Q7 — зеркала
Счётчиков generated/hard-valid по сторонам нет (добавим в V3-H). Все 6 победителей
corner_left=false потому, что перебор «оригинал → отражение» первым чистым: SKU в сете
приходят corner_left=false, и оригинал везде вставал. Механизм доказан юнит-сценой
(280×430, дверь восток: встаёт только отражение), но regression-пруфа в наборе нет —
принимаю твои сцены A/B: №272/273 append-only (left-only-valid / right-only-valid).

## Q9 — visual_balance
Считается: центроид масс = сумма центроидов футпринтов, взвешенных ПЛОЩАДЬЮ (роль не
взвешивается); ковёр ИСКЛЮЧЁН; reference — центр W/2,D/2 (bbox), НЕ centroid полигона —
для L-комнат это и даёт завышенные 30% на №268: центр bbox лежит в вырезе. Признано:
для контурных комнат reference надо брать centroid реального полигона (V3-I). До этого —
diagnostics only, как ты и требуешь.

## Q10 — template identity
Данные есть в солвере (variant знает build_block, mirror — Placement.item), но на export
layer уходит только имя зоны+версия (`tpl_id`) — теряются variant/mirror/candidate.
V3-H добавляет zone-instance блок: template_id/variant_id/mirror/candidate/why_selected.

## Q11 — missing_templates.md
Он генерится (`tools/scout/template_gaps.py`), но лежит рядом с конвейером и в zip не
включён — включим. Классов «региона нет» vs «шаблона нет» сейчас НЕТ — все 52 события
записаны как island_candidates_failed. Принята таксономия: NO_FEASIBLE_REGION /
QUALITY_REJECTED / PRODUCT_RULE_SKIPPED / TEMPLATE_GAP (истинный); в отчёт — только
истинные, с frequency.

## Q12 — storage/окно по высоте
Высота у SKU есть (`h_cm`), и hard уже существует: WINDOW_BLOCKED бьёт предмет с
h > max(подоконник, 80) ближе 10 см к проёму. Сцены 263/264/265 — комоды НИЖЕ
подоконника 90 → легальны по действующему правилу. В V3-I экспортируем результат
проверки (флаг + высоты), чтобы это было видно из zip без чтения кода.
