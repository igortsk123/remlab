## В3. Бюджет комнаты 30 секунд

### Вывод

Убрать wall-clock из семантики поиска. Основной лимит должен быть детерминированным: фиксированное число cache-miss вызовов решателя на стиль, а лучше — число расширенных состояний/кандидатов внутри решателя. Wall-clock оставить только внешним эксплуатационным таймаутом стадии.

### Доказательства

Сейчас результат напрямую зависит от `time.time()`:

- `fit_extras` имеет собственный временной срез: [trial_bedroom.py:509](/home/pakar/igor/remlab/.claude/worktrees/bed-memo-1112/tools/scout/trial_bedroom.py:509).
- `furnish_style` прерывает перебор по deadline и возвращает `budget`: [trial_bedroom.py:810](/home/pakar/igor/remlab/.claude/worktrees/bed-memo-1112/tools/scout/trial_bedroom.py:810).
- `furnish_room` делит остаток wall-clock между оставшимися стилями: [trial_bedroom.py:944](/home/pakar/igor/remlab/.claude/worktrees/bed-memo-1112/tools/scout/trial_bedroom.py:944).

Поэтому один медленный стиль уменьшает лимит следующих, а scheduler машины меняет набор опубликованных стилей. Ваш замер aRQV, где при одинаковых четырёх успехах меняются сами стили, является прямым проявлением этой схемы.

### Рекомендация

- Удалить проверки `time.time()` из `furnish_style` и `fit_extras`.
- Ввести фиксированный независимый budget каждого стиля:
  - N cache-miss вызовов `solve_bedroom`;
  - отдельно ограниченные `EXTRA_TRIES`;
  - при необходимости внутренний счётчик расширенных состояний решателя.
- Cache hit либо стоит 0 единиц, либо имеет явно закреплённую стоимость.
- Не перераспределять «неиспользованный бюджет» между стилями: это снова создаёт зависимость от порядка.
- Исчерпание счётчика называть `search_exhausted`, а не `no_space` и не общим `budget`.
- Подобрать N по корпусу туров так, чтобы три контрольных тура полностью проходили все стили.
- `time.monotonic()` использовать только для метрик и SLO.

Сам поиск уже существенно ограничен константами `MAX_CORES`, `BEDS_PER_TEMPLATE`, `EXTRA_TRIES`, beam решателя и memoization. Поэтому сначала стоит измерить фактический максимум cache-miss solve-вызовов; возможно, временной рубеж можно удалить без большого нового cap.

### Альтернативы

| Подход | Оценка |
|---|---|
| Увеличить 30 секунд | Только временная страховка. Нагрузка передвинет тот же порог, а худшее время комнаты вырастет. |
| `process_time()` | Лучше wall-clock для профилирования, но всё ещё зависит от CPU/архитектуры, C-кода и cache behavior; при перегрузе 5 CPU-секунд могут превратиться в долгое ожидание пользователя. |
| Число вызовов решателя | Лучший ближайший вариант. Считать нужно cache misses, иначе memoization меняет эффективный объём поиска. |
| Число состояний/кандидатов | Наиболее строгий вариант, но требует инструментировать решатель. |
| Дешёвые проверки раньше | Полезное дополнение, не замена детерминированному budget. Их следует переставлять внутри стиля, не менять порядок стилей. |
| Параллелить стили | Рискованно: `used` и `room_used` общие, поэтому порядок завершения изменит товары и результат. |

### Необходимые тесты

- Один план при искусственно медленном и быстром решателе даёт одинаковые варианты и причины отказов.
- Одинаковое число cache-miss solve-вызовов при разной скорости часов.
- Каждый стиль имеет независимый фиксированный cap.
- Исчерпание cap даёт `search_exhausted`.
- Два запуска под нагрузкой и без неё дают одинаковый сериализованный результат, кроме полей timing.
- Goldens по трём турам.
- Внешний timeout не публикует частично готовую спальню как успешную.
- Метрики p50/p95/p99: время комнаты, solve calls, cache hits и expanded states.

Допущение: одинаковые план, каталог и правила должны давать одинаковый набор стилей. Если продукт сознательно принимает best-effort «что успели за 30 секунд», текущая схема допустима, но это прямо противоречит сформулированной цели владельца.
