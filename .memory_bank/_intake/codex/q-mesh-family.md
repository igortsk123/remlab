# Критика схемы: один меш на МОДЕЛЬ (цветовые варианты — одна форма)

Контекст: план mesh-owner-audit завершён (страница /lab/mesh-audit в проде, реестр поколений
`mesh_generations`, инбокс переделок). Владелец 05.09 увидел на странице «ТВ-тумба Модерн 140x65
Белый» и «… Графитовый» и потребовал убрать дубли; выбрал: ОДИН меш на модель, цвета — варианты
одной формы, перекраска по фото варианта — потом (линия mesh-color, ADR-0145).

## Факты
- В `products.params` (jsonb из фида) у divan.ru (mid 112923, 4479 товаров с mesh_required):
  «Вариант модели» = «Модерн 140x65» у всех 5 цветов; у кресла «Тилар» = «Тилар» для всех тканей
  и цветов (Рогожка/Мех × 9 цветов). Покрытие: «Вариант модели» 4190/4479, «Серия» 4462 (слишком
  грубо: сливает размеры), «Модификация» = ткань+цвет.
- 114667/114082 (747+617): есть «Серия» (BOSS) и «Ткань» («Рогожка Мальмо»), имя вида
  «Диван Босс двухместный Рогожка Мальмо серый»; «Вариант модели» нет.
- 99272 (5602 — самый большой): params без серии/варианта, цвет внутри имени
  («Стол обеденный TC pure white 107+46x76 см»).
- Среди сгенерированных: по эвристике «имя минус последнее слово» 271 семейство × варианты =
  774 карточки (503 лишних меша); в оставшейся очереди 10 523 заданий, из них 4 363 — варианты.
- Потребители готовности: `mesh_ready.py` (по SKU + glb_sha ориентации), `render_strategy.asset_ready`,
  `mesh_bind.py` (products.mesh_uri/mesh_generation_key), `mesh_dims.py`, `reserve.py`,
  `mesh_priority.py` (очередь по products.mesh_required и mesh_status<>'ready'),
  `mesh_audit_sync.current_items` (одна карточка на sku).

## Предлагаемая схема
1. `products.mesh_family` (text) + `products.mesh_family_rep` (sku представителя), заполняет новый
   `tools/scout/mesh_family.py` (чистая функция `family_key(shop, name, params, dims, role)` +
   `--fill` + `--selftest`). Ключ по магазинам: 112923 → «Вариант модели»; 114667/114082 → имя
   минус «Ткань» минус последнее слово (цвет), только если «Ткань» найдена в имени; 99272 и прочие →
   имя минус хвостовой цвет из словаря (иначе имя целиком = семейство из одного). Во всех случаях
   ключ включает роль и габариты w×d×h (округлённые) — разные размеры не сливать.
2. Представитель семейства: детерминированно — вариант, у которого уже есть меш (самый ранний по
   generated_at); иначе стоящий в сетах; иначе наименьший sku. Решение владельца на странице
   адресуется мешу представителя.
3. Очередь (`mesh_priority.rank`): одно задание на семейство (представитель); варианты не встают.
   Готовность варианта = готовность представителя (`mesh_ready`, `asset_ready`): привязка
   `mesh_bind` вешает на ВСЕ варианты uri/поколение представителя. Лишние уже сгенерированные меши
   вариантов остаются в реестре как история (superseded), не удаляются.
4. Страница: одна карточка на семейство с подписью «+N вариантов: цвета»; sync пушит только
   представителей, остальные карточки уходят в retire (кроме тех, где уже есть решение владельца —
   тогда представитель = этот вариант).
