## 1. Вывод

Идея сравнивать два ETA вернее текущего правила, но предложенная формула всё ещё слишком оптимистична относительно замены.

Главная ошибка: `eta_fresh` — не медиана скачивания образа. Альтернатива текущей ноде выглядит так:

```text
T_replace = время reallocate → выделение машины → скачивание/кэш → запуск контейнера → health.warm
```

Сегодня выделение занимало до 9 часов, поэтому fallback 25–30 минут способен вызвать бесконечную пересадку.

Рекомендую двухуровневое правило:

### Уровень 1 — очевидный мертвяк

```text
age_downloading ≥ 10 мин
AND max_progress < 5%
AND есть ≥3 свежих наблюдения
→ кандидат на reallocate
```

Это именно абсолютный прогресс, не прирост за окно. Пример `1,77% за 9 минут` будет снят на десятой минуте.

### Уровень 2 — ETA, только после накопления статистики

```text
T_keep = (1 - progress) / r_optimistic + tail_time
T_replace = P75(reallocate → health.warm)

reallocate, если:
T_keep > 1.5 × T_replace
два последовательных тика
AND progress < 80%
AND новая нода успеет помочь текущей очереди
```

До появления хотя бы 8–10 успешных `reallocate→warm` от нескольких `machine_id` ETA-правило не включать. Только deadman. `k=1.2` слишком мал для шумного, тяжёлохвостого процесса; начать с `1.5`.

Ноды на 80–100% защищать: снимать только после отсутствия реального прогресса 15–20 минут.

## 3. Как измерять скорость

Собирать progress на каждом общем poll супервизора, сейчас это 45 секунд — [ssh_run.py:42](</home/pakar/igor/remlab/tools/scout/salad/ssh_run.py:42>). Решение о снятии принимать раз в пять минут.

Для каждого instance хранить ряд `(time, progress)`:

1. Превратить progress в монотонную огибающую:

```text
p_monotonic[i] = max(p_monotonic[i-1], p_raw[i])
```

2. Если raw откатился более чем на 10 п.п., считать это новым download epoch, а не скрывать навечно.

3. `r_recent` — медианный наклон/Theil–Sen за последние 10–15 минут.

4. `r_lifetime` — средняя скорость текущего epoch.

5. Для решения о снятии использовать оптимистичную оценку:

```text
r_optimistic = max(r_recent, r_lifetime)
```

Это не «лучшая оценка скорости», а защита от ложного снятия: ноду снимаем, только если даже при благоприятной оценке она хуже замены. Поздний настоящий stall ловит отдельный таймер неподвижности.

Простой максимум без stall-правила плох: ранняя высокая скорость навсегда замаскирует позднее зависание.

## 4. Как оценивать новую ноду

Не моделировать вероятность cache-hit вручную. Логировать фактические события:

```text
reallocate_requested_at
instance_allocated_at
download_started_at
progress_100_at
health_warm_at
machine_id
```

И использовать распределение `reallocate_requested_at → health_warm_at`. Оно уже включает:

- ожидание свободной машины;
- холодную загрузку;
- возврат прежнего `machine_id` с кэшем;
- запуск контейнера и прогрев worker.

Брать P75, не медиану: распределение бимодальное и тяжёлохвостое. Если половина машин приходит с кэшем, медиана станет почти нулевой и начнёт бездумно выбрасывать нормальные холодные загрузки.

Незавершённые reallocations нельзя игнорировать: статистика только по успешно прогретым нодам имеет survivorship bias. Если текущие замены ждут 60 минут, `T_replace` должен быть не меньше этих 60 минут.

## 5. Защита от цикла пересадок

На группу:

- максимум 2 reallocations за тик;
- максимум 4–6 в час, хотя API разрешает больше;
- не более 25% downloading-флота за один тик;
- всегда сохранять лучшую из скачивающихся нод;
- после трёх reallocations без появления новой warm-ноды — заморозить culling на 30 минут;
- кандидатов сортировать по наибольшему выигрышу `T_keep − 1.5*T_replace`, а не в порядке API.

Если весь флот медленный, P75 `reallocate→warm` вырастет, и правило автоматически перестанет дёргать машины.

### Учитывать остаток работы

Вместо размытого «рабочих нод достаточно»:

```text
T_queue = pending_jobs × median_job_time / active_workers
```

Если `T_queue ≤ T_replace`, новая нода не успеет принести пользу — текущую скачивающуюся машину пересаживать бессмысленно.

Это требует передавать в culler `pending_jobs`, `active_workers`, `median_job_time`; нынешний вызов без аргументов этого не позволяет.

## 6. Хранение истории

История нужна обязательно: процессы короткие, а загрузка длится десятки минут.

Практичный вариант — локальная SQLite/JSONL вне репозитория, например в `~/scout-scenes/`:

- observations: group, instance_id, machine_id, image version, timestamp, state, progress;
- reallocations;
- warm events.

Текущее состояние можно компактировать, но события лучше не перезаписывать. При рестарте:

- продолжать историю только для всё ещё существующего `(group, instance_id)`;
- статистику replacement-time хранить 7–14 дней;
- разделять по версии/digest образа: новый 40-ГБ образ нельзя сравнивать со старым 30-ГБ.

`instance_id` нужен для текущего epoch, `machine_id` — для анализа возврата физической машины.

## 7. Граничные случаи

- `progress=1.0`, но state ещё `downloading`: вероятны распаковка/проверка; дать минимум 20 минут tail grace.
- Прогресс идёт слоями: пятиминутное плато не обязательно означает нулевой сетевой поток.
- Инстанс сменил ID, но сохранил machine/cache — это новая попытка, но связанная статистически.
- Поменялся digest образа — старые ETA неприменимы.
- API не вернул progress — не снимать.
- Один запрос `/instances` упал — не чистить историю всей группы.
- Очередь заканчивается через пять минут — никакая новая нода уже не поможет.
- Все ноды скачивают медленно из-за общей CDN-проблемы — fleet-relative baseline важнее константы.
- Reallocate может вернуть ту же медленную машину без полного кэша; нужен machine-level журнал, но не автоматический blacklist без данных.
- API-список может быть неупорядочен; при лимите снятий сначала надо ранжировать кандидатов.

## Альтернативы

1. **Только кривая age×progress:** например `<5%/10 мин`, `<25%/20 мин`, `<60%/35 мин`. Просто и предсказуемо, но не адаптируется к дефициту Salad и смене размера образа.

2. **Жёсткий timeout 60 минут.** Не создаёт частой чехарды, но владелец продолжит ждать очевидные 2%/15 мин.

3. **Полная survival-модель/Kaplan–Meier.** Корректнее работает с незавершёнными загрузками, но для десяти нод сейчас избыточна.

## Рекомендация

Сейчас отключить нынешнее правило «15% за 5 минут»: оно математически не является скользящим окном и уже доказанно уничтожает почти готовые ноды.

Первой версией внедрить:

- сбор progress каждые 45 секунд;
- deadman `<5% после 10 минут`;
- защита `progress ≥80%`;
- максимум 2 reallocations за тик и 4–6/час;
- persistent event log;
- queue-horizon guard.

После накопления минимум 8–10 полных событий `reallocate→warm` включить ETA с `P75`, `k=1.5` и двумя последовательными подтверждениями.

Вывод изменился бы, если Salad предоставит достоверный byte-rate/ETA загрузки или гарантированный срок повторного allocation. Сейчас `pulling_progress` и малое число наблюдений не позволяют честно оправдать более агрессивную формулу.
