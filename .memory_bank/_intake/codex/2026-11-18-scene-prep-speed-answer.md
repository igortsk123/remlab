## Conclusion

**Optimize the browser dump and Python export together, but do not start with incremental scene reuse.** On the measured cold miss, the two branches run concurrently: roughly 17 s for Chromium and 15.9 s for Python. Saving 3 s in Python alone may save **nothing** from preparation wall time. Conversely, speeding up Chromium alone soon exposes Python as the limit. The safest route is to measure subphases, remove demonstrated unnecessary work, then introduce tightly bounded reuse of *inputs and parsed assets* rather than reuse of a previous variant’s finished scene.

A ≈15 s end-to-end target is **not yet supported by the measurements**. A warm GPU consumes ≈10 s; that leaves ≈5 s for preparation **and** transfer, queueing, and finalization. The stated normal preparation alone is 9–12 s. Treat 15 s as a goal to validate against complete request traces, not a promised result of one optimization.

Establish why that delay exists before replacing it with a specific readiness condition. Expected saving: **up to 1.5 s**, with additional gains only if measurements expose avoidable fetch/parse work. |
| **Bounded pre-imported Python exporter** | Worth testing, not assuming. Imports account for ≈2.8 s; a pre-imported process can remove much of that **per export**, but initially saves 0–≈2.8 s of *parallel preparation* while the browser remains slower. `draft_render._scene3d_parts` already caches parsed meshes within a process (`tools/scout/draft_render.py:2982`); a persistent worker might also reuse them, at a memory and freshness cost. Prefer a pre-imported parent that forks a fresh, job-isolated child over an indefinitely reused mutable child. |
| **Persistent browser with a fresh page per job** | Potentially valuable after profiling: it can avoid some of the ≈4 s startup/page-load portion in the supplied measurement. Keeping the **same scene/page** is substantially riskier. `buildDemoScene` constructs a `FlatViewer` and assigns scene state to `window` (`tools/scout/cycles_probe/demo_scene_entry.ts:74`); the current program closes the browser after each dump (`tools/scout/cycles_probe/demo_scene_dump.mjs:130`). Test browser reuse with a fresh context/page first, then separately test asset reuse. |
| **Remove pixel-render work from the export-only path** | Promising but requires a deliberate refactor and parity proof. `main_export` calls `scene3d_frame` to record meshes (`tools/scout/cycles_probe/export_scene.py:180`), while that function also compiles/renders a clay image and calls `paint_beyond` (`tools/scout/draft_render.py:3694`). The supplied profile attributes ≈3.1 s and ≈2.1 s respectively. A recorder that preserves placement, openings, collision adjustments, mesh ordering, cameras, and metadata but does not compute unused pixels could save several Python seconds. Do **not** simply skip those calls without tracing their side effects. |
| **Content-addressed immutable asset reuse** | Prefer this to variant-level incrementality. Reuse a GLB’s decoded geometry or texture by content/version fingerprint, with bounded eviction; recompute transforms, support adjustment, shell, decor, and the complete scene description for each snapshot. It may recover part of the measured ≈2.7 s `load_parts`, but requires memory measurements and exact-output comparisons. |
| **Uncompressed NPZ, changed MD5, skipped trimesh copy** | Experiments, not primary plan. NPZ compression costs ≈0.9 s and MD5 ≈0.8 s of **Python** time, not necessarily wall time. Larger NPZ files can increase packaging, network, and GPU-load time. `geom.copy()` precedes transforms and normalization (`tools/scout/mesh_render.py:22`); removing it without replacing mutation isolation risks corrupting reused geometry or textures. |
| **Previous-variant incremental export; speculative requests** | Defer. They have attractive best cases but high correctness or operational cost. A sofa swap can change support relationships, soft-item placement, shell accents, decor, QA metadata, or both views. Speculation shifts latency only when the predicted selection is submitted; it spends scarce DEV slots and memory on misses. |

## Design and ordered plan

1. **Establish a per-request critical-path trace.** Record bundle lookup, data write, Python import/scene/mesh/texture/serialization, browser launch/load, remote fetches, `liveApartment`/`resolveScene`, `buildShell`, `syncObjects`, plants, GLB export, file output, preparation cache store, transfer, and GPU time. Measure normal-load p50/p95 and two simultaneous jobs. The current `timing['export']` measures the *parallel wall interval*, whereas `timing['dump']` measures the dump branch (`tools/scout/render_exec.py:385`); neither explains the browser’s 11 s internally. **Saving: 0 s; prevents optimizing the noncritical branch.**
2. **Fix cache identity before broadening reuse.** `_prep_key` uses `scene_hash`, code, bundle, and mode (`tools/scout/render_exec.py:287`). But the snapshot hash’s `room` contribution contains dimensions, not all room geometry/finish (`tools/scout/render_snapshot.py:197`); `_dump_cached` hashes `data.json`, bundle *directory name*, and mode (`tools/scout/render_exec.py:442`). The dump also obtains live remote runtime mesh information (`tools/scout/cycles_probe/demo_scene_dump.mjs:64`). Verify and explicitly fingerprint every output-affecting input—including relevant local assets and remote data or a pinned copy—before treating partial results as immutable. Key by content, never hard-coded room/item/tour IDs. **Saving: 0 s; correctness prerequisite.**
3. **Make the browser branch cheaper without preserving scene state.** Remove the 1.5 s delay only after a readiness/parity test; trace GLB and material fetch/parse and `GLTFExporter.parseAsync` separately (`tools/scout/cycles_probe/demo_scene_dump.mjs:70`, `tools/scout/cycles_probe/demo_scene_entry.ts:121`). Trial one persistent browser with fresh pages and an unchanged origin, strict serialization or a measured concurrency cap, memory ceiling, recycling, timeout, and fallback to the present subprocess. **Expected incremental preparation saving: ≈1–4 s**, conditional on Python no longer being equally slow.
4. **Trial Python pre-import plus an export-only recorder.** Pre-import outside job timing, fork a fresh child per job, retain the current per-job directory/log, timeout, missing-mesh retry, and process-tree termination semantics (`tools/scout/render_exec.py:139`, `tools/scout/render_exec.py:409`). First measure pre-import alone; then factor out unused pixel rendering while retaining `_push_from_supports`, which can move chairs based on table mesh supports (`tools/scout/draft_render.py:3478`). Keep an opt-out to the existing subprocess. **Expected incremental saving after browser gains: ≈2–5 s**, to be established by A/B timings rather than summed cProfile entries.
5. **Only then test bounded immutable asset caches and serialization.** Compare complete output manifests and parsed geometry/materials for a sofa swap, a moved chair, changed camera, changed openings/finish, missing GLB followed by retry, and two concurrent jobs. Benchmark both preparation **and GPU receipt/load** before adopting uncompressed NPZ. **Additional saving: unknown, plausibly 0–3 s; reject if end-to-end worsens.**

Existing cache tests cover exact-repeat links, changed snapshot/version, incomplete entries, and pruning (`tools/scout/render_gpu/tests_render_executor.py:897`). Extend them for cache-input changes, two simultaneous cold misses, worker crashes, and byte/semantic parity. The GPU package requires more than the GLB: scene info, exported finish, UUID metadata, and dump keys travel with it (`tools/scout/render_exec.py:725`). Test those files too. No live `remlab-render` restart or production experiment is needed for the initial offline comparison.

## Risks and uncertainties

- **Persistent state:** Python has module-level mesh/orientation caches, and the browser has viewer, materials, WebGL, and remote asset state. A job failure must not contaminate the next job. A browser refresh may recover startup time but lose most asset reuse; preserving a page may retain stale objects. `FlatViewer.dispose` explicitly releases resources (`lib/viewer3d/viewer.ts:2484`).
- **Memory and concurrency:** Two jobs currently each start Python and Chromium. Long-lived parents outside `heavy-slot` can consume RAM while idle; a shared worker needs a queue and per-job RSS accounting. Fork copy-on-write savings must be measured after geometry and textures are touched, not inferred from initial RSS.
- **Determinism:** Exact file bytes are the strongest test where feasible, but regenerated GLB/NPZ/container metadata may differ without changing Blender inputs. Where bytes differ, compare decoded vertices, faces, UVs, textures, transforms, scene descriptions, and final frames. Do not accept merely “looks similar.”
- **Cache correctness:** Live remote fetches, local material files, omitted nested Python dependencies, and source changes during a warm worker’s lifetime can make a content key lie. Pin inputs/version per job or restart workers on version changes. Preserve atomic publication and immutable linked files.
- **Unknown 11 s:** The page’s “scene built” timer includes the remote runtime fetch immediately before `buildDemoScene` (`tools/scout/cycles_probe/demo_scene_dump.mjs:63`). It does not by itself prove GLB parsing, shell building, or the solver dominates. The measured 1.5 s delay is the one certain constituent.

**What would change my recommendation:** traces showing Python, rather than Chromium, dominates *normal-load* misses would move the export-only recorder and pre-import trial first; traces showing browser time is mostly remote downloads would favor pinned/local asset caching over persistent pages. A parity-tested, low-memory partial exporter with measured >5 s end-to-end benefit could justify incrementality. Conversely, if transfer, queueing, or finalization consumes most of the non-GPU 15–30 s, the ≈15 s product goal needs work outside scene preparation.
