# Аудит Кодекса (gpt-5.6, xhigh) — независимая экспертиза алгоритма расстановки (15.08)

Запрос: полный разбор архитектуры + Q-A (политика композитора) / Q-B (вторая зона) / Q-C (FAR-large). Исходники переданы инлайн (654KB, 16 файлов). Все 6 ключевых фактических утверждений выборочно проверены Клодом по коду — подтвердились.

## Краткий вывод

REMLab уже силён как движок безопасной и объяснимой геометрии: реальные габариты SKU, полигоны Г-диванов, атомарные зонные блоки, hard-валидация, трассы поиска и детерминированные каскады — хорошая база.

Но как оптимизатор качества он пока существенно слабее, чем следует из описания. Фактически это не единый лексикографический solver, а цепочка локальных жадных решений:

`банк → первая подходящая ступень посадки → первая удачная схема → локально лучшая позиция → последовательное достраивание зон`.

Главный системный дефект: старое решение часто перестаёт участвовать в сравнении после появления более богатого инвентаря. Поэтому добавление кресла закономерно меняет победителя, богатая посадка вытесняет более функциональную, а FAR растёт. Это не проблема одного веса — пространство вариантов преждевременно обрезается.

# 1. Архитектура и текущий алгоритм

## Что сделано хорошо

- Hard-физика отделена от soft-предпочтений и проверяется на полном плане. Это видно в `planner/template.py — _best_block` и `planner/validate.py — validate`.
- Геометрия работает с фактическими SKU, включая реальный шестиугольный след Г-дивана: `planner/geometry.py — footprint, _corner_polygon`.
- Есть полезная атомарная модель зон: посадка, dining, media, storage собираются блоками, а не россыпью предметов.
- Для dining реализована действительно хорошая диагностическая модель: классы island/compact/edge, независимая проба региона, счётчики и классификация причины отказа.
- Экспортируемые следы поиска и dry-run-подход — правильный фундамент для каузальных изменений.

При этом инвариант атомарности выдерживается не везде; ниже есть конкретные контрпримеры.

## Ключевые слабые места

### 1. Победитель посадки выбирается до сравнения полных планов

В `planner/zones.py — _solve_zoned_core` лестница перебирается сверху вниз и останавливается на первой ступени, для которой встали посадка и какой-либо носитель:

```python
for _g in _ladder_steps:
    ...
    if _m0:
        block, group = ...
        break
```

Ниже расположенная ступень уже не рассматривается, даже если она дала бы:

- нормальную дистанцию ТВ вместо FAR;
- полноценную столовую;
- лучший маршрут;
- вторую разговорную зону;
- меньше щелей.

`dining_sacrifice` частично переигрывает это только при полном отсутствии dining. Он не исправляет FAR, плохую вторую зону или просто качественно худший богатый вариант.

Следствие: глобальная заявленная иерархия

`circulation → functional_relationships → zone_quality → aesthetics`

фактически подчинена невидимому более высокому критерию: «первая богатая ступень лестницы».

### 2. `_best_block` оптимизирует позицию внутри одной схемы, но не сравнивает схемы

`planner/template.py — place_template` идёт каскадом:

- focus round;
- настоящий столик / pouf-table;
- допуски столика;
- список схем.

При первом успехе функция сразу возвращает план. `_best_block` сравнивает позиции одной инстанцированной схемы, но:

- `default` не сравнивается с `facing`;
- один зазор столика не сравнивается с другим;
- одна ступень посадки не сравнивается с другой;
- один носитель не сравнивается с альтернативным носителем.

Исключение — зеркала Г-дивана: там обе стороны действительно сравниваются лексикографически. Эту модель стоило бы распространить на остальные дискретные альтернативы.

### 3. «Генератор пары ТВ↔диван» в реальности не сохраняет пару

`planner/tv_sofa.py — generate_pairs` возвращает координаты и медиа, и дивана. Но `planner/template.py — _pair_sofa_candidates` выбрасывает координаты медиа и превращает результат только в якорь дивана:

```python
p = Placement(... sofa_x, sofa_y ...)
```

Конкретная медиа-позиция `Pair.media_x/media_y/media_wall` больше не используется. Позже `place_media` независимо ищет другой носитель.

Поэтому это не поиск пары, а генератор диванных кандидатов, подсказанный предполагаемой парой. Заявленный контракт MASTER-tv-sofa-pair не выполнен.

Дополнительно в `_best_block` место носителя проверяется лишь экзистенциально. Финальный ключ посадочной позиции строится через:

```python
score_layout(room, base + ps)
```

то есть без проверенного носителя. Дистанции диван↔ТВ в этом ключе вообще нет.

### 4. Порядок зон в коде расходится с `zone_priority`

Данные задают:

`dining → seating_extra → storage`.

Боевой цикл в `planner/zones.py — _solve_zoned_core` выполняет:

`dining → storage → storage2 → quiet → reading`.

Это прямой контрактный разъезд. Более низкоприоритетное хранение дважды забирает стены и остаточный регион до `place_quiet`.

Таблица приоритетов используется для резервов и статусов, но не определяет фактический порядок исполнения. Следовательно, утверждение «порядок только в данных» неверно.

### 5. Лестница не является монотонной лестницей

`rules/zones.json — seating_ladder` не монотонна ни по местам, ни по футпринту. Например:

- `sofa_2armchairs`: 5 мест, 11.2 м²;
- следующая `sofa_facing_sofa`: 6 мест, 10.0 м²;
- `sofa_lamp`: 3 места, 3.1 м²;
- следующая `compact_sectional`: 3 места, 7.4 м²;
- `sofa_solo`: 2.9 м²;
- следующая `armchair_pair`: 4.6 м².

Поэтому:

- «ступень ниже» не обязательно освобождает место;
- `dining_sacrifice skip=N` не имеет стабильного геометрического смысла;
- «соседние альтернативы» нельзя определять просто соседством в списке;
- band-cap может открывать группы, которые не являются реальным уменьшением предыдущей.

Нужен граф совместимых составов или хотя бы порядок по структурной семье и фактическому конверту, а не один глобальный список.

### 6. Банк сета фактически предрешает планировку

В `tools/scout/compose2.py — _zone_group` композитор выбирает одну группу ротацией по band/tier. Затем основной цикл прямо отбрасывает кресло или пуф, если роль не входит в эту группу:

```python
if role in ('кресло','пуф') and role not in _zreq and role not in _zopt:
    continue
```

Это противоречит модели «сет — банк кандидатов». Банк уже кодирует конкретную ступень посадки, а solver потом лишь спускается по тем подмножествам, которые случайно остались достижимы.

Дополнительные источники предрешённости:

- `exclusive_by_band` запрещает одновременно иметь кресло и пуф;
- альтернативы считаются в общий floor-cap как будто будут поставлены вместе;
- тип группы меняется от `bi+ti`, то есть tier произвольно влияет на топологию;
- dining отсекается скалярной оценкой `usable − reference footprint`, рассчитанной на синтетической прямоугольной комнате.

Dry-run с виртуальным креслом обнаружил именно этот архитектурный эффект, а не отдельную аномалию четырёх сцен.

### 7. Инвентарь не монотонен

Добавление необязательного предмета должно только расширять множество доступных планов: старый план обязан остаться кандидатом. Сейчас это не гарантируется.

`planner/template.py — place_template` передаёт в `build_block` все optional-роли группы. Если в банке появился пуф или торшер, он автоматически затекает в шаблон. Если этот предмет ломает схему, прежний вариант без него может исчезнуть.

Есть и прямое нарушение атомарности: в `build_block` обязательный пуф для `sofa_pouf` перебирает две позиции, но если обе конфликтуют, пуф просто не добавляется, а блок всё равно может быть возвращён. `_actual_step` затем переименовывает фактический состав в меньшую группу. Это маскирует разбор шаблона вместо его запрета.

Атомарной сущностью должен быть точный вариант состава: например, `sofa_armchair`, `sofa_armchair+pouf`, `sofa_armchair+lamp`, а не группа с автоматически поглощаемыми optional-предметами.

### 8. Лексикографическая таксономия неполна

`planner/score.py` создаёт термы:

- `sofa_table_dist`;
- `seats_group`;
- `storage_spacing`.

Но `planner/zones.py — _TERM_LEVEL` содержит `sofa_table`, а не `sofa_table_dist`, и не содержит два остальных. Они молча падают в `zone_quality`.

Таким образом, часть функциональных отношений сравнивается на неправильном ярусе. Консервативный fallback удобен при разработке, но скрывает drift. Тест должен требовать, чтобы каждый терм `score_layout` был явно классифицирован.

### 9. Метрики заполнения — три разные метрики под одним названием

- Композитор `_fill_now`: ковёр исключён, пристенная мебель считается за половину.
- `zones.py — _fill_pct`: то же, но свой код.
- `geometry.py — floor_used_pct`, используемый score/validate: ковёр входит в union полностью, пристенная мебель не делится пополам.

Следовательно, composer, fill-добор, `FLOOR_OVERFILL` и `floor_overfill` оценивают разные величины. Это может одновременно считать банк пустым и план переполненным.

### 10. `quality.not_worse` не означает «не хуже»

`planner/quality.py — failed_axes` допускает:

- падение маршрута со 120 до 75 см;
- рост sliver на 0.35 м²;
- уход фокуса с 10 до 40 см.

Это может быть разумной пороговой политикой, но название и документация говорят о сохранении достигнутого. В описании пользователя фигурирует `max(было, 75)`, а код использует `min(было, 75)`.

Кроме того:

- маршрут качества меряется только от первой двери;
- focus-гейт почти инертен: добавляемые зоны не двигают уже установленный носитель;
- `functional_coverage` в `score.py` использует convex hull всех предметов и может награждать разбрасывание мебели по разным концам комнаты.

### 11. Правила в JSON не являются исполняемым контрактом

Примеры:

- `zones.py — route_reserve` читает `route_width_cm`, затем не использует его: `_ = w_route`; реальная ширина задаётся `±20`.
- `validate.py — check_media_cardinality` реализует «не более одного», хотя данные заявляют `exactly_one`.
- `templates.json` объявляет `focus_visible`, `symmetry`, `sku_dimensions_intact`, но `invariants.py — check_block` их непосредственно не проверяет.
- `templates.json` содержит условия `u when >25`, полный контракт `window_back`, media-between-windows и другие схемы, которые код либо не читает, либо реализует частично.
- Severity в `validate.py` задаётся default-параметром `_v` и явными `Severity.SOFT`, а не читается из `severity.json`.
- `compose2.py` продолжает читать `tools/scout/occupancy.json`, тогда как заявленный канон находится в `services/planner-solver/rules/occupancy.json`.
- В коде остаются предметные пороги: quiet `45 м²`, large enrichment `40 м²`, sliver budget `0.35`, tv-range `120`, `0.92`, условная глубина носителя `40`.

Вывод: `rules_audit = 0` доказывает наличие пруфов у известных ему записей, но не доказывает полноту потребления правил и отсутствие параллельных чисел.

### 12. Скрытая глобальная изменяемая state-модель

`_FOCUS_LEVEL`, `_MEDIA_TOE_RELAXED`, `LAST_*`, `_SCREEN_WINDOW_WAIVED` и временная подмена `middle_candidates` делают solver непотокобезопасным и нерentrant.

Особенно опасен `_SCREEN_WINDOW_WAIVED`: это process-wide env-флаг, а не свойство конкретной media-постановки. Финальный validate снимает правило для всего плана, а при параллельном решении — потенциально для другой сцены.

# 2. Q-A — политика композитора

## Рекомендация

Не делать правило «в каждой комнате от 17 м² кресло обязательно ставится». Сделать правило:

> В каждом банке с диваном должна быть покрыта основная ступень и ровно одна более богатая структурно соседняя альтернатива; нижняя альтернатива обеспечивается подмножеством инвентаря.

Для sofa-only/sofa+pouf банка естественная минимальная добавка — одно кресло. Поэтому для номинальных band 17+ я бы действительно обеспечивал одно кресло в банке по умолчанию, но:

- как `alternative-only`, а не член обязательной композиции;
- без требования, что solver его использует;
- без суммирования его футпринта с взаимоисключающим пуфом;
- только если кресло завершает реальный паспорт `sofa_armchair`;
- старый вариант без кресла обязан оставаться кандидатом.

## Как ограничить разрастание

Не замыкать банк по всем 13 ступеням. Для выбранной базовой сигнатуры `S0`:

1. Найти более богатую группу той же структурной семьи: тот же главный диван, без обязательной смены на второй диван.
2. Выбрать группу с минимальной разностью мультимножеств ролей.
3. Добавить только эту разность.
4. Не добавлять ещё одну альтернативу, если она не создаёт новой полной сигнатуры шаблона.

Практически:

- до ~15 м²: максимум одно кресло или пуф как альтернативный flex-seat; существующий policy допускает 0–1 кресло;
- 17–25 м²: у банка с диваном обеспечить одно кресло, если его ещё нет;
- 25+ м²: второе кресло добавлять только если оно завершает `sofa_2armchairs` или явно нужно портфелю второй зоны;
- второй диван не считать «соседней добавкой» к креслу: это другая топология и отдельная ветвь банка.

## Что должно зависеть от style/tier

Style и tier должны выбирать конкретный SKU кресла, но не решать, существует ли геометрическая альтернатива.

Сейчас неиспользованный предмет не входит в смету, поэтому нет оснований делать премиум-банк функционально богаче эконома только из-за tier. Если в нужном стиле/тире нет подходящего кресла, это должно экспортироваться как `coverage_gap`, а не тихо менять топологию банка.

## Необходимое изменение контракта композитора

У сета должны появиться:

- `preferred_signature`;
- `covered_signatures`;
- `alternative_pools`/`mutually_exclusive`;
- причина отсутствия соседней альтернативы.

Поле `group` сейчас вводит в заблуждение: solver его не соблюдает. Его стоит переименовать в `composition_seed` или заменить списком покрываемых шаблонов.

Ключевой metamorphic-тест:

> Для банка B и супермножества B+chair все планы, достижимые из B, остаются достижимыми; новый победитель может измениться только после явного сравнения старого и нового планов одним ключом.

# 3. Q-B — почему quiet не ставится и как исправить

Нулевая постановка объясняется кодом почти полностью. Проблема не доказывает отсутствие подходящего шаблона.

## Причины

### 1. Жёсткий отсев до 45 м²

`planner/template.py — place_quiet`:

```python
if room.width_cm * room.depth_cm < 45 * 10_000:
    return None
```

Все сцены 35–44.99 м² исключены до генерации кандидатов. Это отдельное определение large, не связанное с `room_mode`, usable area или существующей политикой `counts.*.zones = 2`.

### 2. Quiet не признан вторичной посадочной зоной валидатором

`planner/validate.py — _in_secondary_zone` знает только:

- `reading`;
- `bay_armchair`.

`quiet` отсутствует. Поэтому кресла quiet проверяются как члены главной диванной группы.

На них распространяются:

- `SEATS_TOO_FAR` относительно главного дивана в `check_distances`;
- `ARMCHAIR_TABLE_DIST` относительно журнального столика основной зоны;
- `ARMCHAIR_BEHIND_SOFA`;
- `ARMCHAIR_AT_TV_WALL`;
- `ARMCHAIR_OUT_OF_ZONE`;
- ковёр главной зоны;
- симметрия пары главной зоны.

Причём в `check_zone` проверка расстояния до главного столика выполняется до `_in_secondary_zone`, поэтому одного добавления `quiet` в список недостаточно: вторичную принадлежность надо проверять в начале цикла по креслам.

### 3. Quiet за диваном запрещает другой валидатор

`planner/validate.py — check_dead_zone_behind_sofa` запрещает роль `кресло` за диваном и не делает исключения по `tpl_id`.

Это противоречит разрешённым secondary seating/reading в residual-полосе. По той же причине потенциально недостижим и `reading_nook` за диваном.

### 4. Кандидаты только пристенные

`place_quiet` передаёт только `wall_candidates`. Но крупнейший незакреплённый регион может быть:

- в центре;
- за floating-диваном;
- в L-ветви;
- в удалённой части вытянутой комнаты;
- отделён от пригодной стены storage/media-блоком.

Площадь региона ≥12 м² не означает наличие подходящего wall anchor.

### 5. Storage имеет фактический приоритет выше quiet

До quiet уже дважды выполняется `place_storage`, несмотря на обратный порядок в `zone_priority`. Даже если пара кресел и пригодная стена были, их могло уже не остаться.

### 6. Композитор создаёт `кресло 3/4` только условно

В `compose2.py — _ENRICH` они появляются только при `m2 >= 40` и только пока fill ниже 30%. Это не гарантия вторичной зоны.

Кроме того, `templates.json — floor_roles_claimable.quiet` всё ещё описывает старый состав и не соответствует `build_quiet`, который требует точные `кресло 3` и `кресло 4`.

## Как расширить постановку без нового шаблона

### Исправить семантику зоны

- Ввести общий предикат `zone_kind(p) == secondary_seating`.
- Включить `quiet`, `reading`, `bay_armchair`, fireplace seating.
- В `check_zone` исключать secondary seating до любых правил главной группы.
- В `check_dead_zone_behind_sofa` разрешать кресла вторичной шаблонной зоны.
- В pair-pattern сравнивать кресла только внутри одного `tpl_id`, а не первые два кресла всей комнаты.

Внутреннюю геометрию quiet продолжит проверять `build_quiet`/`check_block`.

### Исправить порядок

Фактическую цепочку строить из `zone_priority`:

`dining → quiet/reading/bay → storage`.

Это устранит один из главных причинных факторов без изменения шаблона.

### Расширить кандидаты

Для существующего `build_quiet` использовать объединение:

- wall candidates;
- `middle_candidates`;
- якоря крупнейших связных компонентов `free`;
- центры/оси `largest_free_rectangles`;
- residual-регион за диваном при `second_zone_mandatory`;
- свободный угол или зона обзора камина, если камин уже поставлен.

Кандидат должен проверяться по фактическому блоку с его клиренсами, а не по порогу площади региона.

### Заменить gate 45 м²

Не вводить новый числовой порог. Условия могут быть полностью дискретно-геометрическими:

- главная посадка уже существует;
- в банке осталась полная пара `кресло 3/4`;
- room policy допускает две зоны (`room_mode`/существующие counts);
- полный quiet-блок hard-valid;
- static route и `not_worse` сохранены;
- блок принадлежит отдельному свободному компоненту/региону.

`largest_unassigned_m2` полезен как генератор и диагностика, но не как hard-гейт: эта метрика не гарантирует форму, доступ и свободную стену.

До этого заводить новый quiet-шаблон не следует. Нынешний шаблон ещё не получил честного поиска.

# 4. Q-C — FAR-LARGE

Рост FAR после обогащения закономерен: богатая ступень принимается первой, даже если она оставляет только далёкий носитель. Есть ещё несколько конкретных ошибок.

## Несогласованные ТВ-функции

### `tv_sofa.py` не использует канонический `distance_target`

`planner/tv_sofa.py — _tv_target_cm` вычисляет:

```python
diag = max(media.w_cm - 20, 80)
return 1.6 * diag
```

Хотя комментарий обещает `planner.tv.distance_target`.

Для стенки 300 см это даёт около 448 см. Каноническая функция `tv.distance_target(..., bearer="стенка")` использует нишу 100–160 см и для стенки 300 см даёт примерно 229 см. Ошибка почти двукратная.

Это особенно опасно, потому что `place_media` всегда сначала пробует стенку и не сравнивает её с тумбой, если стенка хоть как-то встала.

### Измеряются разные дистанции

- `tv_sofa._pair_metrics` использует center-to-center.
- `validate.check_distances` использует расстояние между footprint/front plane.
- Для Г-дивана валидатор использует фронт главной секции.
- `_tv_probe` стреляет лучом из центра якоря до границы комнаты и вычитает условные 40 см.

Генератор оптимизирует не ту величину, которую затем валидирует.

### `tv_range` не знает фактического носителя

`planner/template.py — _tv_range_candidates` вызывает:

```python
distance_range(120.0)
```

для любой сцены и любого носителя, затем добавляет условную глубину 40 см и позицию `hi * 0.92`.

Это параллельная модель ТВ, не связанная с выбранной стенкой/тумбой и её глубиной.

## FAR не полностью отражён в финальном score

`validate.check_distances` ставит `SOFA_TV_FAR` при дистанции выше:

```python
min(soft_hi, hi)
```

Но `score.score_layout` штрафует `sofa_tv_dist` только выше `hi`.

Поэтому диапазон `soft_hi … hi` одновременно:

- считается FAR валидатором;
- имеет нулевой штраф в ключе выбора позиции.

Это прямой случай «метрика меряет не то».

Кроме того, на этапе выбора посадки actual bearer отсутствует в `score_layout`, поэтому даже этот штраф ещё не доступен.

## Как системно снизить FAR без новых чисел

### 1. Один канон ТВ на всех слоях

- `tv_sofa._tv_target_cm` заменить вызовом `tv.distance_target(media.w_cm, bearer=base_role(media.role))`.
- Все диапазоны брать через `distance_range` с фактической ролью носителя.
- Измерять одну и ту же величину: `seat_axis_origin/front plane → plane носителя`.
- Убрать 120, 40, 0.92 из tv-range; координату якоря выводить из реальной глубины обоих блоков.

### 2. Сохранять настоящую пару

Кандидат primary-сцены должен включать:

- полный seating block;
- конкретный media block;
- конкретные координаты обоих.

Оба атомарных шаблона остаются отдельными, но их положения валидируются и сравниваются совместно. Координаты media из `Pair` нельзя выбрасывать.

### 3. Ввести пороговые классы, а не новый вес

Использовать уже существующие границы:

- `TV_COMFORT`: `lo ≤ d ≤ min(soft_hi, hi)`;
- `TV_FAR`: выше comfort, но ниже hard max;
- hard-invalid: слишком близко или выше hard max.

В large сначала искать hard-valid primary-планы класса `TV_COMFORT` по всем допустимым ступеням. Только если их нет — разрешать `TV_FAR` как явно трассируемый fallback.

Это можно реализовать даже до полноценного общего beam двухпроходной лестницей:

1. все ступени с `require_media_comfort=True`;
2. если пусто — те же ступени с FAR-разрешением.

Так богатая FAR-группа перестанет автоматически побеждать более компактную группу с нормальной дистанцией. Это соответствует уже заявленной иерархии: functional relationships выше zone quality/богатства состава.

### 4. Сравнивать стенку и тумбу

`place_media` сейчас использует first-feasible ladder «стенка → тумба». Нужно решить обе альтернативы и сравнить полный лексикографический ключ. Иначе широкая стенка может предопределить FAR, хотя тумба даёт правильную пару.

### 5. Не давать WallScore необратимо обрезать пул

`generate_pairs(top_k=6)` ранжирует кандидатов одной взвешенной суммой до полного validate. Вес окна или длины стены может вытеснить комфортную дистанцию.

Лучше сохранять квоты кандидатов по классам:

- comfort/far;
- opposite/floating/window-back;
- по пригодным медиастенам.

Затем применять общий лексикографический отбор. Веса могут остаться только tie-breaker внутри одного класса.

# 5. Важные риски и edge cases

- `usable_polygon` при MultiPolygon оставляет только крупнейший компонент. Отдельная пригодная ветвь комнаты может полностью исчезнуть из поиска.
- Для контурных комнат много мест используют bbox-площадь и четыре номинальные стены: quiet, fill, floor cap, residual, tv-range, corner candidates. L-комната может считаться большой по bbox, но иметь значительно меньший реальный пол.
- `quality.route_width_cm` учитывает только первую дверь. Сцена с двумя дверями или балконом может пройти gate, ухудшив второй маршрут.
- Угловые media-кандидаты, вероятно, почти мёртвые: `check_facing` требует точной разницы поворотов 180°, а главная посадка обычно осевая.
- `SCREEN_WINDOW_WAIVED` привязан к процессу, а не к placement. Это риск тихого ослабления чужого варианта и гонок.
- `focus_offset_cm` считает камин носителем фокуса наравне с ТВ. Это может скрыть отсутствие media в quality/sacrifice.
- `dining_sacrifice` также считает камин сохранённым media.
- `check_access` проверяет пересечения access-зон с предметами, но не видно общей проверки, что access-зона целиком остаётся внутри комнаты.
- `functional_coverage` через convex hull может считать хорошо покрытой комнату, где несколько предметов просто разнесены по периметру.
- Паспортные optional-роли не оформлены как отдельные атомарные варианты; добавление инвентаря способно ухудшить достижимость старого плана.
- `exactly_one_carrier` не является hard-кардинальностью в валидаторе: ноль носителей допустим.

# 6. Альтернативные подходы

## Ограниченный best-first поиск по шаблонным состояниям

Не нужен ML и не нужен перебор отдельных предметов. Состояние:

- seating template + variant + position;
- media template + position;
- dining class;
- secondary zone;
- storage zones.

После каждого слоя сохранять небольшой Pareto/lexicographic frontier. Это устранит большинство жадных ошибок, сохранив атомарность и Shapely-валидацию.

## Граф возможностей композитора

Вместо глобальной лестницы построить граф сигнатур:

- вершина — мультимножество ролей шаблона;
- ребро — минимальная добавка/удаление инвентаря;
- отдельные семейства: straight sofa, sectional, two-sofa, armchair-only.

Композитор решает bounded set-cover: покрыть базовую и одну соседнюю возможность минимальным числом SKU.

## Типизированный rule IR

Сейчас JSON часто является документацией, а не исполняемым источником. Стоит компилировать из единого IR:

- порядок и статус зон;
- required/optional/mutex/cardinality;
- инварианты;
- числовые параметры;
- классификацию score-термов.

Тесты должны падать при неиспользуемом поле, неизвестном терме или числовом fallback.

# 7. Что делать следующим

## Топ-3

1. **Сделать primary-поиск совместным seating+media и привести всю ТВ-геометрию к `tv.py`.**

   Это исправляет фундаментальную ошибку цели, затрагивает 60% больших сцен с FAR и возвращает функциональному ярусу реальный приоритет. Ввести comfort-first/FAR-fallback по существующим порогам и сравнивать стенку с тумбой.

2. **Разблокировать существующий quiet-шаблон.**

   Включить quiet в secondary seating, перенести исключение до правил главной группы, исправить `DEAD_ZONE_BEHIND_SOFA`, выполнить seating_extra до storage и добавить middle/residual/free-region candidates. После этого повторить 105 сцен с поэтапными счётчиками. Новый шаблон до этого не нужен.

3. **Переделать композитор с «одной выбранной группы» на bounded capability coverage.**

   Для sofa-банков от 17 м² обеспечить одно кресло как альтернативный SKU, но сохранить исходную lean-композицию и не считать взаимоисключающие варианты вместе в fill-cap. Добавить inventory-monotonicity тест и экспорт `covered_signatures`.

## Чего не делать

- Не повышать вес `sofa_tv_dist`: FAR возникает до стадии, где вес способен помочь.
- Не делать FAR новым hard-запретом: в некоторых геометриях дальняя постановка — единственная.
- Не добавлять кресло как обязательный предмет выбранной планировки от 17 м².
- Не создавать новый quiet-шаблон до устранения недостижимости существующего.
- Не превращать `largest_unassigned ≥12 м²` в hard-гейт: площадь не доказывает форму и доступ.
- Не ослаблять маршруты, sliver или SKU-конверты ради роста coverage.
- Не двигать регрессионные планки по агрегатам без per-scene causal diff.

# 8. Неопределённости и нужные эксперименты

В приложенных материалах нет `candidates.py`, `room_map.py`, `models.py`, `beam.py`, тестов и самих `plan-NNN.json`. Поэтому я не могу достоверно установить:

- распределение причин hard-reject у quiet;
- долю FAR по стенкам против тумб;
- сколько из 105 сцен имеют точные свободные роли `кресло 3/4` после dining/storage;
- какие comfort-пары были сгенерированы, но отсечены top-K;
- реальную семантику expansion `qty → кресло 2/3/4`.

Эксперименты, которые могли бы изменить приоритеты:

1. Для FAR экспортировать по каждому кандидату: carrier role/width, canonical lo/comfort_hi/hard_hi, единый измеренный gap, группа, схема, причина отбраковки. Отдельно стенка и тумба.
2. Для quiet снять воронку:

   `pair in keep → gate area → generated wall/middle → fits → hard-valid → quality-valid`

   и top hard-коды. Патчи запускать изолированно: secondary membership, порядок, кандидаты, area gate.
3. Для композитора прогнать не 4, а все 272 сцены с контрфактуалами:

   - исходный банк;
   - +1 кресло;
   - +1 пуф;
   - +2-е кресло.

   Проверять не только победителя, но сохранение старого кандидата, FAR, dining, route, quiet, seating capacity и слепую человеческую оценку.
4. Если люди систематически предпочитают богатую FAR-группу компактной comfort-группе, это изменит продуктовую иерархию. Но тогда нужно явно пересмотреть правило «functional relationships выше zone quality», а не прятать решение в порядке лестницы.
