# T-20261110-05/1 · задание — пересборка готового тура «как есть» (новый код страницы и бандла) + журнал разбора без буфера (план agent-trial-08)

На прошлые задачи не опирайся — бриф самодостаточный.

## Факт
1. Тур агента собирается один раз. Правки страницы и бандла (уникальные имена товаров, вкладка плана с дверями, порядок комнат —
   `tools/scout/trial_bundle.py`, `tools/scout/flat215-demo/index.html` под `TRIAL()`) на уже готовые туры не попадают. «Обустроить»
   (`conveyor.Rebuild`, очередь `trial_rebuilds`) берёт только комнаты «ждут проверки» и на полностью обставленном туре отвечает
   `nothing_to_furnish`. Тур закреплён на своей копии `index.html` (`ensureJobRelease`).
2. Разбор плана (`tools/floorplan/pipeline.py`, его запускает `tools/floorplan/worker.py:run_child`, лог `pipeline.log`) пишет вывод с
   буфером: 10.11 попытка разбора большого листа упала через 456 с с `pipeline rc≠0`, а `pipeline.log` пуст — причину не узнать.

## Что сделать
1. Режим пересборки «как есть» для оператора: тур пересобирается на ТЕКУЩЕМ коде страницы и бандла из сохранённого результата
   (стены, мебель, размеры — без нового разбора плана и без нового подбора мебели, 0 $), новая версия, закрепление на новой копии
   страницы. Ставит оператор (скрипт/команда, не кнопка агента), можно пачкой «все туры младше N дней». Если для какой-то части
   нужны входы, которых уже нет (исходник плана удаляется через 24 ч), — пересобирать то, что можно, и честно писать, что осталось
   прежним. Новая строка в `trial_rebuilds` (`kind`) или отдельный путь — реши по коду, объясни в отчёте; миграция — только если
   без неё никак (тогда файл `db/init/027-*.sql`, идемпотентный).
2. `pipeline.log` — без буфера (`python -u` или `PYTHONUNBUFFERED=1` в `run_child` для разбора и стадий), плюс при rc≠0 без
   `error.json` — в `fail` строка с последними строками лога и сигналом (rc < 0 → имя сигнала).
3. Тесты: юнит на режим «как есть» (обставленный тур → новая версия с новым именованием товаров, мебель та же), на rc<0 → сигнал в
   причине сбоя.
