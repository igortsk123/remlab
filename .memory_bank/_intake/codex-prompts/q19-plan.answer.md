## Вывод

План в текущем виде не стоит показывать владельцу как путь к внедрению. Его надо сократить до проверочного спайка с жёсткими stop/go-гейтами.

Главные проблемы:

1. `image_url = clay`, а вне мебельной маски предлагается оставить исходник побитово. Значит стены и пол останутся clay, а не фотографией. Это внутреннее противоречие цели.
2. Наличие `mask_image_url` в API не доказывает работу регионального IP-Adapter. В актуальном Diffusers есть открытый дефект: FLUX принимает IP-маски, но не применяет их.
3. Остаточный дефект мелких предметов может иметь гораздо более дешёвый корень: текущий код сам исключает из разметки и товарного листа предметы с видимой маской меньше 400 px.

Итого: FLUX regional стоит проверить, но главным кандидатом я бы сделал нынешний GPT-путь плюс исправление мелких объектов и локальный repair только при обнаруженном браке.

## 1. Реалистичность FLUX regional

На уровне API один вызов технически возможен, но рабочий контракт плана пока не подтверждён.

| Проблема | Что обнаружено | Следствие |
|---|---|---|
| Фон | План копирует clay вне `mask_all` | Получится фотографическая мебель в серой комнате |
| ControlNet | fal поддерживает только один обычный `controlnet`; для него обязательны `path` весов и control image | `depth + segmentation` двумя ControlNet сейчас не работает |
| Regional IP | Для IP-Adapter обязательны `path`, `image_encoder_path`, `image_url`, scale; план указывает только фото и маску | Payload архитектурно неполон |
| Региональные маски | В Diffusers для FLUX маски сейчас могут приниматься и игнорироваться | Возможна ложная уверенность без ошибки API |
| Segmentation | Наша карта — произвольные instance-id цвета, не классовая палитра обученного segmentation-ControlNet | Такой control скорее даст шум |
| Маски сцены | `instances` — только видимые после z-buffer пиксели прокси | Реальный товар может быть обрезан маской |
| Идентичность | IP-Adapter передаёт визуальные признаки, но не гарантирует точный SKU | Особенно плохо для похожих товаров и мелких объектов |

fal действительно декларирует списки `controlnets` и `ip_adapters`, но одновременно пишет «only one controlnet is supported». IP-Adapter требует конкретных весов и image encoder; недокументированного лимита на число адаптеров нет, а значит N предметов нельзя считать поддержанным production-сценарием без замера 1/2/4/8 адаптеров. [Документация fal FLUX General Inpainting](https://fal.ai/models/fal-ai/flux-general/inpainting/api).

Критический риск: в свежем отчёте по Diffusers показано, что `ip_adapter_masks` для FLUX принимаются, но не используются — zero-mask и full-mask дают идентичный результат. fal может иметь собственную исправленную реализацию, но это надо доказать причинностным тестом. [Hugging Face Diffusers issue #13584](https://github.com/huggingface/diffusers/issues/13584).

Правильный первый тест:

- Один seed, один prompt, один товар.
- Прогон с полностью чёрной и полностью белой региональной маской.
- Затем два разных товара и перестановка их масок местами.
- Результат обязан меняться только в соответствующих регионах.
- Если этого нет — весь regional-путь закрывается до выяснения версии backend.

Обычная документация IP-Adapter требует бинарную маску на каждое reference image и её точное выравнивание под выходное разрешение. Приведённые примеры относятся прежде всего к SDXL, а не являются доказательством исправной реализации FLUX. [Diffusers: IP-Adapter masking](https://github.com/huggingface/diffusers/blob/main/docs/source/en/using-diffusers/ip_adapter.md).

Дополнительный риск — выбранные веса. Например, InstantX использует encoder 384 px и прямо предупреждает, что image guidance может конфликтовать с текстом; опубликованные веса имеют non-commercial-лицензию. Коммерческая отметка самого fal-endpoint не обязательно переопределяет лицензию стороннего checkpoint. [InstantX FLUX.1-dev IP-Adapter](https://huggingface.co/InstantX/FLUX.1-dev-IP-Adapter).

### Маски и глубина

[`compile_scene`](/home/pakar/igor/remlab/services/planner-solver/planner/scene.py:342) выдаёт качественные аналитические карты, но `instances` содержит только видимую часть предмета: ближайшая грань перезаписывает дальнюю через z-buffer. Поэтому маска должна быть не буквальным `instances == id`, а:

- стабильный `instance_id`, не имя роли;
- видимый силуэт плюс небольшой object-relative dilation;
- отдельный узкий `contact_shadow_band`;
- с учётом окклюзии более близкими предметами.

Пол под предметами нельзя объединять в широкую связанную область: это даст модели пространство для миграции и дублирования. Проект уже фиксировал, что ограничение силуэтом прокси обрезает реальный товар — [anti-pattern 94](/home/pakar/igor/remlab/.memory_bank/anti-patterns.md:234).

Для depth нужно переиспользовать [`depth_for_controlnet`](/home/pakar/igor/remlab/tools/scout/viz_base.py:56), который корректирует полярность и гамму. Простая «нормировка по кадру» из плана расходится с уже проверенным контрактом. Сильный depth внутри мебельных масок тоже опасен: он закрепит коробочный прокси и будет мешать форме настоящего товара.

### Стоимость и время

fal показывает около 14,7 с для простого 1024×768-прогона без набора товарных адаптеров и цену $0.075/MP. [fal pricing/example](https://fal.ai/models/fal-ai/flux-general/inpainting).

Для 1344×896 это 1,2 MP; консервативно надо закладывать $0.15/кадр, если применяется округление вверх до целого MP, и проверить фактический биллинг. Три сцены × два вида × три scale × три seed — уже 54 результата, до Seedream/Klein. Время с 4–10 адаптерами и cold load документацией не ограничено — его надо измерять, а не оценивать по числу HTTP-вызовов.

## 2. Более дешёвый корень дефекта

Самое важное упущение плана — порог мелких предметов.

В [`anchors()`](/home/pakar/igor/remlab/tools/scout/draft_render.py:362) предмет с видимой маской `<400 px` просто пропускается. Затем именно из `anchors` строятся:

- номера и цветовая привязка;
- товарный лист через [`_identity()`](/home/pakar/igor/remlab/tools/scout/draft_render.py:933);
- JSON-легенда через [`_legend()`](/home/pakar/igor/remlab/tools/scout/draft_render.py:1061).

То есть маленький торшер или столик может остаться серым объёмом, но не получить ни номера, ни товарного референса, ни явного элемента JSON.

Выбор камер также считает предмет видимым только при площади ≥60 px на уменьшенном кадре 336×224 — примерно ≥960 px в итоговом 1344×896. См. [`_cam_score()`](/home/pakar/igor/remlab/tools/scout/draft_render.py:270). Камеры оптимизируются в основном по крупной мебели.

Есть и явное противоречие промпта: сначала правильно сказано, что эталоны находятся в Image 3, а ниже модель просят брать реальный товар из Image 2 — служебной разметки. См. [`build_full_prompt()`](/home/pakar/igor/remlab/tools/scout/draft_render.py:1595).

Минимальный порядок:

1. Развязать «предмет входит в JSON/эталоны» и «на нём можно красиво нарисовать номер». В список и эталоны должны входить все видимые предметы.
2. Убрать абсолютный порог 400 px либо заменить его роль- и размер-зависимым; для совсем маленького пятна использовать увеличенную внешнюю метку.
3. Выбирать два кадра с hard-условием: у каждого обязательного предмета есть хотя бы один кадр, где он достаточно крупный для идентификации.
4. Исправить `Image 2` → `Image 3` и сократить повторяющиеся инструкции.
5. Повторить текущий GPT baseline.

Если останется один переехавший предмет, дешевле делать локальный repair:

- tight crop вокруг ожидаемой позиции;
- один товарный референс;
- маска с небольшим окружением;
- склейка обратно только внутри feathered region.

Это может быть GPT Image, Seedream, Klein или FLUX — выбирать по A/B именно на repair-кропе. Маска GPT Image тоже не является точным геометрическим контролем: OpenAI прямо описывает её как prompt guidance, которая может не соблюдаться пиксельно. [Официальная документация OpenAI](https://developers.openai.com/api/docs/guides/image-generation#edit-an-image-using-a-mask).

Ещё более детерминированная альтернатива уже зафиксирована проектом: товарная вырезка/3D ставится собственной геометрией, затем выполняется один согласующий проход. См. [ADR-0060–0063](/home/pakar/igor/remlab/.memory_bank/decisions.md:924) и [anti-pattern 80/82](/home/pakar/igor/remlab/.memory_bank/anti-patterns.md:220).

## 3. Метрика приёмки

«Центр попал в маску ±5% кадра» слишком слабая метрика. На 1344×896 допуск равен примерно 67×45 px — зачастую больше самого торшера. Пройдут:

- огромный предмет, накрывший нужную область;
- правильный товар плюс лишний дубликат;
- предмет, у которого только центр попал в маску;
- соседний объект с близким центром;
- неверная ориентация и масштаб.

Нужны четыре независимых измерения:

1. Геометрия:

   - normalized center error относительно диагонали ожидаемого bbox;
   - доля обнаруженного предмета внутри расширенного ожидаемого envelope;
   - отношение площади/высоты результата к ожидаемой;
   - правильные отношения left/right, near/far и нужная стена.

2. Состав:

   - presence;
   - omission;
   - duplicate;
   - extra object.

3. Идентичность:

   - поиск правильного SKU среди 4–8 похожих товаров той же категории;
   - top-1 и margin до ближайшего неправильного SKU;
   - слепая человеческая проверка спорных случаев.

4. Итог сцены:

   - pass только если все обязательные видимые предметы на месте и нет лишних;
   - средняя доля предметов не должна скрывать один катастрофический перенос.

Для честного пилота:

- три сцены: известный дефект мелочи, плотная сцена с окклюзиями/одинаковыми стульями, простая контрольная;
- два вида;
- минимум три фиксированных seed на конфигурацию;
- scale подбирать на отдельном calibration-кадре, не на тех же шести результатах;
- `gpt-4.1-mini` использовать как предварительный разметчик, а не как единственный oracle.

Шесть единичных картинок годятся для smoke, но не для решения о смене архитектуры.

## 4. Что убрать и добавить в план

Убрать:

- segmentation-ControlNet по произвольным instance-цветам;
- широкую маску «предметы плюс пол под ними»;
- требование побитового clay-фона как критерий готовой фотографии;
- утверждение, что regional IP уже «технически возможен»;
- создание четырёх production-скриптов до проверки причинности масок;
- одну VLM-модель как окончательного судью;
- подбор scale до теста, что маска вообще влияет.

Seedream оставить как baseline, но не называть его координатным API: публичный контракт содержит `image_urls[]` и prompt, а не числовые маски/координаты. Он принимает до десяти reference images. [fal Seedream 5 Pro Edit](https://fal.ai/models/bytedance/seedream/v5/pro/edit).

FLUX.2 Klein уже существует, допускает максимум четыре входных изображения и не принимает mask/depth/ControlNet. Он подходит для нынешних трёх листов или локального repair, но не является альтернативой regional-пайплайну. [fal FLUX.2 Klein 4B Edit](https://fal.ai/models/fal-ai/flux-2/klein/4b/edit/api).

Добавить:

- Gate 0: zero/full/swapped-mask causality test.
- Явный checkpoint, commit, encoder и лицензия для каждого ControlNet/IP-Adapter.
- Замеры 1/2/4/8 адаптеров: успех, latency cold/warm, стоимость, bleed.
- Проверку полярности и ресайза каждой маски.
- Fixed seed, request ID, полный payload и billed cost в артефакте.
- Отдельные `object_envelope`, `visible_mask`, `shadow_band`.
- Baseline после исправления `<400 px` и ошибки Image 2/3.
- Stop-условия до начала эксперимента.

## 5. Проверка узнаваемости товара до вложений

Сначала отдельный identity stress test без сложной комнаты:

- 12 SKU: четыре визуально уникальных, четыре похожих внутри одной категории, четыре мелких/тонких;
- для каждого — правильный референс плюс 4–8 hard-negative товаров;
- одинаковые позиция, экранный размер и ракурс для GPT, FLUX, Seedream/Klein;
- три seed;
- blind top-1 выбор владельцем/независимым рефери;
- автоматический embedding/retrieval — только вспомогательная метрика.

Ключевой результат — не «похож на кресло», а правильный SKU чаще ближайшего похожего товара. Если FLUX проигрывает текущему GPT по identity либо маленький объект занимает слишком мало пикселей для различения, regional-путь прекращается независимо от качества комнаты.

## Допущения и неопределённости

Неизвестны точная версия backend fal, максимальное практическое число IP-Adapter, поведение повторной загрузки одного checkpoint и биллинг при 1,2 MP.

Мой вывод изменится, если:

- fal подтвердит и тестом покажет работающие regional IP masks именно на используемом backend;
- исходником для hard-composite будет не clay, а уже фотографический и геометрически точный фон;
- выяснится, что все переезжающие предметы имели >400 px и присутствовали в эталонах/JSON;
- FLUX пройдёт stress test точных SKU не хуже GPT при нужном разрешении.
