## Что изменилось в плане — проверь именно это
1. Идентичность: НЕ меняю `revision_key` (точное равенство в `mesh_scheduler._queue`,
   prefix в `mesh_ready`/`enforce_ready_invariant` сломались бы), а добавляю таблицу
   `mesh_generations` (строка на физический меш: sku|sha16|pipeline|seed|glb8, путь, вердикт
   владельца, prod_decision_id). Решение владельца адресуется generation_key.
2. Ingest: `asset_revisions.status='owner_reject'` сохраняется ТОЛЬКО пока `excluded.glb_sha =
   asset_revisions.glb_sha` (тот же физический меш); новый glb_sha (перегон) возвращает
   `generated`, старый вердикт остаётся в `mesh_generations`. Иначе новый хороший меш унаследовал
   бы отказ через общий revision_key.
3. Отказ владельца = товар БЕЗ меша до перегона: `mesh_bind` НЕ воскрешает старые попытки
   (seed 0, который приёмка уже завернула), а ставит `mesh_status='rejected'`, `mesh_uri=null`.
   Тогда `mesh_priority.products()` (`mesh_status != 'ready'`) сам вернёт товар в очередь на его
   законном ярусе — «общая очередь» без обгона, без новой логики ярусов. `enforce_ready_invariant`
   не вернёт ready, т.к. статус ревизии `owner_reject`.
4. Очередь: инбокс `mesh_rework_requests` (prod_decision_id unique, next_seed). В живой JSON
   ничего не дописываем. `mesh_priority.py --build-queue` для товаров с pending-переделкой пишет
   `seeds:[next_seed]` и переводит запрос в `queued` с built_at снимка. Снимок пересобирается
   ТОЛЬКО оператором при старте волны (курсор позиционный, сброс до 0) — до этого страница честно
   показывает «принято, ждёт сборки очереди», не «в очереди».
5. Прогресс — per-item `seen_at` (сбрасывается при новом поколении), не по номерам страниц.
6. Партии: staging → манифест → атомарный rename → переключение → удаление предыдущей; порог
   `свободно − партия − запас ≥ 7 ГБ`; активы под `/opt/remlab/test/mesh-audit/` (том уже
   смонтирован в caddy), отдельный `handle_path /test/mesh-audit/*` с кэшем вместо `no-store`.
7. Клик на проде — одна транзакция (актуальность generation_key → лимит 2 в scope
   sku+source_sha+pipeline → insert решения → update item), 409 для устаревшей вкладки; на DEV
   ledger по prod_decision_id, курсор двигается после успешной локальной транзакции, атомарно.
8. Python-тесты — `--selftest` без БД (так устроен CI `scout-selftest`), TS — vitest.
