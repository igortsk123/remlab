## Что сделать (код в `tools/scout/render_gpu/`, worktree `render-gpu`, от свежего main после моего «влито»)
1. **Контроллер** `render_machine.py on|off|status [--by <кто>]` — ОДИН держатель желаемого состояния (файл состояния вне репо, например
   `~/remlab-logs/render-machine/state.json`: желаемое on/off, поколение, кто нажал, время, расход за день). Идемпотентно: повторный `on`
   не плодит групп и не перезапускает живую; `off` гасит и проверяет `stopped`. Одна группа `render-3090` (имя/параметры — данными в
   `rules/salad-groups.json`, не в коде). Учти грабли: PATCH остановленной группы не применяется → смена образа = новая группа по правилу.
2. **«Прогрелась»** — когда `running` и `/ready` вернул PROBE_OK: ОДНО сообщение владельцу за запуск («Машина рендера готова, фото
   считается ~15–30 с; выключить — /render_off»). Деградация (/ready падает, машина пропала) — отдельным сообщением, без спама.
   Канал отправки — найди готовый путь оповещений проекта (как шлют `money_guard`/сторожа) и используй его; токены не читать и не копировать.
3. **Предохранители** (независимые, данными): автостоп через N мин (по умолчанию 20) после последней ГОТОВОЙ пары или после `on` без
   заказов; максимум непрерывной работы (по умолчанию 4 ч); дневной потолок $ (по умолчанию $2) — превышение = стоп + сообщение.
4. **Сторож render-*** — отдельный короткий скрипт по крону (как `salad-deadman.py` для мешей, но только `render-*`): контроллер не
   отмечался > 10 мин → гасит только render-группы. Меш-группы не трогать (тест на `decide()`).
5. **Для кнопок ботов** — CLI `render_machine.py on|off|status` с понятным однострочным ответом RU (EN парой в коде); сами кнопки в
   плагине Telegram на трёх машинах ставит директор — опиши в README, какую команду вызывать и что она печатает.
6. **Проверка вживую ≤ $1**: on → прогрелась → status → повторный on (та же группа) → off → stopped; автостоп на коротком N (например 3 мин);
   потолок на маленьком $ — логом. Расход — в отчёте.
