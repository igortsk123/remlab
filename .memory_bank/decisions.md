# Decisions — ADR-лог

> Полные ADR с контекстом/последствиями — в `docs/DECISIONS.md`. Здесь — короткая навигация по решениям.

## [2026-07-01] Стек проекта
**Решение:** TypeScript (strict) end-to-end: Next.js (App Router, full-stack) + Drizzle + Zod (контракты на границах) + Inngest (durable jobs) + внешний инференс (Vertex/fal/Replicate за провайдер-интерфейсом) + YooKassa + Sentry + PostHog + Vitest/Playwright + GitHub Actions.
**Почему:** соло + не-кодер → один рантайм и сквозные типы убирают класс ошибок, которые владелец не читает.
**Альтернативы:** Python+TS два рантайма — отвергнуто (два деплоя, рассинхрон).
**Влияет на:** `core/architecture.md`, структуру `/modules`, `/contracts`.

## [2026-07-01] Self-host на exit-fi вместо Vercel — ADR-0001 (docs/DECISIONS.md)
Изолированный docker-compose на Hetzner exit-fi. Причина: свой сервер, контроль, дёшево. Fallback — Vercel+Supabase.

## [2026-07-01] БД в контейнере postgres:17+pgvector — ADR-0002
Не Supabase Cloud (полный self-host Supabase не влезает рядом с VPN). Auth/Realtime — интерим (anonymous id + polling), позже отдельным ADR.

## [2026-07-01] TLS Let's Encrypt TLS-ALPN-01 на :443 — ADR-0003
Домен GoDaddy A→сервер напрямую; :80 закрыт. Caddy авто-выпуск/продление на :443.

## [2026-07-01] Щедрые лимиты памяти контейнеров — ADR-0004
app 1G / pg 1G (shared_buffers 128MB) / caddy 128M — защита VPN-ноды от OOM.

## [2026-07-01] Дисковая гигиена/автоочистка + swap 4G — ADR-0005
Ротация логов Docker, scoped-очистка образов, weekly timer, ротация бэкапов, df-watchdog, swappiness=10.

## [2026-07-01] Образы под linux/arm64 — ADR-0006
exit-fi оказался ARM (aarch64). Собираем кросс-сборкой buildx `--platform linux/arm64` + binfmt. `deploy.sh` делает это сам. Обычный amd64-билд не запускается на сервере.

## [2026-07-01] Провайдер ИИ = Gemini для обеих задач (M0) — ADR-0007
**Решение:** и генерацию картинок, и анализ фото делаем через Google Gemini одним ключом:
картинки `gemini-3.1-flash-image` (Nano Banana 2), текст/зрение `gemini-flash-latest`. Провайдер за
интерфейсом (`lib/providers/`), сменный под задачу. Детали доступа — `core/access-and-integrations.md`.
**Почему:** ключ Gemini доступен и проверен; Nano Banana 2 силён в editing/consistency по эталонному
фото (наш кейс «перерисовать комнату, сохранив её»); анализ фото у всех стоит доли цента — не рычаг;
OpenAI-ключа в наличии нет. Одна интеграция = проще.
**Альтернативы:** OpenAI GPT-Image (дороже ~$0.167 hi; выше в бенчах text-to-image, не в editing) /
Imagen 4 Fast ($0.02, слабее в editing) — отложены, подключаемы через сменный провайдер.
**Влияет на:** `core/access-and-integrations.md`, `lib/providers/*`, экономику M4/paywall (резолюция).

## [2026-07-01] Каркас Stage 1: in-memory store + Zod как источник формы — ADR-0008
**Решение:** для каркаса Stage 1 источник правды по данным — Zod-контракты (`/contracts`, тип через
`z.infer`), рантайм-хранилище — за интерфейсом `ProjectRepository` с in-memory реализацией
(`modules/store/`). Модель упрощена до одного агрегата `Project` (вместо 11 таблиц спеки §4).
Настоящий Postgres/Drizzle подключается на шаге деплоя заменой реализации Repository.
**Почему:** локальной БД нет, CI должен быть герметичным/быстрым, миграции без живой БД дают дрейф.
Абстракция даёт рабочий проходимый flow сейчас и чистую замену на PG позже без правок вызывающих.
**Альтернативы:** поднимать Postgres в CI/локально сразу — отложено (лишняя связность на этапе каркаса).
**Влияет на:** `modules/store/`, `contracts/*`, план деплоя (там PgRepository + миграции).

## [2026-07-01] Postgres активирован + авто-деплой через GitHub — ADR-0011
**Решение:** (1) БД — Postgres (`projects` = jsonb-агрегат, `db/schema.ts` Drizzle, `modules/store/pg-repository.ts`).
Выбор реализации в `repo()`: `DATABASE_URL` задан → PG (прод), иначе in-memory (локально/тесты). Миграция —
`tools/migrate.mjs` (идемпотентно) + `db/init/002-projects.sql` (свежая БД); на сервере применяется через
контейнер db (`psql -f`, deploy.sh шаг 5b). (2) Деплой **по умолчанию автоматический через GitHub Actions**:
`.github/workflows/deploy.yml` запускается после зелёного «CI gate» на main, собирает arm64-образ **в раннере**
(не на боевом сервере — VPN-нода) и катит через `deploy.sh` (save|ssh load|compose up|migrate|smoke|rollback).
**Требует (owner, разово):** секреты репозитория `DEPLOY_SSH_KEY` (ssh root@сервер) и `DEPLOY_HOST=89.167.127.0`;
на сервере `/opt/remlab/.env` должен содержать `GEMINI_API_KEY` (+ `POSTGRES_PASSWORD`). Без секретов деплой-джоба
безопасно пропускается. Прямой SSH к проду мной не используется (только через GitHub-автоматизацию).
**Почему:** тяжёлая сборка вне фрагильного сервера; воспроизводимый, откатываемый деплой без ручных шагов.
**Влияет на:** `docker-compose.yml` (GEMINI_API_KEY в app), `deploy.sh`, `.github/workflows/*`, `core/access-and-integrations.md`.

## [2026-07-01] Observability = PostHog (без Sentry на старте) — ADR-0012
**Решение:** аналитика и ошибки — через **PostHog** (бесплатный тариф: 1M событий/мес, EU-хост `eu.i.posthog.com`
для RU-данных). Лёгкий серверный слой `lib/analytics.ts` (`track`/`captureError`) — no-op без `POSTHOG_KEY`.
Sentry отдельно НЕ заводим на старте (PostHog free покрывает и ошибки).
**Почему:** один бесплатный инструмент вместо двух; события + ошибки в одном месте; включается ключом без правок кода.
**Влияет на:** `lib/analytics.ts`, `app/actions.ts`, `app/api/p/[id]/generate`, `.env.example`, `core/access-and-integrations.md`.

## [2026-07-02] Трейсинг AI-пайплайна (подробный лог + «номер генерации») — ADR-0013
**Решение:** сквозной трейсинг каждого прогона пайплайна. (1) **Захват — в слое провайдеров:**
`getImageProvider/getVisionProvider` оборачиваются инструментированно (`lib/providers/traced.ts`) —
любой вызов LLM логирует шаг в активный прогон; прогон открывается в оркестраторе через `runWithTrace`,
контекст — AsyncLocalStorage. Так лог не отстаёт при смене модели/промпта/шага (новый вызов логирует
себя сам). (2) **Данные:** таблицы `generation_runs` (seq = человекочитаемый номер генерации через
sequence), `generation_steps` (модель/промпт/настройки/вход-выход/время/стоимость/ошибка),
`generation_assets` (картинки — **байты на диске/томе**, в БД только ссылка; base64 в БД не пишем).
(3) **Версионирование:** реестр промптов `lib/prompts/registry.ts` (id+version) и реестр пайплайнов
`lib/pipelines/registry.ts` (сценарий = шаги+модель+промпт) — точка расширения под Nano→GPT→ControlNet/SD.
(4) **Сжатие:** сервис **imagor** (Go+libvips, internal-only, как в SUP2 ADR D18) уменьшает фото
(`fit-in 1536`, webp q80) ПЕРЕД LLM → экономия токенов; сохранённый input-ассет = то, что реально ушло.
(5) **Разбор:** скилл `/trace` + `pnpm trace <N>` + admin-роут `/api/trace/<N>` (краткий+подробный+фото);
кнопка «Сообщить о проблеме» (`/api/trace/report`) для пользователей. Ретеншн `TRACE_RETENTION_DAYS=90`.
**Почему:** владельцу нужны сотни тестов пайплайна (сравнение моделей/промптов/настроек по номеру),
быстрый разбор ошибок и пользовательские жалобы по номеру генерации; логирование не должно требовать
переписывания при эволюции пайплайна. **Альтернативы (отклонены):** сторонний LLM-observability (Langfuse
и т.п.) — лишняя внешняя зависимость/данные вне периметра; логирование в каждом модуле вручную — рассинхрон
при смене пайплайна. **Влияет на:** `lib/trace/*`, `lib/providers/*`, `lib/prompts/`, `lib/pipelines/`,
`lib/images/compress.ts`, `db/schema.ts`, `tools/migrate.mjs`, `db/init/003-traces.sql`, `app/api/trace/*`,
`app/p/[id]/preview`, `docker-compose.yml` (imagor+том), `.claude/rules/pipeline-tracing.md`,
`core/observability-tracing.md`. **Решение владельца:** диск для фото, все фазы сразу, ретеншн 90 дн.

## [2026-07-02] Пивот бизнес-модели v0.2 → v0.3 (affiliate-first freemium) — ADR-0014
**Решение:** принят **Master Project Brief v0.3** (`docs/master-brief-v0.3.md`) как мастер-документ с
приоритетом выше v0.2. Ключевые сдвиги: (1) **freemium-граница** — бесплатно полноценный подбор **до N
(3–5) реальных товаров из фидов с открытыми реф-ссылками** (двигатель affiliate, доход ~3%, сеть Гдеслон);
платно — «комната целиком» (все элементы) + сервисный слой (Cost Engine, чек-лист, план, PDF, workspace).
Товары/ссылки БОЛЬШЕ НЕ за paywall. (2) **Три ступени монетизации складываются:** affiliate → paid room pack
(розница ~2 990 ₽; дизайнеры-B2B ~990 ₽/комната от 10) → застройщики «квартира+ремонт в ипотеку» (~5% с чека,
vision/Stage 4). (3) **Product matching** = «генерация → поиск похожего в большой базе фидов по embeddings»
(pgvector), метрика similarity с 1-го дня. (4) **Рынок РФ→UK, locale-agnostic** (валюта/фиды/сети/rates через
абстракции). (5) **Канал** — дешёвый инфо-трафик DIY-кластера (~10 ₽ CPC) + SEO (SSR/SSG); **главная
falsifiable-гипотеза** юнит-экономики (1 покупка/~45 визитов, чек ~30 000 ₽, доход ≈ 2× CAC), kill-критерий
в Stage 0. (6) **Второй вход** «найти похожую мебель по фото» (без генерации). (7) **Сегмент F** — дизайнеры
(B2B-опт, batch/выгрузки, Stage 1.5).
**Уточнения владельца (2026-07-02) — граница free/paid = уровень «что сделать с комнатой» (3 варианта):**
1. **«Освежить без ремонта» — БЕСПЛАТНО:** визуализация + подбор до 3 реальных предметов мебели по
   визуализации (открыто, реф-ссылки, можно заменить). Без материалов/сметы/плана.
2. **«Недорого обновить» — ПЛАТНО ~1 490 ₽** (розница; владелец называл ~1000 — параметр): мебель в любом
   количестве + материалы. Без расчёта стоимости ремонта, без чертежей/дизайнера.
3. **«Ремонт под ключ» — ПЛАТНО 9 900 ₽** (гипотеза, рынок сверен 2026-07-02): мебель + материалы +
   гайды + чертежи + **смета (Cost Engine)** + **услуга живого дизайнера**. Замена дизайнера, но в 5–10×
   дешевле (дизайн-проект комнаты в РФ ~45–100 тыс Москва / ~25–50 тыс регионы).
- Реф-ссылки во всех вариантах (affiliate). Материалы подняты в платные Stage 1 (в брифе были Stage 2).
- **Код-долг:** структура `FREE_VISIBLE=3` верна для вар.1; нужно реальные товары из фидов + реф-ссылки
  (сейчас seed), добавить варианты 2/3, согласовать с `interventionLevel`. «Раздать всё бесплатно» — НЕВЕРНО.
- **Postgres self-host подтверждён владельцем** — «Supabase» из брифа не берём (ADR-0001/0002). Конфликт закрыт.
**Почему:** товарная инфраструктура (фиды Гдеслон) + измеримый DIY-спрос делают affiliate реалистичным
первичным потоком; открытые товары максимизируют клики; paid продаёт объём+сервис, а не доступ к ссылкам.
**Альтернативы (отклонены):** v0.2-граница «товары за paywall» — душит affiliate-двигатель; inpainting
реальных товаров в Stage 1 — сложно/дорого, выбран matching по embeddings. **Влияет на:**
`docs/master-brief-v0.3.md` (новый), `source-of-truth.md`, `CLAUDE.md`, `product_brief.md`, `core/market.md`,
`core/user-flow.md`, `core/data-model.md`, `core/access-and-integrations.md`, `project-state.md`, `INDEX.md`;
код (позже): `modules/ideas` (открыть товары+реф-ссылки), `app/p/[id]/preview`+`/paywall`, новый пайплайн фидов
и affiliate-трекинг. **Открытые параметры (тесты):** N (3/5), цена room pack, порог similarity, лимит генераций.

## [2026-07-02] Git-workflow: всегда коммитить+пушить в GitHub — ADR-0015
**Решение:** по указанию владельца — после каждого завершённого изменения кода Claude **сам коммитит и
пушит в GitHub** (`origin` = git@github.com:igortsk123/remlab.git), не дожидаясь отдельной команды «коммить».
**Почему:** владелец не пишет код и хочет, чтобы история и деплой-артефакты всегда были в удалённом репо
(бэкап, авто-деплой через GitHub Actions, ADR-0011), без ручных напоминаний. **Влияет на:** переопределяет
пункт «commit/push только по просьбе» из `.claude/rules/agent-workflow.md` — теперь коммит+пуш это дефолт
завершения работы. Коммиты — с co-author trailer. **Границы:** ветки фич `feature/<area>`; секреты не
коммитим (только `.env` на сервере); разрушительные git-операции (force-push, reset --hard) — по-прежнему
с подтверждением. **Альтернативы (отклонено):** копить локально и пушить по запросу — владелец теряет из виду
состояние и рискует потерять работу.

## [2026-07-11] Пивот концепции v0.4 «Смета-first» — ADR-0016
**Решение:** владелец утвердил новую концепцию продукта целиком: ядро — «Смета-лист» (расчёт
количеств и стоимости ремонта/материалов → сохранённый список с реф-ссылками → комиссия с покупок,
в т.ч. по ссылкам, которые пользователь принёс сам, через deeplink). Два входа: А «калькуляторы
материалов» (~70–90k показов/мес, ответ-числом сразу) и Б «сколько стоит ремонт» (~52k+, вилка
трёх бюджетов). AI-визуализация по фото и мебельный подбор — ступень воронки («как будет
выглядеть»), а не вход; мастера — партнёрский лид после сметы (не свой каталог). Мастер-план —
`plans/MASTER-cost-first.md` (М0–М7); утверждённый пользовательский сценарий — там же.
**Почему:** ценовой спрос на порядок больше AI-дизайнерского (52k+90k против 15–18k) при клике
7–36 ₽ (против 62–194 ₽ у «под ключ»); интент момента покупки материалов монетизируется рефами
с высокой конверсией («он покупает то, что сам выбрал»); чек материалов 50–200 тыс. ₽.
**Альтернативы (отклонены):** пивот в лидген бригад (красный океан: Яндекс Услуги/Профи, чужой
бизнес-профиль); остаться в мебельном AI-дизайне как ядре (мал спрос, гики-туристы в трафике).
**Влияет на:** `CLAUDE.md` (шапка), `project-state.md`, `product_brief.md`, `core/goals.md`,
`core/user-flow.md`, `core/market.md` (пометки пивота, полная переработка — по ходу М-этапов);
ревизия планов: commercial-master-plan и MASTER-roadmap + 8 sub-планов → архив (таблица «Судьба
прежних планов» в мастере); кампании Директа: Этап 2/4 становятся главными посадочными.
`docs/master-brief-v0.3.md` остаётся исторической базой (мебельная часть = ступень М5).

## [2026-07-12] Сквозная навигация по сценариям + разделы-каркасы — ADR-0017

«Посчитать материалы» (`/calc`) и «Сколько стоит ремонт» (`/calc/remont`) + лёгкие ссылки Дизайн

вбок (без «гамбургера»); решение владельца — «все разделы на виду, две кнопки выделить». Добавлены

## [2026-07-31] Количество материала не считаем по молчаливым дефолтам — ADR-0034
**Решение:** количество (рулоны/шт/литры/упаковки) показываем ТОЛЬКО когда параметры материала

фактом. Для плитки это уже было починено 22.07 (`ab49573`, флаг `qtyUnknown`) — решение
распространяет прежнее правило на обои/краску/ламинат. Владелец 31.07: «ничего не нужно писать,

## [2026-08-02] Прод-ядро расстановки: hard-фильтр перед скорингом + beam search — ADR-0052
**Решение:** движок `services/planner-solver/` (Python, shapely+pydantic, БЕЗ ML) строится по схеме
кандидаты → hard-фильтр → beam search (луч 20 × 8 кандидатов) → скоринг по весам → локальное
уточнение → top-K с объяснениями. Три несущих принципа: (1) **клиренс вычитается из свободного
полигона вместе со следом** (механика ProcTHOR) — «перед диваном» физически некуда поставить
кресло; (2) **hard-правила отсекают кандидата ДО скоринга** (границы, коллизии, дуга двери,
радиатор, окно, диван∥ТВ, хранение только у стены, целостность зоны, линия взгляда на ТВ);
(3) **порядок «ТВ первым»** — тумба самая ограниченная и задаёт ось зоны, диван строится
напротив неё (приоритет ProcTHOR: Television раньше Sofa).
**Почему:** жадный DFS + пост-фиксы давал ~80–85% чистых раскладок и разваливал зону; правила
как пост-проверки ловили дефект, но не мешали его создать. Замер после: 60 тестов, 1.5–2.2 с на
гостиную из 6 предметов, ≥2 валидных РАЗНЫХ варианта, детерминизм байт-в-байт.
**Побочно:** канон правил `occupancy.json` перенесён из gitignore'нутого `tools/scout/` в
`services/planner-solver/rules/` — теперь в git и в CI (был риск потерять источник истины).
Веса скоринга — `services/planner-solver/rules/weights.json` (относительная важность термов из Infinigen, таргеты наши).
**Влияет на:** scout-конвейер (Э7: переключение флагом `--engine beam`); витрина; план
[[prod-layout-engine]]. Clean-room выдержан: стороннего кода не скопировано, атрибуция —
`services/planner-solver/LICENSES/THIRD_PARTY_NOTICES.md`.

## [2026-08-04] Панорама — единственный источник кадров комплекта — ADR-0056
**Решение:** на комплект делается ОДНА генерация — цилиндрическая панорама от двери
(камера `P`, 140°×~63°, 2048×1024 + апскейл ×2). Все обычные кадры (налево / прямо / направо)
не генерируются, а ВЫРЕЗАЮТСЯ из неё с правильной перспективой

## [2026-08-04] Товары вклеиваются геометрией, нейросеть — только на согласование — ADR-0057

**Решение:** товар, которому плоская вырезка врёт (камера видит его сбоку), превращается в 3D
один раз: `fal-ai/trellis` (фото → GLB, ~56 с, ≈$0.02, кэш на SKU), а КРУТИМ и рендерим модель

## [2026-08-05] Приёмка коллажа как ворота перед оплатой генерации — ADR-0061
**Решение:** конвейер сам сверяет каждый предмет коллажа с аналитическим эталоном
(`tools/scout/collage_audit.py`): ширина и высота относительно места, отрыв от пола, смещение
центра. Ненулевой код возврата = «не отправлять». Считается локально, стоит 0 ₽.
**Почему:** брак ловил глазами человек, и это не масштабируется (владелец: «надо системно, чтобы
конвейер делал это без тебя»). Приёмка нашла шесть системных причин брака, которые я бы искал
руками: пропорция карточки сажала широкие предметы на 60% места; ковёр закрашивал ножки мебели,
стоящей на нём; пол перекрывал низ низкой мебели; тонкие детали терялись при выборке;
камера вставала внутрь мебели; мебель торчала за стену.
**Как считается:** эталон — прямоугольник по следу предмета, шириной в видимую ширину следа и
высотой в видимую высоту (габарит + завал крышки под углом взгляда). Предметы, закрытые другими
или обрезанные краем кадра, из числовой проверки исключаются.
**Влияет на:** `collage_audit.py`, `viz_build.py`, `viz_paste.py` (карта «что куда легло»).

## [2026-08-05] 3D подставляется только там, где фото провалило приёмку — ADR-0062
**Решение:** по умолчанию в коллаж идёт ФОТОГРАФИЯ товара. 3D-рендер подставляется, только если
(1) предмет напольный, (2) он провалил приёмку кадра или развёрнут к камере ≥30°, и (3) сама
модель прошла самопроверку. Оркестрация — `viz_build.py`: фото → приёмка → 3D непрошедшим → приёмка.
**Почему:** фотография — настоящий вид товара, наша главная ценность (решение владельца: «для
всего остального вставлять как есть»). Подвесное (люстра, бра) не моделим никогда: генератор не
восстанавливает тонкие рожки и стекло — выходит мятая железка. Мелочь на мебели (ваза, лампа)
тоже не моделим.
**Самопроверка модели** (`mesh_make.mesh_trusted`): рендер под ракурсом карточки обязан совпасть
с её силуэтом (≥60% IoU по лучшему из правдоподобных ракурсов) И по среднему цвету (расхождение
≤55). Только силуэта мало: диван с белой обивкой прошёл на 88% и приехал с чёрной спинкой.
**Влияет на:** `mesh_need.py`, `mesh_make.py`, `viz_paste.mesh_source`, `viz_build.py`.

## [2026-08-05] Фотореалистичная основа комнаты по нашим картам — ADR-0063
**Решение:** база под вклейку — не clay-рендер, а фотореалистичная ПУСТАЯ комната, сгенерированная
`fal-ai/sdxl-controlnet-union` по нашим картам глубины, сегментации и нормалей (`shell_make.py`).
Товары ставятся поверх своими фотографиями и 3D-рендерами. Основа кэшируется ПО КОМНАТЕ И ТОЧКЕ
СЪЁМКИ — она не зависит от набора мебели (≈2 ₽, ~100 с, один раз на 126 комплектов в 7 метражах).
**Почему:** проверено тремя опытами на комплекте 21. (а) Основа по картам: геометрия совпала с
планом, приёмка вклейки 9 из 10. (б) Черновик СРАЗУ с мебелью → GPT: реализм отличный, но

## [2026-08-05] Подбор сетов: геометрия — ограничение, эстетика — только среди допустимых — ADR-0064
**Решение:** пропорции и функция товара проверяются ЖЁСТКО и ДО скоринга. Товар вне допустимых
рамок выбывает; попадание в предпочтительный диапазон даёт бонус уже среди прошедших.
Одна точка правды — `tools/scout/proportions.json` (9 правил с источниками) и `proportions.py`.
**Почему:** раньше пропорции давали ±1,5 балла внутри общей суммы, а стиль и палитра +2…+4, и
габаритный промах перекрывался. Замер по 126 сетам ДО: ковёр мал во всех 126, столик в 107, пуф в
88, высота столика в 79, высота пуфа в 72, диван к стене в 61. ПОСЛЕ: ноль нарушений.
**Основание:** Design-MLLM (arXiv 2603.13312) и FlairGPT (CGF 2025, arXiv 2501.04648) —
допустимость проверяется программно, эстетика оценивает только допустимых.
**Детали:** у углового дивана правило считается к ПРЯМОЙ секции (`corner_arm_ratio` 0,41), высота
сиденья = 48% общей высоты (заводской чертёж 88/42).
**Влияет на:** `compose2.py`, `proportions.*`, `item_function.py`, `proportion_check.py`.

## [2026-08-05] Функциональный подтип вместо роли-категории — ADR-0065
**Решение:** у многозначных ролей определяется `functional_subtype`: пуф (подставка / доп. сиденье
/ пуф-стол / хранение / банкетка), комод (хранение / ТВ-опора / консоль), стеллаж (перегородка /

размеров. Неопределённый подтип в сет НЕ пускается — угадывать нельзя.

креслами-мешками; отсюда «пуф размером со столик» (владелец). Пуф-стол при этом законен и

**Влияет на:** `item_function.py`, `compose2.py`, оба плана P0.

## [2026-08-05] Ковёр: две схемы или ничего — ADR-0066
**Решение:** ковёр кладётся по схеме «передние ножки» (от 1,15 длины дивана) либо «только под
столиком» (от 1,15 длины столика, берётся наибольший подходящий). Не проходит ни одна — ковра в
сете нет, в лог пишется дыра каталога. Схема хранится в товаре (`rug_scheme`).
**Почему:** правило владельца «лучше не достроить, чем достроить неверно». Ковров для гостиной в
каталоге НЕТ: 609 товаров со словами ковёр/коврик/палас/дорожка во всех 7 фидах — ванные,
придверные и дорожки, крупнейший 100×150 см. Для дивана 230 нужен от 265.
**Результат:** 69 сетов из 126 получили ковёр под столик, 57 остались без ковра.
**Влияет на:** `compose2.py` (ветка ковра), `proportions.json` (правило `rug_len_vs_table`).

## [2026-08-05] Модели обогащения: цены из первоисточника, не «дешёвая mini» — ADR-0067

**Решение.** Выбор модели для обогащения каталога фиксируется реестром в
`domain/catalog-enrichment.md` с ценой и ДАТОЙ проверки на официальной странице

## [2026-08-05] Обогащение хранится отдельно от товара, дельта — по хешам — ADR-0068

**Решение.** Обогащённые признаки живут в отдельной таблице `product_enrichment`, а не в колонках
`products`: фид перезаписывает только операционные поля (цена, наличие, ссылка), обогащение не
трогается никогда. Что изменилось, определяют раздельные хеши: `commercial` (цена+наличие+ссылка),
`text` (название+описание), `geometry` (нормализованные размеры), `image`/`perceptual` (байты и
визуальный отпечаток картинки). ИИ запускается только при смене трёх последних. Вместо булева
`in_stock` — статусы `active / out_of_stock / missing / archived`; исчезнувший товар
деактивируется, но обогащение сохраняется. Перцептивный хеш — только триггер: «тот же товар»
подтверждается визуальным эмбеддингом, иначе одна модель мебели в разных цветах склеится.

**Почему.** Сейчас признак изменения — сам факт присутствия в фиде, поэтому решение
«пересчитывать или нет» принимается грубо, а вернувшийся через месяц товар обрабатывается заново.
Магазин меняет URL картинки, не меняя картинку, — без перцептивного хеша мы платим за повторный
анализ того же изображения.

**Влияет на.** `load3.py`, новые `phash.py` и `sets_incremental.py`, миграция `db/init/`,
план `MASTER-catalog-ai` К1.

## [2026-08-06] Роль товара — из дерева категорий фида, не из регекса по названию — ADR-0070

**Решение.** Роль определяется КАТЕГОРИЕЙ из фида (`products.cat_role`, карта

## [2026-08-06] Стиль товара — сумма наблюдаемых признаков с рангами, а не ярлык от модели — ADR-0071

**Решение.** Модель отвечает на вопрос «что видишь» (признаки под категорию, `style-matrix.json`),
а стиль собирается правилами: **маркер 3.0 / поддержка 1.5 / фон 0.6**, вето обнуляет стиль.
Три защиты: ранг понижается по частоте признака ВНУТРИ категории, «свой маркер» категории не
опускается ниже поддержки, нормировка идёт внутри товара. Если ни один собственный признак
категории не сработал в плюс — товар **нейтральный**, победитель не назначается.
Одна таблица `style-matrix.json` — источник и для вопросов модели, и для весов.

**Почему.** Прямая классификация стиля по одному предмету даёт 0.41–0.49 точности на эталонном
датасете Bonn Furniture Styles (90 298 фото, 17 стилей, arXiv 1812.03570); признаковый разбор —
принятый и объяснимый подход (ACM TIST 10.1145/3065951, arXiv 2412.13947). Ошибку в «ножки
конические» видно глазами, ошибку в «сканди 0.8» — нет. Замер по 671 тестовой карточке и полному
прогону 23 028 товаров: минимализм 49%, сканди 21%, современный 12%, неоклассика 11%, лофт 4%,
джапанди 3%, нейтральных 11%.

**Влияет на.** `style_rules.json`, `style_attrs.py`, `role_prompt.py`, `matrix_build.py`,
`enrich_bridge.py`, подбор комплектов.

## [2026-08-06] Всё платное — сперва пробной партией, потом массово — ADR-0072

**Решение.** Любая массовая операция, которая стоит денег, идёт этапами: скачать вход в кэш →
пробная партия (сотни позиций, ПОРОВНУ ИЗ ВСЕХ категорий) → проверка осмысленности результата →
массовый прогон с ограниченной параллельностью. Массовый шаг обязан печатать прогресс и счётчик
отказов; молчаливый `except` в коде, который тратит деньги, запрещён. Предохранитель: качество
входа ниже порога (картинок < 90%) — прогон не отправляется вовсе.

**Почему.** Правило владельца 2026-08-06 после потери ≈6–8 $: первый полный прогон обогащения
ушёл в модель ВСЛЕПУЮ — CDN магазина отдаёт 403 при 24 потоках, картинки не скачивались, и
фото получили 287 запросов из 2000. Молчаливый `except` это скрыл, ошибка нашлась только по
странному результату (87% «нейтральных»).

**Влияет на.** `enrich.py` (этапы `--download`, `--limit`, стоп-предохранитель), `golden_label.py`
(дисковый кэш картинок, ретраи, счётчик), любые будущие платные прогоны.

## [2026-08-06] Батч-дисциплина: отправка заблокирована при незабранном пакете — ADR-0073

**Решение.** Единая точка отправки пакетов (`run_batch` в `enrich.py`) отказывается отправлять,

## [2026-08-08] Зоны-first: состав и расстановка от посадочных групп и полезной площади — ADR-0074

**Решение.** Компоновка перестроена с «предмет-first» на «зоны-first» ([[MASTER-zones-first]]):
(1) полезная площадь = контур − дверные дуги − радиаторы − входной резерв (`services/planner-solver/planner/zones.py:
usable_polygon`); (2) посадочная ГРУППА выбирается по ней из библиотеки 10 групп с reference-футпринтами
(`services/planner-solver/rules/zones.json`, Dimensions + оба верифицированных документа владельца) и диктует состав

## [2026-08-08] Обеденная группа геометрически возможна; новые роли по исследованию рефери — ADR-0078

**Решение.** (1) Члены одной функциональной группы (стол↔стулья, диван↔кресло/пуф) НЕ блокируют
зоны подхода друг друга и в валидаторе тоже — `check_access` получил group-исключение

(2) Якоря стульев — к КРОМКЕ стола (+2 см, не «под стол» −8: `_Fitter` требует полного
попадания в свободный полигон — прежние якоря браковались все); длинная сторона стола даёт два
места симметрично (`candidates.py`) — «стулья выровнены» (вердикт владельца).
(3) Экземпляры ролей («стул 2..4», «кресло 2») нормализованы через `base_role` в
candidates (якоря, group_of), clearances (clearance_for), geometry (free_space
ignore_access_of) — раньше экземпляры не получали ни якорей, ни клиренсов, ни групп.
(4) Обеденная за спинкой дивана ЛЕГАЛЬНА (рефери: floating sofa — разделитель зон): стол/стул
убраны из DEAD_BEHIND_ROLES; разговорную зону охраняет DINING_IN_LIVING_ZONE, проходы — циркуляция.
(5) По исследованию рефери (план `plans/inventory-additions.md`): SERVICE_SURFACE (S1, 48-й код,
`check_service_surface`) — у каждого primary-места поверхность ≤75 см, coverage-семантика;
«приставной» = subtype узкого столика ≤55 см (typical-dims, ярус optional, compose A2);
«картина» = роль категорий 112923:4948–4950 + composition.non_floor + viz-промпт (числа
wall_art в occupancy были готовы, объект не был подключён к конвейеру); спеки
side_table/console/service_surface — `rules/zones.json group_scheme`; flex_seat семантика
(пуф/банкетка — временная посадка). Реестр: 48 кодов — H0×9/H1×26/S1×10/S2×3.
**Почему.** Вердикт владельца 08.08 («минимум 2 стула, выровнены») был нереализуем из-за (1)-(3);
дроп обеденной 107/252 на приёмке вскрыл цепочку. Исследование рефери подтверждено фактами
каталога (роли приставной/консоль отсутствуют — subtype-путь; картины были вне 76 категорий).
**Влияет на.** validate/candidates/clearances/geometry, приёмку (перегон после фиксов),

## ADR-0088 — Шаблон = паспорт + машинные инварианты; конверт применяется при подборе (2026-08-12)
**Решение.** Шаблон зоны — ОБЪЕКТ с паспортом (`services/planner-solver/rules/templates.json`):
состав, приоритет схем с обоснованием, предусловия, инварианты, пруфы. Инварианты проверяет
машина на СБОРКЕ схемы (`services/planner-solver/planner/invariants.py`, вызов —
`template._valid`): нет самопересечений · ножки посадочных на ковре · столик в досягаемости ·
в зоне ≥2 предмета · габарит == SKU. Не прошла — схема недействительна, каскад берёт следующую.
**Конверт −20/+10 применяется ТОЛЬКО при подборе товара в сет** (`tools/scout/compose2.py`,
жёсткий фильтр для ВСЕХ слотов с идеалом); солверу менять габарит SKU ЗАПРЕЩЕНО — расхождение
роняет прогон (`zones.solve_zoned` → `phantom_dimensions`).
**Почему.** Владелец: «почему солвер систематически нарушает правила шаблона?». Разбор: правило
ковра было реализовано 8 раз независимо, 2/3 чисел стояли без пруфа, 33% посадочных не доставали
до ковра, солвер ужимал ковёр/столик на 10–20% «чтобы влезло» (выдуманная мебель = неверная смета).
Архитектура «шаблон = жёсткое тело» держалась на ОДНОМ выходе из семи: шесть `return` в
`build_block` шли мимо проверки.
**Прослеживаемость.** У каждого размещения `tpl_id`/`tpl_version` + `_set_hash` в артефакте;
предмет без `tpl_id` при `LAYOUT_ONLY_TEMPLATES=1` — ошибка. Сторож —
`services/planner-solver/tests/test_template_integrity.py` (5 проверок), пруфы чисел —
`tools/scout/rules_audit.py` (RULE-NO-PROOF: было 70, стало 0 в наших файлах).
**Влияет на.** [[layout]], `template.py`, `zones.py`, `compose2.py`, будущие волны шаблонов.

## ADR-0089 — Сет собирается ПОД шаблоны; приоритет зон и фокус-стена (2026-08-12)
**Решение.** (1) Напольная роль в сете обязана быть слотом хотя бы одного шаблона
(`templates.json` → `floor_roles_claimable`); иначе вылетает из состава. Причина: владелец
«шаблона на два стула нет — как они попали в сет?» (27 из 126 сетов уезжали со стульями без
стола). (2) Приоритет зон: посадка → медиа → столовая → хранение; **медиа приоритетнее
хранения** — стена напротив посадки резервируется за носителем ТВ, пока он не поставлен
(`zones._tv_wall_reserved`). (3) За спинкой ОТОДВИНУТОГО дивана (>90 см до стены) полоса
держится за СТОЛОВОЙ (веб-канон RU: вторая зона гостиной — столовая/бар). (4) Хранение:
≤2 предметов в зоне, ≤2 зон на комнату, вторая — на другой стене.
**Медиа-стенка** — свой паспорт `media_wall`: 2.5–4 м стены, глубина 30–43, центр экрана
105–115 см, компактная ≤240 для комнат ≤20 м²; несёт и ТВ, и хранение, флангов не имеет.
**Влияет на.** [[layout]], `zones.py`, `template.py`, `compose2.py`.

## ADR-0090 — Дверь: четверть круга у петли + проход 76 см (2026-08-12)

## ADR-0091 — Дизайнерский порядок: фокус важнее позиции, гейт деградации, fill — диагностика (2026-08-12)
**Решение.** Расстановка следует порядку дизайнера (свод владельца по его ресёрчу):
фокус-стена → диван → циркуляция → носитель ТВ → ковёр/столик → доп. посадка → хранение →
свет → декор. Реализация БЕЗ разрушения правила «ставим только шаблоны»:
- **Фокус — три круга в `place_template`** (`_FOCUS_LEVEL` 2→1→0): позиция схемы посадки
  принимается, только если носителю ТВ есть место В ОСИ взгляда (≤40 см); нет — любое чистое
  место; нет и его — посадка без требования (лучше зона, чем пустая сцена).
- **Гейт деградации** на вторичных зонах (`zones.py` + `services/planner-solver/planner/quality.py`): зона принимается,
  только если не ухудшила маршрут (≥75 см от двери), не нарастила «щели» уже 45 см и не сбила
  фокус. «Нет хорошего места — лучше не ставить» вместо «впихнуть максимум».
- **fill 30–45% понижен до ДИАГНОСТИКИ** (отмена части прежнего решения): цель заполнения
  рождала кашпо в щели и кресло, портящее проход.
- Ковёр и столик ОСТАЮТСЯ внутри шаблона посадки (уточнение владельца) — блок двигается целиком.
**Замер 12.08 (252 сцены):** чисто 252/252 · медиа-зона 223 (было 133 утром) · смещение носителя
от оси: медиана 27 см (было 68), >40 см в 55 из 223 (было 163 из 231) · маршрут ≥70 см во всех
сценах, медиана 120 · хранение 242 · столовая 72. Сторожа — 8 тестов
(`services/planner-solver/tests/test_template_integrity.py`), пороги только вверх.
**Влияет на.** [[layout]], `template.py`, `zones.py`, `quality.py`, `services/planner-solver/rules/zones.json`
(`quality_gate`), приёмка.

## ADR-0092 — Режимная триада small/transitional/large; машина остатка R; пары ТВ↔диван (2026-08-13)
**Решение.** Расстановка режимная: `planner/room_map.room_mode` (small ≤18 м² или короткая
сторона ≤350; large ≥25 м² или ось ТВ ≥500 или длина ≥600; между — transitional) — единый
источник, двойники удалены. Large: пристенный диван при V_wall>1.5×V проигрывает floating
(«ТВ→5 м пустоты→диван» не существует); остаток R за спинкой решается машиной из паспорта
`residual_behind_sofa` (<90 ничего / ≤150 проход+узкое хранение / ≤255 стена / ≥260 столовая
обязательна). Small: медиа+посадка — ОДНО ядро (сторож связности ≤420 см), циркуляция — главный
вес WallScore, столовая масштабируется (4→2→складной), хранение вертикальное, уровни

(`services/planner-solver/planner/tv_sofa.py`, WallScore из паспорта, длина стены — tie-breaker) + карта ограничений
(`services/planner-solver/planner/room_map.py`: участки стен, маршруты старше мебели).
**Все правила — в терминах шаблонов**: единица — неделимый паспорт; спуск/деградация — только
сменой шаблона; 12 сторожей в CI. Свод и пруфы — планы large-room-mode / small-room-mode
(completed) и MASTER-tv-sofa-pair.
**Влияет на.** [[layout]], room_map/tv_sofa/zones/template/invariants, services/planner-solver/rules/templates.json.
