# Уроки: распознавание плана и проба агента

- **594 (10.11)** — лист C на /try дважды падал `pipeline_error` через 7–9 мин с ПУСТЫМ `pipeline.log`. Причина — segfault OpenCV:
  `cv2.connectedComponents` от массива нулевого размера роняет процесс (rc=139), а не бросает исключение (OpenCV 5.0: так же
  `connectedComponentsWithStats`; `dilate/erode/morphologyEx/warpAffine` дают `cv2.error`). Пустое окно — подпись без своего контура отдана ближайшему
  контуру без предела расстояния (`tools/floorplan/bench.py` owner) и легла за краем панели. Лог пуст, потому что вывод `pipeline.py` буферизован.
  Правило: окно/срез перед OpenCV — проверка `fpcore.empty_img`; «упал без вывода» — повторить с `PYTHONUNBUFFERED=1 python -X faulthandler`. (T-20261110-06)
- **595 (10.11)** — наш собственный пример на /try (`public/try/plan.jpg`) разбирался в 1 комнату 346 м²: `bench.auto_cfg` выбрал «синюю» маску стен, потому
  что синего ≥ 1 % — а это тонкие обводки выделенных комнат и «Furnish →» (снимок нашего же интерфейса), настоящие стены тёмные и втрое толще.
  Правило: выбор маски по цвету сверять с толщиной (тонкая цветная графика ≠ стены); пример для пользователя — план без подсветки интерфейса;
  «помогла перерисовка» — сперва выяснить, ЧТО она убрала. (T-20261110-08)
- **596 (10.11)** — исход «гостиной нет» закрывал задание «серым туром», но страница тура закрепляется только при публикации версии данных — у серого
  тура её нет, и агент навсегда видел белую страницу «not ready». Тесты проходили: каждый путь проверялся отдельно, сквозной прогон по неудачному
  исходу не делали. Правило: у каждого исхода задания — открываемая страница; сквозной /try ведущий гоняет и на плане, который распознаётся плохо. (T-20261110-07)
- **597 (10.11)** — перерисовка плана нейросетью (gemini-3.1-flash-image) честно держит стены, но переписывает текст: выдуманная площадь (795→705 м²),
  стёртые подписи. Правило: из сгенерированной картинки брать только геометрию; текст и числа — только с оригинала (ADR-0364).
- **598 (11.11)** — «21 лист байт в байт» сравнивал два снимка уже с правкой T-38 и пропустил потерю настоящих дверей на английских планах
  (rgK 162 → 66). Правило: регресс разбора — по комнатам (двери, окна, ядро) и только против кода ДО правки (`tools/floorplan/regress.py cmp`).
- **599 (11.11)** — правки страницы /demo не видны в турах до публикации витрины и перевыпуска (тур закреплён за релизом витрины,
  `lib/trial/tour-bundle.ts:ensureJobRelease`); правки разбора плана не доходят до уже загруженных туров вовсе (пересборка берёт сохранённый разбор).
- **600 (11.11)** — ранний запрос данных (T-40) на медленной сети отвечал раньше, чем дочитана разметка, запуск падал на функциях нижних
  `<script>`, `.catch` глотал: /demo без фото 20/20 на 2 Мбит/с. Правило: пробы страниц — и на медленной сети (2/150, 8/80) с ловлей ошибок
  внутри `.catch`; prepush не гоняет `services/planner-solver/tests` — перед вливанием правок 3D/проёмов гонять их руками.
- **601 (10.11)** — на листах с тонкими перегородками (8 px при средней толщине стен 34 px) настоящие двери глубиной 8–11 px считались
  «зазубриной» (`tools/floorplan/fpcore.py:is_notch` сравнивал с ОБЩЕЙ толщиной) → стена → «нет входа». Правило: порог проёма — от
  локальной толщины у торцов и по сквозному разрыву (`fpcore.passes_through`, `thin_partition_t`); мебель без найденной двери не ставить. (T-33, T-36)
- **602 (10.11)** — ответ VLM `panels` по большому листу оборвался по лимиту (`finish: length`, рассуждение съело 7952 из 8284 токенов), а
  `vlm.parse` молча «починил» JSON — выжил один этаж из трёх. Правило: обрыв — повтор с меньшим effort и флаг `vlm_truncated:<вид>`
  (`pipeline.py:_retry_truncated`), оборванный ответ не использовать; этажи делить по подписям этажей, не по контурам. (T-27)
- **603 (10.11)** — строка объявления «Bedroom 1 - 3,290.0mm x 3,754.0mm - 10' 10" x 12' 4"» не читалась: футы брались, мм с разделителем
  тысяч уходили в имя → 0 из 5 сопоставлено → масштаб по толщине стены → площади ×1/3. Правило: парсер объявлений — мм/см/м главнее
  футов, синонимы комнат, строго один к одному (`tools/floorplan/listing.py`); сквозной /try — на настоящих объявлениях. (T-29)
- **604 (11.11)** — id задания на «-» (base64url, ~1 из 64) ронял разбор: `--job-id`, `jid` раздельно → argparse «expected one argument»;
  «ceiling» без числа («Floor to ceiling tiles») брал число следующей строки → потолок 4,45 м. Правило: id в аргументах — `--job-id=<id>`;
  число — только из той же фразы и в пределах (2,2–4,0 м, `listing.py:ceiling_height`). (T-04, T-07)
- **605 (11.11)** — проём в нишу лестницы стал «окном»: правило «окно — только на наружной стене» смотрело `g.exterior`, а ниша, открытая к
  краю листа, по нему наружная. Правило: окно со стрелкой открывания → дверь (`FP_ARROW_WIN`), решать по стрелке, а не по замкнутости. (T-11)
- **606 (11.11)** — кэш регресса разбора с ключом `regress.code_sha` по одним `tools/floorplan/*.py` выдал бы старый результат после правки
  импортов scout/ops или окружения. Правило: ключ кэша — весь код снимка + содержимое листа и объявления + VLM-кэш + окружение + интерпретатор. (T-18, Codex)
- **607 (10–11.11)** — «тур грузится медленно» при быстром сервере: в данных `cams: []`, страница подбирала ракурсы на главном потоке
  (до 16 с, кнопки не отвечают); второй раз — шаг ракурсов 140 с не уложился в `CAMS_TIMEOUT` 120. Правило: замер — долгие задачи
  (`PerformanceObserver longtask`, профиль CDP), а не время `load`; ракурсы — на сервере параллельно (`tools/scout/cams_par.py`). (T-32, T-21, T-23)
- **608 (11.11)** — правка Python воркера влита, а воркер DEV жил на коде 11:48 → пустой `confirm` давал `no_match`. Вливание не
  перезапускает `remlab-trial-worker`; `reissue.py` без окружения воркера падает «нет TRIAL_WORKER_TOKEN». Правило: после вливания
  `tools/scout/trial*`/`tools/floorplan` при пустой очереди — `systemctl --user restart remlab-trial-worker`; перевыпуск — после
  `set -a; . ~/.config/remlab/env; set +a`. (T-19/2)
