### из «Уроки 396–399 (04.09, работа над ошибками пула)»

**399. `pkill -f` снова убил обёртку (04.09, 4-й раз).** В тесте приёмника — `pkill -f receiver.py`
→ exit 144, харнесс убит. Правило стоит в памяти с 10.08 и всё равно сработало «на автомате».
Убивать только по PID из `ss -ltnp`/`ps -eo pid,comm`; сам факт повторения — повод не писать
`pkill -f` даже в одноразовых командах.

**399-бис. Мёртвый Bash после `pkill` — не обязательно последствие `pkill`.** Вечером 04.09
оболочка отвечала `Exit code 1` без вывода на ЛЮБУЮ команду (включая `/bin/echo` и `true`), и у
субагентов тоже. Я приписал это уроку 399 и советовал владельцу перезапускать сессию — не
помогло ни `--resume`, ни Reload Window, ни удаление `~/.claude/shell-snapshots/`. Настоящая
причина — **`EDQUOT` (исчерпана квота ФС) на служебном каталоге сессии**: bash не может записать
свой снимок и падает до исполнения команды. Диагноз занимает одну попытку — записать любой файл
в scratchpad инструментом Write: `EDQUOT` ловится там, где Bash не даёт вообще никакого текста.
Новая сессия НЕ лечит, лечит освобождение места (`/tmp` — tmpfs ~788 МБ, см. инцидент 01.08).
Класс ошибки: одинаковый симптом («ничего не работает после моей ошибки») приписан ближайшему
подозреваемому вместо проверки — при этом безобиднее было бы сперва измерить, чем каяться.

### из «Уроки 400–404 (04.09, вечер — тарифы, автостарт, пересадка)»

**407. Гард, написанный по шаблону команды, ловит рассказ о команде.** PreToolUse-хук, блокирующий
`pkill -f`, заблокировал `git commit` — потому что этот шаблон был в ТЕКСТЕ сообщения коммита,
внутри heredoc. Проверять надо то, что исполнится: перед сопоставлением вырезать тела heredoc и
строки в кавычках (`tools/hooks/guard-bash.mjs`, тест `guard-bash.test.mjs`).

**409. Красный автодеплой отключает страховку молча.** «Deploy prod» падал 4 суток на каталожной
миграции в `db/init`, но падал ПОСЛЕ `compose up -d` — образ выкатывался, прод не отставал, и
внешне всё было живо. При этом GitHub пропускает шаги после упавшего: шаг «Smoke + откат» не
выполнялся ни разу, то есть авто-откат был выключен и об этом не сообщал никто. Провал шага
деплоя = провал ВСЕЙ страховки; проверку живости прода вешать на `!cancelled()`, а не на успех
предыдущего шага.

**410. Файл, удалённый из репозитория, продолжает жить на сервере.** Каталог `db/init`
доставляется `scp`-ом и применяется на проде глобом целиком. Перенос лишних миграций одним
`git mv` НЕ починил бы деплой: их копии остались бы на сервере и падали дальше (находка Codex,
проверена: `ls /opt/remlab/db/init/` показывал 001–009 после переноса в репо). Каталог, который
принадлежит репозиторию, синхронизировать только с удалением (`rsync --delete`).

**411. Цель отката, которую никто не проверял, протухает.** `docker tag ${IMAGE}:latest
remlab-app:prev` не срабатывало ни разу: сервер тянет образ по SHA, локального `:latest` у него
нет, а ошибку глушило `|| true`. `remlab-app:prev` оставался образом от 22.07 — «откат» вернул бы
прод на 6 недель назад. Цель отката брать по image ID реально работающего контейнера и проверять
её так же, как сам деплой.

**412. Smoke по коду 200 подтверждает чужой успех.** При сорванном выкате сайт отвечает 200 на
СТАРОЙ версии, и smoke по одному HTTP-коду отмечает деплой удачным. Проверять именно целевую
версию (`/api/health` → `version == TARGET_SHA`), иначе проверка измеряет «сайт вообще жив», а не
«выкат состоялся».

**413. `workflow_run` деплоит не тот коммит, что прошёл CI.** Для этого события `github.sha` —
HEAD ветки по умолчанию на момент запуска, а не SHA проверенного прогона; `checkout ref: main` —
тоже движущаяся цель. Пока чинился деплой, успевал прилететь следующий пуш. Брать
`github.event.workflow_run.head_sha` и пронести его одним значением через сборку, активацию и smoke.

### из «уборка памяти 2026-09-05»
**414. Шаг CI и его инструмент — одним коммитом.** Шаг `memory-project-audit` в `ci.yml` уехал на
GitHub чужим push'ем раньше самого инструмента и тестов (они были untracked) → гейт красный у всех,
деплой соседней сессии пропущен, пока файлы не догнали (afbd43b). Правило: workflow-шаг и то, что он
запускает, — в одном коммите; перед push смотреть `git status` на `??` рядом с изменённым workflow.

**416. Zod `optional()` не принимает `null`.** DEV-мост слал `null` в необязательное поле и ловил 400
каждый тик. Правило: пустые ключи не отправлять и/или на границе `.nullable().optional()`.
**417. `psql -t -A -F '\x1f'`: строка из одних пустых полей исчезает** — `str.strip()` считает `\x1f`
пробелом. В проверках — сентинел «-» в каждом поле, не пустая строка.
**419. Шаги минутного тика — независимы, а фоновый исполнитель обязан отчитаться `failed`.** Тик
моста mesh-audit шёл `pull → постеры → push → партия` одной цепочкой; 502 прода во время деплоя
уронил `pull`, и вместе с ним не случились постеры и запуск публикатора, а сам публикатор, упав
на том же 502 до заливки, оставил партию в `requested` без объяснения. Правило: каждый шаг тика —
свой `try/except` с записью в лог; любой сбой фонового исполнителя до/во время работы → явный
статус `failed` с текстом на проде, чтобы кнопку можно было нажать снова (`mesh_audit_sync.py`,
`mesh_audit_publish.py`).
**420. Номер каталожной миграции — по `ls`, не по памяти.** `007-mesh-owner-audit.sql` совпал с уже
лежавшим `007-photo-origin.sql`; `db_migrate.py 007` применил оба (идемпотентно, обошлось).
Правило: перед созданием `tools/scout/NNN-*.sql` смотреть последний номер в каталоге.
**421. Принадлежность к залитой партии — по sku, не по номеру страницы.** Страница приёмки решала
«есть 3D» по формуле «страница → партия»; после снятия четырёх карточек ковров нумерация сдвинулась,
и последние карточки страницы 10 указывали на модели, которых в залитой партии не было (404, владелец
10:47). Правило: публикатор отдаёт состав партии списком sku, страница ищет модель по sku в
активной/уходящей партии; любая перенумерация (снятие, схлопывание вариантов) безопасна.
**422. Исполняющийся bash-скрипт не править на месте.** Bash читает сценарий порциями по смещению в
байтах; правка строки выше текущей позиции (BATCH 200 → 2000 + комментарий) сдвигает смещения, и
интерпретатор может выполнить обрубок строки. 05.09 `mesh_wave_start.sh` был на шаге drain — снял по PID
и перезапустил с готовым файлом. Правило: править копию и подменять атомарно (`mv`) — процесс
дочитает старый inode; переменные, уже присвоенные в начале, правка всё равно не изменит.
**428. `docker compose up -d <сервис>` тянет за собой зависимости — и откатывает прод.** Правка тома
caddy применялась как `docker compose up -d caddy`; из-за `depends_on: [app]` пересоздалось и приложение,
причём БЕЗ `REMLAB_IMAGE` — то есть на дефолтном `remlab-app:latest` шестинедельной давности. Сайт отвечал
200, но страницы последних недель отдавали 404; поймано проверкой соседнего маршрута сразу после правки.
Правило: один сервис — только `up -d --no-deps <сервис>`; боевой образ закреплять в `.env` сервера
(`deploy-remote.sh`, ADR-0202); после любой правки инфраструктуры проверять НЕ ТОЛЬКО изменённый адрес,
но и живость приложения (`/api/health` + любая свежая страница).
**429. Обратные кавычки в двойных кавычках ssh-команды выполняются.** В комментарии, который писался в
`.env`, стояло `` `docker compose up` `` — bash выполнил это как подстановку команды прямо на проде:
контейнеры поднялись в foreground, ssh завис на таймауте, приложение второй раз откатилось на дефолтный
образ. Правило: удалённые команды со спецсимволами — только файлом (`scp` скрипта + `bash файл`), не
инлайном; в инлайне никаких обратных кавычек даже внутри текста комментариев.

## Новые (после 2026-09-05)

**437. Прод без журнала обращений — расследование вслепую.** Когда в контейнере приложения пошли
чужие команды, ответить на вопрос «каким запросом» было НЕЧЕМ: Caddy писал только ошибки. Пришлось
включать журнал по ходу инцидента и ждать следующей атаки. Запрос нашёлся за минуту
(`POST /adfa`, `Next-Action: x`) — и сразу стала понятна и дыра, и заплатка. Журнал обращений на
боевом контуре должен быть ВСЕГДА, до инцидента.

**438. Фоновая команда, чей вывод идёт в файл настроек, убивает прод тихо.** Скрипт закрепления
образа писал лог туда же, куда значение переменной: в `/opt/remlab/.env` дописались 716 строк
вывода `docker compose` вместе с управляющими символами. Compose перестал читать файл целиком
(«unexpected character \x1b in variable name»), и любое пересоздание контейнеров падало — узналось
только через два часа, при попытке вычистить майнер. Перенаправление вывода и запись значения —
разные файлы; после автоматической правки конфигурации обязательна проверка, что он читается
(`docker compose config --quiet`).

**439. «Мы просто не обновились» — реальный сценарий взлома, а не теория.** Дыра
(CVE-2025-55182, десериализация в React Server Components) закрыта в Next.js 15.5.7, у нас стоял
15.5.4 — разрыв в три патча стоил майнера в боевом контейнере. Обновление заняло 10 минут и
прошло зелёным (patch-версия внутри той же линии). Отставание по патчам фреймворка, у которого
есть публичные RCE, надо считать инцидентом, а не задачей «на потом».

## Публичные маршруты Caddy и рассинхрон конфига (28.09.2026)
- **Адрес без слэша — ДРУГОЙ маршрут.** `handle_path /x/*` не матчит `/x`: запрос проваливается
  в `reverse_proxy` на Next.js и отдаёт 404. Маршрут статики = блок `handle_path` + парный
  `redir /x /x/ 301`. Симптом «ссылка не работает» у владельца — сперва проверить оба варианта.
  Живой пример: `/demo` редирект имеет и работает, `/test` — нет, поэтому `/test` = 404, `/test/` = 200.
- **Конфиг на сервере может быть НОВЕЕ репо.** `caddy/Caddyfile` в git не содержал блок `log` и
  матчер `@nextrce` (заслон от RCE серверных действий Next.js, инцидент 08.09) — они появились
  прямой правкой на сервере. Копирование репо-версии поверх СНЯЛО БЫ заслон. Перед любой правкой
  Caddyfile: `diff` сервер↔репо, серверные блоки перенести в репо дословно, только потом править.
  Это повтор урока 07.08 (деплой затирал серверный блок) — тогда лечили сведением, а разошлось снова.
- **Прибитый в коде публичный путь дорого переносить.** `/test/` встречается абсолютным путём в
  91 месте в 38 файлах `tools/`, каталог 4.6 ГБ. Новый адрес вводить alias-маршрутом на тот же
  `root` (+ точечные редиректы только для корня), а не переносом файлов и правкой всех ссылок:
  иначе ломаются и генераторы, и уже разосланные адреса.
- **Проверять конфиг ДО перезагрузки:** `caddy validate` и `caddy adapt` в одноразовом контейнере
  того же тега; `redir` в Caddyfile вычисляется раньше `handle`/`handle_path`.
**461. Фиксированное `waitForTimeout` в e2e — это не ожидание, а ставка на скорость машины.**
02.10 гейт CI упал на тесте «из гостиной можно дойти до коридора» в коммите, который НЕ трогал
ни одного файла 3D-квартиры (проверено `git diff --name-only`): полчаса назад тот же код прошёл
зелёным. Тест нажимал «идти вперёд», ждал ровно 5 с и проверял комнату — путь фиксированной
длины, а шаг за кадр зависит от частоты кадров, и на медленном раннере (в CI программный рендер
swiftshader) человек просто не доходил. `retries: 1` не спасает: медленная машина валит и повтор,
поэтому «флейк» выглядит как настоящая поломка и блокирует выкатку чужой работы. Правило: в e2e
ждать ПРИЗНАК, а не секунды — `expect.poll` на состояние движка (интервал 200 мс, запас 30 с) и
один помощник «сцена готова» на весь файл; клавишу/жест отпускать в `finally`, иначе упавшая
проверка оставляет сцену в движении и следующий шаг читает чужое состояние. Побочно быстрее:
локально тест стал 9,2 с вместо 14 с слепого ожидания.

**473. Листинг каталога + «временная» папка данных = публичные ПДн.** 13.10: `/test/*` раздаётся с
`file_server browse` (служебный хаб), а скрипт рендера положил очередь «отправить себе» с телефонами в
папку test/share/_queue — два файла с контактами были видны любому. Правило: данные людей — только в базу;
новый файл под веб-корнем — спросить «кто его увидит снаружи» и проверить `curl`-ом до публикации
(ADR-0248, план `b2b-01-security-hardening`).

**474. Код, доложенный `docker cp` в работающий контейнер, живёт только в его слое.** 13.10: сервис кадров
`remlab-draft` работал с сегодняшним кодом, а его образ и папка сборки `/opt/remlab/draft` были от 27.08 —
обновления годами клали `docker cp` прямо в контейнер. Пересоздание контейнера ради нового секрета молча
вернуло бы августовский код. Правило: перед пересозданием такого контейнера — `docker commit` в снимок и
запуск ИЗ снимка, старый контейнер остановить и переименовать, не удалять (`infra/server/draft-run.sh`);
лечение навсегда — сервис в compose из репозитория (план `b2b-08`).

**475. Проверка защиты сперва должна покраснеть на старом проде.** 13.10: `tools/security-smoke.sh`
прогнан ДО выкатки — 9 из 13 пунктов красные (вебхуки отвечали 200, заголовков не было). Только такая
проверка доказывает, что зелёный после выкатки — заслуга правки, а не слепота теста (тот же принцип,
что «не упало — не проверка»). Правило: новый сторож/смоук — сначала прогон на текущем состоянии с
ожидаемым провалом, число провалов — в лог плана.

**477. `git add` со списком путей молча не добавил ничего из-за одного несуществующего пути.** 13.10:
`git add -A <пути…> 2>/dev/null` — в списке был только что удалённый скрипт заведения менеджера, команда упала целиком,
ошибку скрыл `2>/dev/null`, и коммит унёс только ранее застейдженное удаление. Правило: не глушить stderr
у `git add`; ПЕРЕД коммитом `git status --short` без строк ` M`/`??` по теме (13.10 повторилось: контракты
не вошли в коммит, а код на них уже ссылался — CI упал бы), после — `git show --stat HEAD`.

**479. Канон, которого нет в git, всплывает при первой сборке «из репозитория».** 13.10 образ сервиса кадров
собирали из репозитория — `tools/scout/styles.json` (паспорта стилей, канон `core/styles.md`, его читает
`improve_mode.py`) проглатывало правило `.gitignore` `tools/scout/*`: файл жил только на DEV и в руками
собранном контейнере. Свежий клон и CI его не видели. Правило: новый каноничный файл в `tools/scout/` — сразу
исключение `!путь` в `.gitignore`; сборка образа в CI (`ci.yml: draft-image`) ловит забытые файлы импортом.

**485. Запасной путь без счётчика прячет поломку на сутки.** 13.10 09:49 `earlyoom` убил DEV-рендер демо; прод
по задумке перешёл на запасной локальный рендер («DEV-бэкенд молчит — рендерю локально») с упрощёнными мешами и
рисовал так до 14.10 14:24 — кадры хуже, тревоги ноль: строка была только в логе контейнера. Правило: у каждого
запасного пути — счётчик в дайджесте (сколько раз за сутки сработал) и сторож главного пути; сервис на DEV без
systemd — крон-подъём раз в 10 минут (`tools/ops/dev-checks.sh` `WARN:dev_render_*`, крон `dev_render_backend.sh`, demo-03).
Причина падений 14.10 (ещё три раза за день): фоновая сборка листа полными мешами для «Улучшить» (пик ~1,5 ГБ) и
параллельные браузеры живых проверок при 7,6 ГБ на машине. Меры: без денег на шлюзе лист не собирается, у сборщика
потолок `RLIMIT_DATA` (`draft_render._src_child`, `SRC_MEM_EXTRA_MB`), живые проверки — `workers: 1`.

**486. Новый модуль сервиса кадров — в трёх местах, не в двух.** 14.10 `draft_jobs.py` добавлен в `COPY` и в
проверку импортов `infra/draft/Dockerfile`, но не в белый список `infra/draft/Dockerfile.dockerignore` — CI
(`draft-image`) упал «not found» и выкатка встала на час. Правило: новый файл образа = `COPY` + проверка импорта +
строка `!путь` в `Dockerfile.dockerignore`; перед push — `docker build -f infra/draft/Dockerfile .` локально (см. 479).

**495. /tmp на DEV — tmpfs 788 МБ с квотой: в нём не держать ни кэши, ни артефакты проверок.** 15–16.10 он забился (scratchpad
сессии 368 МБ + кэш GLB рендера 161 МБ + 116 брошенных вырезок `tmp*-cut.png`), и headless-браузер живых проверок падал
«Page/Target crashed» при свободной ОЗУ. Корни: `viz_paste.cutout` кладёт «кэш» `-cut.png` рядом с файлом, а
`mesh_orient.photo_mask` давал ему временный файл — вырезка оставалась навсегда (теперь удаляется в `finally`); кэш
`draft_render.SCENE3D_CACHE` жил в /tmp (теперь `~/scout-scenes/mesh3d-cache` с потолком `tools/scout/rules/dev-tmp.json`). Защита:
`tools/ops/dev-checks.sh` — `WARN:tmp_full` с топ-3, ночной шаг `tmp_sweep` (`tools/ops/tmp-sweep.sh`). Правило агентам:
снимки и сборки проверок — на диск (`~/scout-scenes/<сессия>/`), scratchpad ≤ 50 МБ, перед браузером — `df -h /tmp`.

**496. «Сборка прошла» = код возврата 0 и `.next/BUILD_ID`, а не «grep error пуст».** 16.10 на DEV сторож памяти (earlyoom)
убивал рабочий процесс `next build` (≈ 2,5 ГБ) — сборка печатала «worker exited … signal: SIGTERM», в ней нет слов «error/failed»,
и проверка `pnpm build | grep -iE "error|failed"` молча считала её успешной. Плюс устаревший `.next/cache` давал CSS без новых
адаптивных классов (`sm:inline`) — локальный e2e падал там, где CI (чистая сборка) прав. Правило: проверять `$?`/`BUILD_ID`;
при сомнении в CSS — `rm -rf .next`; когда DEV без памяти (разбор волны) — сборку и e2e оставить CI и не выдавать за свои.

**497. Красный CI без логов — включи аннотации, а не гадай.** 16.10 e2e /flat падал на разных коммитах, логи шагов без токена
закрыты (gh на DEV просрочен). Отчёт Playwright `github` (`playwright.config.ts`) кладёт текст ошибки в аннотации запуска — их
отдаёт публичный API (`/check-runs/<job>/annotations`). Дальше — бисекция откатом подозреваемого и прогон упавших тестов против
прода (`-g`, без записи данных): прод зелёный → дело в нагрузке CI (параллельные вкладки с программным WebGL) → e2e на CI в
один поток, постоянный цикл кадров невидимой/неподвижной сцены — гасить.
