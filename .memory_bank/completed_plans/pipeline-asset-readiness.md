## Цель
Закрыть три дыры, из-за которых канонический порядок (`core/pipeline-order.md`) пока остаётся
декларацией поверх старого конвейера: готовность считается одним `mesh_ready`, задания на
генерацию создаются на весь спрос, а измерять успех нечем.

## Источник задачи
Владелец 29.08: «у мягкого декора мешей быть не может… количество подходящих товаров не равно
количеству мешей, мешей должно быть меньше. Доделывай, чего не хватает, строй план, потом
деплой, чтобы был конвейер». Список дыр — из критики Codex по порядку этапов.

## Что делаем

### 1. `asset_ready(strategy)` вместо `mesh_ready`
Готовность предмета зависит от того, КАК он рисуется, а не от наличия меша. Стратегия выводится
из роли (`render_strategy.py`):

| Стратегия | Роли | Что значит «готов» |
|---|---|---|
| `mesh` | диван, кресло, стул, комод, тв-тумба, стеллаж, стенка, витрина, камин, столик, стол обеденный, шкаф, пуф, банкетка | принятая ревизия текущего фото + решённая ориентация |
| `cutout` | ваза, кашпо, статуэтка, растение, лампа, торшер, часы, зеркало, картина | вырезка с вердиктом `ok` |
| `flat` | ковёр, плед, подушка, шторы, полка | живое фото + известные габариты |

`asset_ready(sku)` — единая точка истины; `reserve.py`, `slot_contract`, покрытие и гейт
считают по нему. `mesh_ready` остаётся частным случаем для стратегии `mesh`.

### 2. Планировщик генерации (между этапами 5 и 6)
Сейчас `mesh_jobs` создаются на весь спрос (1083 в очереди), а генерится ~10/день — очередь не
рассосётся никогда, и каждый прогон одинаково бесполезен. Вводим `mesh_demand.status='eligible'`
и `mesh_scheduler.py`, который выбирает ДНЕВНУЮ ПАРТИЮ по приросту готовых сетов:

1. предметы опубликованных сетов, которым не хватает меша (замыкают то, что уже показано);
2. дефицит готовых заменителей у занятых слотов;
3. минимальный набор, замыкающий следующий полный сет в ячейке `band × style × tier`;
4. стратифицированный пилот проблемных ролей (по вердиктам обрезки);
5. хвост.

Дневной предел — `MESH_DAILY_BATCH` (по умолчанию 10, как на пилоте). Задания создаются только
на выбранную партию.

### 3. Метрики — мерить сеты, а не меши
`pipeline_metrics.py` + шаг в цепочке + блок на `/test/set-changes/`:
полностью готовых сетов · покрытие ячеек `band×style×tier` · доля слотов с 1/2 готовыми
заменами · сколько слотов разблокировал каждый принятый ассет · p50/p95 «в очереди → принят» ·
возраст старейшего задания каждого приоритета.

### 4. Гейт — по свойству СЕТА, не по глобальному проценту
`rolling` переводит сет в жёсткий режим, когда у НЕГО 100% предметов `asset_ready`. Общая доля
по каталогу для этого решения не годится: 80% каталога бесполезны, если не хватает одного
обязательного класса диванов.

## Скоуп — что НЕ входит
- Судья (этап 8) и feasibility-проверка перед ним — отдельная задача, у неё своя цена за прогон.
- Атомарная публикация ассета одним пакетом — делаем «готовность», хранение остаётся как есть.
- Переименование сцен с номеров на `set_id`.

## Файлы
Новое: `tools/scout/render_strategy.py` · `tools/scout/mesh_scheduler.py` ·
`tools/scout/pipeline_metrics.py`.
Меняем: `mesh_ready.py` (обёртка над asset_ready) · `reserve.py` · `slot_contract.py` ·
`mesh_queue.py` (статус `eligible`) · `refresh_daily.sh` · `set_changes_page.py`.

## Проверка
1. `asset_ready` для мягкого декора = живое фото + габариты, БЕЗ меша (сегодня такие слоты
   числятся непокрытыми — покрытие обязано вырасти).
2. Планировщик при `MESH_DAILY_BATCH=10` создаёт ровно 10 заданий и первыми — предметы
   опубликованных сетов.
3. Повторный прогон без изменений даёт 0 новых заданий.
4. Метрики считаются и печатаются; «полностью готовых сетов» — число, а не оценка.
5. Ночная цепочка проходит целиком (`bash -n` + прогон шагов вхолостую).

## Completion summary (2026-08-29)
**Сделано.** `render_strategy.py` — готовность по способу отрисовки (mesh/cutout/flat), подключена
в `reserve.py` и `slot_contract.py` вместо `mesh_ready` · `mesh_scheduler.py` — дневная партия по
ярусам полезности, задания создаются только на неё (из `mesh_queue.run` постановка убрана) ·
`pipeline_metrics.py` — готовые комплекты, покрытие ячеек, возраст очереди, p50/p95 ·
шаги `cutout`, `mesh_schedule`, `pipeline_metrics` в `refresh_daily.sh`.

**Проверено.** Покрытие резерва выросло 0% → 8.6% (плоский декор перестал числиться
непокрытым — он и не должен требовать меша) · планировщик берёт 10 заданий, все яруса 1
(предметы опубликованных комплектов), повтор берёт СЛЕДУЮЩИХ, экспорт отдаёт только их ·
метрики считаются: 0 из 126 готовых комплектов, ближайший к готовности №1 (4 из 13).

**Миграция.** Удалены 1084 задания, созданные прежней логикой «на весь спрос»: ни одно не
отправлялось (attempts=0, batch_id пуст), планировщик пересоздаёт нужные в порядке полезности.

**Уроки.**
- «Сеты только с мешами» невыполнимо буквально: у мягкого декора мешей не бывает. Готовность
  надо мерить ПО СПОСОБУ ОТРИСОВКИ, иначе покрытие врёт вниз и гейт останавливает сборку.
- Очередь без планировщика при малой пропускной способности бесполезна: 13 000 заданий по
  алфавиту SKU дают меши, размазанные по каталогу, и ни одного показываемого комплекта.
- Мерить надо готовые СЕТЫ, а не число мешей: это разные величины, и вторая не отвечает
  на вопрос «что уже можно показать».

**Осталось за рамками:** судья (этап 8) и feasibility-проверка перед ним; атомарная публикация
ассета одним пакетом; переключение `MESH_GATE_PHASE` по свойству сета (описано, не внедрено).
