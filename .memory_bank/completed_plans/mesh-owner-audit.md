## Цель
Ссылка, где владелец глазами проверяет меши: по 20 карточек на страницу (одна карточка на
товар), у каждой вертящаяся 3D-модель и одна кнопка «переделать». Нажатие фиксируется в БД как
ручная проверка, меш выводится из сетов и встаёт в общую очередь на перегенерацию — так, чтобы
решение НЕ ТЕРЯЛОСЬ и не отменялось следующим прогоном конвейера.

## Источник задачи
Промпт владельца 05.09 + уточнения в той же сессии: 3D-модель (не картинки); переделка в общую
очередь (без обгона); максимум 2 ручные переделки на товар с обязательной пометкой; модели возить
партиями с кнопкой «следующая партия»; удалять только КОПИИ на проде, исходники — никогда.
Ответы на вопросы: одна карточка на ТОВАР (1291, 65 страниц); авто-перегон системы в лимит двух
ручных НЕ входит; прогресс «смотрел» считать автоматически. Затем: «сделай аудит плана ещё раз,
поправь» → второй аудит (свой + Codex №2), план одобрен через Plan Mode 05.09.

### Что нашли аудиты (Codex №1 → свой → Codex №2; всё подтверждено по коду)
1. **Ревизии схлопываются**: `ingest_registry.py` пишет все seed одного товара в одну строку
   `sku|sha|v1`, обходит папки по алфавиту (не по времени) и при каждом прогоне возвращает
   статус в `generated`. Колонки `generation_variant`/`rejected_reason` заведены
   (`006-mesh-binding.sql`), но не заполняются.
2. **Привязка** `mesh_bind.py:95` берёт свежайший файл по mtime, отказ владельца не смотрит;
   отвязки нет вовсе.
3. **Готовность** `mesh_ready.py:45` связывает ориентацию по SKU → перегон наследует ориентацию
   старого меша. В `mesh_dims.py:58` уже есть честная сверка по `glb_sha`.
4. **Дозапись в живой `mesh-queue-v1.json`** запрещена регламентом `rules/mesh-priority.json`
   (§identity: позиционный курсор запрещён, завершённость по `job_key` с seed), затирается
   `mesh_priority.py --build-queue`; `batch_show.py:636` считает `total` один раз.
5. **Seed**: `apply_repairs.py` сам заказывает seed+1 для seed 0 → ручной и авто-перегон могут
   заказать один seed и получить cached.
6. **Legacy-читатели** `gallery_build.py:195` и `topview_render.py:255` смотрят sidecar
   `owner_reject.json` в папке меша — отказ из БД они не увидят.
7. **Партия «удалить → лить 12 минут»** оставляет владельца без моделей; порог диска ≥6 ГБ
   ниже порога приёмника (7).

## Решения (после двух аудитов)
1. **Идентичность физического меша — аддитивно.** `revision_key` не меняем. Таблица
   `mesh_generations` (`generation_key = sku|sha16|v1|seed|glb8`, путь, `generated_at`,
   `machine_verdict`, `owner_verdict`, `owner_decision_id`) + указатели
   `asset_revisions.current_generation_key`, `products.mesh_generation_key`. «Текущее» — по
   монотонному `generated_at` с tie-break по ключу; порядок обхода диска на итог не влияет.
2. **Отказ не наследуется перегоном.** `owner_reject` у ревизии держится ТОЛЬКО пока
   `current_generation_key` = отвергнутое поколение; новое поколение → `generated`. Ingest
   никогда не затирает человеческий вердикт поколения.
3. **Отказ = товар без меша до перегона.** Старые попытки НЕ воскрешаются. Одна DEV-транзакция:
   ledger по `prod_decision_id` → `owner_verdict` поколению → ревизия в `owner_reject` при CAS
   → очистка `products.mesh_uri/mesh_at/mesh_generation_key`, `mesh_status='rejected'` → запрос
   переделки; sidecar `owner_reject.json` в папке поколения (для legacy-читателей). Тогда
   `mesh_priority.products()` (`status != 'ready'`) сам вернёт товар в очередь на его ярусе.
4. **Готовность по `glb_sha`** — в `mesh_ready.py` условие из `mesh_dims.py`.
5. **Единый allocator seed**: первый свободный среди `mesh_generations`, pending-переделок,
   `mesh-reseed.json` и активного снимка очереди.
6. **Лимит буквально: 2 ручные переделки на SKU за всё время**, авто-перегоны не считаются;
   обнуление при смене фото — без отдельного решения владельца не вводим. Параллельные клики:
   `for update` + уникальность `(sku, manual_attempt_no)`.
7. **Очередь честно**: инбокс `mesh_rework_requests`; в снимок — при `--build-queue`
   (`seeds:[next_seed]`, `queued` только после атомарной записи снимка). До этого карточка:
   «принято, ждёт сборки очереди». Процедура «старт волны» документируется и скриптуется;
   в `batch_show` курсор выводится из имени `MESH_SAMPLE`.
8. **Прогресс — `seen_at` у карточки**, таблицы просмотров страниц нет.
9. **Активы под `/opt/remlab/test/mesh-audit/`**, `handle_path /test/mesh-audit/*` с кэшем.
10. **Смена партии с grace**: новая активна после проверки манифеста; предыдущая удаляется
    через 10 минут; вкладка опрашивает состояние и просит обновиться.
11. **Два замка**: минутный sync и 12-минутный публикатор — разные процессы и lock'и.
12. **Тесты двух уровней**: `--selftest` без БД (CI), `--dbtest` на одноразовой БД в
    `remlab-devdb` (DEV, перед приземлением), vitest на проде.
Отвергнуто из Codex №2: постеры «только для партии» (делаю для всех, в порядке партий);
рефактор `mesh_jobs.job_key` под seed — follow-up.

### Уроки (ОБЯЗАТЕЛЬНО)
- Два аудита Codex ДО кода нашли 7 реальных дефектов учёта (ревизии схлопывались по алфавиту
  job_id, `owner_reject` затирался ingest-ом, готовность по SKU давала ложные 12) — правило

  хвостовые пустые поля тоже режутся — в проверках сентинел «-» (урок 417).

- Шаги минутного тика — независимы (try/except на каждый): 502 прода во время деплоя иначе
  отменяет и постеры, и партию; публикатор любую ошибку ДО заливки обязан отметить `failed`.
