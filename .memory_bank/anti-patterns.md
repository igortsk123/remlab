# Anti-patterns — каталог граблей

> Записывай сюда повторяющиеся ошибки (особенно от кодогена). Используется как чеклист в ревью
> и читается вместе с `core/lessons.md` перед планированием (`agent-workflow.md`, Этап 1).
> Чем конкретнее «как детектить в diff» — тем полезнее. Устаревшие помечай (`~~…~~`), файл
> целиком не переписывай (протокол — как у lessons: инкрементальные правки).

## Формат записи
```
## N. Короткое название проблемы
**Симптом:** как выглядит в коде.
**Причина:** почему это происходит (особенно у кодогена).
**Convention:** как правильно.
**Детект в diff:** что грепать / на что смотреть в ревью.
**Фикс:** конкретное исправление (find/replace или вручную).
```

## 1. Пример: локальное переобъявление общего типа
**Симптом:** тип/интерфейс объявлен заново в фиче вместо импорта из общего модуля.
**Причина:** кодоген не «видит» существующий тип и создаёт дубль.
**Convention:** импортировать из единого источника типов.
**Детект в diff:** новое `interface X`/`type X`, имя которого уже есть в общих типах.
**Фикс:** удалить локальный, импортировать общий.

## 2. Zod `z.preprocess` стирает поля при частичном патче
**Симптом:** автосейв/partial-update обнуляет поля, которые пользователь не трогал.
**Причина:** `z.preprocess(fn, schema).optional()` — `fn` вызывается и на ОТСУТСТВУЮЩЕМ ключе;
типичная проверка `v == null` истинна для `undefined` → absent превращается в `null` → поле стирается.
**Convention:** хелперы полей без `preprocess` — `z.union([z.null(), z.literal("").transform(()=>null), …]).optional()`.
**Детект в diff:** `z.preprocess` в схеме патча/частичного апдейта.
**Фикс:** убрать preprocess; тест: частичный патч `{одно_поле}` → в выходе ТОЛЬКО это поле.

## 3. Доверие клиентскому патчу (mass-assignment)
**Симптом:** объект из запроса пишется в БД целиком (`update(table).set(patch)`).
**Причина:** не отфильтрованы server-controlled поля (id/ownerId/status/role/timestamps).
**Convention:** валидировать вход Zod-схемой, куда server-controlled поля НЕ включены — `.parse()` их стрипает.
**Детект в diff:** `.set(patch)` / `{...patch}` без схемы; патч прямо из `req.body`/`formData`.
**Фикс:** прогнать через `schema.safeParse` → писать только `parsed.data`.

## 4. Тяжёлые вычисления в request-пути
**Симптом:** парсинг больших файлов / отчёты / массовые операции прямо в хендлере → таймауты, блокировки.
**Причина:** синхронная тяжёлая работа в горячем пути запроса.
**Convention:** разовое лёгкое — ок в роуте; тяжёлое/массовое — в воркер/очередь.
**Детект в diff:** циклы на тысячи элементов, парс больших буферов, генерация Excel/PDF в server action/route.
**Фикс:** вынести в фоновую задачу; в ответе — статус/прогресс.

## 5. (base-ui / headless Menu) онклик и обязательные обёртки
**Симптом:** пункт меню «молча не срабатывает» (особенно на тач); ИЛИ страница падает в error-boundary.
**Причина:** `Menu.Item` активируется по `onClick`, не `onSelect` (typecheck не ловит — `onSelect` есть как
DOM-событие). А `Menu.GroupLabel` требует родителя `Menu.Group` — иначе рантайм-ошибка (краш страницы).
**Convention:** в пунктах меню — `onClick`; `GroupLabel`/label-части оборачивать в `Group`.
**Детект в diff:** `onSelect=` на `*MenuItem`; `*MenuLabel` напрямую в `*MenuContent` без `*MenuGroup`.
**Фикс:** `onSelect`→`onClick`; обернуть label в group. (Минифицированный код ошибки прод-сборки —
расшифровывай из исходника пакета: `node_modules/<pkg>/**/*Context.js`, рядом dev-сообщение.)

## 6. UI-мелочи, которые читаются как баг (навигация, sticky, подсказки)
**Симптом:** «меню обрезано» (гориз. скролл без видимого скроллбара); шапка мерцает при скролле
вверх; активная кнопка обведена «тонкой рамочкой» (принимают за сбой фокуса); совет «введите
размеры» висит ПОД полями и читается запоздало.
**Причина:** скрытый индикатор прокрутки; гистерезис sticky-коллапса МЕНЬШЕ дельты высоты
сворачиваемого блока + scroll-anchoring браузера гоняет `scrollY` через оба порога; активное
состояние наружным `box-shadow`-кольцом = внешний вид `:focus-visible`; двуликий блок
(пусто = подсказка / заполнено = результат) с фиксированной позицией под формой.
**Convention:** навигация переносом (`flex-wrap`), не скроллом; зазор порогов коллапса > дельты
высоты + `overflow-anchor: none`; активное состояние — заливка/inset-тень; приглашение к вводу —
НАД полями, результат — ПОД (паттерн `SizedBlock`, `components/calc/RoomPanel.tsx`).
**Детект в diff:** `overflow-x: auto` в навигации; пороги в scroll-хендлере ближе высоты
скрываемого узла; `box-shadow: 0 0 0 Npx` у `--active`; note-блок всегда после формы.
**Фикс:** см. Convention; проверять в узком окне (≤700px), не только на десктопе.

## 7. Иконка-подсказка в отдельной строке / у зоны действий
**Симптом:** широкая пустая полоса в карточке (строка на всю ширину ради иконки 18×18); ИЛИ
справочная иконка стоит вплотную к разрушающему действию и читается как кнопка.
**Причина:** `<div class="row" style="justify-content:flex-end">` с единственным `.help` внутри —
строка + gap + падинг дают ~50px пустоты; правый край строки — зона действий («удалить»).
**Convention:** справочную иконку ставить в строку заголовка СРАЗУ ПОСЛЕ поясняемого текста
(левая, «контентная» сторона); дублировать в списке не надо — один раз, у первого элемента.
**Детект в diff:** `row`/`flex` контейнер, где единственный ребёнок — `.help`/иконка; `.help`
соседствует с `удалить`/`сбросить`.
**Фикс:** перенести иконку в заголовок; если она у ЛЕВОГО края — `.help--start`
(`left: 0; right: auto`), иначе тултип (`right: 0`) уезжает за край экрана.

# Анти-паттерны ПАМЯТИ (уроки эксплуатации — актуальны любому проекту с Memory Bank)

## M1. Знание утекло в авто-память харнесса, банк пуст
**Симптом:** `~/.claude/.../memory/` полна живых фактов, `.memory_bank/` замёрз на недели.
**Причина:** харнесс пишет в авто-память по умолчанию; захват в банк не запускался.
**Convention:** `/memory-check` Этап 1.5 МОСТ реконсилит слои; проектное живёт только в банке.
**Детект:** авто-память растёт, `core/*` не меняются; SessionStart-баннер показывает возраст.

## M2. project-state распух в журнал (50 КБ хроники вместо снимка)
**Симптом:** «где проект сейчас» = прочитать весь лог; токены жгутся при каждом resume.
**Convention:** снимок ПЕРЕПИСЫВАЕТСЯ (≤10 KB); хронология — append в `changelog/project-history.md`.
**Детект:** audit BLOATED.

## M3. Фича в проде, но её нет в decision tree
**Симптом:** целые домены (интеграции, воркеры, каталоги) не находимы по INDEX→core.
**Convention:** новая функциональная область ⇒ `core/<домен>.md` до завершения плана
(гейт в plans/_template + `/memory-check` Этап 1.4).
**Детект:** audit NO-TIER1; ручная проверка «найду ли фичу за 1 drill».

## M4. Слой знаний замёрз, а аудит молчит
**Симптом:** core/ и domain/ отстают от реальности на недели, попарный STALE молчит
(оба слоя замёрзли ВМЕСТЕ), audit «✓ чисто» — ложная уверенность.
**Convention:** свежесть меряется против project-state (audit LAGGING), не только попарно.

## M5. Две `.memory_bank` (док-директория + код-репо)
**Симптом:** планы коммитятся в одну копию, память ведётся в другой; никто не знает канон.
**Convention:** ОДНА `.memory_bank` в репо кода (`DEPLOY.md` «Каноничное расположение»);
вторую свести и заменить README-указателем.
**Детект:** audit DIVERGENCE; `_memory-canon.txt` фиксирует канон.

## Архив уроков июля 2026 (из core/lessons.md, перенос 2026-08-02)

- **Bind-монтирование ФАЙЛА ломается при правке:** `sed -i` и запись из Python подменяют inode,
  контейнер держит старый файл и докладывает «config is unchanged», хотя на диске правка есть.
  Править через `cp`/`tee` в существующий файл либо монтировать каталог. 28.08, Caddyfile.

- **НЕ чистить кэш docker при итеративной сборке.** `builder prune --filter until=Nh` режет по
  ВОЗРАСТУ СОЗДАНИЯ: старейшие слои — это база (apt, torch), самые дорогие. «Уберу мусор от
  неудачных попыток» — иллюзия, мусор молодой и под фильтр не попадает. 28.08: час пересборки
  на ровном месте, при том что места ХВАТАЛО. Чистить только упёршись в диск, сначала ВНЕ
  docker (pip/npm/vscode-server), `builder prune` — последним и при остановленной сборке.
- **Кэш buildkit чистится САМ при нехватке диска:** «инкрементальная» пересборка молча
  становится полной. Проверять число `CACHED` в первых строках лога — секунда против часа.
  Тяжёлую базу и свой код разносить по двум Dockerfile (`Dockerfile.patch`): наш код
  наращивается поверх готового образа за секунду.

- **Чужой requirements — источник истины, мы ДОПОЛНЯЕМ.** Свой список рядом с апстримовским
  переопределил 9 пинов Hunyuan (huggingface-hub на 3 версии назад): сборка зелёная, ломается
  на ноде при загрузке весов (ADR-0132).
- **Зелёная сборка ≠ рабочий артефакт:** шаг, способный «успешно» ничего не сделать (скрипт
  без pybind11 отдаёт 0 и кладёт пустой `.so`), заканчивать явной проверкой результата.
- **`cd` в фоновой команде не переживает вызов** (дважды): `docker build .` собрал Next.js
  вместо Hunyuan под чужим тегом. Для docker — `-f` и контекст абсолютными путями.

- **Внешние пины протухают:** `bpy==4.0` исчез с PyPI, официальный Dockerfile Tencent не

- Свежий pip изолирует сборку: `setup.py` с импортом torch требует `--no-build-isolation`.

142. [08-04] Ширина вырезки берётся как ВИДИМАЯ ширина следа под текущим углом (проекция footprint на горизонтальную ось камеры), а не w_cm из паспорта: пуф 71×57, повёрнутый углом, занимает по горизонтали больше 71 см, и вырезка вылезала за свой след.
143. [08-04] Разбор промпта внешней моделью дал ТРИ наших бага: (1) габариты в легенде брались из сырой карточки, у дивана глубина 0 — теперь из геометрии; (2) ориентация «фасадом к» утыкалась в предмет, стоящий НА этой же мебели (тумба→тв, комод→ваза) — такие исключены, описание через стены; (3) противоречие «не добавляй декор» + «можешь добавить декор» — теперь разрешены только картины в рамах. Плюс добавлены иерархия источников (прямоугольник → план → размеры → фото) и список условий брака.
144. [08-05] Признак «часть предмета» считается по ЧЕСТНОЙ доле видимости: предмет рендерится отдельно в уменьшенном кадре, его площадь сравнивается с реально попавшей в кадр. Прежний признак по касанию края кадра врал на подвесных предметах (маска люстры доходит до верха из-за подвеса).
145. [08-05] Четвёртая картинка запроса — эталоны внешнего вида только для товаров, видных ЧАСТЬЮ; в промпте роли всех картинок описаны по номерам, и сказано, что эталон даёт только внешний вид, но не место и не размер.
146. [08-05] Модель перестраивала комнату: замер положения вертикального угла показал сдвиг до 70% ширины кадра. Запрет вынесен в САМУ ЗАДАЧУ отдельным абзацем («архитектура зафиксирована: плоскости стен, угол, линии пола и потолка, камера; ты перекрашиваешь комнату, а не строишь заново») — сдвиг упал до 4–6%.
147. [08-05] Архитектуру держит ЧИСЛО, а не слова: в запрос для каждого кадра подставляется положение вертикального угла комнаты в процентах ширины (`corner_brief`). До этого нижний кадр уезжал на 28,8% при геометрических 49,4%; после — 49,4–49,6%. Замер «на глаз» по максимальному градиенту врал (ловил штору и мебель) — мерить надо в полосе стены выше мебели.
148. [08-05] Плоская вырезка ПРИНЦИПИАЛЬНО не может выглядеть одинаково с двух камер: она всегда смотрит в объектив. Полное решение — 3D-модели товаров, но только там, где фото реально провалило приёмку (ADR-0062).
149. [08-05] Вход генератора 3D — ТОЛЬКО на белом фоне. Вырезку RGBA переводили в RGB, прозрачность становилась чёрной, и генератор запекал черноту в текстуру.
150. [08-05] Рендера готового меша на fal НЕТ — крутить модель приходится у себя; на CPU это реально, свой z-буфер на numpy, 1,3 с на вид (ADR-0060).
151. [08-05] Части GLB рендерим ПО ОТДЕЛЬНОСТИ: склейка теряет UV. Диагностика черноты — сперва смотреть яркость самого атласа, а не подозревать растеризатор.
152. [08-05] СЕРЫЙ ОБЪЁМ вместо непоставленного товара — вред: он даёт модели ложную форму, и она рисует мебель-обрубок. Достаточно контура следа на полу и эталона товара; приёмка помечает позицию «нет фото».
153. [08-05] Обрезка вклейки ПО МАСКЕ рвёт рендер в лоскуты: ортографический рендер и перспективная маска не совпадают пиксель в пиксель. Маска задаёт только место и размер, перекрытия решает порядок вклейки (ковёр первым, дальние раньше ближних).
154. [08-05] Легенда НЕ ДОЛЖНА врать: у непоставленного товара стоял номер и текст «виден целиком». Видимость берётся из журнала вклейки, а не из геометрии.
155. [08-05] Замер по габаритным прямоугольникам врёт на Г-мебели: солвер рапортовал 37 см до столика там, где до выступающего плеча было 9. Меряем по настоящему следу текущей расстановки.
156. [08-05] Движки ставят мебель по ТИПОВЫМ габаритам, а в раскладку уходят КАТАЛОЖНЫЕ — комод и стеллаж уезжали за стену на 4-5 см. Центр прижимается так, чтобы след целиком лежал в комнате.
157. [08-05] Камера не должна стоять внутри мебели (угловой диван занимает угол целиком). Занятый угол не отменяем и не уводим внутрь комнаты — иначе разваливается диагональ и второй вид пустой; отходим ВДОЛЬ СТЕНЫ.
158. [08-05] Мебель у стены отплывала на 45 см ради комфортных 300 см до ТВ. Сдвиг только при нарушении ЖЁСТКОГО предела, иначе на плане это читается как ошибка.
159. [08-05] Лист эталонов обязан покрывать ВСЕ позиции кадра: модель рисует верно ровно то, что видела фотографией, остальное придумывает по названию (проверено дважды, ADR-0063).

160. [08-05] В промпте свойства должны жить В САМОМ ТОВАРЕ (`appearance_source`, `has_footprint`, `support.parent_id`), а не в абзацах со списками номеров — иначе при другом наборе мебели промпт переписывается руками.
161. [08-05] Пропорции нельзя чинить весами: пока геометрия — слагаемое общей суммы, цвет и стиль её перекрывают. Только жёсткие рамки ДО скоринга (ADR-0064; замер 126 сетов: было 107 маленьких столиков, стало 0).
162. [08-05] «Пуф» — не одна роль, а шесть разных вещей. Из 23 пуфов каталога 4 банкетки и 3 кресла-мешка. Роль-категория не задаёт правил размеров — задаёт функциональный подтип (ADR-0065).
163. [08-05] Ковров для гостиной в каталоге нет вообще: 609 товаров со словом ковёр/коврик — ванные и придверные, крупнейший 100×150. Прежде чем чинить алгоритм, проверь, есть ли товар в принципе.
164. [08-05] У 100% офферов есть фото (и витринное, и оригинал). Миниатюр у нас мало не потому, что фото нет, а потому что качаем их только для кандидатов — это кэш, а не покрытие.
165. [08-05] Перцептивный хеш один не доказывает «тот же товар»: CLIP B/32 на 224 px не видит фактуру — один диван в рогожке и велюре дал косинус 0.983. Нужна сверка цвета (сетка 8×8, ≤14 из 255) и порог 0.985; при сомнении отвечаем «изменилось» (`tools/scout/phash.py`).
166. [08-05] Не всякий .sql в папке — миграция: `db_migrate.py` уронил прогон на `bootstrap.sql` (первичная схема с `create or replace view` падает поверх живой базы). Мигрируем только `NNN-*.sql`.
167. [08-05] Правило разнообразия проверяло не того кандидата: `overlap_ok` считал пересечение по всему комплекту, и после превышения лимита отсекался ЛЮБОЙ следующий товар — комплекты теряли весь декор разом. Проверять надо только кандидата, который увеличивает пересечение.
168. [08-05] Лист эталонов строим от состава комплекта, а не от номеров в кадре: номер получает только видимое, поэтому ваза вне кадра выпадала из «эталонов на все позиции» (`viz_final.identity_sheet`).
169. [08-05] `open(f,'w')` в одном выражении с `open(f).read()` ОБНУЛЯЕТ файл: интерпретатор открывает на запись раньше, чем читает. Так уже терялся этот самый архив уроков — и потерялся второй раз. Читать в переменную, потом писать.
169. [08-05] Дешёвая модель дешевле только по прайсу: `gpt-5-nano` при цене вчетверо ниже выдала 342 тыс. токенов выхода против 53 тыс. у `gpt-5.6-luna` — разрыв схлопнулся до 1.6×, а функциональный подтип развалился (43% против 89.8%). Считать надо цену за КОРРЕКТНО обработанный товар.
170. [08-05] Сравнение моделей без доверительных интервалов — не сравнение: на 256 товарах 2% это шесть карточек. Решение обосновано тем, что интервалы не пересеклись (88–100% против 77–88%).
171. [08-05] «Главный стиль» — негодная метрика: векторы плоские (у товара 2-3 стиля на одном уровне), и argmax скачет от монетки. Сравнивать надо ВЕСЬ вектор: текст↔фото расходятся в среднем на 0.39 ступени из 3, у 86% товаров разница ≤1 ступени. Прежний вывод «стиль по тексту не работает» был артефактом метрики.
172. [08-05] Картинку в API надо слать БАЙТАМИ, а не ссылкой магазина: на URL `imgng.gdeslon.ru` приходило 400 на каждой шестой карточке (5 из 29). С base64 512px — 29 из 29.
173. [08-05] Среди «фото товара» попадаются инфографика с характеристиками, интерьерная сцена и голая панель — по ним стиль недостоверен. Поле `image_type` из исходного документа я ошибочно выбросил из схемы; вернул, и модель сама пометила ровно те карточки, что нашёл глазами.
174. [08-05] Описание из фида — источник только у 12.3% пула: 7 813 текстов на 3 551 уникальный, 969 диванов делят одну маркетинговую фразу. Классификация до промпта — `desc_quality.py`.
175. [08-06] Стиль по одному предмету напрямую определяется плохо даже в исследованиях: 0.41 точности на Bonn Furniture Styles (90 298 фото, 17 стилей), 0.49 с сиамскими признаками; сочетаемость решается лучше (AUC 0.72). Поэтому спрашиваем ПРИЗНАКИ, а стиль собираем правилами (`style_rules.json`).
176. [08-06] Вопросы должны быть СВОИ для каждого типа предмета: у дивана выдаёт подлокотник и стёжка, у комода ручки и основание, у люстры каркас и плафон, у ковра ворс и узор. Общий список на всех дал 2-4 признака из 8 и разброс оценки 4.7-6.5; вопросы под роль — 60 значений и разброс 1.6-9.2.
177. [08-06] Проверка 50 карточек глазами нашла дыры не в модели, а в моей спецификации: у корпусной мебели не спрашивался орнамент (резная консоль прошла как гладкая), у текстиля узор, у столов не было варианта «крестовина на колёсах» (игровое кресло), у декора форм «арка» и «классическая урна». Модель отвечала верно ровно в тех рамках, что я ей дал.
178. [08-06] Роль товара надо брать из ДЕРЕВА КАТЕГОРИЙ фида, а не из регекса по названию: магазин уже разделил «Шторы и тюль» (474), «Карнизы» (190) и «Шторки для ванной» (165), а все 636 наших «кашпо» лежали в ветке «Товары для сада». Дерево — 1 931 категория, 5 уровней (`feed_taxonomy.py`, `category_map.py` → `products.cat_role`).
179. [08-06] Атрибут родителя категории в фидах бывает `parentId` И `parent_id` — читая только первый, дерево схлопывается в один уровень и вся вложенность теряется.
180. [08-06] Регекс без границы слова: `ковер` ловил «гай**ковер**т» — 27 гайковёртов числились коврами гостиной.
181. [08-06] Поправка «на редкость стиля» множителем даёт обратный перекос: редкие языки систематически побеждают. У пяти люстр подряд выходил «лофт», включая белую классическую и хрустальную. Правильно нормировать каждый стиль по ЕГО собственной шкале (среднее и разброс сырых очков по каталогу, `style-stats.json`): средний товар — пятёрка по любому стилю. Стало: сканди 38%, минимализм 26%, неоклассика 22%, современный 12%.
182. [08-06] Ковров для гостиной в каталоге НОЛЬ даже после чистки по дереву категорий: все 26 позиций «Ковры машинной работы» — коврики 45×80…90×150 и одна противоскользящая подложка. Ни одного с длинной стороной ≥200 см.
183. [08-06] Определяющий маркер стиля обязан быть РЕДКИМ: назначил маркером сканди «мягко скруглённые линии» (есть у половины каталога) — сканди стал побеждать в 45% случаев. Ранг понижается по частоте автоматически (`attr-freq.json`).
184. [08-06] Нормировать надо ту же величину, что измеряешь: статистика по каталогу со старым набором признаков против карточек с новым давала перекос — у новых просто больше свидетельств. Стили нормируются ВНУТРИ товара.
185. [08-06] Вопросы модели и веса оценки должны жить в ОДНОЙ таблице «категория × признак» (`style-matrix.json`): пока это были два места, у пледа спрашивали про ножки, а «отсутствие декора» весило одинаково у комода и вазы. После объединения доля ответов «не применимо» упала с трети до 1.5%.
186. [08-06] Когда алгоритм назначает стиль там, где его нет (искусственная орхидея, детский коврик), лечится не весами, а честным флагом «нейтральный»: если ни один собственный маркер категории не сработал — победителя нет. План `completed_plans/style-neutral-items.md`.

187. [08-06] «Стиля нет» — законный ответ: без него алгоритм назначает победителя там, где выбирать не из чего (детский коврик и искусственный букет получали сканди). Товар нейтрален, если ни один собственный признак категории не сработал в плюс.
188. [08-06] Порог нейтральности ставится замером, а не рассуждением: требование «сработал маркер» объявило нейтральными 66% каталога, «любой вклад своего признака» — 24% при цели 15-35%.
189. [08-06] Всё платное — сперва пробной партией, потом массово (правило владельца). Нарушил: запустил 25 028 запросов сразу, CDN отдал 403 при 24 потоках, молчаливый `except` скрыл это, и прогон ушёл в модель ВСЛЕПУЮ — фото получили 287 запросов из 2000, потеря ≈6-8 $. Теперь: кэш картинок на диск, 6 потоков с ретраями, счётчик отказов в логе и стоп-предохранитель при доле картинок < 90%.

## Уроки 190–195 (2026-08-06, перенесены из core/lessons.md)

190. [08-06] Completed у провайдера ≠ результат в БД: батч «без ошибок» по счётчикам OpenAI, а 2 000 строк в базу не сели. Забор проверять по строкам В БАЗЕ; отправку блокировать, пока прошлый пакет не забран (ADR-0073).

191. [08-06] Ворота качества нужны и ПОСЛЕ дорогого шага: приёмка до оплаты есть, после генерации — нет, брак ловят глаза. При переезде пайплайна QA и ретраи теряются молча — сверять чек-лист старой ветки.

192. [08-06] Зелёная метрика, меряющая не то, хуже её отсутствия: solver_check «ok» при расстановках, которые владелец бракует. Метрику калибровать вердиктами владельца.

193. [08-06] Бенчмарк живёт вместе с данными: «beam 122/126» от 02.08 не перегнали после очистки каталога — честный baseline оказался 79/126, и виноватыми сначала выглядели свежие правки. Сравнение движков перегонять после каждой смены данных.

194. [08-06] Пороги одного правила — в одном источнике: пуф-пороги (60/180) жили только в scout-проверках, ядро о них не знало и массово ставило пуф в 61–80 см. Порог, который проверяется в двух местах, обязан жить в occupancy.json.

195. [08-06] LLM-слою расстановки нельзя доверять КООРДИНАТЫ: пробная партия Э6 (20 сетов) — все варианты с hard-нарушениями после снапа, 100% фолбэк на beam. Словесные схемы разумны — LLM годится для выбора зон/отношений, геометрию должен решать солвер.

**Tier 2:** ../anti-patterns.md (детект в diff; UI — §6–7)

196. [08-08] **Внешние системы расстановки:** ProcTHOR/Holodeck/Infinigen/Function2Scene разобраны по коду и данным — замена ядра не оправдана; формула: полезные абстракции и данные забирать МОДУЛЬНО (asset-groups уже в ядре, нормативы полок уже в правилах), вердикты — «на нашем бенчмарке», не «X слабее Y вообще». Полный разбор: https://remont-lab.online/test/zones-vs-external/ (`tools/scout/pages/`).

197. [08-08] **Массовые прогоны — параллельно, с покадровым resume:** последовательный приёмочный прогон 504 солвер-запусков занял бы ~8 ч; `acceptance_run.py` — N воркеров + jsonl-запись каждой сцены: обрыв/рестарт теряет ноль (169 сцен спасены парсингом старого лога). LAYOUT_SUFFIX уникален на СЦЕНУ — иначе параллельные воркеры дерутся за файлы.

198. [08-08] **Правило-конкурент vs группа:** exclusive-пары («пуф vs кресло» в малых) должны уступать ролям, ТРЕБУЕМЫМ посадочной группой, а невыполнимые группы (кресло 2 при kreslo_max=1) — фильтроваться до выбора: иначе сет заявляет группу, которой физически не собрал (сет 17).

199. [08-08] **Правило в данных ≠ правило в силе:** камин 200–450 см и «диван у окна» жили в zones.json/occupancy.json, но валидатор их НЕ проверял — вердикты владельца поймали оба на проде (set91). Заводя правило в JSON, сразу пиши чек (или явную пометку `_enforce: none`) — иначе правило декоративное.

200. [08-08] **Один лейбл движка — один алгоритмический путь (ADR-0076):** под ENGINE=zoned после планнера молча гонялись 6 DFS-попыток и при меньшем числе нарушений ПОДМЕНЯЛИ результат — A/B контаминирован, таймауты, ×2 время сцены. Скрытые кросс-движковые «спасения» делают цифры бенчмарка недоказуемыми; инвариант закреплён тестом (test_engine_purity).

201. [08-08] **«Просадка» метрики ≠ регресс кода:** прогон с W-правками дал 221/252 против 239 — но 22 из 31 провала оказались «состав стал амбициознее (обеденная/стенка), а required-семантика старая». Прежде чем чинить солвер, разложи провалы по причинам: правки правил, правки составов и качество движка меняются независимо. Фикс — семантика ярусов (retention-priority, дроп ярусом), а не «откат правил».

## Ситуационные каноны и приоры — запрещённые приёмы (19.08, ADR-0112)
- **Сумма ordinal-рангов по разным возможностям** как цель выбора — это скрытые веса: плохой исход
  у окна «компенсируется» углом, а число углов меняет масштаб цели. Приор — только локальный
  тайбрейк при полностью равном верхнем префиксе ключа.
- **Частота как квота**: 28/19/17 — порядок распространённости, а не доли, которые обязан
  воспроизвести детерминированный one-best солвер.
- **Полная декартова матрица «функция × якорь»** — заставляет документировать бессмысленные клетки
  (dining×камин, media×свободный угол). Объявляем только применимые сочетания.
- **Нестабильные ID возможностей** (по индексу во входном массиве) — при перестановке проёмов
  объяснение меняется; ID из канонической геометрической сигнатуры.
- **Повторный запуск солвера ради сертификата** — сертификат обязан проецировать фактический
  search trace, а не считать заново.
- **Классификация исхода по первой встреченной роли в полосе** (скамья у окна ≠ edge_nook) —
  исход определяется по `tpl_id`/якорю схемы.

## Уроки 303–307 (28.08, вырезка фона — застыли в `tools/scout/mask_bench/`, ADR к записи)
- 303 [28.08] **«Тяжелее и в большем разрешении» ≠ лучше.** `birefnet/v2` General Use (Heavy) @2048 выглядел очевидным апгрейдом, а на замере 36 товаров дал 11 провалов против 3 у дефолта: принимает декоративный узор на фасаде комода за фон и стирает фасад в кружево, теряет распорку проволочного столика. Matting @2048 делает крупные светлые фасады полупрозрачными. Апгрейд настроек модели — только через прогон, никогда «по описанию режима».
- 304 [28.08] **Вердикт по стороннему эндпоинту протухает молча.** Анти-паттерн 92 (04.08: `bria/background/remove` проигрывает, ореол 14.8%) стал неверным — fal подменил эндпоинт на RMBG 2.0, и теперь он бьёт `birefnet/v2` (86% против 79% удержания деталей 1–2 px). Перед опорой на старый замер чужого API — перепроверять, дата замера не гарантия.
- 305 [28.08] **Метрика, опирающаяся на тот же признак, что и алгоритм, льстит алгоритму.** «Удержание тонкого» считается по «не фон по цвету», и гибрид пользуется тем же цветом — его 95% частично засчитаны по построению. Сравнение независимых вариантов между собой честно; приёмка алгоритма, который делит признак с метрикой, — глазами.
- 306 [28.08] **Контактную тень нельзя отбраковывать правилом «целиком ниже товара»** — она примыкает к ножкам вплотную, её верх выше нижней кромки соседних частей, и правило пропускает её целиком (поймано на 4 креслах: гибрид приклеивал тёмное пятно под сиденьем). Работает признак по столбцам: пиксель ниже нижней кромки товара В СВОЁМ столбце + низкая насыщенность. Тень, попавшая в маску, становится у генератора плоской геометрией.
- 307 [28.08] **`opening` и заливка дыр в маске запрещены на мебели:** opening убивает однопиксельную проволоку, заливка дыр заклеивает просветы проволочного основания и реечных спинок — то самое, ради чего маску и улучшали.
- 308 [28.08] **Обрывок фона в маске — брак для 3D, а не косметика.** У стула Wishbone (tvoydom, фото-баннер) BRIA RMBG 2.0 оставила зелёный хвост плашки в верхнем углу; для картинки это мелочь, для генератора — геометрия из ниоткуда. Поймал владелец. **Правило: маска перед генератором обязана проходить отбраковку компонент** (`tools/scout/salad/components.py`): держим главное тело, всё, что примыкает к нему ближе 6 px, и крупные (≥25% главного) самостоятельные куски НЕ у края кадра; остальное — фон. По площади не удалять (уйдут второй стул в комплекте, просвет спинки) — признак не размер, а связь с товаром.
- 309 [28.08] **Фото-коллаж (баннер магазина) не чинится вычисткой маски — такой SKU не отдаём на меш.** В кадре плашка с названием, свойства текстом, интерьерная сцена со своим светом и нередко ВТОРАЯ копия товара с другого ракурса (стол Aligery: после вычистки в маске осталась вторая столешница, потому что она крупная и не у края). Детектор — `tools/scout/salad/collage.py`: неровный фон ПЛЮС второй признак (плашка/текст/забитый кадр). **Вызывать ТОЛЬКО после вырезки, передавая настоящую маску:** без маски фактура товара уходит в «текст строками» и мозаичная ваза с рельефным кашпо на чистых карточках ловятся как коллажи (2 ложных из 8 просмотренных на выборке 400).
- 310 [28.08] **Фон нельзя мерить квантилем расстояния по пограничной полосе** — широкий товар во всю ширину кадра залезает в полосу, и чистая белая карточка получает «разброс 312» (комоды, тв-тумбы уезжали в коллажи). Мерить ДОЛЮ пограничных пикселей, непохожих на медиану полосы: товар занимает малую часть полосы, доля устойчива.
- 311 [28.08] **«Насыщенная область большой площади» — не признак баннерной плашки:** зелёный корпус тв-тумбы на белой карточке давал «плашку 0.32». Плашка = насыщенная область, которая упирается в край кадра И залита ровно (разброс цвета внутри < 18); у товара всегда есть текстура и градиент.
- 312 [28.08] **Приблизительная маска в проверке может ПЕРЕВЕРНУТЬ вывод, а не просто огрубить его.** Замер доли коллажей среди мебельных ролей дал ровные 0 из 363 — и это был артефакт: вместо маски сети подставлена аналитическая («не фон по цвету»), а на коллаже она покрывает 88% кадра, снаружи товара не остаётся ничего, и признаки баннера физически некуда попасть. Оба заведомых коллажа с ней тоже читались как «не коллаж». Правило: подменяя вход проверки суррогатом, сперва прогнать суррогат на ИЗВЕСТНЫХ положительных примерах — «ноль находок» подозрителен сам по себе.
- 313 [28.08] **Готовность артефакта надо привязывать к ВЕРСИИ входа, а не к объекту.** `mesh_ready` брал любую принятую ревизию SKU — магазин менял фото, а меш от старой картинки продолжал числиться готовым, и «заменитель с готовым мешом» оказывался мешом другого на вид товара. Сверка идёт по `source_sha` текущего фото (`split_part(revision_key,'|',2)`), ориентация — по той же `revision_key`, иначе вердикт старой ревизии подтверждает новую, которую никто не смотрел.
- 314 [28.08] **`least(old,new)` в upsert приоритета делает приоритет липким:** товар, однажды побывавший в сете, навсегда оставался приоритетом 1, и очередь генерации выстраивалась по прошлому, а не по спросу. Производные поля пересчитывать, а не «минимизировать».
- 315 [28.08] **Идентичность объекта заводить ДО того, как на неё начнут ссылаться.** Сцены приёмки названы по НОМЕРУ сета (`setN-base`), отчёты хранят `"set": 72` — перестановка массива молча переадресует их на соседние комплекты, и точечная пересборка честно считает не те сцены. Стабильный `set_id` (`tools/scout/set_identity.py`) детерминирован по полям ЗАМЫСЛА, а не состава: замена товара сет тем же сетом и оставляет.
- 316 [28.08] **Жёсткое правило, включённое разом, останавливает систему.** «Замена только на товар с готовым мешом» при покрытии резерва 0% обнулило бы ночное лечение: каждый выбывший товар оставлял бы дыру. Вводится этапно (`HEAL_REQUIRE_MESH=prefer|require`), лечение идёт двумя проходами — сперва кандидаты с мешом, потом остальные. Та же логика у `PHOTO_FIT_PHASE` и `MESH_GATE_PHASE`.
- 317 [28.08] **Пороги «из головы» дороже, чем кажется.** Первые ворота пригодности фото (минимальная сторона товара по ролям) забраковали бы 78% каталога: у торшера и стеллажа короткая сторона мала по природе предмета. Мерить длинную сторону, пороги брать из распределения и ставить ниже наблюдавшегося минимума.
- 318 [28.08] **Измерения и политику хранить раздельно.** `photo_assessment` держит ВСЕ метрики по (байты фото, версия оценщика), `photo_fit.py` — только пороги. Иначе смена порога требует заново считать маски всему пулу, а смена алгоритма переписывает историю.
- 319 [29.08, наблюдение владельца] **Полупрозрачное и «фон сквозь товар» — известный класс отказов вырезки, ~5%.** Симптомы: у ковра вырезается основа, а узор остаётся (или наоборот); прозрачное стекло в декоре теряется целиком. Причина не в пороге: **оптическая альфа и геометрическая занятость — разные величины**, а сеть даёт первую. Для формы стеклянной панели нужна occupancy-маска (предмет ЕСТЬ, хотя сквозь него видно), иначе генератор честно строит пустоту; для ковра узор и основа получают разную альфу и распадаются на компоненты. Решение владельца 29.08: **оставить как есть** — 5% не оправдывают отдельного `alpha_shape`. Ковры и мягкий декор в меши и так не идут (`MESH_EXCLUDE`), так что бьёт это в основном по витрине. Вернуться, когда появится пилотная статистика по стеклянным ролям (витрина, столик со стеклом).
- 320 [29.08] **Сбой проверки нельзя записывать как отрицательный вердикт.** `img_alive._probe` возвращал False на ЛЮБОМ исключении — таймаут, обрыв, троттлинг CDN. Ночной обход `imgng.gdeslon.ru` упирался в лимит темпа, и живые товары получали «фото мертво» на 14 дней: в кэше 12 632 мёртвых, при спокойной перепроверке 150 ссылок живыми оказались **122 (81%)**. Бьёт прямо в продукт: `_slot_ok` спрашивает `alive_now`, значит живой товар молча выбрасывался из сетов, а пул «может попасть в сет» выглядел как 5.7k вместо ~14.7k. Проба стала трёхзначной (True/False/**None**): приговор — только по явному ответу сервера (404/410 или 200 с не-картинкой), «не смог проверить» в кэш не пишется. `PROBE_V` поднят до 3, чтобы ложные приговоры перепроверились.
- 321 [29.08] **Правку вырезки применять по роли, а не глобально.** Рост маски по связности вернул ковру потерянное поле (сеть держала только линии узора), но на мебели цеплял мягкую тень и подложку — увидел владелец на контрольных снимках. Отказы у разных ролей разные по природе: у ковра низкоконтрастное поле на белом, у стеллажа настоящие просветы. Поэтому `hybrid_mask.GROW_ROLES = {'ковёр'}` и `components.SOLID_SILHOUETTE_ROLES = {'ваза','кашпо','статуэтка'}` — точечно, остальные 95% идут как раньше. Мебель со сквозными просветами (стеллаж, витрина) в заливку не входит: там просветы настоящие.
- 322 [29.08] **Прозрачность и занятость — разные величины, и потребители у них разные.** Сквозь стеклянную вазу видна карточка, сеть честно ставит альфу к нулю, и от вазы остаётся ободок: витрине так и надо, а генератору меша нужен СИЛУЭТ, иначе он строит пустоту. Лечится не порогом, а знанием роли: у вазы/кашпо/статуэтки сквозных просветов не бывает, значит внутренние дырки можно заливать не спрашивая, что внутри. Явного «стекла» в пуле мало — 46 товаров по названию и материалам, из них 39 вазы.
- 323 [29.08] **Инцидент: сломанная проба выбросила 126 товаров из комплектов за одну ночь.** Ночное лечение 29.08 заменило по товару в КАЖДОМ из 126 комплектов с причиной «умерло фото» — сработал урок 320: `img_alive._probe` записывал троттлинг CDN как приговор. Проверка починенной пробой: из 126 выброшенных **119 живы, 0 мертвы, 7 не проверились**. Уроки: (1) **лимит «одна замена на сет за ночь» ограничил ущерб, но не предотвратил его** — при системной ошибке предиката он даёт ровно N сетов вместо всех слотов; нужен ещё и предохранитель на ДОЛЮ сетов, затронутых за прогон (126 из 126 — это не лечение, это авария); (2) журнал замен окупился в первый же день — без `set_id` и `old_sku` точечный откат был бы невозможен; (3) прежде чем чинить предикат, надо смотреть, что он уже успел натворить.

- 325 [29.08] **«Есть строка в таблице» ≠ «этап пройден».** Конвейер заводит строку `product_enrichment` новинке СРАЗУ (заглушка: `model_name IS NULL`, `enriched_at IS NULL`, качества нет), а LLM приходит позже — и 12 дней не приходил (`openai.off` с 17.08). - 326 [29.08] **Текстовый маркер «нет в наличии» нельзя применять без проверки на заведомо живых.** `health.MARK` находил «Нет в наличии» в ШАБЛОНЕ каждой страницы divan.ru (переключатель вариантов) — на пяти живых по фиду товарах маркер соврал 5/5, и `health.py` за ночь погасил `in_stock` у 119 товаров комплектов (все divan.ru). Починка: положительный признак (кнопка «В корзину», qty>0) сильнее любого текста; sold-out верим только у заголовка товара; сбой сети → None, наличие не трогается. Каскад инцидента: битые вердикты → утреннее лечение заменило 119 слотов → откат по журналу → «119 вне контракта» → раскопка до корня. Каждый слой честно работал по лживому входу.

Вскрылось лишь потому, что воскреситель дал «0 живых» против ручного теста. Правило: каждый программный patch — с `assert old in s` (как в остальных правках сессии) И с прогоном на живом примере ПОСЛЕ записи файла, а не до.
- 328 [29.08] **Порог живучести обязан ПЕРЕКРЫВАТЬ время старта.** Проверка готовности Salad имеет потолок (задержка ≤1200 с), а холодный старт ноды ~35 мин — инстанс при живом сервисе навсегда помечался неготовым, шлюз отдавал 503, нода 15 часов тарифицировалась впустую. Не подгонять пороги, а убирать зависимость: `/health` = «жив», гейт готовности — в рабочем эндпоинте.
- 329 [29.08] **Облако тарифицирует СОСТОЯНИЕ, а не работу карты:** `running` идёт в счёт целиком, включая прогрев, докачку весов и простой. Скачивание образа при этом бесплатно — значит тяжёлый образ с весами внутри дешевле лёгкого с докачкой (ADR-0135). Гасить группу сразу после прогона.
- 330 [29.08] **На exit-fi `INPUT DROP`:** контейнер не достучится до сервиса, поднятого на шлюзе docker-сети. Сервис для контейнеров ставить КОНТЕЙНЕРОМ в ту же сеть, а не на хост: iptables на машине с боевым VPN не трогаем.
- 331 [29.08] **Скрипты scout с кодом на уровне модуля** (`health.py`, `style_score.py`) исполняют ПОЛНЫЙ прогон при `import` — поймали дважды за день (импорт health в тесте запустил скан 716 страниц и чуть не перезаписал наличие). Читать чужой модуль перед импортом; функции доставать парсингом файла, если модуль «исполняемый».
- 332 [31.08] **Пул исполнителей, снятый один раз на старте, не переживает эластичное облако.** `salad/ssh_run.py:run()` собирает тёплые ноды перед созданием очереди и держит по потоку на порт: волна из 91 задания шла на ОДНОЙ ноде ~3,5 часа, пока Salad поднимал рядом вторую и третью — прогон их не видел. Сопутствующие дефекты того же места: `transport_failed` пишется в результаты и НЕ возвращается в очередь; `ssh_run` всё равно выходит с кодом 0, а `batch_show` прибавляет к `done` ВЕСЬ размер пачки (в логе «заданий 5, готово 3» → счётчик +5) — задания теряются молча, счётчик пилота завышен; мёртвая нода может мгновенно провалить весь хвост очереди; `cull_slow_pulls()` вызывается только в паузах ожидания, то есть во время долгого прогона зависшие загрузки никто не пересаживает; `stop_group()` не в `finally` — при исключении группа остаётся тарифицироваться. Правило: у динамического пула исполнителей должен быть супервизор (периодический discovery по стабильному id инстанса, а не по ssh-порту — порты переиспользуются), а у задания — жизненный цикл с возвратом в очередь и терминальным статусом; счётчик прогресса двигать по терминально закрытым заданиям, а не по размеру пачки. Разбор с Codex и правка — `plans/mesh-dynamic-node-pool.md`.
