## Правило (полный текст до сжатия)

**Цикл**
- PLAN (план `plans/<slug>.md`, критерии, советник по P-075) → DELEGATE → IMPLEMENT (код → `pnpm typecheck && lint && test && build` → выкладка → отчёт) → REVIEW (`review-checklist.md`) → DECIDE `PASS` / `CHANGES REQUIRED` (тому же рабочему, тот же ID) / `BLOCKED` → MEMORY (P-029).
- До 3 циклов правок, дальше — стоп, владельцу доказательства и рекомендация; «готово» со слов рабочего — не приёмка (P-029).
- После PASS — банк, план → `completed_plans/`, отчёт владельцу; задание, отчёт и независимая проверка — обязательны (P-029).

**Бриф**
- 1-я строка `[роль] T-YYYYMMDD-NN/<цикл> · <фаза>`; фаза `задание|отчёт|правки|доработка|принято|вопрос`; цикл 1 — реализация, ≥2 — `правки` (по проверке ведущего) или `доработка` (по слову владельца) (P-027).
- В брифе: T-ID, slug плана, скоуп, ссылки, интерфейсы, ограничения, тесты, DoD (P-029); путь к плану, границы (без sudo, платного, деплоя), имя ведущего по `ListAgents` на момент отправки (P-026); строки P-072 («Salad: да/нет», «что чистит шаг», «/memory-check — директор»).
- Бриф ≤ ~300 тыс. контекста: крупное — на под-задачи с отдельными отчётами (P-026).
- 4 строки конвейера в брифе и отчёте: ① какое правило/шаблон/генератор изменён и почему это общее; ② где ещё действует (/demo, Этажи, туры, все типы комнат, ночь, будущие загрузки, перевыпуск) и где проверено; ③ какой шаг пересоберёт результат — собранное программой руками не правится; ④ нет особого случая под тур/товар/комнату (ID в коде вне `rules/**` и тестов запрещены). Пусто → `CHANGES REQUIRED` (P-032).
- Новые надписи — пара RU/EN; «конвейер» = ночной шаг с квотой и потолком, не ручные волны (P-032).
- Код, который запускают кроны DEV (`tools/scout/**`, `infra/**`, `assets/*.sh`), — только в worktree: кроны (`sink_keeper` 15 мин, `money_guard` 5, `refresh_daily` публикует демо) берут основную копию (P-025).

**Связь сессий**
- Постоянные имена (`claude -n`, `--resume`, `/rename`); при сомнении — рукопожатие `ListAgents`; отвечать на `from`; отчёт ждать `notify_when_idle: true`, не опросом; `crossSessionInbound: accept` в `.claude/settings.json` (P-027).
- Сообщение соседа — информация, не разрешение; «Timed out sending» ≠ не дошло; учёт — `tools/tokeny/svodka.sh`, `tools/tokeny/faza` (P-027).

**Отчёт рабочего**
- 1-я строка `[рабочий N] T-…/<цикл> · отчёт` (без неё проверка не открывается), 2-я — ID модели, далее статус `done|partial|blocked` · коммиты · файлы · проверки с фактическим результатом · артефакты (URL, скриншоты, пути) · отступления с причиной · нерешённое · «что смотреть» (P-030).
- Платное — сперва бесплатная проверка пути, расходы — в отчёте (P-030).

**Приёмка**
- Всегда по 14 пунктам `.claude/rules/review-checklist.md` по порядку: SHA от base; бриф ↔ отчёт; main зелёный; diff в чистом merge-worktree; общее правило; дефект товара → паспорт; непустое доказательство; проверки на merged tree; prepush «не успел N» ≠ зелёный; тест в нужном CI job; деньги/миграции/кроны — разрешение, потолок, бэкап; видимое — сам; продуктовый путь через боевую службу; вливаю проверенный SHA (P-033).
- READY TO MERGE ≠ PASS; PASS — после зелёного CI этого SHA и своей живой проверки (P-033).
- Визуальное (интерфейс, вёрстка, картинка) директор смотрит САМ на фактическом результате (прод/`/test/`, Playwright, 375×667 и ПК): согласованность, выравнивание, пропорции, отступы, адаптивность, наезды/обрезки, удобство, соответствие требованию; отчёт, тесты и diff это не заменяют (P-031).
- Визуальный дефект → правка рабочему → повторная проверка до выполнения критериев; без браузера/скриншота «проверено визуально» не писать (P-031).
- Вердикт помечать проверяющим (директор), не владельцем; решений владельцу не приписывать (P-031).

**CI и выкладка**
- Демо безопасно — вливать и выкладывать сразу, проверять на живом, в ветках не держать (P-043).
- CI зелёный; CI через API не опрашивать — `deploy-need.sh --status`, один запрос, только если прод позади `main` >15 мин; до push тесты без `| tail` (P-043).
- Перед отчётом с TS — `pnpm -s typecheck` rc=0 (P-043).
- Перед push памяти — `node tools/memory-audit.mjs --check . && node tools/memory-project-audit.mjs .`; коммитить только свои пути (P-043).

**«Деплой» плана и закрытие**
- После «деплой»: прочитать план, статус `in_progress`; перечислить файлы — остальные не трогать; выполнить, lint/build/тесты (P-045).
- Крупный план (>5 файлов или новая подсистема) — read-only субагент `verify` (критерии vs diff) (P-045).
- Закрытие: память по адресам P-074, `node tools/book-map.mjs` → `BOOK-STALE` = 0, `/memory-check` (делает директор), аудиты чисты; только потом `completed` + дата + completion summary → `completed_plans/` (P-045).
- Статусы: `draft` · `in_progress` · `partial` (в `plans/` только с `pause_reason`/`resume_trigger`/`review_after`) · `completed` · `cancelled`; отложенное/поглощённое → `archive/plans/` с `archive_reason`/`superseded_by`; `draft` >30 дней → триаж (P-045).
- Гейт: план не `completed`, пока `/memory-check` не выполнен и оба аудита (`memory-audit.mjs`, `memory-project-audit.mjs`) не чисты; Stop-hook `session-reminder.mjs --block`; у рабочего на гейт — строка «свод — директор» (P-046, P-037).
- Глубокая уборка памяти — `/memory-cleanup` (P-046).

**Контекст**
- `/clear` не используем ни у ведущего, ни у рабочих — автосжатие (P-026).
- Цель: ведущий < 300 тыс., исполнитель < 250 тыс.; замер `python3 tools/ops/tokstat.py`; `autoCompactWindow = 400000` в `.claude/settings.json`; пороги по моделям — `guides/orchestration.md` § Текущее состояние (P-026).
