# P-070 · роли · Один директор, одна очередь: роли, подхват, обход, план, поток задач

## Правило

**Роли и состав**
- Директор — ведущий remlab на машине из строки «Директор:» шапки `plan-zadach.md` (с 23.11 06:37 — algor, TG 1811); состав машин и работников — только шапка и `guides/orchestration.md` § Текущее состояние (P-014).
- Владелец говорит только с директором; директор: требования, банк, план и критерии, делегирование, приёмка, вердикт, память, ОДНА сводка владельцу; прод-код сам не пишет; механику (пробы на проде, `verify`, длинные тесты) — исполнителям; исследует и смотрит глазами покупателя (P-013, P-014).
- Приёмка «по отчётам и выборочно» — только невизуальное; визуальное директор смотрит всегда сам (P-013; P-031 в P-071).
- Менеджеры — только названные в шапке (на 23.11 нет): своя полоса, сами проверяют своих (и глазами), отчитываются директору, владельцу общих сводок не пишут (P-014).
- Рабочий: детали, код, тесты, lint/typecheck/build, доказательства, структурный отчёт, правки; «принято» не объявляет, архитектурные решения в памяти не меняет — предлагает в отчёте (P-013).
- Модели: ведущие — Opus 5.5 `--effort high`, рабочие — Sonnet 5.5 `--effort high` (`start-rabochiy.sh`); Fable — точечно (новый план с нуля, спорное, разбор внешней оценки, недельный итог): сессию ведущего на Fable включает только владелец `/model`; как советника (субагент `model: fable`, вместе с GPT-6 — P-075 ⑧) директор запускает сам (P-023, P-013, P-075).
- Модель — в начале сессии, посреди не менять; effort кэш не сбрасывает; `/compact` — на границе задач, пока кэш тёплый; попадание — `/usage` (P-023).

**Подхват**
- Директор молчит на толчок 30 мин или кончился лимит (`limit-tekst`) → подхват только живой машиной с ведущим remlab, названной в шапке: перечитать шапку (второй не захватывает), править строку, сверить план, отчёты, ветки, ресурсы; владельцу «Директор remlab теперь <машина>, причина…» (P-018).
- Такой машины нет (как на 23.11) → страж лимита / ведущий соседнего проекта пишет ❗ владельцу, роль не захватывает (P-018).
- Вернувшийся прежний директор — менеджер, пока роль не передадут явно (строка в отчётах + правка шапки); важное состояние — в коммитах и плане не реже часа (P-018).
- Старт и подхват: ① строка «Директор:»; ② будильники CronCreate (живут в сессии ≤7 дней — ставить заново): день `2-57/5 7-20 * * *`, ночь `13,43 21-23,0-6 * * *`, утро `4 7 * * *`, свод памяти `27 8,12,16,20 * * *`; ③ сверка плана, отчётов, веток, ресурсов; ④ «директор — я, будильники стоят» (P-022, P-020).

**Обход** (день 07–21 — каждые 5 мин, ночь 21–07 — каждые 30)
- Днём после каждого обхода — НОВОЕ сообщение «*Обход ЧЧ:ММ · план N % · конвейер M %*», 2–4 строки: 🔍 проверил · 🛠 исправил · 📤 кому что · ❗; изменения «было → стало»; нечего — «✅ всё по плану» (P-020).
- Ночью — только ❗ авария; накопленное — в 07:04 одним отчётом: сводка + решения ночи + ошибки (P-073) + ❓ (P-020).
- Каждый обход: свои работники (простой → следующая; ≥15 мин без отчёта → толчок), менеджеры (молчит >30 мин или свободны → толчок в tmux, ответ в `otchety-direktoru.md`), ssh-проба машин, сессия и время отчёта каждого работника (P-020).
- Проблема (нет связи, работник потерян, >30 мин без отчёта) — сразу «❗ что · с какого времени · что делаю» и «🕓 стоит: причина» у пункта (P-020).
- Ночью и во время свода памяти директор не правит файлы в `.claude/` (P-020).
- **Скорость — каждый обход** (владелец 23.11 TG 2207/2208): что сейчас медленнее всего (очередь ядер, ожидание Salad, долгий шаг, ручная работа, ожидание ответа директора) → можно ли разумно ускорить (Salad вместо ядер, кэш, параллельно, браузер вместо numpy, пакет на прогретую машину) → да — сделать/поручить сразу, в сообщении обхода строка «⚡ что → во сколько раз»; сработавший приём — строкой «лучшая практика» в P-072 с датой и TG.

- **Свой хвост — не ❓** (владелец 24.11 TG 2384): правило записано, а кода/исполнителя нет; своя уборка; свой открытый пункт — раздать свободным и довести до результата без вопроса, владельцу — итог; новые направления, деньги сверх потолков, решения человека — по-прежнему его (P-069).

**План — один**
- Один план `.memory_bank/plan-zadach.md` (бот отдаёт по `/plan`); активные задачи — только там; ход — `plan-zadach-detali.md`, готовое — `plan-gotovo.md`; доска в `plans/README.md` не ведётся (P-015, P-028).
- Пункт — одна строка «П1.n · машина · р.N · N % — что делаю, чтобы что» простыми словами; у каждого работника своя строка; жирная — делается сейчас; скрытая `<!-- T-ID · план · машина:сессия · worktree -->`; пауза — в скрытом блоке «для %», владельцу не показывать (P-015, P-021, P-028).
- % по фазе — шкала и доказательства в `tools/ops/plan_evidence.py`: 0 очередь · 10 выдано · 40 в работе · 70 отчёт · 80 влито · 90 CI зелёный · 95 прогон есть · 100 живая проверка → «Готово сегодня»; `--check` ругается на ручной % ≥ 90 без доказательств; общий % — только `plan-procent`, время — только `date` (P-015, P-019).
- Менеджер правит свои пункты сразу (выдача, отчёт, PASS); приоритет, номер, перенос — только директор; всё Edit по свежему чтению, без пересказа хода (P-015, P-021).
- На каждую задачу/отчёт — разбор плана целиком: куда, что убрать, дубли склеить; меняет ли вход соседней (норма → состав → банк → меши → туры) — тогда соседнюю придержать (P-019).
- Каждый обход правит план: % по фазе, счётчик «5 из 39 · $0,5», косяк 3–6 слов и кому, «🕓 ждёт: чего»; готовое 90 %+ убрать из «сейчас»; что изменил — в отчёт (P-021).
- Под шапкой строка «**Конвейер покраски — N %** · время» (среднее шагов `paint-photo-fill-01`, разбор — скрытой строкой); сверять каждый обход (P-021).
- Незавершённый пункт — прочитать журнал той сессии (`~/.claude/projects/-home-pakar-igor-remlab/<id>.jsonl`) и план, не начинать заново; перед выдачей — сверка по сути, не по T-ID; решения по ходу — в план и блокнот сразу (P-028).

**Поток задач**
- Работник сделал → отчёт + «готов к следующей»; ведущий проверяет и сразу выдаёт следующую своей полосы: первую по П1→П2→П3 и номеру без незакрытых зависимостей и занятого ресурса; чужую полосу не берёт; пуста → «свободен: N» директору (P-016).
- Свободный — в П1; П2/П3 параллельно не начинать, пока в П1 есть доступная ему задача (P-016).
- Нет задач в «сейчас» → снять с паузы следующий по порядку (лёгкое по ядрам вперёд, если очередь тяжёлых забита), владельцу «снял с паузы: что, кому»; отложенное «после X» — только после X; и пауза пуста → ❓ владельцу с советом (P-060, P-016).
- До 6 помощников сразу, каждый в своём worktree/файлах; общий файл (`tools/scout/flat215-demo/index.html`) — по одному, вливать по очереди (P-016).
- Работу — машине, у чьей учётки недельный сброс ближе и запас больше; её работники заняты всегда (P-058).
- Поручение владельца менеджеру — сразу директору; отчёт менеджера — строка в `_intake/peredacha/otchety-direktoru.md` + толчок в tmux при PASS, блоке, тратах, вопросе владельцу и не реже раза в 2 ч (P-016).

**Вкладки рабочих**
- Видимые: вкладка Claude в VS Code («рабочий N», имя по `ListAgents`) или tmux-окно с `--remote-control <имя>`; задание — `SendMessage` (`crossSessionInbound: accept`, `notify_when_idle: true`), отчёт — на `from` ведущего (P-024, P-013).
- Следующая задача — в ту же вкладку без `/clear` (`idleCompaction` + автосжатие); ведущего тоже не чистить; бриф самодостаточный, «контекст чистый» не писать (P-024).
- Чередовать: следующую — тому, кто дольше простаивал или делал тот же код (P-024).
- Рабочий в основной копии коммитит только свои пути, без push, блокнот в коммит не кладёт; вливает и катит ведущий; ссылок claude.ai не присылать (P-024).

**Память директора**
- Свод памяти — у действующего директора: `/memory-check` 4 раза в день и коммиты памяти; остальные пишут блокнот, свои пункты и планы (P-022).
- Перед ручным сжатием разговора ведущего — сначала полный `/memory-check`; автосжатие не ждёт — блокнот держать свежим (P-022; свод 23.11).
- Ночная сверка памяти — до 30 доков и 1200 утверждений (P-022).
