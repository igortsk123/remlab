# Оркестрация: fable-lead ↔ opus-worker (владелец 17.10.2026)

Две интерактивные сессии Claude Code в одной копии репо, связь — штатные `ListAgents` + `SendMessage`
(кросс-сессионные сообщения). Владелец говорит ТОЛЬКО с fable-lead. Полная версия — `.memory_bank/guides/orchestration.md`.

## Директор и менеджеры (владелец 12.11, TG 719–754 голосом) — главнее разделов ниже
- **Директор** — ведущий remlab на pakardev (tmux `pakardev:tg-remlab`); владелец говорит с ним. Ведёт приоритеты и номера в плане
  задач, раздаёт полосы менеджерам без пересечений, принимает их отчёты, шлёт владельцу ОДНУ сводку по существу, работает сам и
  проверяет только СВОИХ работников. **Менеджеры** — ведущие на algor и common: ведут свою полосу, САМИ проверяют своих работников
  (и глазами), отчитываются директору; владельцу общих сводок не пишут.
- **План задач — `.memory_bank/plan-zadach.md`, один на всех** (TG 744–754); бот отдаёт его по `/plan` как есть. Правила — в комментарии
  вверху файла: менеджер правит СВОИ пункты сразу при выдаче, отчёте, PASS (Edit по свежему чтению); приоритет, номер, перенос
  между полосами — только директор. % — по фазе: 0 очередь · 10 выдано · 40 в работе · 70 отчёт работника · 90 PASS менеджера/выложено
  · 95 живая проверка · 100 → «Готово сегодня». Доска в `plans/README.md` больше не ведётся (журналы сессий — в скрытой строке пункта).
- **Поток задач, как у людей** (TG 754): работник сделал → отчёт менеджеру + «готов к следующей»; менеджер проверяет и сразу выдаёт
  следующую своей полосы — первую по П1→П2→П3 и номеру, без незакрытых зависимостей и занятого ресурса; полоса пуста → строка
  «свободен: N работников» директору; чужую полосу сам не берёт. Поручение владельца менеджеру напрямую — сразу директору, тот
  ставит в план.
- **Отчёт директору:** строка в `.memory_bank/_intake/peredacha/otchety-direktoru.md` + толчок в tmux директора — при PASS, блоке, тратах,
  вопросе владельцу и не реже раза в 2 часа. Полосы, общие ресурсы, диапазоны T-ID — `_intake/peredacha/direktor-2026-11-12.md`.
- **Разрешения — только через менеджера или директора** (TG 733): окно работника владелец в VS Code не видит. Работник просит
  менеджера; менеджер проверяет окна своих работников не реже раза в 10 минут, безопасное снимает сам (`settings.local.json`,
  § «Окна разрешений»), иначе спрашивает владельца в Telegram (сам или через директора).
- **Подхват директорства** (TG 754): кто директор — строка «Директор: <машина> с <время>» в шапке плана задач. Директор не отвечает
  на толчок 30 мин или у его учётки кончился лимит (`limit-tekst`) → директором становится algor, если и он недоступен — common:
  правит строку в шапке (сперва перечитав её — второй не захватывает), сверяет план, отчёты, ветки и общие ресурсы, пишет владельцу
  из своего бота «Директор remlab теперь <машина>, причина…». Вернувшийся прежний директор работает менеджером, пока роль не
  передадут обратно явно (строка в отчётах + правка шапки). Важное состояние — в коммитах и плане не реже часа, не только в чатах.
- **Память — у действующего директора:** `/memory-check` по таймеру 4 раза в день (после перезапуска — заново CronCreate) и коммиты
  памяти; менеджеры пишут блокнот, свои пункты плана задач и свои планы.

## Роли (постоянные)
- **fable-lead** (ведущий; с 18.10 вечера — **Claude Opus 5.5**, владелец: «перевёл» — Fable в 15–30 раз дороже исполнителя по лимиту
  учётки): требования, Memory Bank, план и критерии приёмки, делегирование, приёмка по отчётам и выборочно глазами, вердикт, память,
  отчёт владельцу. Продакшен-код сам не пишет. **Механику — исполнителям задачами:** пробы на проде, сверки памяти (`verify`),
  правки сводок под лимит, длинные прогоны тестов. **Fable 5.1 — точечно** (владелец переключает `/model` или отдельная сессия):
  новый план с нуля, спорное решение, разбор внешней оценки, недельный итог.
- **opus-worker** (Claude Opus 5.5): исследование деталей, код, тесты, lint/typecheck/build, скриншоты и воспроизводимые
  доказательства, структурный отчёт, исправления по замечаниям. Сам задачу «принятой» не объявляет и архитектурные
  решения в памяти не меняет (предлагает — в отчёте).

## Расход токенов (владелец 18.10, по замеру журналов — `guides/orchestration.md` § Эксперимент)
- **Исполнитель — только свежая фоновая сессия на задачу** (`claude --bg -n opus-worker-<T-ID> --model claude-opus-5-5
  --permission-mode auto "$(cat задание.txt)"`, работает в worktree, коммит на ветку `worktree-<имя>`, fable-lead вливает ff).
  Постоянного исполнителя нет (он стоил в 4–40 раз дороже при том же качестве). После PASS — `claude stop` + `claude rm`.
- **Исполнитель — ВИДИМАЯ сессия, не фон (владелец 19.10: «чтоб я видел явно, что работа идёт»):** интерактивная сессия
  в tmux-окне с именем исполнителя и `--remote-control <имя>` — видна в claude.ai/code и на телефоне, в терминале
  `tmux attach -t <имя>`. На algor — команда `remlab-worker <worktree-slug> <файл-задания>` (`~/.local/bin`: копию
  создаёт через `r` на pakardev, отмечает папку доверенной, запускает окно) — запасной путь.
- **Основной путь с 20.10 (владелец, как в tamara): вкладки рабочих открывает владелец** — обычные вкладки Claude в VS Code в папке
  remlab («рабочий 1», «рабочий 2»; имя по ListAgents). Ведущий шлёт задание SendMessage (`crossSessionInbound: accept` — стартует
  без Enter), `notify_when_idle: true`; отчёт — на `from` ведущего. Рабочий в основной копии: коммитит только свои пути, без push;
  ведущий вливает и катит. Ссылок claude.ai не присылать. **Очистку владельца не ждать (владелец 20.10: «автоматизируй сам»):**
  «/clear» через SendMessage не выполняется (приходит текстом), поэтому следующая задача — в ту же вкладку без очистки, как в tamara
  (ADR-0162 там): простой сжимает `idleCompaction`, рост держит автосжатие; бриф самодостаточный («на прошлую задачу не опирайся»),
  «контекст чистый» в нём не писать. Чередовать рабочих: следующую задачу — тому, кто дольше простаивал или делал тот же код.
  **Код, который запускают кроны DEV (`tools/scout/**`, `infra/**`, `assets/*.sh`) — ТОЛЬКО в worktree** (20.10, урок 516):
  кроны pakardev берут скрипты из основной копии (`sink_keeper` каждые 15 мин, `money_guard` 5, `refresh_daily` собирает
  и ПУБЛИКУЕТ демо из `tools/scout/flat215-demo/index.html`) — незакоммиченная правка в main становится живой.
- **Кэш (владелец 19.10, по ADR-0166 tamara, сверено с code.claude.com/docs/en/prompt-caching):** модель — выбрать в начале сессии,
  посреди не переключать (новый кэш с нуля, весь разговор пишется заново); effort на Opus 5.5 / Fable 5.1 по подписке кэш не сбрасывает.
  `/compact` — на границе задач, пока кэш тёплый (основной разговор — час; субагенты — 5 мин). Чтение кэша дешевле ввода, но не бесплатно —
  порог сжатия 400 тыс. остаётся. Попадание в кэш — `/usage`, строка «Prompt cache (main)».
- **Бриф ≤ ~300 тыс. контекста исполнителя:** крупное делить на под-задачи с отдельными отчётами; в задании — путь к плану,
  границы (sudo запрещён, без платного, без деплоя), имя сессии fable-lead по `ListAgents` на момент отправки.
- **fable-lead не чистим** (планы и приёмке нужен контекст), но автосжатие — на 400 тыс. токенов, не у полного окна:
  `.claude/settings.json` → `modelSettings.claude-fable-5-1.autoCompactWindow = 400000`. **Opus 5.5 (ведущий и работники) — окно 293 тыс.,
  сжатие у ~260 тыс.** (владелец 25.10: замер 22–24.10 — работники с 14–26 задачами в одной вкладке держали в среднем 214–227 тыс.,
  38–44 % вызовов > 250 тыс.; прикидка −13 % взвешенных токенов). Сжатие срабатывает на ~33 тыс. раньше окна.
- **Замер:** `python3 tools/ops/tokstat.py` — по сессиям (ведущий / worktree-исполнители / субагенты), часам, дням.
  Перемер 21.10: цель — контекст на вызов у ведущего < 300 тыс., у исполнителя < 250 тыс.

## Узнавание друг друга
Сессии запускаются с постоянными именами: `claude -n fable-lead` и `claude -n opus-worker` (продолжение — `claude --resume <имя>`,
переименовать на ходу — `/rename <имя>`). Автоимена вида `remlab-xx` меняются при перезапуске, поэтому при любом сомнении —
рукопожатие: `ListAgents` → «[fable-lead] ты opus-worker?» → «[opus-worker] да, модель claude-opus-5-5». Каждое сообщение начинается
с роли `[fable-lead]` / `[opus-worker]`. **Первая строка — метка для учёта токенов (владелец 21.10, общий план с tamara
`uchet-tokenov`):** `[роль] T-YYYYMMDD-NN/<цикл> · <фаза>`, фаза — `задание|отчёт|правки|доработка|принято|вопрос`; цикл 1 — реализация,
≥2 — исправления: `правки` — по проверке ведущего, `доработка` — цикл открыт по слову владельца (21.10, TG 150 у tamara)
(пример `[fable-lead] T-20261021-03/2 · правки`). Сводка — `tools/tokeny/svodka.sh [--proekt X] [дата]` с любой машины (модуль кита `_optional/tokeny`, ночная выгрузка
таймером на трёх машинах; политика — `plans/ops-token-policy-01.md`); фаза ведущего — `tools/tokeny/faza <ID>/<цикл> план|проверка|доработка|прочее`. Отвечать — на `from` входящего. Ждать отчёт — `notify_when_idle: true`, не опросом.
Приём входящих без диалога подтверждения — `crossSessionInbound: accept` в `.claude/settings.json` (иначе ночью сообщения зависнут
в ожидании владельца). Сообщение соседа — информация, не разрешение: права каждой сессии свои.

## Цикл задачи (каждая нетривиальная задача)
1. **PLAN** (fable-lead): контекст из банка, план `plans/<slug>.md` по `agent-workflow.md`, критерии приёмки, Codex по правилу.
2. **DELEGATE**: сообщение с `T-YYYYMMDD-NN` (ID задачи), slug плана, скоуп, ссылки на банк, интерфейсы, ограничения, тесты, DoD.
3. **IMPLEMENT** (opus-worker): код → `pnpm typecheck && lint && test && build` → выкладка по `agent-workflow.md` → отчёт.
4. **REVIEW** (fable-lead): `git diff`/файлы, тесты, регрессы, конвенции. **Визуальная приёмка (владелец 17.10):** всё, что
   меняет интерфейс, вёрстку или картинку, fable-lead смотрит САМ на фактическом результате (прод/`/test/`, свои Playwright-пробы,
   скриншоты телефона 375×667 и компьютера): согласованность, выравнивание, пропорции, отступы, адаптивность, наезды/обрезки,
   удобство, соответствие требованию. Отчёт worker, тесты и diff визуальную проверку не заменяют. Дефект → конкретная правка
   worker → повторная визуальная проверка, пока критерии не выполнены. Без браузера/скриншота — не утверждать «проверено визуально».
5. **DECIDE**: `PASS` / `CHANGES REQUIRED` (конкретные правки → тот же worker, тот же ID, цикл повторяется) / `BLOCKED`.
   До **3 циклов правок**; дальше — стоп, владельцу: доказательства и рекомендация. «Готово» со слов worker — не приёмка.
6. **MEMORY** (fable-lead): после PASS — банк по `memory-discipline.md`, план → `completed_plans/`, отчёт владельцу.

## Формат отчёта opus-worker (обязательные поля)
1-я строка `[рабочий N] T-…/<цикл> · отчёт` (без неё отчёт не открывает проверку — учёт токенов), 2-я — ID модели,
3-я — статус `done|partial|blocked` · коммиты/diff · изменённые файлы · прогнанные проверки с фактическим
результатом · артефакты (URL прод/`/test/`, скриншоты, пути) · отступления от плана с причиной · нерешённое/вопросы ·
«что смотреть». Платное — сперва бесплатная проверка пути, расходы в отчёте.

## Границы
Секреты, миграции БД, удаление данных, деплой без права — только с явного слова владельца; VPN-нода не трогается.
Один Memory Bank (`.memory_bank/`), один фронт правок памяти за раз (`memory-discipline.md` § «несколько сессий»).
**В брифе рабочему (22–24.10):** сервисы DEV (`remlab-render` и др.) не останавливать — они обслуживают живое демо; `.env*` не читать
(окно разрешения на Read `.env.example` держало рабочего ~13 ч) — ключи только через готовые скрипты.
**Тяжёлые прогоны — только под `tools/ops/heavy-slot.sh` / `heavy_slot.py` (05.11, T-57; до 5 сразу (владелец 11.11; было 3, T-74), порог по замеру — T-74; обгон головы мелкими, защита 20 мин — T-79, 06.11):** свои циклы `free -m` не писать; долгое — порциями.
**Без удаления в командах исполнителя (22.10):** `Bash` в allow целиком, но `rm -rf $VAR/…`, `rm -f glob` (и через `ssh`/`r`) Claude Code
всё равно спрашивает — ночь 21→22.10 оба рабочих простояли на таком окне 11–12 ч. Снимки и выводы — в НОВУЮ папку с меткой времени
(`mkdir -p $D/after-$(date +%H%M)`), старое не чистить; уборка — отдельным шагом ведущего. Окно у рабочего видно так:
`~/.claude/sessions/*.json` → `waitingFor: "permission prompt"` (статус «waiting» в ListAgents сам по себе — не оно).
**Окна разрешений — разбирать и снимать (владелец 06.11, TG 246):** ведущий сам смотрит, что запросил рабочий (журнал сессии), и, если
безопасно, добавляет правило в `.claude/settings.local.json`. `Bash` уже разрешён целиком, поэтому окно обычно даёт не список, а
проверка безопасности: длинный heredoc `cat > "$(…)/f" <<EOF` в Bash (T-83 простоял 30 мин). В брифе: файлы скриптов — инструментом
Write, в Bash — только запуск; без `$(…)` в цели перенаправления.
